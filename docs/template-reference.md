# Справочник шаблона отчёта

Шаблон — JSON-объект, который хранится в таблице `report_templates` (ADR-21) и валидируется
схемой `frontend/src/template/schema.js` + семантическим валидатором `validate.js`;
те же правила повторяет сервер (`backend/src/validate.cc`).
Канон схемы — `frontend/src/template/schema.js`, файл `docs/template.schema.json` генерируется из него
(`npm run schema:json`).

## Общая структура

```json
{
  "version": 2,
  "id": "sales-by-region",
  "title": "Продажи по региону",
  "description": "Необязательное описание для экрана списка отчётов",
  "params": [],
  "datasets": {},
  "blocks": []
}
```

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `version` | integer | да | версия формата шаблона, сейчас `2` (миграции ниже) |
| `id` | string | да | идентификатор отчёта; он же ключ в `report_templates` и в URL `?report=<id>` |
| `title` | string | да | заголовок страницы и карточки в списке |
| `description` | string | нет | пояснение на карточке списка отчётов |
| `params` | array | нет | параметры, которые пользователь задаёт перед построением |
| `datasets` | object | да | именованные наборы данных: `имя → { sql, params }` (ADR-27, ADR-36) |
| `folder` | string | нет | папка в каталоге отчётов (ADR-30) |
| `autoLoad` | boolean | нет | загружать ли данные сразу при открытии; `false` — только по кнопке «Обновить» (ADR-89) |
| `refreshSeconds` | integer | нет | автообновление данных на экране, 0…3600 с; пусто — выключено (ADR-39) |
| `live` | boolean | нет | обновлять по событию: сервер сам сообщает о публикации шаблона (ADR-42); не смешивается с `refreshSeconds` |
| `tags` | string[] | нет | теги для фильтра в каталоге |
| `blocks` | array | да | блоки вывода по порядку: текст, таблица, диаграмма |

### Автозагрузка при открытии (autoLoad)

По умолчанию отчёт запрашивает данные сразу, как только загрузились справочники параметров.
Для тяжёлых отчётов автозагрузку можно выключить — тогда данные появятся только после нажатия
«Обновить»:

```json
{ "version": 2, "id": "manual-load", "autoLoad": false, ... }
```

- при открытии показывается подсказка «Данные не загружены — нажмите «Обновить»», блоки таблиц и
  диаграмм скрыты до первой загрузки (текстовые блоки видны);
- изменения параметров и URL сами данные не перезапрашивают — единственный триггер — кнопка;
- `refreshSeconds` и `live` при `autoLoad: false` не работают: валидатор выдаёт предупреждение;
- во время загрузки это видно на кнопке («Загрузка…», кнопка неактивна) и в шапке страницы
  («загрузка…») — для любого отчёта, не только с `autoLoad: false`;
- пример: шаблон `manual-load` — 50 000 строк, загрузка ~2,5 с, видно и надпись, и индикатор.

### Автообновление и обновление по событию

Два независимых способа держать экран свежим:

- `refreshSeconds` — страница сама перезапрашивает данные каждые N секунд (ADR-39). Просто, но при периоде
  меньше TTL кэша (`REP_CACHE_TTL_SECONDS`, по умолчанию 60) данные приходят из кэша;
- `live: true` — страница держит одно SSE-соединение `GET /api/report/events?report=<id>`; сервер пишет
  в поток сразу после публикации или отката шаблона, страница перечитывает шаблон и данные (ADR-44).
  Раз в 15 с сервер шлёт комментарий-пульс, клиент переподключается сам. Запросов в простое нет,
  задержка — доли секунды; цена — открытое соединение на каждого зрителя.

```json
{ "live": true }
```

## Версия формата и миграции

`version` — версия формата шаблона, сейчас **2**. Поддерживаются 1 и 2:

| Версия | Отличие | Что делает миграция |
|---|---|---|
| 1 | `chartType` у диаграмм был необязательным | при сохранении подставляется `bar` |
| 2 | `chartType` обязателен | — |

- шаблон без `version` считается версией 0 и получает актуальную;
- шаблон версии больше текущей отклоняется: «шаблон версии N, сервер поддерживает до 2 — обновите сервер»;
- сервер мигрирует при сохранении, публикации и загрузке в память (в БД хранится нормализованное тело);
- админка мигрирует при открытии и сообщает об этом в статусе;
- валидатор предупреждает о старой версии, но не блокирует сохранение.

## params[] — параметры отчёта

Значения в SQL всегда уходят через binding (`$1…$N`), в шаблон — по ссылке `$name` в `datasets`.
Пользователь видит `label`, а в запрос уходит `value`.

| Поле | Тип | Смысл |
|---|---|---|
| `name` | string | имя параметра, `^[a-z][a-z0-9_]*$`; на него ссылаются `datasets.*.params` и `{{name}}` в тексте |
| `type` | enum | `date`, `datetime`, `int`, `float`, `text`, `bool`, `select` |
| `label` | string | подпись в форме |
| `required` | boolean | обязателен ли параметр (иначе бэкенд вернёт 422) |
| `default` | string/number/bool | значение, выбранное по умолчанию (для `lookup` — `value` одного из пунктов) |
| `emptyOption` | object | явный первый пункт списка `{value, label}`; только у `lookup`, не с `multiple` (ADR-84) |
| `multiple` | boolean | множественный выбор; допустим только при `source.kind` = `lookup` или `static` |
| `options` | array | устаревший способ задать статический список; используйте `source.options` |
| `source` | object | откуда берётся значение (см. ниже) |

### source — способ получения значений

```json
{
  "kind": "lookup",
  "dataset": "region_lookup"
}
{
  "kind": "lookup",
  "dataset": "category_lookup",
  "dependsOn": "region"
}
{ "kind": "static", "options": [{ "value": "all", "label": "Все строки" }] }
{ "kind": "date" }
```

SQL справочника живёт в блоке данных — это обычный набор `datasets.<ключ>` со своим `sql`
и, при необходимости, `connection` (ADR-78):

```json
"datasets": {
  "region_lookup": {
    "connection": "main",
    "sql": "SELECT id::text AS value, name AS label FROM reports_examples.regions ORDER BY name"
  },
  "category_lookup": {
    "connection": "main",
    "sql": "SELECT DISTINCT category AS value, category AS label FROM reports_examples.sales WHERE region_id = :region::int ORDER BY 1"
  }
}
```

| `kind` | Что даёт | Требования |
|---|---|---|
| `date` | контрол `input[type=date]` | `type` = `date`, без `queryId`/`options` |
| `datetime` | контрол `input[type=datetime-local]` | `type` = `datetime` |
| `static` | список из `source.options` | непустой `options`, `type` = `select`, без `queryId` |
| `lookup` | список из `GET /api/reports/{reportId}/lookups/{param}` | обязателен `dataset` — ключ набора в `datasets` (ровно две колонки: `value`, `label`), `type` = `select`, без `options`, `queryId` и `connection` |

Пример параметра даты и времени (ADR-87):

```json
{ "name": "dt_from", "type": "datetime", "label": "События с", "required": true,
  "default": "2026-03-01T00:00", "source": { "kind": "datetime" } }
```

- в форме это `input[type=datetime-local]`: дата и время, точность — минута; значение приходит
  строкой `ГГГГ-ММ-ДДTЧЧ:ММ` (нативное значение браузера, без таймзоны);
- в SQL приводите его кастом: `WHERE logged_at >= :dt_from::timestamp`; сервер проверит формат и
  вернёт 422 с понятным сообщением, если пришло не дата-время;
- `type` и `source.kind` должны совпадать: `datetime`/`datetime` (для даты — `date`/`date`);
- в тексте `{{dt_from}}` выводится как есть, в ISO: `2026-03-01T00:00`;
- готовый пример: `ops-events` — «Журнал сервиса: выбор даты и времени» (события из
  `reports_examples.ops` с колонкой `logged_at`, ИТОГО по выбранному интервалу).

Дополнительно:

- `dataset` — набор, из которого берутся значения; `sql` набора использует плейсхолдеры `:name`,
  они подставляются из query-строки (binding). Сами SQL и `connection` живут в `datasets`,
  параметр на них только ссылается; старый `source.sql` — ошибка валидатора.
- Клиенту SQL не отдаётся: `GET /api/reports/{id}` вырезает его на сервере (как и `connections`).
- `:name` — плейсхолдер только вне литералов и комментариев: `to_char(ts, 'HH24:MI')`, 'текст :x',
  "идентификатор:с:двоеточием", `$$ ... $$` и `-- :комментарий` остаются как есть.
- `dependsOn: "<имя>"` — каскад: значение родителя передаётся в запрос справочника как его параметр.
  Родитель обязан быть объявлен **выше** (это же исключает циклы) и не может быть множественным.
- `multiple: true` — выпадающий список с чекбоксами (`MultiSelect.vue`), наружу значение уходит строкой
  через запятую; в SQL используйте `= ANY(string_to_array(:param, ','))`.
  `value` справочника может быть любого типа: числа тоже приходят строкой («1,3»), для числового
  сравнения приводите список к массиву — `region_id = ANY(string_to_array(:regions, ',')::int[])`.
  Пример: `multi-int` — «Мультивыбор: value — число, label — текст», где `value` — `id` региона
  (`integer`), `label` — название; в тексте `{{regions}}` печатаются подписи «Север, Запад»,
  в SQL уходит `1,3`, а в шапке таблицы появляется ИТОГО по выбранным регионам.
- Пустой пункт списка интерфейс сам **не добавляет**: ни «—», ни пустого `option`. Если он нужен
  (обычно «Все центры»), объявите его в шаблоне — `emptyOption`; нет `emptyOption` — нет и пустого
  пункта, выбирается значение из данных:

  ```json
  {
    "name": "cost_center",
    "type": "select",
    "label": "Центр затрат",
    "default": "",
    "emptyOption": { "value": "", "label": "Все центры" },
    "source": { "kind": "lookup", "dataset": "cost_center_lookup" }
  }
  ```

  `value` пустого пункта может быть любым (`""`, `0`, `all`) — важно, чтобы SQL набора или данных
  понимал это значение так же; `label` обязателен. Дубликат (`value` уже есть в данных) не выводится
  дважды.
- Поведение по умолчанию: выбирается `default`; если его нет — объявленный `emptyOption`; если нет
  и его — первое значение списка (для `multiple` — все значения). Пустая строка в URL (`?p=`)
  считается «ничего не выбрано» и заменяется этим же правилом.
- В текстовом блоке `{{name}}` печатается **подпись** выбранного значения (`label`), в SQL уходит
  `value`. Это касается и пустого пункта: при `emptyOption` значение `""` печатается как
  «Все центры» (ADR-86). Для множественного выбора подписи склеиваются через запятую. Если
  значение пришло из URL и его нет в справочнике, печатается само значение — метки для него нет.

### Арифметика дат в `default` (ADR-92)

У параметров `date` и `datetime` значение по умолчанию может быть выражением от текущего момента —
не нужно переписывать шаблон каждый месяц:

```json
{ "name": "from", "type": "date", "label": "Период с", "default": "month(*)-1m",
  "source": { "kind": "date" } }
```

| Выражение | Значение |
|---|---|
| `*` | текущий момент (для `date` — сегодняшняя дата, для `datetime` — время до минут) |
| `today(*)` | сегодня, 00:00 |
| `week(*)` | понедельник текущей недели, 00:00 |
| `month(*)` | первое число текущего месяца, 00:00 |
| `quarter(*)` | первое число месяца начала квартала, 00:00 |
| `year(*)` | 1 января текущего года, 00:00 |
| `+N`/`-N` | смещение после базы: `h` — часы, `d` — дни, `m` — месяцы, `y` — годы |

Смещения можно нанизывать: `*-5h`, `*-30d`, `month(*)-1m`, `*-1d+2h`. Считается всё в **локальном
поясе браузера**: «начало месяца» — месяц пользователя, а не сервера.

- выражения пересчитываются при **каждой** загрузке данных: «Обновить», автообновление,
  смена параметров — `*-5h` не застывает на моменте открытия;
- значение, выбранное пользователем вручную, выражение не перезаписывает; значение из URL
  (`?from=2026-03-01`) тоже считается ручным;
- опечатка в выражении — **ошибка валидации** шаблона (`params.<i>.default: default: неизвестное
  начало выражения «month2(*)»`): шаблон не сохранится, а не отдаст пустое значение;
- константы (`2026-03-01`, `2026-03-01T00:00`) работают как раньше;
- готовый пример: `period-defaults` — «Период по умолчанию: арифметика дат» (`year(*)`, `*`, `*-5h`).


## datasets — наборы данных

```json
"datasets": {
  "sales": {
    "sql": "SELECT region, category, product, amount, profit, order_date FROM reports_examples.sales WHERE order_date >= :from::date AND order_date <= :to::date",
    "params": { "from": "$from", "to": "$to" }
  }
}
```

| Поле | Смысл |
|---|---|
| `sql` | запрос набора данных; плейсхолдеры `:name` подставляются через binding (ADR-27) |
| `params` | отображение «параметр SQL → `$<имя параметра отчёта>`»; необязательно, если имена совпадают |
| `connection` | ключ источника из блока `connections`; не задан или `default` — сервер из окружения (ADR-76) |

`queryId` и реестр `backend/config/queries.json` для наборов данных больше не используются.

## connections — где брать данные (ADR-76)

Блок описывает подключения: адрес, базу, пользователя, схему и **имя переменной окружения
с паролем**. Самого пароля в шаблоне нет и быть не может — это правило проекта: секреты
живут в окружении сервера, шаблон можно хранить в БД, отдавать в админку и показывать в git.

```json
"connections": {
  "default": { "kind": "postgres" },
  "finance": {
    "kind": "postgres",
    "host": "10.0.0.5",
    "port": 5432,
    "database": "finance",
    "user": "report_reader",
    "passwordEnv": "REP_CONN_FINANCE_PASSWORD",
    "schema": "public",
    "sslmode": "require",
    "connectTimeout": 5,
    "statementTimeoutMs": 2000
  }
}
```

| Поле | Смысл |
|---|---|
| `kind` | `postgres` (по умолчанию) или `rest` — второй пока зарезервирован: шаблон с ним валидируется, но запрос отвечает `422 CONNECTION_ERROR` «ещё не поддерживается» |
| `host`, `port`, `database`, `user` | адрес и учётная запись источника |
| `passwordEnv` | имя переменной окружения с паролем: `PGPASSWORD`, `REP_CONN_FINANCE_PASSWORD`. Поле `password` в шаблоне — ошибка валидатора |
| `schema` | `search_path` сессии; имя схемы, не путь |
| `sslmode` | `disable`, `allow`, `prefer`, `require`, `verify-ca`, `verify-full` |
| `connectTimeout` | секунды, 1…120 |
| `statementTimeoutMs` | предел запроса, 0…600000 (0 — без ограничения) |
| `baseUrl` | для `kind=rest`: адрес API (структура под будущее расширение) |

**Подстановка окружения.** Поля `host`, `port`, `database`, `user`, `schema` могут быть целиком
ссылкой на переменную окружения — `${PGHOST}`, `${REP_RO_DB_USER}`. Так блок остаётся явным
(видно, что и откуда берётся), но шаблон переносим между стендами: адрес и база не зашиты.

```json
"main": {
  "kind": "postgres",
  "host": "${PGHOST}", "port": "${PGPORT}", "database": "${PGDATABASE}",
  "user": "${REP_RO_DB_USER}", "passwordEnv": "REP_RO_DB_PASSWORD",
  "schema": "reports_examples"
}
```

Подстановка допускается только целым значением поля: `"db-${ID}"` — ошибка валидатора.
Незаданная переменная — `422 CONNECTION_ERROR` с её именем (а не тихий уход на localhost).
Все шаблоны примеров используют `main` с этими подстановками, поэтому работают и на dev-базе
(`reporting`, роль `reporting_ro`), и на CI (`reporting_ci`, роль из `REP_RO_DB_USER`).

Ключ `default` — это подключение самого сервера (`PGHOST`… и пул только-чтения); его можно
не объявлять, а если объявить, то только как `postgres`. Наборы данных и справочники
ссылаются на источник полем `connection`:

```json
"datasets": {
  "shipments": { "connection": "finance", "sql": "SELECT … FROM warehouse.shipments" }
},
"params": [
  { "name": "region", "type": "select",
    "source": { "kind": "lookup", "connection": "finance", "sql": "SELECT id, name FROM regions" } }
]
```

Ссылка на необъявленный ключ — ошибка валидатора на обоих уровнях (клиент и сервер, parity).
Источник открывается **только на чтение**: в строке подключения выставляется
`default_transaction_read_only=on`, поэтому даже ошибочный SQL в шаблоне не изменит данные.
Выгрузка в Excel/CSV и рассылка читают тот же источник, что и экран.

Секреты задаются там, где запускается сервер:

```bash
REP_CONN_FINANCE_PASSWORD=…   # из хранилища секретов, не из репозитория
```

Если переменная не задана, запрос отвечает `422 CONNECTION_ERROR` с её именем — без утечки
значения. Публичный `GET /api/reports/{id}` вырезает блок `connections` целиком: клиенту
достаточно ссылки `connection`, адреса и логины видны только в админке.

Пример в каталоге — `sales-external`: продажи из БД сервера и отгрузки из отдельной базы
`reporting_ext` (схема `warehouse`). Вторая база создаётся `./db/examples/external.sh`.
Типы колонок сервер определяет по результату запроса. Валидатор проверяет, что `sql` задан,
а каждая ссылка `$name` указывает на объявленный параметр. Клиенту `sql` не отдаётся:
`GET /api/reports/{id}` вырезает его так же, как SQL справочников.

## blocks[] — блоки вывода

### Печать (ADR-28, ADR-98)

Кнопка «Печать / PDF» печатает отчёт в A4 landscape с полями 10×8 мм; таблица нарезается на
страницы, шапка повторяется, объединения пересчитываются по границам страницы. Лимит — 5000 строк
модели (с подытогами): больше — предложение выгрузить в Excel.

- Первая порция строк короче остальных: из 660 px печатной полосы вычитается место, занятое
  заголовком отчёта и текстовыми блоками над таблицей, — иначе браузер переносил таблицу целиком
  на вторую страницу, а первая оставалась пустой (ADR-98);
- плоская таблица (без группировок) печатается одним куском — браузер сам рвёт её по страницам и
  повторяет шапку только сверху; куски сгруппированной таблицы помечены `no-break` и целиком
  переносятся на следующую страницу, чтобы шапка не оказывалась в середине (ADR-99);
- вторая и следующие таблицы считаются так, будто начинаются с новой страницы;
- сетка блоков (`span`) на печать не переносится: блоки идут в одну колонку.

### Выгрузка в Excel: лист на каждую таблицу (ADR-97)

Кнопка «Excel» выгружает **все** табличные блоки отчёта, каждый на своём листе; последним идёт
лист «Параметры» с подписями и значениями. Имя листа — `title` блока:

- нет `title` — «Таблица N» по порядку блоков;
- одинаковые названия получают суффикс: «Продажи», «Продажи (2)»;
- длиннее 31 символа — Excel не принимает: имя обрезается и помечается «…»;
- запрещённые Excel символы `* ? : \ / [ ]` заменяются на «·».

Одна таблица — один лист отчёта и «Параметры», как раньше. Диаграммы в книгу не попадают
(ADR-36), текстовые блоки — тоже. Пример с двумя таблицами: `two-sets-styles` — листы «Продажи по
регионам — светлая…» и «Сервисы — тёмная тема».

### Раскладка блоков: сетка 12 колонок (ADR-96)

Блоки лежат в сетке из 12 колонок, ширина задаётся `span`:

```json
"blocks": [
  { "type": "text",  "span": 12, "text": "Заголовок и пояснение" },
  { "type": "table", "dataKey": "sales", "span": 7, "columns": [ … ] },
  { "type": "chart", "dataKey": "sales", "chartType": "bar", "span": 5, "xField": "category", "yField": "amount" },
  { "type": "table", "dataKey": "ops",   "span": 6, "columns": [ … ] },
  { "type": "text",  "span": 6, "text": "Пояснение рядом с таблицей" }
]
```

| `span` | Ширина |
|---|---|
| 12 | вся строка (по умолчанию) |
| 6 | половина |
| 4 | треть |
| 1…12 | любая доля; ряды собираются сами — блоки встают рядом, пока сумма ≤ 12 |

- высота блоков в ряду **не выравнивается**: у каждого своя (таблица — своя, текст — по
  содержимому), выравнивание по верхнему краю; высота задаётся `height` (см. ниже);
- при ширине окна **меньше 900 px** и в печати всё выстраивается в одну колонку — две таблицы
  рядом на узком экране нечитаемы;
- старый `width` (`full`/`half`) работает как раньше: `full` = 12, `half` = 6, но `span` главнее;
- на печать и в Excel раскладка не влияет: Excel выгружает данные блока, а не сетку;
- пример: шаблон `layout-horizontal` — таблица 7 + диаграмма 5 в одном ряду, ниже две половины.

### Высота блока (height)

У табличного блока и диаграммы высоту можно задать в шаблоне — пикселями или в процентах от
высоты окна (ADR-85):

```json
{ "type": "table", "dataKey": "sales", "height": "60%", "columns": [ … ] }
{ "type": "chart", "dataKey": "by_region", "chartType": "bar", "height": 320, "xField": "region", "yField": "amount" }
```

| Значение | Смысл | Границы |
|---|---|---|
| `480` | пиксели, целое число | 160…2000 |
| `"60%"` | процент от высоты окна браузера | 10…100 |

- Процент пересчитывается при изменении размера окна; в печати берётся текущая высота окна.
- У таблицы фактическая высота — минимум из `height` и высоты содержимого, поэтому короткий
  список не оставляет пустого места; у диаграммы высота ровно заданная.
- Без `height`: таблица 460 px, диаграмма 320 px. У текстового блока `height` запрещён —
  это ошибка валидатора.
- Пример: шаблон `layout-heights` (таблица `"60%"`, диаграмма `320`, таблица `240`).

### Текст

```json
{ "type": "text", "text": "Регион {{region}}, период {{from}} — {{to}}", "width": "full" }
```

`{{name}}` — значение параметра (для справочников — подпись). Необъявленный параметр — ошибка валидации.
Ширина — `span` 1…12 (см. «Раскладка блоков»); старый `width`: `full` (12) или `half` (6).

### Агрегация на сервере (ADR-37)

```json
"block": {
  "type": "table",
  "dataKey": "sales",
  "aggregate": {
    "groupBy": ["category"],
    "measures": [{ "field": "amount", "agg": "sum" }, { "field": "profit", "agg": "sum" }]
  }
}
```

`groupBy` — колонки набора, которые остаются в результате (минимум одна); `measures` — колонки
с агрегатом: `sum`, `avg`, `min`, `max`, `count`. Сервер выполняет `GROUP BY` в PostgreSQL и отдаёт
уже сгруппированные строки — клиент не получает детализацию.

Что проверяется на сохранении: `groupBy` — непустой массив, `measures` — непустой массив объектов
`{field, agg}`, агрегат только из списка (иначе `blocks.<n>.aggregate.measures.<i>.agg`).
Существование полей в SQL на этапе валидации не проверяется — колонки запроса известны только базе:
неверное имя вернёт 422 при построении отчёта (и xlsx/CSV-экспорте). Колонки таблицы при этом
перечисляют те же поля, что возвращает `GROUP BY`.

### Drill-through в табличном блоке (ADR-29)

```json
"drill": {
  "report": "sales-drill",
  "label": "Детали по группе",
  "params": { "region": "group.region", "category": "group.category", "from": "param.from", "to": "param.to" }
}
```

| Значение | Смысл |
|---|---|
| `group.<field>` | значение группы этой строки (поле должно быть колонкой-группой) |
| `param.<name>` | текущее значение параметра отчёта |
| любая другая строка | литерал |

Ссылкой становится ячейка группы (детальная строка или подытог), параметры уходят в URL целевого отчёта.
Если целевой отчёт объявил их обязательными, у него должны быть значения по умолчанию — иначе открытие
из каталога даст 422.

### Drill-through с диаграммы (ADR-43)

```json
{
  "type": "chart",
  "dataKey": "sales",
  "chartType": "bar",
  "xField": "category",
  "seriesField": "region",
  "yField": "amount",
  "drill": {
    "report": "sales-drill",
    "label": "Детали по региону и категории",
    "params": { "category": "x", "region": "series", "from": "param.from", "to": "param.to" }
  }
}
```

| Значение | Смысл |
|---|---|
| `x` | категория точки, по которой кликнули (значение `xField`) |
| `series` | имя серии точки (значение `seriesField`; у круговой диаграммы его нет) |
| `param.<name>` | текущее значение параметра отчёта |
| любая другая строка | литерал |

У диаграммы курсор становится указателем, клик по столбцу/сектору открывает целевой отчёт с параметрами
в URL. `group.<field>` в диаграмме не поддержан — там нет групп таблицы; валидатор такую ссылку отклонит.

#### Переход из цепочки уровней sankey (ADR-72)

У многоуровневого sankey (`levels`) узел и связь несут значения своих уровней, поэтому в переходе можно
ссылаться на уровень по имени поля:

```json
"drill": {
  "report": "sales-drill",
  "params": {
    "from": "param.from", "to": "param.to",
    "region": "level.region", "category": "level.category"
  }
}
```

| Значение | Смысл |
|---|---|
| `level.<поле>` | значение уровня цепочки (поле должно быть в `levels`) |
| `node` | значение кликнутого узла (подпись без служебного префикса) |
| `x` / `series` | концы связи: источник и приёмник |

Переход выполняется, только если в кликнутом элементе есть **все** уровни, на которые ссылается `drill`:
на связи «категория → товар» региона нет, и клик по ней ничего не откроет — иначе в детали ушёл бы фильтр
шире клика. Пример: `sales-path` — переход по связям «регион → категория» в `sales-drill`.

### Таблица

```json
{
  "type": "table",
  "dataKey": "sales",
  "collapsible": true,
  "grandTotal": true,
  "nullText": "—",
  "columns": [
    { "field": "category", "title": "Категория", "group": true, "subtotal": true },
    { "field": "product", "title": "Продукт" },
    { "field": "amount", "title": "Сумма", "type": "int", "aggregate": "sum", "format": "number" },
    { "title": "Рентабельность", "expression": "sum(profit) / sum(amount)", "format": "percent" }
  ]
}
```

| Поле | Смысл |
|---|---|
| `dataKey` | имя набора из `datasets` (обязательно) |
| `title` | подпись блока; в экспорте становится именем листа Excel |
| `detailOrder` | порядок деталей при раскрытии группы: `[{ field, dir }]`, 1…4 поля, только вместе с `aggregate`; без него — порядок набора, затем по содержимому строки |
| `aggregate` | агрегация на сервере: `{ groupBy: [...], measures: [{ field, agg }] }` (ADR-37, ниже). Группу можно раскрыть — детали подгружаются маршрутом `POST /api/report/group` страницами по 200 строк (ADR-65, ADR-70); остаток добирается кнопкой «ещё N» в панели таблицы, потолок одной страницы — 5000. Порядок деталей задаёт
`detailOrder` (например `[{"field": "profit", "dir": "desc"}]`): он должен ссылаться на колонки, которые
выбирает SQL набора — поле вне SELECT даст 422. «Развернуть всё» тянет группы до конца, но не больше
20 000 строк за операцию; остаток остаётся кнопкой «ещё N» (ADR-71) |
| `collapsible` | разрешить сворачивание групп (шеврон в ячейке групповой колонки); `false` — группы всегда раскрыты: нет шевронов и кнопок «Свернуть/Развернуть всё» (ADR-90), а в Excel книга выгружается без структуры — без `outlineLevel`, подытоги и ИТОГО остаются (ADR-94) |
| `grandTotal` | печатать строку общего итога; в Excel-книге плоская таблица (без `group`) выгружается всеми строками, а «ИТОГО» встаёт в первую колонку (ADR-95) |
| `nullText` | текст для пустых значений (по умолчанию `(пусто)`) |
| `width` | `full` / `half` |
| `columns` | колонки таблицы (обязательно, минимум одна) |
| `styles` | оформление блока (см. «styles») |
| `rules` | правила условного форматирования (см. «rules») |
| `drill` | переход к детальному отчёту (ADR-29) |

### column — колонка таблицы

| Поле | Тип | Смысл |
|---|---|---|
| `title` | string | заголовок (обязателен) |
| `field` | string | поле из набора данных |
| `expression` | string | вычисляемое значение (см. `expressions.md`); с `field` несовместимо |
| `group` | boolean | колонка группировки; групповые колонки обязаны идти **первыми** |
| `subtotal` | boolean | печатать подытог по группе; только у `group`-колонки |
| `aggregate` | enum | `sum`, `avg`, `min`, `max`, `count`, `countDistinct`; требует `field` |
| `format` | enum | `number`, `percent`, `currency`, `date`, `integer` |
| `type` | enum | `int`, `float`, `text`, `date`, `bool` (подсказка для формата) |
| `decimals` | integer 0…6 | знаков после запятой (для `percent` по умолчанию 1) |
| `width` | integer ≥ 40 | ширина в px |
| `align` | enum | `left`, `right`, `center` |
| `children` | array | вложенные колонки для двухуровневого заголовка (без `field`/`expression`/`aggregate`/`group`) |

### Форматирование

- `number` / `integer` — `Intl.NumberFormat('ru-RU')`: `1 356 707 500`;
- `percent` — значение × 100, `decimals` (по умолчанию 1) знаков, запятая: `0,205 → 20,5 %`;
- `currency` и `date` пока не реализованы рендерером — выводятся как строка;
- колонка с `aggregate` форматируется как число, даже без `format`;
- пустое значение в агрегатной/вычисляемой колонке печатается как `—` (или `nullText`).

### Диаграмма

```json
{
  "type": "chart",
  "dataKey": "sales",
  "chartType": "bar",
  "title": "Сумма по категориям",
  "xField": "category",
  "yField": "amount",
  "aggregate": "sum",
  "width": "half"
}
```

| Поле | Смысл |
|---|---|
| `chartType` | `line`, `bar`, `pie`, `area`, `scatter`, `gauge`, `sankey` (см. таблицу ниже) |
| `xField` / `yField` | категория и значение; проверяются на наличие в наборе данных |
| `seriesField` | необязательное разбиение на серии (см. ниже) |
| `sourceField` / `targetField` / `valueField` | узлы и вес потока — только для `sankey` |
| `levels` | `sankey`: цепочка из 2…4 полей (регион → категория → товар) вместо `sourceField`/`targetField`; узлы нумеруются по уровню, подписи показывают исходные значения |
| `height` | высота области диаграммы, 240…900 px (по умолчанию 320); для многоуровневого sankey нужно больше |
| `min` / `max` / `unit` | шкала и суффикс подписи — только для `gauge` |
| `thresholds` / `zoneColors` | границы цветовых зон и их цвета — только для `gauge` (см. «Цветовые зоны») |
| `aggregate` | агрегат: у `line`/`bar`/`pie`/`area`/`scatter` — по `yField`, у `sankey` — по `valueField`, у `gauge` — по единственному значению (`sum` по умолчанию) |
| `title` | заголовок блока (у `gauge` он же подпись под шкалой) |
| `width` | `full` / `half` |

Обязательные поля зависят от вида: `line`, `bar`, `pie`, `area`, `scatter` требуют `xField` и
`yField`; `gauge` — только `yField` (и не принимает `xField`/`seriesField`); `sankey` —
либо `sourceField`, `targetField`, `valueField` (три разных поля), либо `valueField` + `levels`
(2…4 неповторяющихся поля; `sourceField`/`targetField` тогда не задаются), и не принимает `xField`/`yField`;
`band` — `xField`, `yField`, `lowField`, `highField` (значение и границы — три разных поля).

### Какие виды диаграмм поддерживаются

| `chartType` | Что рисует | Нужны поля |
|---|---|---|
| `line` | линия по категориям, `seriesField` даёт несколько линий | `xField`, `yField` |
| `bar` | столбцы, `seriesField` — группы столбцов | `xField`, `yField` |
| `pie` | круговая по категориям (одна серия) | `xField`, `yField` |
| `area` | линия с заливкой до оси | `xField`, `yField` |
| `scatter` | точки без соединения | `xField`, `yField` |
| `gauge` | спидометр: одно число на шкале | `yField`; необязательно `min`, `max`, `unit` |
| `sankey` | потоки между узлами (категория → регион и т. п.) или цепочка уровней (регион → категория → товар) | `sourceField`, `targetField`, `valueField` **или** `levels` + `valueField` |
| `band` | линия значения и закрашенный коридор между границами | `xField`, `yField`, `lowField`, `highField`; необязательно `bandColor` |

`gauge` без `min`/`max` сам подбирает верх шкалы выше значения (низ — 0). Отрицательные и нулевые
потоки `sankey` не рисуются и отбрасываются; строки с пустым источником или приёмником
пропускаются, поэтому диаграмма не падает на «грязных» данных.

Коридоров у `band` может быть несколько (до четырёх): `bands: [{lowField, highField, color, name}]`. Порядок
в массиве задаёт порядок закраски — при пересечении диапазонов верхний рисуется поверх нижнего. Пример:
`backend/templates/ops-corridors.json` — разброс по сервисам и среднее ± σ на одном графике.

В цепочке `levels` связь строится только между соседними уровнями, вес суммируется по парам, а строка,
у которой пуст хотя бы один уровень, отбрасывается целиком (иначе поток «перепрыгнул» бы шаг).
Пример: `backend/templates/sales-path.json` — регион → категория → товар.

### Пример: gauge — одно число

```json
{
  "type": "chart",
  "dataKey": "margin",
  "chartType": "gauge",
  "yField": "margin_pct",
  "aggregate": "max",
  "min": 0,
  "max": 100,
  "unit": "%",
  "title": "Маржа за период"
}
```

Набор `margin` возвращает одну строку с посчитанной в SQL маржой; `aggregate: "max"` берёт это
значение как есть. Для выборки из многих строк годятся `sum`, `avg`, `min`, `max`, `count`.

### Цветовые зоны gauge

Число границ N даёт N+1 зону: каждая граница — это «стык» двух цветов, поэтому цветов нужно ровно N+1.
Порядок цветов слева направо совпадает с порядком зон на шкале.

```json
{
  "chartType": "gauge",
  "yField": "margin_pct",
  "aggregate": "max",
  "min": 0,
  "max": 40,
  "unit": "%",
  "thresholds": [10, 15, 25, 30],
  "zoneColors": ["#c62828", "#f9a825", "#2e7d32", "#f9a825", "#c62828"]
}
```

| Что | Значение |
|---|---|
| `thresholds` | 2…8 чисел, строго возрастают (`p1 < p2 < …`) |
| `zoneColors` | `thresholds.length + 1` цветов: hex (`#rgb`, `#rrggbb`), `transparent` или имя из `styles.palette` |
| зона 1 | `min … p1` — первый цвет (в примере красный) |
| зона 2 | `p1 … p2` — второй (жёлтый) |
| зона 3 | `p2 … p3` — третий (зелёный) |
| зона 4 | `p3 … p4` — четвёртый (жёлтый) |
| зона 5 | `p4 … max` — пятый (красный) |

В примере выше шкала 0…40, границы 10/15/25/30, значение 20,54 % попадает в зелёную зону —
указатель и число окрашиваются в её цвет. Полоса прогресса при заданных зонах не рисуется
(она закрыла бы цвета). Границы вне `min…max` обрезаются по шкале; если цветов не столько,
сколько зон, валидатор сообщает об ошибке, а страница рисует шкалу без зон вместо падения.

Готовый пример — шаблон `margin-zones` («Маржа: цветовые зоны по четырём границам»).

### Пример: sankey — потоки между узлами

```json
{
  "type": "chart",
  "dataKey": "flows",
  "chartType": "sankey",
  "sourceField": "category",
  "targetField": "region",
  "valueField": "amount",
  "aggregate": "sum",
  "title": "Категория → регион, сумма продаж"
}
```

Сервер отдаёт строки как есть, пары «источник → приёмник» и суммы по ним считает клиент.
Узлы нумеруются в порядке появления, поэтому диаграмма стабильна между обновлениями.

### Пример: band — значение и коридор

Точка графика описывается тремя числами: значение, нижняя и верхняя границы. Диапазон между
границами закрашивается цветом `bandColor` (hex или токен `styles.palette`).

```json
{
  "type": "chart",
  "dataKey": "days",
  "chartType": "band",
  "xField": "day",
  "yField": "value_ms",
  "lowField": "low_ms",
  "highField": "high_ms",
  "bandColor": "#2e7d32",
  "title": "Время ответа, мс: значение и коридор min…max"
}
```

| Поле | Смысл |
|---|---|
| `xField` | категория (день, сутки, интервал) |
| `yField` | само значение — линия с точками |
| `lowField` / `highField` | нижняя и верхняя границы одного коридора |
| `bandColor` | цвет заливки (по умолчанию `#2e7d32`), непрозрачность 0,22 |
| `bands` | до четырёх коридоров `[{lowField, highField, color?, name?}]` вместо пары `lowField`/`highField` |

Правила: границы — разные поля, значение не может совпадать с границей, `seriesField` в полосе
не используется. Если у строки нет границ, точка рисуется без полосы; если границы перепутаны
(`low > high`), полоса вырождается в нулевую и не ломает график. Повторяющаяся категория берётся
один раз — линия не идёт назад.

Несколько коридоров задаются массивом `bands` (до четырёх):

```json
{ "chartType": "band", "xField": "day", "yField": "value_ms", "height": 460,
  "bands": [
    { "lowField": "min_ms", "highField": "max_ms", "color": "#2e7d32", "name": "разброс по сервисам" },
    { "lowField": "sd_low_ms", "highField": "sd_high_ms", "color": "#1565c0", "name": "среднее ± σ" }
  ] }
```

Каждый коридор рисуется своим стеком, поэтому диапазоны не наслаиваются друг на друга; порядок в массиве
задаёт порядок закраски — при пересечении верхний диапазон рисуется поверх нижнего. Подсказка перечисляет
значение и все коридоры, под графиком появляется расшифровка цветов (когда коридоров два и больше).
Правила те же: границы — разные поля, значение не может быть границей, `bands` вместе с `lowField`/`highField`
не задаются, `bands` допустимы только для `band`.

Готовые примеры: `ops-band` («Время ответа: значение и коридор») — одна полоса от минимума до максимума
по сервисам; `ops-corridors` — два коридора на одном графике (разброс по сервисам и среднее ± σ).

Drill из `sankey` подставляет источник в `x`, приёмник — в `series`; у `gauge` ни `x`, ни `series` нет —
ссылки на них валидатор считает ошибкой (можно `param.<name>` и литералы).

Диаграммы не попадают ни в Excel, ни в печать — это записано в `docs/dod.md`.

## styles — оформление таблицы

Необязательная секция (ADR-23). Порядок применения: умолчания версии 1.0 → `styles.preset` →
`styles` → `styles.<зона>` → `datasets.<ключ>.styles` → `blocks[].styles` → `styles.columns.<поле>`.

| Поле | Смысл |
|---|---|
| `preset` | `default`, `compact`, `print`, `dark` — встроенные наборы |
| `font` | `family` (allowlist), `size` 8…32, `weight` 300…800, `style`, `lineHeight` 1…2 |
| `colors` | `text`, `background`, `border` — `#rgb`, `#rrggbb`, `transparent` |
| `layout` | `rowHeight`, `headerHeight`, `subtotalHeight`, `grandtotalHeight` (16…120), `cellPadding`, `borders` (`none`/`horizontal`/`grid`), `zebra`, `stripeColor`, `tableLayout` (принимается для совместимости, на раскладку не влияет — см. ADR-64) |
| `header` / `body` / `subtotal` / `grandtotal` | стиль зоны: `font`, `colors`, `align`, `verticalAlign`, `padding` |
| `columns.<field>` | `width` (px или `"20%"`), `minWidth`, `maxWidth`, `align`, `headerAlign`, `font`, `colors`, `padding`, `format` |
| `layout.numericAlign` | выравнивание числовых колонок по умолчанию: `right` (по умолчанию), `left`, `center`, `inherit` |
| `blocks[].styles` | те же ключи, но только для этого блока таблицы |
| `datasets.<ключ>.styles` | те же ключи для всех блоков этого набора; блок перекрывает своими `styles` (ADR-91) |

### Разные стили для разных наборов данных

В отчёте с несколькими наборами вид задаётся у самого набора — `datasets.<ключ>.styles`; блок берёт
стили своего `dataKey`. Это избавляет от копирования одного и того же `styles` в каждый блок:

```json
"datasets": {
  "sales": { "sql": "...", "styles": {
    "font": { "family": "Inter", "size": 13 },
    "header": { "colors": { "background": "#e6efff", "text": "#12324f" } },
    "layout": { "zebra": true, "stripeColor": "#f2f6ff" }
  } },
  "ops": { "sql": "...", "styles": {
    "font": { "family": "monospace", "size": 12 },
    "colors": { "text": "#e6edf3", "background": "#111820" },
    "header": { "colors": { "background": "#1d2733", "text": "#9fc4ff" } },
    "layout": { "borders": "horizontal" }
  } }
},
"blocks": [
  { "type": "table", "dataKey": "sales", "columns": [...] },
  { "type": "table", "dataKey": "ops", "columns": [...] }
]
```

Приоритет: глобальные `styles` → стили набора → `blocks[].styles` (блок сильнее набора, недостающие
ключи наследуются) → `styles.columns.<поле>`. Стиль набора проверяется так же, как блочный: цвета —
hex или из `styles.palette`, `columns.<поле>.format` — только для полей, объявленных в блоках набора
(иначе предупреждение). Готовый пример: `two-sets-styles` («Два набора — два стиля») — продажи
светлой темой и сервисы тёмной в одном отчёте.

### Насыщенность шрифта (weight)

`font.weight` — это CSS `font-weight`: насыщенность начертания, а не размер и не «жирность в
пикселях». Допустимы 300, 400, 500, 600, 700, 800:

| weight | CSS-имя | Как выглядит |
|---|---|---|
| 300 | light | тонкий |
| 400 | normal | обычный текст (по умолчанию для `body`) |
| 500 | medium | чуть плотнее обычного |
| 600 | semibold | полужырный (по умолчанию для `header`, `subtotal`) |
| 700 | bold | жирный |
| 800 | extra bold | очень жирный (по умолчанию для `grandtotal` в примерах) |

Где применяется: зоны `styles.header`, `styles.body`, `styles.subtotal`, `styles.grandtotal`,
а также `rules[].style.font.weight` и `columns.<поле>.style.font.weight`. Рендерер передаёт
значение в CSS-переменную `--rt-<зона>-font-weight`, поэтому оно действует на всю зону.

Почему «изменение не видно» — три частые причины:

1. **Зона не на экране.** `grandtotal` — строка ИТОГО в самом низу таблицы, `subtotal` —
   строки итогов групп. В виртуализированной таблице они появляются в DOM только когда попадают
   в окно: прокрутите до конца или нажмите «Свернуть всё», иначе видите только детальные строки
   с весом `body`.
2. **У шрифта нет такого начертания.** Браузер использует установленный шрифт; если в нём только
   Regular и Bold, то 400/500/600 отображаются одинаково, а 700 — настоящий Bold, 800 —
   синтезированный (faux bold, шире настоящего). Проверить можно по ширине текста: у Noto Sans
   строка «ИТОГО 1 356 707 500» при 400 и 600 занимает одинаковые 125,5 px, при 700 — 127,5,
   при 800 — 137,5. Семейства из `font.family` (Inter, Roboto, Georgia…) должны быть установлены
   на машине пользователя: шаблон лишь просит их, а не привозит с собой.
3. **Шаблон не обновлён в БД.** Отчёт читает шаблон из `reports.report_templates`, а не из файла
   в репозитории. После правки `backend/templates/*.json` нужен `./db/load-examples.sh` (или
   публикация через админку); иначе на экране прежняя версия.

Готовый пример: шаблон `font-sizes` — «Размеры шрифта: зоны и колонки». Шапка 14 px / 700, тело
12 px, подытоги 13 px / 600, строка ИТОГО 18 px / 800; в колонках «Товар» 11 px, «Сумма»
16 px / 700, «Прибыль» 10 px. В нём видно и приоритет правил: переопределение колонки задаёт
размер шрифта, а вес берётся из зоны, если колонка не задала свой.

Проверить фактическое значение можно в консоли браузера:
`getComputedStyle(document.querySelector('.rt')).getPropertyValue('--rt-g-font-weight')` и
`getComputedStyle(document.querySelector('.rt-table tr.grandtotal td')).fontWeight`.

### Форматы чисел и дат

`format` задаётся у колонки (`columns[].format`) или в стиле (`styles.columns.<field>.format`);
стиль колонки перекрывает колонку. Допустимы строка-псевдоним и объект:

| Параметр | Значения | По умолчанию |
|---|---|---|
| `style` | `number`, `integer`, `percent`, `currency`, `date` | `number` |
| `decimals` | 0…6 | как у Intl (до 3), для `percent` — 1, для `currency` — 2 |
| `group` | разделитель тысяч (до 3 символов) | неразрывный пробел |
| `decimal` | десятичный разделитель (1 символ) | `,` |
| `prefix`, `suffix` | до 4 символов | пусто |
| `negative` | `minus` или `parentheses` | `minus` |
| `pattern` | шаблон даты: `YYYY`, `YY`, `MM`, `M`, `DD`, `D`, `HH`, `H`, `mm`, `ss` и разделители | нет — `DD.MM.YYYY` (+ `HH:mm`, если есть время) |

Примеры: `1356707500 → 1 356 707 500`, `{style:'number', decimals:0, suffix:' ₽'} → 58 300 ₽`,
`{negative:'parentheses'} → (1 500)`, `0.2054 → 20,5 %`, `2026-03-05 → 05.03.2026`,
`2026-03-05T14:30 → 05.03.2026 14:30`.

#### Шаблон даты (pattern, ADR-88)

Колонка с датой форматируется по шаблону; регистр букв значим (`MM` — месяц, `mm` — минуты):

```json
{ "field": "logged_at", "title": "Дата и время", "format": { "style": "date", "pattern": "DD.MM.YYYY HH:mm" } }
{ "field": "day", "title": "ISO", "format": { "pattern": "YYYY-MM-DD" } }
```

- `style: "date"` можно не указывать: наличие `pattern` само включает формат даты;
- допустимы токены `YYYY`, `YY`, `MM`, `M`, `DD`, `D`, `HH`, `H`, `mm`, `ss` и разделители
  (пробел, `. , : / ; -` и `T`); любые другие буквы — ошибка валидатора;
- формат можно задать и в `styles.columns.<field>.format` — стиль колонки сильнее колонки;
- время, которого нет в значении, печатается как `00` (`DD.MM.YYYY HH:mm` для даты без времени
  даст `05.03.2026 00:00`);
- клиентский Excel получает тот же шаблон как числовой формат (`YYYY→yyyy`, `DD→dd`, `HH→hh`);
  серверный `.xlsx` (libxlsxwriter) выводит даты строкой — это известное ограничение;
- пример: шаблон `date-formats` — четыре вида одной даты, включая формат из `styles.columns`.

Примеры оформления и форматов: `docs/styling-examples.md`, шаблон `sales-formatted`, шаблоны `finance-print` (preset print) и `ops-dark` (preset dark).

## rules — условное форматирование

Правила задаются в блоке таблицы (`blocks[].rules`) и меняют только оформление, не данные.

```json
"rules": [
  { "when": { "column": "profit", "op": "<", "value": 0 },
    "apply": { "colors": { "text": "danger" }, "font": { "weight": 600 } } },
  { "when": { "column": "Маржа", "op": "between", "value": [0, 0.2] },
    "apply": { "colors": { "background": "warningBg" } }, "priority": 1 },
  { "when": { "column": "amount", "op": ">=", "value": 50000 },
    "apply": { "colors": { "background": "rowHighlight" } }, "scope": "row" },
  { "when": { "column": "amount", "op": ">", "value": 0 },
    "apply": { "colors": { "background": "totalBg" } }, "scope": "row", "zones": ["grandtotal"] }
]
```

| Поле | Значения | Смысл |
|---|---|---|
| `when` | `{column, op, value}` или `{all: [...]}` / `{any: [...]}` (без вложенности) | условие по сырому значению |
| `op` | `=`, `!=`, `>`, `>=`, `<`, `<=`, `between`, `empty`, `notEmpty`, `contains` | оператор сравнения |
| `apply` | стиль-объект: `font`, `colors`, `align`, `padding` | что меняем |
| `scope` | `cell` (по умолчанию) — колонка-цель, `row` — вся строка | область действия |
| `target` | имя колонки для `scope: cell` (по умолчанию `when.column`) | что красить |
| `zones` | `detail`, `subtotal`, `grandtotal` (по умолчанию `detail` + `subtotal`) | на каких строках |
| `priority` | число | порядок слияния, большее побеждает |

Колонка адресуется полем (`amount`) или заголовком вычисляемой колонки (`Маржа`).
Семантические цвета берутся из `styles.palette`: `"danger": "#b42318"` → `"text": "danger"`.
Порядок применения: зона → `styles.columns` → правила по `priority`.

Правила действуют в трёх местах одинаково (ADR-100):

- на экране — inline-стили ячейки;
- в **печати** — фон строк и цвет шрифта сохраняются: печатный слой просит браузер печатать
  цвета как есть (`print-color-adjust: exact`), иначе Chrome/Edge по умолчанию фоны не печатают
  (цвет текста печатается всегда — поэтому раньше «красный» был, а «жёлтого фона» нет);
- в **Excel** — цвет и фон записываются в стили книги (`font.color`, `fill.fgColor`); правила зоны
  `detail` в книге соответствуют детальным строкам, `subtotal`/`grandtotal` — строкам итогов.

Готовый пример: `sales-rules` («Условное форматирование») — красный текст у отрицательной прибыли,
жёлтый фон у маржи ниже 20 %, светлая заливка строк с суммой от 50 000, свой цвет ИТОГО.

## Просмотр черновика

Черновик не опубликован, поэтому его SQL не исполняется обычными запросами. Просмотр
(`report.html?report=<id>&draft=1`) передаёт серверу флаг: `draft: true` в теле
`/api/report/data`, `/api/report/aggregate`, `/api/report/group`, `/api/report/export.*`
и `?draft=1` у справочников. Сервер считает по телу `draft`, а не по опубликованному.

Правила:

- черновик доступен только автору и администратору, зрителю — `403 DRAFT_FORBIDDEN`;
- после публикации черновик выгружается, `draft: true` даёт `404 DRAFT_NOT_FOUND`;
- рассылка и любые фоновые расчёты всегда используют опубликованную версию;
- кэш результатов у черновика отдельный (ключ с `|draft`), данные не смешиваются.

Это позволяет смотреть новый отчёт до публикации: админка создаёт каркас без `datasets`,
и без режима черновика такой просмотр падал с `TEMPLATE_INVALID`.

## Что проверяет валидатор

Схема (типы, обязательность, `additionalProperties: false`) плюс семантические правила:

- `dataKey` объявлен в `datasets`; `xField`/`yField`/`seriesField` существуют в таблице набора;
- в колонке ровно одно из `field` / `expression`; `aggregate` требует `field`;
- групповые колонки идут до обычных; `subtotal` только у групповых; у группы с `children` нет `field`;
- есть хотя бы одна листовая колонка, если включён `grandTotal`;
- `{{name}}` в тексте и `$name` в `datasets` ссылаются на объявленные параметры;
- правила `source`: `lookup` → `sql` (и запрет `queryId`); `static` → непустой `options`; `date`/`datetime` → без `sql`
  и `options`; `multiple` только для `lookup`/`static`; `dependsOn` — на объявленный выше параметр,
  не множественный;
- стили: форматы цветов, диапазоны высот и размеров шрифта, allowlist шрифтов, `minWidth ≤ maxWidth`,
  стиль колонки только для существующего поля; предупреждения — невидимый текст (цвет = фон),
  слишком малая высота строки, больше 15 переопределений колонок;
- выражения разбираются статически: синтаксис (`+ - * /`, скобки, функции `sum/avg/min/max/count/countDistinct`)
  проверяется как **ошибка** (`round()`, `>`, `%` — недопустимы), а имя поля, которого нет в колонках
  таблицы, даёт **предупреждение** (`!`) — оно не блокирует загрузку, но видно в выводе.

Запуск: `cd frontend && npm run validate -- ../backend/templates/*.json`.
