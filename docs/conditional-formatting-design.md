# Условное форматирование — проектный план

Цель: выделять значения по условию — красный текст для отрицательной прибыли, подсветка строки
при превышении порога, «светофор» по проценту исполнения. Правила задаются в шаблоне, рядом со стилями,
и не требуют правки кода.

Основание: требование PO от 2026-11-05 (вынесено за объём 1.1 осознанно — см. `styling-design.md` §9).

## 1. Что есть сейчас (факты кода)

| Механизм | Где | Что даёт |
|---|---|---|
| Зоны | `styles.header/body/subtotal/grandtotal` → CSS-переменные на `.rt` | базовый вид ячейки |
| Колонка | `styles.columns.<field>` → `cellStyle()` в `ReportTable.vue` | выравнивание, шрифт, цвета, формат для одной колонки |
| Значения | `TableView.flatView/groupedView` → `row.values[]` | значение уже посчитано (включая вычисляемые колонки) |
| Витрина | `ReportTable` рисует окно ~25–40 строк | оценка правил по видимым ячейкам дешева |
| Форматы | `report/format.js` | правило сравнивает **сырое** значение, а не отформатированную строку |

Отсюда главное следствие: правила применяются в момент вывода ячейки, поверх зоны и колонки,
и не участвуют в построении модели — иначе 50 000 строк получат лишний проход.

## 2. Модель правил в шаблоне

Правила живут в блоке таблицы (`blocks[].rules`), потому что зависят от набора колонок:

```json
{
  "type": "table",
  "dataKey": "sales",
  "rules": [
    {
      "when": { "column": "profit", "op": "<", "value": 0 },
      "apply": { "colors": { "text": "#b42318" }, "font": { "weight": 600 } },
      "scope": "cell"
    },
    {
      "when": { "column": "amount", "op": ">=", "value": 300000 },
      "apply": { "colors": { "background": "#fff7e6" } },
      "scope": "row"
    },
    {
      "when": { "column": "margin", "op": "between", "value": [0, 0.1] },
      "apply": { "colors": { "text": "#8a5a00", "background": "#fff4d6" } },
      "zones": ["detail", "subtotal"]
    }
  ]
}
```

| Поле | Значения | Смысл |
|---|---|---|
| `when.column` | имя поля или вычисляемой колонки (`columns[].field` / `title`-колонки с `expression`) | что сравниваем |
| `when.op` | `=`, `!=`, `>`, `>=`, `<`, `<=`, `between`, `empty`, `notEmpty`, `contains` | оператор; `contains` только для текста |
| `when.value` | число, строка, `[min, max]` для `between` | с чем сравниваем |
| `apply` | тот же стиль-объект, что у зоны: `font`, `colors`, `align`, `padding` | что меняем |
| `scope` | `cell` (по умолчанию) — стилизует ячейку колонки-цели; `row` — всю строку | область |
| `zones` | `detail`, `subtotal`, `grandtotal` (по умолчанию `detail` + `subtotal`) | на каких строках работает |
| `target` | имя колонки для `scope: "cell"` (по умолчанию = `when.column`) | какую колонку красить |
| `priority` | число, по умолчанию 0 | порядок слияния, большее побеждает |

Порядок применения: зона → `styles.columns` → правила по возрастанию `priority` (при равенстве —
в порядке объявления). Свойство, заданное правилом, перекрывает всё нижнее; не заданное — не трогается.

## 3. Почему декларативные условия, а не выражения

`engine/expr.js` умеет `+ - * /`, скобки и агрегаты, но не умеет сравнений и логики. Два пути:

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Декларативные условия (`when` объект) | проверяется схемой, читается без парсера, нет риска сломать существующие выражения | не выразить сложную логику (`margin < 10% AND region = 'Восток'`) |
| B. Расширить грамматику выражений (`> < AND OR`) | одна грамматика на всё | меняет семантику существующих колонок, ломает `null`-правила, валидатор и тесты |

**Рекомендация: A в версии 1.2.** Для сложных случаев — `when: { "op": "expression", "expression": "..." }`
добавить отдельным шагом после расширения грамматики; в 1.2 только декларативные операторы
и `all`/`any` из 2–3 условий (см. §9, вопрос 1).

## 4. Точки интеграции

1. **Новый модуль** `frontend/src/report/rules.js`:
   - `compare(value, op, expected)` — приведение типов: число, строка, дата (ISO-сравнение), `null`;
   - `matches(rule, row, columns)` — попадает ли строка под правило (берёт `row.values[index]` по колонке);
   - `cellStyleFromRules(rules, row, columnIndex, zone)` — слияние применимых правил в объект стиля;
   - `rowClassesFromRules(rules, row, zone)` — набор CSS-классов для `scope: "row"` (цвет фона строки).
   Модуль чистый, без Vue — тестируется юнит-тестами.
2. **`TableView.vue`**: передаёт `block.rules` и соответствие «имя колонки → индекс» в `ReportTable`;
   определение зоны строки (`detail`/`subtotal`/`grandtotal`) уже есть в модели.
3. **`ReportTable.vue`**: в `cellStyle(index)` добавить слияние с правилами; для `scope: "row"` —
   класс на `<tr>`, чтобы фон применялся ко всем ячейкам, включая объединённые группы.
4. **Валидатор** (`validate.js`): проверка операторов, типов значений, существования колонок
   (`when.column`, `target`), диапазона `priority`, `between` = массив из двух чисел, `contains` только
   для текстовых полей; предупреждения: правило красит фон, который совпадает с фоном зебры/подытога;
   больше 20 правил — «шаблон сложно поддерживать».
5. **Схема** (`schema.js`): `$defs.rule`, `$defs.condition`, `$defs.ruleStyle`; `blocks[].rules`.
6. **Диаграммы** — не затрагиваются (правила только для таблиц).

## 5. Производительность

Правила считаются на ячейку окна: ~40 строк × 8 колонок × N правил. При 10 правилах это ~3 200 сравнений
на кадр прокрутки — доли миллисекунды. Замер после реализации: рендер 50 000 строк не должен вырасти
больше чем на 5 % от 1,63–1,71 с (принятый бюджет 2 с).

Чтобы не деградировать: не вычислять правила для строк вне окна, не менять модель строк,
не добавлять inline-стили строкам целиком (только классы + CSS-переменные для цветов).

## 6. Пример шаблона

`sales-rules` на данных продаж:

- `profit < 0` → красный текст и жирный, ячейка прибыли;
- `margin between [0, 0.1]` → янтарный фон ячейки рентабельности;
- `amount >= 300000` → подсветка всей строки `#fff7e6`;
- итог и подытоги — без правил (по умолчанию), чтобы не мешать чтению.

## 7. Работы, сроки, критерии приёмки

| ID | Работа | Проверка | Дни |
|---|---|---|---|
| 6.1 | `rules.js`: сравнения, зоны, слияние, приоритеты | 12 юнит-тестов: числа, строки, даты, `null`, `between`, `contains`, конфликт правил | 1,0 |
| 6.2 | Схема и валидатор правил | 10 тестов; 4 битых шаблона дают ошибку с путём | 0,5 |
| 6.3 | Интеграция в `TableView`/`ReportTable` (ячейка и строка) | e2e: цвет текста, фон ячейки, фон строки, правило не задевает итог | 1,0 |
| 6.4 | Шаблон `sales-rules`, разделы в справочнике и примерах | ревью PO, `npm run validate` | 0,5 |
| 6.5 | Замеры и e2e на 50 000 строк | рендер ≤ 1,8 с; правил 10, окно 25–40 строк | 0,5 |
| 6.6 | Скриншот-эталон одного правила | 3 стабильных прогона | 0,5 |
| | **Итого** | | **4,0** |

Критерии приёмки:

1. правило по числу, строке и дате работает; `null` не ломает сравнение;
2. `scope: "cell"` красит только целевую колонку, `scope: "row"` — всю строку, включая объединённые ячейки групп;
3. итог и подытоги затрагиваются только если это явно указано в `zones`;
4. правило не меняет данные, форматы и объединения — только оформление;
5. ошибка в `op`, `column` или `target` — сообщение валидатора с путём, а не молчаливое игнорирование;
6. шаблон без `rules` рендерится идентично версии 1.1;
7. рендер 50 000 строк — не медленнее 1,8 с.

## 8. Риски

| ID | Риск | Реакция |
|---|---|---|
| R1 | Правила конфликтуют между собой | явный `priority`, слияние в порядке объявления, e2e на конфликт |
| R2 | Подсветка фона ломает зебру и подсветку итогов | правило применяется после зебры; предупреждение валидатора при совпадении цветов |
| R3 | Правило на вычисляемую колонку сравнивает не то | сравниваем `row.values[]` (уже посчитанное значение), а не текст; тест на `expression`-колонку |
| R4 | Разрастание правил до нечитаемого шаблона | предупреждение при > 20 правил, рекомендация вынести в пресет позже |
| R5 | Доступность: цвет как единственный носитель смысла | в документации требовать дублировать смысл (жирность/значок), предупреждение при разнице только цвета |
| R6 | Производительность при 50 000 строк | правила только по окну; замер 6.5 как часть приёмки |

## 9. Открытые вопросы к PO

1. **Логика условий**: только одиночные условия в 1.2 или сразу `all`/`any` из 2–3 условий?
   Рекомендация: одиночные + `all`/`any` в пределах объекта (без вложенности), сложные выражения — позже.
2. **Что красить по умолчанию**: только ячейку или ячейку и подытог группы? Рекомендация: ячейка + подытог,
   итог — только по явному `zones`.
3. **Формат правила**: один стиль-объект или ещё «значок» (▲/▼) и «данные-бары»? Рекомендация: в 1.2 только
   стиль; значки и бары — отдельной задачей.
4. **Где хранить правила**: в блоке таблицы (предлагается) или в общей секции `styles.rules`, действующей на все
   таблицы отчёта? Рекомендация: в блоке — правила зависят от колонок набора.
5. **Нужна ли обратная совместимость с пресетами**: правило может ссылаться на «семантические» цвета
   (`danger`, `warning`, `success`) вместо hex, чтобы тёмная тема оставалась читаемой?
   Рекомендация: да, добавить палитру в `styles.palette` и разрешить `colors.text: "danger"`.
