# Администрирование отчётов — проектный план

Цель: список отчётов с действиями, создание нового отчёта, редактирование шаблона в браузере
с подсветкой синтаксиса и проверкой ошибок до сохранения, удаление. Сейчас всё это делается файлами
и `scripts/templates-push.mjs` с последующим рестартом сервиса.

Границы: это **не** визуальный конструктор отчётов из ТЗ §6 (перетаскивание колонок, предпросмотр
без JSON). Редактор работает с JSON-шаблоном, но с подсветкой, валидацией и подсказками.

## 1. Что есть сейчас (факты кода)

| Механизм | Состояние |
|---|---|
| API | только чтение: `/api/health`, `/api/reports`, `/api/reports/{id}`, `/api/reports/{reportId}/lookups/{param}`, `POST /api/report/data` |
| Хранение | `report_templates(id, title, body jsonb, updated_at)` |
| Загрузка | при старте сервиса в память (`templates`, `templatesRaw`); **hot-reload нет** (ADR-21) |
| Запись | только `scripts/templates-push.mjs` (upsert), затем рестарт |
| Валидация | полная — на фронтенде (Ajv + семантический `validate.js`); в сервисе проверок шаблона нет |
| Права БД | соединение под `postgres` (superuser), read-only роль отложена (5.9) |
| Аутентификация | отсутствует (ТЗ §6 выводит её за объём) |

Следствие: любая админка немедленно даёт **возможность исполнять произвольный SQL на сервере**
под суперпользователем. Это главный риск плана, а не UI.

## 2. Что добавляется

### 2.1 API записи

| Метод | Маршрут | Смысл |
|---|---|---|
| `GET` | `/api/admin/reports` | список с `updated_at` и размером тела (для админ-таблицы) |
| `POST` | `/api/reports` | создать: тело `{id, title, body}`; 409 при существующем id |
| `PUT` | `/api/reports/{id}` | заменить шаблон целиком; `id` в теле обязан совпадать с URL |
| `DELETE` | `/api/reports/{id}` | удалить (с подтверждением на клиенте) |
| `POST` | `/api/reports/{id}/validate` | структурная проверка без записи (для кнопки «Проверить») |

Все маршруты записи отвечают `404`, если сервис запущен без `REP_ADMIN=1` — то есть в обычном
демо-режиме их физически нет.

### 2.2 Горячая перезагрузка вместо рестарта (ADR-26)

После успешной записи сервис обновляет `templates` и `templatesRaw` **под мьютексом**: парсинг нового
тела во временные объекты, затем атомарная замена элемента map. Ошибка парсинга → 422 и запись
в БД не выполняется. Это отменяет часть ADR-21: «изменение шаблона требует рестарта» → «рестарт не нужен,
если шаблон сохранён через админку»; `templates-push.mjs` по-прежнему требует рестарта (он пишет в обход
процесса).

### 2.3 История версий

Новая таблица `report_templates_history(id, report_id, body, title, saved_at, saved_by)` — append-only.
При каждом `PUT`/`DELETE` туда уходит предыдущая версия. В админке — «История» и «Откатить» (откат =
обычный `PUT` старой версии, тоже с записью в историю).

### 2.4 Валидация: два уровня

| Уровень | Что проверяет | Почему так |
|---|---|---|
| Клиент (полный) | JSON Schema + семантика: колонки, выражения, `rules`, стили, параметры | валидатор уже есть, двойной порт на C++ дал бы расхождение |
| Сервер (структурный минимум) | JSON разбирается; `version = 1`; `id` = URL; `title` непустой; `params`/`datasets`/`blocks` — массивы/объекты; у `lookup` есть `sql` и нет `queryId`; размер тела ≤ 256 КБ | защита от записи заведомо битого шаблона и от обхода UI |

Честно: сервер **не** повторяет семантическую проверку. Значит шаблон, сохранённый в обход админки,
может сломать рендер — но не данные. Это осознанный компромисс; альтернатива — портировать
`validate.js` на C++ (≈3 дня и риск расхождения правил).

### 2.5 UI: `/admin.html`

- **Список**: `id`, `title`, описание, `updated_at`, кнопки «Открыть», «Изменить», «Дублировать», «Удалить», «Создать».
- **Редактор**: CodeMirror 6 (MIT) с JSON-подсветкой, номерами строк, сворачиванием блоков, поиском;
  панель ошибок валидатора с путём (`blocks.2.columns.4`) и кнопкой «перейти к ключу».
- **Панель действий**: «Проверить», «Сохранить», «Сохранить как…», «Открыть отчёт», счётчик размера.
- **Предпросмотр**: см. вопрос 1 (рекомендация — «сохранить и открыть», без отдельного draft-режима).
- Код админки грузится отдельным чанком: CodeMirror не попадает в бандл отчёта.

## 3. Безопасность

| Риск | Мера |
|---|---|
| SQL из шаблона исполняется под `postgres` | до выполнения 5.9 включить серверный guard: SQL справочников и `datasets` допускается только с `SELECT`/`WITH`, без `;`, `--`, DML/DDL; нарушение → 422 |
| Нет аутентификации | админка и API записи только при `REP_ADMIN=1`; демо-стенд запускается без флага |
| Доступ из сети | `demo.sh` слушает 127.0.0.1; в README — требование не выставлять админку наружу |
| Случайное удаление | подтверждение по вводу `id`, история версий и откат |
| Огромное тело шаблона | лимит 256 КБ, ответ 413 |

Read-only роль (5.9) остаётся обязательной перед любым использованием админки вне локальной машины.

## 4. Работы, сроки, критерии приёмки

| ID | Работа | Проверка | Дни |
|---|---|---|---|
| 7.1 | API записи + `REP_ADMIN` + лимит тела + коды (409/413/422/404) | интеграционные тесты curl-уровня и e2e | 1,5 |
| 7.2 | Hot-reload под мьютексом, атомарная замена | тест: сохранение меняет отчёт без рестарта; битый JSON не ломает работающий сервис | 1,0 |
| 7.3 | История версий, миграция схемы, откат | тест: две правки → две записи истории → откат возвращает прежнее тело | 1,0 |
| 7.4 | Серверный guard SQL (только SELECT), 422 с указанием места | тест: `DROP TABLE`, `UPDATE`, `;` → 422; обычный SELECT проходит | 0,5 |
| 7.5 | Экран списка `/admin.html` с действиями и поиском | e2e: создание, дублирование, удаление | 1,0 |
| 7.6 | Редактор CodeMirror: подсветка, панель ошибок, переход к ключу | e2e: битый JSON показывает ошибку с путём и не сохраняется | 2,0 |
| 7.7 | Превью (по решению вопроса 1) | e2e по выбранному варианту | 1,0 |
| 7.8 | Документация: `docs/admin.md`, README, ADR-26 | ревью PO | 1,0 |
| | **Итого** | | **9,0** |

Критерии приёмки:

1. создать отчёт из админки → он сразу есть в списке и открывается **без рестарта**;
2. сохранить шаблон с синтаксической ошибкой невозможно: валидатор показывает путь, сервер отвечает 422;
3. `queryId` в справочнике и не-SELECT SQL отклоняются на сервере;
4. удаление требует ввода `id`; предыдущая версия доступна в истории и восстанавливается;
5. без `REP_ADMIN=1` маршруты записи отвечают 404, демо-стенд ведёт себя как раньше;
6. отчётная страница не потяжелела: CodeMirror в её бандл не попадает;
7. все 12 существующих шаблонов открываются и редактируются без миграции.

## 5. Риски

| ID | Риск | Реакция |
|---|---|---|
| R1 | Произвольный SQL под superuser через админку | guard SELECT-only (7.4) + 5.9 перед выносом из localhost |
| R2 | Порча шаблона ломает отчёты | серверная структурная проверка, история и откат |
| R3 | Гонка при hot-reload | мьютекс, замена только после успешного парсинга |
| R4 | Расхождение серверной и клиентской валидации | серверная — только структурный минимум, документировано |
| R5 | Вес редактора | отдельный чанк, ленивая загрузка, замер LCP админки |
| R6 | Нет аутентификации → любой в локальной сети может править | флаг `REP_ADMIN`, 127.0.0.1, предупреждение в README |

## 6. Открытые вопросы к PO

1. **Предпросмотр данных**: (а) «сохранить и открыть» — просто, честно, но требует сохранения;
   (б) draft-режим `?draft=1` (шаблон в памяти, без записи в БД); (в) отдельный `POST …/preview`
   с телом шаблона. Рекомендация: (б) — видно результат до публикации, без мусора в списке.
2. **Редактор**: CodeMirror 6 (MIT, ~180 КБ gzip, отдельный чанк) или Monaco (тяжелее, но «как в VS Code»)?
   Рекомендация: CodeMirror 6.
3. **История**: писать снапшот при каждом сохранении (рекомендация) или достаточно `updated_at`
   и отката нет?
4. **Защита SQL**: серверный guard «только SELECT» до 5.9 (рекомендация) или сначала 5.9, потом админка?
5. **Доступ**: только `REP_ADMIN=1` + 127.0.0.1 (рекомендация) или простой токен из env
   (`REP_ADMIN_TOKEN`, заголовок `X-Admin-Token`)?
