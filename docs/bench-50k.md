# Замер рендера: 50 000 строк (DoD §5)

## Что измеряем (ADR-113)

| Метрика | Откуда до куда | Зачем |
|---|---|---|
| `fullMs` | навигация → первая строка таблицы в DOM | то, что чувствует пользователь; **критерий приёмки DoD — 2 000 мс** |
| `renderMs` | конец ответа `/api/report/data` → первая строка | разбор JSON, нормализация строк, рендер — здоровье клиента |
| `apiMs` | запрос и ответ сервера | работа БД и подготовка JSON |

Ранее в DoD приводились цифры 1,63 / 1,71 / 1,47 с без указания границ измерения — их нельзя
сравнивать с полным циклом. Действующее определение — `fullMs`, оно и проверяется скриптом.

## Как воспроизвести

```bash
./scripts/build.sh                 # фронтенд рядом с бинарником
./demo.sh                          # сервер :8080
cd frontend && npx playwright install chromium   # если ещё нет
npx playwright test e2e/global-setup.js --reporter=line   # сохраняет .auth/admin.json
npm run bench                      # node scripts/bench-render.mjs
```

Отчёт `bench-50k` (`backend/templates/bench-50k.json`) — вся таблица `reports_examples.sales`
(50 000 строк, 8 колонок) без фильтров и агрегации. Скрипт меряет `Date.now()` от навигации,
Resource Timing запроса, число строк в DOM и прокрутку в середину; код выхода 1, если `fullMs`
выше 2 000 мс.

## Результат после ADR-114 (компактный ответ)

| Прогон | `fullMs` | `renderMs` | `apiMs` | Строк в DOM | Прокрутка |
|---|---|---|---|---|---|
| 1 | 1 526 мс | 861 мс | 358 мс | 28 | 416 мс |
| 2 | 1 859 мс | 1 084 мс | 399 мс | 28 | 407 мс |
| 3 | 1 551 мс | 839 мс | 360 мс | 28 | 408 мс |

**Бюджет выполнен:** все три прогона ниже 2 000 мс (запас 141–474 мс).

## Как было до ADR-114

| Прогон | `fullMs` | `renderMs` | `apiMs` | Ответ |
|---|---|---|---|---|
| 1 | 2 273 мс | 871 мс | 1 023 мс | 11,9 МБ JSON |
| 2 | 2 000 мс | 780 мс | 872 мс | 11,9 МБ |
| 3 | 1 982 мс | 750 мс | 876 мс | 11,9 МБ |

Сервер отдаёт строки массивами значений (`columns` + `rows: [[...]]`) вместо объектов с именем на
каждое поле, сборка идёт строкой без `Json::Value` на строку. Ответ — с 11,9 МБ до **4,3 МБ**, время
сервера — с 872–1 023 мс до **358–399 мс**. Клиент платит приведением массивов к объектам
(~840–1 080 мс `renderMs` против 750–871 мс), суммарный выигрыш 400–750 мс.

Прочее не изменилось: gzip включён, в DOM 28 строк из 50 000, прокрутка ~0,4 с.

## Вывод

- `fullMs` **1 526–1 859 мс** при бюджете 2 000 мс — критерий DoD выполнен;
- `renderMs` 839–1 084 мс — рендер и приведение строк, с запасом до 2 с;
- `apiMs` 358–399 мс — сервер перестал быть узким местом;
- резерв остаётся в клиенте: приведение строк дороже самого рендера (в DOM всё равно 28 строк);
  следующий шаг, если понадобится, — учить движок работать с массивами напрямую.
