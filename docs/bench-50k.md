# Замер рендера: 50 000 строк (DoD §5)

## Что измеряем (ADR-113)

| Метрика | Откуда до куда | Зачем |
|---|---|---|
| `fullMs` | навигация → первая строка таблицы в DOM | то, что чувствует пользователь; **критерий приёмки DoD — 2 000 мс** |
| `renderMs` | конец ответа `/api/report/data` → первая строка | разбор JSON, нормализация строк, рендер — здоровье клиента |
| `apiMs` | запрос и ответ сервера | работа БД и подготовка JSON |

Ранее в DoD приводились цифры 1,63 / 1,71 / 1,47 с без указания границ измерения — их нельзя
сравнивать с полным циклом. Действующее определение — `fullMs`, оно и проверяется скриптом.

## Как воспроизвести

```bash
./scripts/build.sh                 # фронтенд рядом с бинарником
./demo.sh                          # сервер :8080
cd frontend && npx playwright install chromium   # если ещё нет
npx playwright test e2e/global-setup.js --reporter=line   # сохраняет .auth/admin.json
npm run bench                      # node scripts/bench-render.mjs
```

Отчёт `bench-50k` (`backend/templates/bench-50k.json`) — вся таблица `reports_examples.sales`
(50 000 строк, 8 колонок) без фильтров и агрегации. Скрипт меряет `Date.now()` от навигации,
Resource Timing запроса, число строк в DOM и прокрутку в середину; код выхода 1, если `fullMs`
выше 2 000 мс.

## Результат (локальная машина, 2026-11-12)

| Прогон | `fullMs` | `renderMs` | `apiMs` | Строк в DOM | Прокрутка |
|---|---|---|---|---|---|
| 1 | 2 273 мс | 871 мс | 1 023 мс | 28 | 416 мс |
| 2 | 2 000 мс | 780 мс | 872 мс | 28 | 407 мс |
| 3 | 1 982 мс | 750 мс | 876 мс | 28 | 408 мс |

Холодный прогон сразу после старта сервера — 3 304 мс (`apiMs` 1 478 мс), в таблицу не входит.

- ответ данных — 11,9 МБ JSON, с `Content-Encoding: gzip` — 855 КБ (сжатие включено);
- в DOM одновременно 28 строк из 50 000 — виртуализация работает, прокрутка перерисовывает окно
  за ~0,4 с;
- клиентская обработка (`renderMs`) — 750–871 мс, с большим запасом до 2 с;
- сервер (`apiMs`) — 872–1 023 мс и он же основной вклад в полный цикл.

## Вывод

- **рендер выполняется с запасом**: 750–871 мс при бюджете 2 000 мс;
- **полный цикл — на границе и выше**: 1 982 / 2 000 / 2 273 мс, то есть бюджет по `fullMs`
  **не подтверждён** (два прогона в бюджете, один выше; разброс 291 мс);
- узкое место — серверная часть (~0,9–1,0 с), а не таблица: 50 000 строк раскладываются в DOM
  за 750–870 мс, из которых рендер видимых 28 строк — доли.

Чтобы `fullMs` стабильно укладывался в 2 с, нужно снять ~300 мс: компактный формат ответа
(колонки + массивы значений вместо объектов на строку) и/или ускорение выборки на сервере.
Это отдельная задача; бюджет рендера при этом уже выполнен.
