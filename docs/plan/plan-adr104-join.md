# ADR-104 (план реализации): объединение наборов из разных источников

Статус: **план на утверждение** (реализация не начата). Вариант A из сравнения
вариантов от 2026-11-12: декларативный `join` в шаблоне, hash join в прокси.
Оценка: 8 рабочих дней, этапы 1–8 ниже.

## 1. Цель и границы

Дать шаблону возможность собрать один набор данных из двух источников — например, факты
из PostgreSQL и справочник регионов/менеджеров из REST-сервиса — связать их по полям и
показать как обычную таблицу с агрегацией, подытогами, экспортом и печатью.

Входит в v1:
- REST-источник (`kind: "rest"`) — GET, JSON, выборка массива по `rowsPath`, объявленные колонки;
- набор вида `join`: левая и правая стороны — объявленные наборы (`sql` или `rest`), связь 1–4 пары полей,
  `inner` / `left`, набор добавляемых колонок правой стороны;
- join-набор участвует в `/api/report/data`, `/aggregate`, `/group`, `/text`, `/export.xlsx`,
  `/export.csv`, справочниках параметров (`lookups`) — то есть везде, где сейчас участвует SQL-набор;
- кеш, лимиты, понятные ошибки, валидация на клиенте и сервере (parity), пример и e2e.

Не входит в v1 (осознанно):
- цепочки join'ов (A⋈B⋈C) — только один уровень;
- REST POST/GraphQL, XML, вложенные объекты в колонках, пагинация REST (один запрос, лимит);
- материализация REST в temp-таблицу PostgreSQL (вариант B) и ETL-staging (вариант C);
- join «много ко многим» с дедупликацией: дубли справа размножают строки (как в SQL), это
  документируется, а не исправляется;
- `join` как источник для другого `join` (запрещено валидатором).

## 2. Схема шаблона

### 2.1. Источник REST в блоке `connections`

```json
"connections": {
  "crm": {
    "kind": "rest",
    "baseUrl": "${CRM_BASE_URL}",
    "headers": {
      "Accept": "application/json",
      "Authorization": "Bearer ${CRM_TOKEN}"
    },
    "timeoutMs": 5000,
    "cacheSeconds": 30
  }
}
```

| Поле | Тип | Правило |
|---|---|---|
| `kind` | string | `"rest"` (было зарезервировано, ADR-76) |
| `baseUrl` | string | `${ENV}` разрешается при первом использовании; `http`/`https`, без query |
| `headers` | object | значения — строки; `${ENV}` разрешается; секреты только так |
| `timeoutMs` | int | 100…30000, по умолчанию 5000 |
| `cacheSeconds` | int | 0…3600, по умолчанию 0 (без кеша) |

Пароль/токен в шаблоне запрещён: значение заголовка с `Bearer ` без `${…}` валидатор
считает ошибкой, как `passwordEnv` для PostgreSQL (ADR-76).

### 2.2. REST-набор

```json
"datasets": {
  "regions": {
    "connection": "crm",
    "rest": {
      "path": "/api/regions",
      "query": { "active": "1" },
      "rowsPath": "items",
      "columns": [
        { "field": "id", "type": "int" },
        { "field": "name", "type": "text", "title": "Регион" },
        { "field": "manager", "type": "text" }
      ]
    }
  }
}
```

- `path` — обязателен, начинается с `/`; `query` — строки (литералы, без `${}`, кроме baseUrl/headers);
- `rowsPath` — путь к массиву через точку (`items`, `data.rows`); пусто — корень ответа;
- `columns` — обязательны, потому что типы из JSON неоднозначны (`"1"` / `1`);
  `type`: `text|int|float|date|datetime|bool`; `title` — для UI и экспорта;
- отсутствующее в ответе поле → пустое значение; лишние поля игнорируются;
- ответ не-массив после `rowsPath` → 422 `REST_INVALID`;
- размер ответа > `REP_REST_MAX_BYTES` (5 МБ) → 422 `REST_TOO_LARGE`.

### 2.3. Набор-объединение

```json
"datasets": {
  "orders": {
    "connection": "main",
    "params": { "from": "$from", "to": "$to" },
    "sql": "SELECT region_id, order_date, amount, qty FROM reports_examples.sales WHERE order_date BETWEEN :from::date AND :to::date"
  },
  "regions": { "connection": "crm", "rest": { "…": "…" } },
  "orders_by_region": {
    "join": {
      "left": { "dataset": "orders" },
      "right": { "dataset": "regions" },
      "on": [{ "left": "region_id", "right": "id", "type": "int" }],
      "type": "left",
      "columns": [
        { "field": "name", "as": "region_name", "title": "Регион", "type": "text" },
        { "field": "manager", "title": "Менеджер", "type": "text" }
      ]
    }
  }
}
```

- `left`/`right.dataset` — ключи из `datasets`; набор-источник обязан быть `sql` или `rest`,
  не `join` (без циклов и цепочек);
- `on[]` — 1…4 пары, `type` по умолчанию `text`; ключи нормализуются по типу перед сравнением
  (`int` → целое, `text` → обрезка пробелов, `date` → ISO `YYYY-MM-DD`);
- `type`: `inner` (по умолчанию) | `left`;
- `columns[]` — колонки правой стороны, попадающие в результат: `field` (имя в правом наборе),
  `as` (имя в результате, по умолчанию = `field`), `title`, `type`;
- колонки результата = колонки левого набора (в его порядке) + `join.columns` (в объявленном порядке);
- имена в `as` не должны совпадать с колонками левого набора — иначе ошибка валидации
  (переименуйте через `as`);
- `join` несовместим с `sql`/`rest`/`params` в одном наборе (ровно один вид набора).

### 2.4. Семантика (одинаково для всех endpoint'ов)

| Ситуация | `inner` | `left` |
|---|---|---|
| совпадение ключа | строка с колонками правой стороны | то же |
| нет совпадения | строка отбрасывается | строка есть, правые колонки пустые |
| пустой ключ слева (`""`, null) | отбрасывается | пустые правые колонки |
| дубли ключа справа | каждая пара — строка (размножение) | то же |
| ключ приведён к int, но не число | считается несовпавшим (в лог — предупреждение) | пустые колонки |

## 3. REST-коннектор: безопасность и поведение

- **Allowlist обязателен.** `REP_REST_ALLOW_HOSTS` — список хостов через запятую
  (`crm.example.com,127.0.0.1:8099`). Пусто — REST-источники отключены, ответ 422
  `REST_FORBIDDEN` с текстом «REST-источники запрещены: задайте REP_REST_ALLOW_HOSTS».
  Это защита от SSRF: шаблон не может ходить на произвольный адрес, включая localhost и
  metadata-сервисы.
- **Секреты** — только `${ENV}`; в логах заголовки не печатаются, при ошибке в текст попадают
  хост и путь без query.
- **Таймауты:** `timeoutMs` (соединение и чтение), общий бюджет запроса —
  `REP_REST_TOTAL_TIMEOUT_MS` (по умолчанию 10000); превышение → 504 `REST_TIMEOUT`.
- **Редиректы** не следуем (иначе allowlist обходится): 3xx → 422 `REST_INVALID`.
- **Кеш ответа:** LRU на 128 записей, ключ = `baseUrl + path + query + hash(headers)`;
  TTL `cacheSeconds`; заголовок ответа `X-Rest-Cache: hit|miss` (для диагностики, не наружу —
  только в логах).
- **Параллельность:** `drogon::HttpClient` (async), не блокируем event loop; join считается
  в пуле потоков (`drogon::async_run`), потому что 50k×5k — 38 мс.
- **Ошибки:** 422 `REST_ERROR` (не 200, не пустая таблица), текст — «источник crm: /api/regions
  ответил 503». Для `left`-join недоступность правой стороны — тоже ошибка, а не пустые колонки:
  иначе отчёт молча покажет неполные данные.

## 5. API и коды ошибок

- `POST /api/report/data` — без изменений в контракте: `{reportId, dataset, params}`; для
  join-набора `dataset` = ключ объединения, ответ тот же `{columns, rows, rowCount, truncated}`.
- `POST /api/report/aggregate`, `/group`, `/text`, `/export.*` — без изменений в контракте,
  внутри исполняют join-набор тем же `fetchDataset`.
- Новые коды: `REST_FORBIDDEN` (allowlist), `REST_ERROR` (не-2xx/сеть), `REST_TIMEOUT` (504),
  `REST_INVALID` (не JSON/не массив/редирект), `REST_TOO_LARGE`, `JOIN_NOT_SUPPORTED`
  (join-набор в join), `JOIN_INVALID` (битая спецификация — не должно доходить из-за валидатора).
- `ROW_LIMIT` (уже есть) — при превышении `REP_JOIN_MAX_ROWS` или `REP_MAX_ROWS`: 422 с
  указанием, какая сторона и сколько строк.

## 6. Производительность и лимиты

Замеры (этот хост, C++17, jsoncpp):

| Сценарий | Время | Память |
|---|---|---|
| hash join 50 000 × 5 000, 8 колонок в результате | 36–38 мс | ~43 МБ peak (с деревом JSON; на строках ~15–20 МБ) |
| REST 5 000 объектов, 441 КБ (локально) | 2–5 мс | — |
| разбор 441 КБ jsoncpp | 7–8 мс | — |
| REST из внешней сети (оценка) | 50–300 мс | — |

- `REP_JOIN_MAX_ROWS` (200 000) — предел строк каждой стороны; выше — 422 `ROW_LIMIT`;
- `REP_MAX_ROWS` (50 000) — предел результата (как сейчас);
- кеш результата (60 с, ADR-32) работает для join-набора как для обычного; REST-кеш —
  отдельный, по `cacheSeconds`;
- при `rowCount` > 50 000 в таблицу не отдаём (существующее поведение), для анализа — агрегация.

## 7. Валидация (клиент, сервер, parity)

Правила (одинаковые в `validate.js` и `validate.cc`):

1. `datasets.<key>` содержит ровно одно из `sql`, `rest`, `join`.
2. `rest`: `connection` обязателен и указывает на `kind: "rest"`; `path` с `/`; `rowsPath` — точки
   между сегментами; `columns` непусты, `type` из списка, имена уникальны; заголовок с секретом
   без `${…}` — ошибка `rest.headers.<name>`.
3. `join`: `left.dataset` и `right.dataset` существуют, оба — `sql`/`rest` (не `join`);
   `on` 1…4, `left`/`right` непусты; `type` из `inner|left`; `columns` непусты; `as` уникальны и не
   пересекаются с колонками левого набора (проверяем по объявленным колонкам `sql`, если они есть
   в блоке; иначе — только `as` между собой).
4. Набор не ссылается на себя (`left.dataset == key` и т.п.) и нет цикла из двух наборов.
5. `public: true` + набор с `rest` — **предупреждение**: «анонимный пользователь получит данные
   REST-источника; убедитесь, что это допустимо».
6. `accessRoles`/`public` — без изменений (ADR-102/103); join-набор доступен по тем же правилам,
   что и отчёт.

Parity: 12 новых фикстур в `docs/fixtures/validation-cases.json` (по одному на каждое правило +
валидные `inner`/`left`/REST), `validate.parity.test.js` сверяет с сервером.

## 11. Риски

| Риск | Как снимаем |
|---|---|
| SSRF через шаблон | allowlist хостов обязателен, без него REST выключен; редиректы запрещены |
| Утечка токена | секреты только `${ENV}`; заголовки не логируются; валидатор ловит литеральные `Bearer …`/`token=…` |
| Объём: два больших набора | `REP_JOIN_MAX_ROWS`, `REP_MAX_ROWS`, 422 с числами; в v1 нет цепочек |
| Размножение строк при дублях справа | документируется; в лог — предупреждение с числом дублей |
| Недоступный REST в момент отчёта | 422 `REST_ERROR` (не пустые колонки); кеш снижает частоту обращений |
| «Свежесть» данных REST | `cacheSeconds` по умолчанию 0; для тяжёлых источников — 30 с в шаблоне |
| Разные типы ключей (`int` vs `text`) | явный `type` в `on[]`, нормализация, иначе несовпадение и предупреждение в лог |
| Регрессия существующих шаблонов | SQL-путь не меняется; parity + полный прогон, e2e «все шаблоны» |
| Публичный отчёт + REST | предупреждение валидатора; решение PO (см. вопрос 5) |

## 12. Приёмка (DoD)

1. Шаблон `sales-crm`: PostgreSQL (50k) + REST (5k) → таблица с колонками правой стороны, ИТОГО,
   подытоги по региону; экран, Excel, печать, CSV.
2. `join` с `left`: строка без пары остаётся, правые колонки пусты.
3. Ошибки: allowlist пуст → `REST_FORBIDDEN`; REST недоступен → `REST_ERROR` с текстом; не-массив →
   `REST_INVALID`; превышение лимита → `ROW_LIMIT` с числами.
4. Валидатор: 12 parity-фикстур зелёные на клиенте и сервере; публикация шаблона с циклом/дублем
   `as`/секретом в заголовке отклоняется.
5. Производительность: 50k×5k — не более 100 мс на join (замер в e2e/логе), память прокси
   не растёт после запроса (без утечек в кеше).
6. Полный `REP_E2E=1 ./scripts/check.sh` — `ALL CHECKS PASSED`; реестр ADR актуален; версия 1.79.0.
