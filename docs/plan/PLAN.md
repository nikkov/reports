## 1. Принятые архитектурные решения (ADR)

Каждое решение закрывает конкретное противоречие или пробел ТЗ. Изменение любого пункта — через раздел 9 (управление изменениями).

Формат записи единый — четыре части, чтобы решение читалось за минуту:

- **Проблема** — что было не так и какое противоречие закрывалось;
- **Решение** — что именно принято (поля, таблицы, маршруты, замеры);
- **Следствия** — что изменилось в коде, поведении и цифрах;
- **Ограничения** — чего решение не делает и где сломается.

Полный реестр с оглавлением и якорями — `docs/adr.md` (генерируется: `node scripts/adr.mjs`);
при добавлении ADR правится этот файл, реестр пересобирается, актуальность и наличие четырёх частей
проверяет `./scripts/check.sh` (`node scripts/adr.mjs --check`).

**ADR-1. Единственный источник истины для таблицы — плоская модель строк.**
- **Проблема:** `mergeCells` в vxe-table адресуется индексами строк и колонок, а сворачивание групп и вставка строк итогов эти индексы меняют. ТЗ называло риски для пар «`footerMethod` × `mergeCells`» и «`subtotals` × `mergeCells`», но не для третьей — «`collapsible` × `mergeCells`».
- **Решение:** Движок отдаёт `FlatRow[]`: `{ kind: 'detail' | 'subtotal' | 'grandtotal', level, groupPath: string[], groupId, visible, cells }`. Колонки, объединения и общий итог выводятся из этого массива, а не из состояния табличного компонента.
- **Следствия:** Все три риска снимаются конструктивно: рендер, объединения и итоги читают одну структуру.
- **Ограничения:** Модель плоская — иерархия живёт только в `groupPath` и `level`; строки отчёта целиком держатся в памяти клиента (до 50 000).

**ADR-2. Общий итог — последняя строка массива, `footerMethod` не используется.**
- **Проблема:** Подвал компонента и объединения ячеек могут разъехаться: подвал считался отдельным проходом (§3 ТЗ).
- **Решение:** Строка общего итога — последняя строка того же массива (ADR-1); `footerMethod` не применяется.
- **Следствия:** Выравнивание по листовым колонкам получается автоматически: итог строится тем же маппингом, что заголовки.
- **Ограничения:** Итог всегда в конце — вставить «промежуточный итог» посреди таблицы нельзя; отдельного API подвала нет.

**ADR-3. Группировка описывается только колонками, `groupBy` в шаблоне отсутствует.**
- **Проблема:** ТЗ содержало два источника истины: `groupBy: [...]` в шаблоне и `columns[].group: true`.
- **Решение:** Оставлен один: порядок колонок с `group: true` задаёт порядок группировки. Подытоги — `subtotal: true` на групповой колонке вместо массива `subtotals`.
- **Следствия:** Одна декларация вместо двух; валидатор требует, чтобы групповая колонка шла до обычных.
- **Ограничения:** Группировать можно только по отображаемым колонкам; скрытая группировка невозможна.

**ADR-4. Шаблоны и SQL живут на сервере.**
- **Проблема:** Шаблон в бандле дублировался бы, а SQL оказался бы в браузере.
- **Решение:** `backend/templates/<id>.json` и `backend/config/queries.json` в репозитории; Drogon валидирует оба на старте и не поднимается при ошибке (fail-fast). Фронтенд получает шаблон по `GET /api/reports/{id}`. В dev-режиме — горячая перезагрузка шаблонов.
- **Следствия:** Единый источник шаблонов и SQL; битый файл останавливает сервис, а не ломает отчёты на ходу.
- **Ограничения:** Хранение шаблонов в БД позже заменило ADR-21; горячая перезагрузка осталась только в режиме `REP_TEMPLATES_SOURCE=files`.

**ADR-5. Параметры — часть шаблона, состояние — в URL.**
- **Проблема:** Ссылку на построенный отчёт нужно передавать и воспроизводить.
- **Решение:** Шаблон объявляет `params: [{name, type, label, required, default, options?}]`; `ReportViewer` строит форму, значения уходят в API и в query-строку (`/reports/sales?from=2026-01-01&to=2026-03-31`).
- **Следствия:** Ссылка воспроизводима, перезагрузка страницы сохраняет выбор.
- **Ограничения:** В версиях 1.0–1.3 `select` брался из статического `options`; справочники из БД появились отдельно (ADR-22, ADR-24).

**ADR-6. SQL — только подготовленные выражения с именованными параметрами.**
- **Проблема:** Подстановка значений в текст SQL открывает инъекцию через параметр отчёта.
- **Решение:** `queries.json` хранит SQL с именованными параметрами (`:from::date`); значения передаются только через binding. Проверка — ревью плюс тест на попытку инъекции.
- **Следствия:** Значения параметров не попадают в текст запроса; `::` остаётся кастом типа.
- **Ограничения:** Сам SQL — доверенный ввод автора шаблона; его прикрывают guard «только SELECT» (ADR-26) и роль только-чтения (ADR-33).

**ADR-7. Агрегация только на клиенте; на сервере — лимиты вместо агрегатов.**
- **Проблема:** ТЗ §2 требует клиентскую агрегацию, но выборка может не влезть в браузер.
- **Решение:** Сервер не считает агрегатов: `maxRows = 50000` (превышение — 422 `ROW_LIMIT`), `statement_timeout` на соединении (сейчас по умолчанию 30 000 мс, `REP_STATEMENT_TIMEOUT_MS`), отмена запроса через `AbortController`. Запасной вариант ТЗ «кэш агрегатов на бэкенде» отклонён.
- **Следствия:** Одна реализация семантики агрегации; браузер защищён лимитом и таймаутом.
- **Ограничения:** 50 000 строк — жёсткий потолок клиентского режима; при росте объёмов нужен серверный `GROUP BY` (сделан в ADR-37).

**ADR-8. Числа: `int` (включая bigint), `float`, `string`, `date`, `bool`; без decimal-типа.**
- **Проблема:** Нужна арифметика денег без ошибок округления и без нового типа.
- **Решение:** Десятичного типа нет: деньги хранятся и агрегируются целыми минорными единицами, округление выполняется только при выводе.
- **Следствия:** `double` точен до 2^53 — при 50 000 строк и значениях в минорных единицах переполнение недостижимо (проверяется тестом-стражем).
- **Ограничения:** Копейки нельзя хранить во `float`; сумма в минорных единицах должна помещаться в 2^53.

**ADR-9. Ошибки и `null` в выражениях — типизированы.**
- **Проблема:** Без правил `null` и деление на ноль давали бы разный результат в разных местах.
- **Решение:** Любой `null`-операнд → `null`; деление на 0 → `null`; `NaN`/`Infinity` → `null`. В ячейке `null` рендерится как `nullText` (по умолчанию «—»), пустая группа или пустой ключ → «(пусто)».
- **Следствия:** Одинаковое поведение движка на клиенте и в тестах.
- **Ограничения:** Пользователь не отличает «нет данных» от «нечисловое значение» — оба показываются как `nullText`.

**ADR-10. vxe-table — только MIT-ядро, фиксированная версия.**
- **Проблема:** В README vxe-table (4.x) как enterprise помечены сводные данные, агрегатные функции, выделение/copy-paste/поиск и встроенные диаграммы — коммерческая лицензия.
- **Решение:** Разрешено только бесплатное ядро: многоуровневые заголовки, подвал, объединения, группировка, виртуальный скролл. Версия пинована, внесена в `THIRD_PARTY.md`, CI проверяет отсутствие enterprise-API регуляркой.
- **Следствия:** Лицензионная чистота подтверждается автоматически.
- **Ограничения:** Позже vxe-table выведен из зависимостей вовсе (ADR-20); проверка осталась стражем на случай возврата.

**ADR-11. Все агрегаты и выражения считает собственный движок.**
- **Проблема:** Библиотеки выражений (`expr-eval` и подобные) не знают областей действия и агрегатных функций.
- **Решение:** Движок выражений и агрегатов написан свой (TypeScript): области row / group / grand total, функции `sum`, `avg`, `min`, `max`, `count`, `countDistinct`.
- **Следствия:** Правила одинаковы во всех зонах; лишней зависимости нет.
- **Ограничения:** Грамматика закрытая: сложные условия выносятся отдельным шагом (ADR-25), `median` и перцентили не поддерживаются.

**ADR-12. Форматы — закрытый каталог.**
- **Проблема:** Произвольные шаблоны форматирования дают расхождения между экраном, Excel и письмом.
- **Решение:** Каталог: `number` (разделитель тысяч — неразрывный пробел, `decimals` 0), `percent` (вход 0..1, вывод ×100, `decimals` 1), `currency` (₽/$/€, `decimals` 2), `date` (dd.MM.yyyy), `integer`. Локаль ru-RU фиксирована.
- **Следствия:** Один код форматирования на экран, `.xlsx` и печать.
- **Ограничения:** Своих форматов нет; локаль не переключается.

**ADR-13. Conan v1 — единственный пакетный менеджер C++; вызов только из venv.**
- **Проблема:** В `PATH` (`~/.local/bin/conan`) стоит Conan 2.28.1 с кэшем `~/.conan2`, а нужен v1 (1.66.0) с кэшем `~/.conan`; смешивание кэшей недопустимо.
- **Решение:** Любой вызов — `~/python_venv/bin/conan` или обёртка `scripts/conan`; `check.sh` падает при версии ≠ 1.66.x. Опции drogon: `with_postgres=True`, `with_orm=True`, `with_boost=False`, `with_brotli=False`, `with_profile=False`.
- **Следствия:** Сборка воспроизводима; генератор `cmake_find_package_multi`, `libcxx=libstdc++11`.
- **Ограничения:** Первая сборка из исходников — 15–25 мин; Conan 2 не поддерживается; brotli выключен, потому что рецепт не прокидывает include-пути.

**ADR-14. Catch2 v3 — тесты C++.**
- **Проблема:** Ядро нужно тестировать без HTTP-слоя и без браузера.
- **Решение:** `catch2/3.7.1`, `Catch2::Catch2WithMain`, отдельная цель `rep_tests`, регистрация в `ctest`. Интеграционные тесты ходят в реальную БД и убирают за собой данные.
- **Следствия:** Парсинг, параметры, агрегация, миграции, валидация и экспорт проверяются за секунды.
- **Ограничения:** Тесты с БД требуют живого PostgreSQL; HTTP-контракт и рендер проверяются e2e, а не Catch2.

**ADR-15. Секреты — только через `.env`.**
- **Проблема:** Пароли БД и SMTP не должны попадать в репозиторий, логи и тексты ошибок.
- **Решение:** `backend/.env` (в `.gitignore`) плюс `.env.example` с плейсхолдерами; DSN и SMTP читаются из окружения, пароли не логируются.
- **Следствия:** Репозиторий чистый; на сервере используется `EnvironmentFile` systemd (путь меняется `REP_ENV_FILE`).
- **Ограничения:** Файл `.env` лежит рядом с бэкендом — при переносе артефактов его нужно положить отдельно.

**ADR-16. Синтетические данные — детерминированный SQL-генератор.**
- **Проблема:** Эталонам и тестам нужны воспроизводимые данные.
- **Решение:** `db/schema.sql` (таблицы `sales`, `finance`, `ops`) и `db/seed.sql` (`setseed()` + `generate_series`): 50 000 фактов, 3 иерархии, намеренные `null`-ключи, нулевые знаменатели, отрицательные суммы, строка-выброс. Экспорт эталонов — через `psql`. Python-генератор не заводится.
- **Следствия:** Один seed питает и стенд, и golden-тесты.
- **Ограничения:** Данные синтетические: 50 000 строк хватает для бюджета рендера, но это не «большие данные».

**ADR-17. PostgreSQL 18.6 на 192.168.0.3:32770 — общий инстанс, работаем только в своей БД.**
- **Проблема:** Инстанс общий: чужие базы и объекты трогать нельзя.
- **Решение:** Работаем в БД `reporting`, DDL — только в схеме `public`; база создаётся идемпотентно `db/init.sh`.
- **Следствия:** Чужие БД не читаются и не меняются; стенд поднимается с нуля одной командой.
- **Ограничения:** Сервер 18.6, клиент `psql` 15.14 — фичи PG18 в коде не используются; локальный Postgres в Docker — только резерв для тестов.

**ADR-18. Типы колонок объявляются рядом с SQL.**
- **Проблема:** Drogon не отдаёт OID и типы колонок результата — только имена.
- **Решение:** Типы перечисляются в описании набора (`columns: {имя: int|float|text|date|bool}`); если колонка не объявлена, тип выводится из первого непустого значения.
- **Следствия:** Фронтенд знает типы до прихода данных — это нужно для форматирования и группировки.
- **Ограничения:** Схема дублируется рядом с SQL; ошибка объявления даёт неверное форматирование, а не падение. После ADR-27 обязательные объявления ушли, осталось выведение по значению.

**ADR-19. (заменён ADR-20) Сгруппированные таблицы рендерятся постранично.**
- **Проблема:** Замер спайка S1: `mergeCells` с большими `rowspan` вместе с виртуальным скроллом блокирует главный поток (> 60 с на 20 000 строк).
- **Решение:** Сгруппированная таблица показывает 200 строк на страницу, объединения считаются в пределах страницы.
- **Следствия:** Страница перестала зависать: 200 строк — 861 мс, 1 000 — 2 690 мс, 2 000 — 4 818 мс.
- **Ограничения:** Объединение не переносится через границу страницы; узкое место оказалось в базовом рендере vxe-table (2,4–4 мс/строку), поэтому решение заменено ADR-20.

**ADR-20. Свой лёгкий рендерер таблиц на Vue вместо vxe-table.**
- **Проблема:** vxe-table рендерит 2,4–4 мс/строку, а `mergeCells` с виртуальным скроллом вешает страницу (ADR-19).
- **Решение:** Собственный компонент `ReportTable`: нативная `<table>`, `rowspan`/`colspan` из модели ADR-1, своя витрина по фиксированной высоте строки, sticky-подпись группы. Это отклонение от ТЗ §2 (там назван vxe-table), согласовано постановщиком.
- **Следствия:** 50 000 строк укладываются в бюджет 1,63–1,71 с; vxe-table выведен из зависимостей; лицензионный манифест сократился.
- **Ограничения:** Свой код вместо библиотеки — сопровождение на нас; печать потребовала отдельного слоя (вариант A, версия 1.4.4).

**ADR-21. Шаблоны отчётов хранятся в БД.**
- **Проблема:** Шаблоны в файлах не редактируются через админку и не имеют истории; кроме того, PO решил хранить их в базе.
- **Решение:** Таблица `report_templates(id, title, body jsonb, updated_at)`; файлы `backend/templates/*.json` остаются источником в репозитории, `scripts/templates-push.mjs` загружает их в БД (upsert, dollar-quoting). Сервис читает шаблоны из БД на старте (`REP_TEMPLATES_SOURCE=db`), валидирует и держит в памяти.
- **Следствия:** Правка шаблона идёт через БД и админку; `GET /api/reports/{id}` отдаёт исходный JSON.
- **Ограничения:** Загруженные скриптом шаблоны требуют перезапуска сервиса; правки через админку применяются без рестарта (ADR-26).

**ADR-23. Внешний вид таблицы задаётся шаблоном (версия 1.1).**
- **Проблема:** Оформление было зашито в CSS компонента: заказчик не мог задать шрифты, цвета, ширины и высоты без правки кода.
- **Решение:** Необязательная секция `styles` + `blocks[].styles` + `columns[].style`: шрифты, цвета, выравнивание, отступы, ширины, высоты зон, границы, зебра. Реализация — CSS-переменные на корне таблицы и классы зон, без inline-стилей на ячейках; виртуализация переведена с умножения на `rowHeight` на префиксные суммы с бинарным поиском.
- **Следствия:** Оформление переносится в шаблон; 50 000 строк сохраняют производительность.
- **Ограничения:** Переменная высота строки (перенос текста) и условное форматирование в 1.1 не входили — они появились отдельными решениями.

**ADR-24. SQL справочников параметров живёт в шаблоне.**
- **Проблема:** Справочники обслуживались реестром `queries.json`: чтобы добавить фильтр, нужно было править серверный файл (требование PO, заменяет часть ADR-22).
- **Решение:** `params[].source` с `kind: "lookup"` содержит `sql` и не содержит `queryId` (валидатор запрещает). `GET /api/reports/{reportId}/lookups/{param}` берёт SQL из шаблона, `GET /api/reports/{id}` вырезает его из публичного ответа.
- **Следствия:** Справочник добавляется вместе с отчётом; браузер SQL не видит; 6 шаблонов переведены на `source.sql`.
- **Ограничения:** Серверного кэша справочников нет (кэш только на клиенте); тяжёлый SQL прикрывают `statement_timeout` и роль только-чтения.

**ADR-25. Условное форматирование — декларативные правила в блоке таблицы (версия 1.2).**
- **Проблема:** Подсветку «плохих» значений нельзя было задать шаблоном, а только кодом.
- **Решение:** `blocks[].rules[]`: `when {column, op, value}`, `apply` (стиль-объект как у зон), `scope` (`cell`/`row`), `zones` (`detail`/`subtotal`/`grandtotal`), `priority`. Операторы `= != > >= < <= between empty notEmpty contains`.
- **Следствия:** Правила сравнивают сырые значения, поэтому работают и для вычисляемых колонок; форматирование чисел применяется после правил; считаются только для видимого окна.
- **Ограничения:** В модель строк правила не попадают — Excel и печать переносят лишь совпадения, пересчитанные на клиенте; сложные условия выражениями не описываются.

**ADR-26. Администрирование отчётов: запись через API с hot-reload (версия 1.3).**
- **Проблема:** Правка отчёта требовала правки файлов, коммита и перезапуска сервиса.
- **Решение:** `GET /api/admin/reports`, `POST /api/reports`, `PUT /api/reports/{id}`, `DELETE /api/reports/{id}`, `POST /api/reports/{id}/validate`; всё доступно при `REP_ADMIN=1`. После записи шаблон в памяти обновляется под мьютексом.
- **Следствия:** Правки из админки применяются без рестарта; история версий — `report_templates_history`, откат = запись прежней версии.
- **Ограничения:** Валидация двухуровневая (клиент — полная, сервер — структурный минимум; позже серверная стала полной, ADR-45); `templates-push.mjs` пишет в обход процесса и по-прежнему требует рестарта.

**ADR-27. SQL наборов данных живёт в шаблоне.**
- **Проблема:** Наборы данных ссылались на реестр `queries.json`: отчёт нельзя было завести без правки серверного файла (требование PO, заменяет ADR-4/ADR-21 в части запросов).
- **Решение:** `datasets.<key>` содержит `sql` (обязателен) и `params` (отображение «параметр SQL → параметр отчёта»); `queryId` запрещён на клиенте и на сервере. Публичный `GET /api/reports/{id}` вырезает `datasets.*.sql`, админский отдаёт полный шаблон.
- **Следствия:** Отчёт самодостаточен; 12 шаблонов переведены на `datasets.sql`; реестр `queries.json` сокращён до служебного `slow_probe`.
- **Ограничения:** SQL исполняется под ролью сервиса — его прикрывают guard «только SELECT» и роль только-чтения; тип параметра определяется кастом в SQL.

**ADR-28. Экспорт в Excel и печатный вид (версия 1.4).**
- **Проблема:** Пользователю нужен файл, совпадающий с экраном (группировка, подытоги, форматы, правила), и печать без потери шапки.
- **Решение:** Excel собирается на клиенте из модели витрины (ExcelJS, MIT, ленивый чанк): объединения шапки, подытоги, `numFmt`, цвета зон, совпадения правил, лист «Параметры». Печать — `@media print` + `window.print()`, шапка повторяется, группы не разрываются.
- **Следствия:** Файл и печать соответствуют экрану «по построению»; лимиты — 100 000 строк в Excel, 20 000 в печать (сейчас 5 000), сверх — отказ с сообщением.
- **Ограничения:** Диаграммы не переносятся ни в Excel, ни в печать; серверный экспорт (ADR-38) появился для объёмов и рассылки, но он плоский.

**ADR-29. Drill-through (версия 1.5).**
- **Проблема:** Из сводного отчёта нужно перейти к деталям по выбранной группе.
- **Решение:** Секция `drill: { report, label?, params }` в табличном блоке; значения — `group.<field>`, `param.<name>` или литерал. Ссылкой становится ячейка группы, параметры уходят в URL целевого отчёта.
- **Следствия:** Переход — обычное открытие отчёта с параметрами: без нового контракта, работает «назад» в браузере.
- **Ограничения:** Доступен только из групп таблицы; диаграммы получили drill отдельным решением (ADR-43), из подытогов и ИТОГО переход не настраивается.

**ADR-30. Каталог отчётов (версия 1.5).**
- **Проблема:** Отчёты находились только по прямой ссылке.
- **Решение:** Папка и теги объявляются в шаблоне (`folder`, `tags`); `GET /api/reports` отдаёт их вместе с описанием и параметрами. Экран списка: папки со счётчиками, фильтр по тегам, поиск по названию/описанию/id/тегам, избранное в `localStorage`.
- **Следствия:** Отдельной таблицы каталога нет: источник истины — сами шаблоны, перенос отчёта в другую папку не требует миграций.
- **Ограничения:** Избранное локальное — на другом браузере его нет; поиск и пагинация позже перенесены на сервер (ADR-41).

**ADR-31. Черновик и публикация (версия 1.6).**
- **Проблема:** Правка шаблона сразу меняла публичный отчёт; согласовать изменения было нельзя.
- **Решение:** Правка пишется в колонку `report_templates.draft`; публикация пишет снапшот прежней версии в историю, переносит черновик в `body` и обновляет память без рестарта. Создание отчёта сразу публикует его.
- **Следствия:** Публичный отчёт не меняется до явной публикации; откат — обычная запись прежней версии.
- **Ограничения:** Черновик один на отчёт — параллельная правка двумя авторами перетирается; метка «черновик от ДД.ММ» не защищает от конфликта.

**ADR-32. Кэш результатов (версия 1.7).**
- **Проблема:** Повторные запросы одного отчёта с теми же параметрами заново читали базу.
- **Решение:** Ответы `POST /api/report/data` кэшируются в памяти по ключу «отчёт + версия шаблонов + параметры»: TTL 60 с, `ETag`, `X-Cache`, поддержка `If-None-Match` (304). Публикация, правка, откат и удаление поднимают версию шаблонов и сбрасывают кэш.
- **Следствия:** Повторные открытия отвечают мгновенно; устаревшие данные не отдаются при правке шаблона.
- **Ограничения:** Кэш на процесс — у нескольких экземпляров свой; ответы больше 2 МБ и ошибки не кэшируются; TTL задерживает свежесть данных.

**ADR-33. Роль БД только-чтения (версия 1.8).**
- **Проблема:** SQL из шаблонов (ADR-27) исполняется под ролью сервиса — ошибка или злой умысел автора могла писать в базу.
- **Решение:** Данные и справочники читаются отдельным пулом под ролью `reporting_ro` (`REP_RO_DB_USER`/`REP_RO_DB_PASSWORD`), которую создаёт `scripts/db-ro.sh`; запись шаблонов и админка остаются на основной роли.
- **Следствия:** `INSERT` отклоняется самой СУБД; `/api/health` показывает `readOnlyRole`.
- **Ограничения:** Если переменные не заданы, чтение идёт основной ролью (совместимость сохранена); права нужно выдавать в каждой новой БД — ошибка, поймана в CI (ADR-47).

**ADR-34. Аутентификация и роли (версия 1.9).**
- **Проблема:** Админка и отчёты были доступны всем, кто открыл страницу.
- **Решение:** `users` (PBKDF2-HMAC-SHA256, 120 000 итераций, соль на пользователя) и `sessions` (токен 32 байта, TTL 12 ч); cookie `rep_session` — `HttpOnly`, `SameSite=Lax`, `Path=/`. Проверка одна, до маршрутизации: матрица «метод + путь → минимальная роль», неизвестные пути требуют admin.
- **Следствия:** Роли viewer/author/admin работают на всех маршрутах; отзыв сессии — удаление строки в БД.
- **Ограничения:** Нет ограничения попыток входа, нет `Secure` (пока нет HTTPS), нет 2FA и смены своего пароля.

**ADR-36. Несколько наборов данных в шаблоне (версия 1.10).**
- **Проблема:** Один шаблон описывал только один запрос, хотя отчёт часто требует разных гранулярностей.
- **Решение:** `datasets` — словарь; блок ссылается на набор через `dataKey`; клиент запрашивает каждый набор отдельно (`POST /api/report/data` с полем `dataset`), без поля сервер отдаёт первый набор.
- **Следствия:** Один шаблон = несколько независимых выборок; ключ кэша включает имя набора.
- **Ограничения:** JOIN через один запрос отклонён (разная гранулярность раздувает выборку); до версии 1.29 диаграммы игнорировали `dataKey` — дефект исправлен в ADR-56.

**ADR-37. Серверная агрегация (версия 1.11).**
- **Проблема:** На 50 000 строк клиентская агрегация упирается в лимит и трафик.
- **Решение:** Блок объявляет `aggregate: {groupBy, measures}`; сервер выполняет `GROUP BY` поверх SQL набора, имена и агрегаты проверяются как идентификаторы, параметры идут тем же компилятором.
- **Следствия:** Детализация не покидает базу; клиент получает уже сгруппированные строки.
- **Ограничения:** Функции только `sum|avg|min|max|count`; клиентская агрегация остаётся для WYSIWYG; существование колонок проверяется не валидатором, а базой (422 при построении).

**ADR-38. Серверный экспорт в Excel (версия 1.12).**
- **Проблема:** Excel нужен без браузера — для рассылки и больших объёмов.
- **Решение:** `POST /api/report/export.xlsx` собирает книгу на сервере (`libxlsxwriter`, BSD-2): шапка и форматы из табличного блока, данные из набора с применением `aggregate` блока, второй лист — параметры.
- **Следствия:** Экспорт работает без клиента; клиентский WYSIWYG (ADR-28) остаётся для точного совпадения с экраном.
- **Ограничения:** Плоская таблица: без подытогов/ИТОГО и без объединений (объединения добавлены в 1.21, ADR-49); диаграммы не экспортируются.

**ADR-39. Автообновление отчёта (версия 1.13).**
- **Проблема:** Экран с операционными показателями устаревал, пока его не перезагрузят.
- **Решение:** Шаблон задаёт `refreshSeconds` (0…3600, меньше 5 — предупреждение); страница перезапрашивает данные с сохранением параметров и состояния групп; тик пропускается в фоне и при активном запросе, есть пауза.
- **Следствия:** Данные обновляются без действий пользователя; сервер ничего не помнит о подписках.
- **Ограничения:** Кэш TTL может отдавать данные с задержкой; несколько открытых страниц дают несколько запросов.

**ADR-40. CSV на сервере (версия 1.14).**
- **Проблема:** CSV нужен для машинной обработки и как вложение письма.
- **Решение:** Отдельный маршрут `POST /api/report/export.csv` (а не параметр `format` у `.xlsx`); расчёт тот же, что у серверного XLSX. Формат: UTF-8 с BOM, `;`, CRLF, кавычки при спецсимволах, числа без форматирования.
- **Следствия:** Excel открывает файл двойным щелчком; CSV пригоден для машинной обработки.
- **Ограничения:** Разделитель `;` не настраивается; числа теряют форматирование шаблона — это осознанно.

**ADR-41. Поиск и пагинация каталога на сервере (версия 1.14).**
- **Проблема:** Каталог грузил все шаблоны и фильтровал на клиенте — при росте числа отчётов это лишний трафик.
- **Решение:** `GET /api/reports` принимает `q`, `folder`, `tag`, `limit`, `offset`; без `limit` отдаёт прежний массив (совместимость), с `limit` — `{items,total}`. Фильтрация по снимку шаблонов в памяти; страница грузит по 10, поиск с задержкой 250 мс.
- **Следствия:** Каталог масштабируется по числу отчётов; старые клиенты и e2e не ломаются.
- **Ограничения:** Избранное осталось в `localStorage`; полнотекстового поиска нет — только подстрока по полям.

**ADR-42. Обновление по событию (long-poll) — заменён ADR-44 (версия 1.14).**
- **Проблема:** Таймер опроса тратит запросы в простое и даёт задержку до периода.
- **Решение:** `GET /api/report/changes?report=<id>` держит запрос до 20 с и отвечает сразу после публикации или отката шаблона; шаблон включает режим полем `live: true`.
- **Следствия:** Нет опроса по таймеру; живёт на штатных таймерах Drogon, без WebSocket.
- **Ограничения:** Висящее соединение на каждого зрителя; заменено на SSE в ADR-44 из-за двух обменов на каждое событие.

**ADR-43. Drill-through с диаграмм (версия 1.15).**
- **Проблема:** Из точки диаграммы нельзя было перейти к деталям, хотя из таблицы уже можно (ADR-29).
- **Решение:** Та же секция `drill`, но ссылки другие: `x` — категория точки, `series` — имя серии; `group.<field>` отклоняется валидатором. Клик обрабатывает `ChartBlock`, решение о переходе принимает `ReportViewer`.
- **Следствия:** URL-схема перехода одна для таблицы и диаграмм.
- **Ограничения:** Круговая диаграмма отдаёт только `name`, поэтому для неё допустим лишь `x`/`param.`/литерал; из gauge подставлять нечего (ADR-56/57).

**ADR-44. SSE вместо long-poll (версия 1.16).**
- **Проблема:** Long-poll (ADR-42) требовал нового запроса после каждого ответа: два HTTP-обмена на событие и вечная ротация соединений в простое.
- **Решение:** Одно SSE-соединение `GET /api/report/events?report=<id>` на всё время работы страницы (`newAsyncStreamResponse` в Drogon); сервер пишет `event: change` после публикации и `: ping` раз в 15 с, отвалившиеся клиенты вычищаются на пульсе.
- **Следствия:** Событие доходит за доли секунды; в простое только пульс.
- **Ограничения:** Потоковые ответы буферизуют прокси — нужен `proxy_buffering off`; Vite-прокси отдавал SSE как `Content-Length: 0`, потребовался собственный проброс (`frontend/sse-proxy.js`).

**ADR-45. Полная серверная валидация (версия 1.17).**
- **Проблема:** Сервер делал «структурную» проверку, а семантика жила в клиентском `validate.js` — шаблон можно было сохранить в обход браузера.
- **Решение:** Правила перенесены в `backend/src/validate.cc` и возвращают список `{path, message}`; клиентский валидатор остался для мгновенной подсказки, истина — сервер. Parity закреплена фикстурами `docs/fixtures/validation-cases.json`, которые читают оба теста.
- **Следствия:** В обход браузера нельзя сохранить заведомо битый шаблон; сервер дополнительно проверяет `id`, уникальность параметров, `chartType`, размер и SQL-гард.
- **Ограничения:** Правила описаны дважды — фикстуры стали обязательной частью изменений; SQL-гард проверяет форму запроса, а не его смысл.

**ADR-46. Рассылка по расписанию (версия 1.18).**
- **Проблема:** Отчёт нужно получать на почту без участия человека; ручная отправка не масштабируется.
- **Решение:** Подписки лежат в БД (`report_subscriptions`), расписание — cron из пяти полей. Планировщик — отдельный поток с собственным соединением libpq: отправка блокирующая и не должна занимать цикл событий. Просроченные подписки забираются одним `UPDATE … FOR UPDATE SKIP LOCKED`. Почта — собственный минимальный SMTP-клиент (OpenSSL): STARTTLS, AUTH PLAIN/LOGIN, вложение base64. Журнал — `subscription_runs`.
- **Следствия:** Одно письмо не уходит дважды; результат каждой отправки виден в админке; файл собирается тем же кодом, что HTTP-экспорт.
- **Ограничения:** Изначально только CSV, без повторов и таймзон (закрыто в ADR-48, ADR-60, ADR-61); SMTP без проверки сертификата; per-user подписок нет.

**ADR-47. E2E в CI (версия 1.19).**
- **Проблема:** Сквозные тесты шли только вручную, регрессии ловились поздно.
- **Решение:** Job `e2e` в GH Actions на сервисе `postgres:16`; стенд поднимает `scripts/ci-e2e.sh` — тот же скрипт работает локально с отдельной БД (`reporting_ci`) и своими портами (8081/5174/1026), поэтому «у меня» и «в CI» проверяют одно и то же.
- **Следствия:** Каждый push проверяется сквозными сценариями; стенд изолирован от рабочей БД.
- **Ограничения:** Сервис Postgres в CI — контейнер с паролем по умолчанию (только внутри job'а); без кэша Conan job выходит за таймаут; первый прогон на раннере так и не наблюдался.

**ADR-48. XLSX в рассылке (версия 1.20).**
- **Проблема:** Письмо уходило только в CSV, хотя подписка может требовать книгу Excel.
- **Решение:** Лист собирает одна функция `buildSheet` (выборка, агрегация блока, колонки с форматами, заголовок, параметры), а форматы — тонкие обёртки: CSV (`toCsv`) и XLSX (`writeXlsx` во временный файл → байты в письмо). Формат — поле подписки (`csv`/`xlsx`), проверяется при сохранении.
- **Следствия:** Письмо, скачивание и экран считаются одним кодом — расхождение невозможно по построению.
- **Ограничения:** Серверный XLSX плоский: без подытогов и outline (подытоги по-прежнему только в браузерном экспорте).

**ADR-49. Объединения и outline в серверном XLSX (версия 1.21).**
- **Проблема:** Сводная книга в письме выглядела плоской таблицей — группировку приходилось восстанавливать глазами.
- **Решение:** `applyGrouping` считает по групповым колонкам вертикальные объединения одинаковых подряд идущих значений и уровни структуры; `writeXlsx` ставит `mergeCells`, `outlineLevel`, `summaryBelow=0`. Порядок строк не пересортировывается — он приходит из SQL и совпадает с экраном.
- **Следствия:** Книга читается как на экране; кириллица не ломает порядок, потому что сортировки по байтам нет.
- **Ограничения:** Сервер не строит подытоги и ИТОГО: в книге детальные строки с объединениями и структурой; полный WYSIWYG даёт только браузерный экспорт.

**ADR-50. Управление пользователями (версия 1.22).**
- **Проблема:** Пользователей заводил только скрипт на сервере (`scripts/auth-init.sh`), то есть человек с shell.
- **Решение:** Админка создаёт и правит пользователей; отключение (`enabled=false`) вместо удаления там, где нужна история: вход запрещён, сессии удаляются сразу. Защита от потери управления: нельзя удалить себя, отключить себя или снять роль с последнего включённого админа (`SELF_PROTECTED`, `LAST_ADMIN`).
- **Следствия:** Управление доступом не требует shell; история действий по пользователям видна в журнале.
- **Ограничения:** Нет смены своего пароля, нет 2FA, нет ограничения попыток входа.

**ADR-51. Версионирование шаблона и миграции (версия 1.23).**
- **Проблема:** `version` был константой «1» и ничего не означал: формат менялся, а старые шаблоны никто не проверял.
- **Решение:** `version` — версия формата: текущая 2, поддерживается 1…2, старые поднимаются цепочкой миграций, новые отклоняются с текстом «обновите сервер». Миграция выполняется на сервере (сохранение, публикация, загрузка в память) и в админке при открытии; логика продублирована на C++ и JS и сверяется общими фикстурами.
- **Следствия:** Шаблоны в БД всегда в актуальном формате; версия 2 сделала `chartType` обязательным (при миграции — `bar`).
- **Ограничения:** Миграции только вперёд и необратимы; шаблон с `queryId` (эпоха ADR-27) миграция не спасёт — SQL из удалённого реестра не восстановить.

**ADR-52. Аудит действий (версия 1.24).**
- **Проблема:** На вопрос «кто это сделал» не было ответа: журнал приложения — это grep по файлам.
- **Решение:** Отдельная таблица `audit_log` (когда, кто, действие, объект, детали `jsonb`, адрес). Событие пишется при успехе; неудачные попытки — только для входа (`auth.login_failed`). Детали — безопасный минимум (логин, роль, формат, число писем). API только на чтение, страница `audit.html`.
- **Следствия:** Разбор инцидента идёт по запросу, а не по логам; журнал нельзя подчистить через интерфейс.
- **Ограничения:** Нет выгрузки в файл/SIEM и нет записи чтения отчётов; ретеншен появился позже (ADR-59).

**ADR-53. Префикс приложения для реверс-прокси (версия 1.25).**
- **Проблема:** Сервер отчётов должен стоять не только в корне домена: у заказчика он живёт рядом с другими системами.
- **Решение:** База сборки задаётся `REP_BASE`, адрес API вычисляется на клиенте из расположения страницы (`/reports/report.html` → `/reports/api`); ассеты подключаются относительными путями (`base: './'`), поэтому `dist` переносим без пересборки. Прокси обязан снимать префикс, для SSE — отдельный блок с `proxy_buffering off`.
- **Следствия:** Одна сборка работает и в корне, и под любым префиксом; переезд не требует пересборки.
- **Ограничения:** Подпрефиксная проверка не входит в обычный `check.sh` (нужен отдельный прогон стенда); cookie живёт на `Path=/` и `Secure` появится только с HTTPS.

**ADR-54. Аутентификация на реверс-прокси (версия 1.26).**
- **Проблема:** В части внедрений вход выполняет прокси (basic, SSO, `auth_request`) — второй вход в приложении не нужен.
- **Решение:** `REP_AUTH=proxy`: логин из заголовка `X-Remote-User`, роль — из `users`, поэтому матрица viewer/author/admin общая для обоих режимов. Заголовок принимается только с адресов `REP_AUTH_PROXY_TRUSTED` и проверяется по безопасному набору символов. Вход и выход в этом режиме отвечают 400 `AUTH_ON_PROXY`.
- **Следствия:** Внешний вход без второго пароля; неизвестный логин — 403, а не «гость»; автосоздание возможно явным флагом и пишется в журнал.
- **Ограничения:** Доверие к заголовку защищено только адресом прокси (без mTLS/подписи); заголовок не несёт групп; роль кэшируется 60 с.

**ADR-55. Схема шаблона — контракт формата (версия 1.28).**
- **Проблема:** Сервер и шаблоны использовали у табличного блока `title` и `aggregate`, а схема их не объявляла — три рабочих шаблона считались невалидными. Причина живучести: в `check.sh` проверка стояла в `npm run … && echo`, левая часть `&&` не подпадает под `set -e`, и провал тонул в успешном выводе.
- **Решение:** Поля, которые реально работают, объявлены в `schema.js`, `docs/template.schema.json` перегенерируется; `check.sh` проверяет код возврата явно и падает с «шаблоны не проходят валидацию»; мёртвые поля из шаблонов убраны.
- **Следствия:** Машиночитаемая схема перестала врать: 15 из 15 шаблонов валидны.
- **Ограничения:** Валидатор проверяет структуру и допустимые значения, но не существование колонок в SQL — неверное имя даёт 422 при построении отчёта.

**ADR-56. Виды диаграмм gauge и sankey (версия 1.29).**
- **Проблема:** Заказчику нужны не только ряды, но и «одно число» и «потоки»: спидометр для KPI и sankey для распределения сумм между категориями и регионами.
- **Решение:** Оба вида — надстройка над блоком `chart`: у `gauge` поля `yField` + `aggregate` и шкала `min`/`max`/`unit`, у `sankey` — `sourceField`, `targetField`, `valueField`. Обязательность полей переехала в семантический валидатор и продублирована на клиенте и сервере с parity-фикстурами. Агрегация остаётся клиентской.
- **Следствия:** Новые виды без третьего типа блока; попутно исправлены два дефекта: диаграммы игнорировали `dataKey` и `aggregate`-строка принималась за серверную агрегацию (422).
- **Ограничения:** Диаграммы не экспортируются в Excel и не печатаются; sankey без промежуточных уровней; gauge показывает одно значение без порогов (зоны добавлены в ADR-57).

**ADR-57. Цветовые зоны gauge (версия 1.30).**
- **Проблема:** Для KPI мало одного числа: нужно «плохо/терпимо/хорошо».
- **Решение:** `thresholds` (2…8 строго возрастающих границ) и `zoneColors` (`thresholds.length + 1` цветов: hex, `transparent` или токен `styles.palette`). N границ дают N+1 зон; полоса прогресса при зонах отключается, чтобы цвета читались. Границы вне `min…max` обрезаются.
- **Следствия:** Шкала и указатель окрашиваются по зоне; при некорректных цветах рисуется шкала без зон, страница не падает.
- **Ограничения:** Пороговая логика только у `gauge` (у таблиц — `rules`, ADR-25); зоны не попадают в Excel; валидатор полей не видит данных.

**ADR-58. Диаграмма band: значение и коридор (версия 1.31).**
- **Проблема:** Для эксплуатационных отчётов нужен не только ряд значений, но и допустимый разброс: у точки три числа — значение, нижняя и верхняя границы.
- **Решение:** Отдельный `chartType: "band"` с полями `yField`, `lowField`, `highField`; заливка рисуется двумя невидимыми стековыми рядами (основание «низ» плюс разница «верх − низ»), значение — третьим рядом.
- **Следствия:** Работает на любых данных, включая отрицательные нижние границы; не нужны ни `custom`-серия, ни расчёт полигонов.
- **Ограничения:** Одна полоса на график; полоса не попадает в Excel и печать; при перепутанных границах вырождается в ноль — валидатор данных не видит.

**ADR-59. Ретеншен журналов (версия 1.32).**
- **Проблема:** `audit_log` и `subscription_runs` растут монотонно, а «чистить руками, когда станет много» — отложенный инцидент.
- **Решение:** Глубина хранения задаётся `REP_LOG_RETENTION_DAYS` (90 дней по умолчанию, `0` — бессрочно), одна настройка на оба журнала. Чистка живёт в отдельном потоке (не в планировщике рассылки), запускается при старте и раз в 6 часов; факт удаления пишется в журнал действием `logs.purge` только при ненулевых удалениях; `/api/health` показывает действующую глубину.
- **Следствия:** Журналы не растут бесконечно; настройка видна на развёрнутом экземпляре без догадок.
- **Ограничения:** Удаление необратимо (архивации в файл/SIEM нет); глубина считается по времени сервера, а не по поясу зрителя.

**ADR-60. Часовой пояс расписания в подписке (версия 1.34).**
- **Проблема:** «Каждый будний день в 9:00» — это 9:00 по месту работы, а не по UTC сервера: до этой версии cron считался в поясе процесса, и рассылка уходила на 3–7 часов позже или раньше ожидаемого.
- **Решение:** Пояс хранится в подписке (`timezone`, IANA-идентификатор), а не в переменной окружения: у подписок бывают разные получатели и регионы. Пересчёт «местное ↔ UTC» с переходами на летнее время выполняет PostgreSQL (`AT TIME ZONE`), в C++ остаётся календарный поиск следующей минуты. Неизвестный пояс отклоняется при сохранении (422).
- **Следствия:** Расписание совпадает с ожиданием получателя; DST обрабатывает база.
- **Ограничения:** Старые подписки получили `UTC` при миграции (их расписание не менялось); производственного календаря (праздников) нет — только дни недели.

**ADR-78. Справочники параметров — это наборы данных (версия 1.51, без обратной совместимости).**
- **Проблема:** после ADR-76 все запросы к БД получили единое место — блок `connections`, — но SQL
  справочников продолжал жить в `params[].source.sql`. В админке шаблон выглядел разорванным:
  данные отчёта описаны в `datasets` (с соединением), а запрос «Центр затрат» — в параметре,
  рядом с которым нет ни соединения, ни набора. Найти все запросы шаблона в одном месте было нельзя.
- **Решение:** справочник становится обычным набором данных: `datasets.<ключ>` с `sql` и
  `connection`, а параметр ссылается на него полем `source.dataset`. `source.sql` и
  `source.connection` удалены из формата и считаются ошибкой валидатора с подсказкой, куда
  переносить (`SQL справочника задаётся набором datasets.<ключ>: source.sql больше не
  поддерживается`). Обратная совместимость сознательно не вводится (решение PO): формат шаблона
  остаётся версии 2, но старые шаблоны не принимаются. Все 21 шаблон репозитория переведены:
  11 справочников в 8 файлах стали наборами (`cost_center_lookup`, `region_lookup`,
  `category_lookup`, `service_lookup`). Справочный набор отличается от отчёточного только
  использованием: блоки на него не ссылаются, а эндпоинт `lookups` берёт из него SQL и соединение.
- **Следствия:** в каждом шаблоне все SQL и все соединения теперь в одном блоке `datasets` —
  это видно и в JSON, и в админке (панель параметров показывает «набор: …» и «источник: …»,
  а сам SQL — из набора). Справочники работают через тот же механизм соединений, что и данные
  (ADR-76): подстановка `${PGHOST}`, read-only сессия, кэш. Каскад (`dependsOn`) сохранён:
  `:region` из query-строки подставляется в SQL набора. Проверено: `cost_center` отдаёт
  «Все центры» + ЦФ-1…ЦФ-N, `region → category` фильтруется, все 21 отчёт отдают данные,
  старый формат отклоняется с `422 TEMPLATE_INVALID` и путём `params.0.source.sql`.
- **Ограничения:** набор-справочник обязан возвращать ровно две колонки `value`/`label` —
  валидатор этого проверить не может (SQL исполняется на сервере), ошибка видна при открытии
  отчёта; один справочник — один набор, повторное использование набора двумя параметрами
  допустимо, но разных списков в одном наборе быть не может; шаблоны, сохранённые до версии
  1.51, нужно перевести вручную (автомиграции нет по решению PO); наборы-справочники попадают
  в общий список `datasets` и видны в админке как наборы — отдельного признака `role: lookup`
  не вводилось.

**ADR-77. Источники в шаблонах примеров: явный блок main и подстановка окружения (версия 1.50).**
- **Проблема:** после появления блока `connections` (ADR-76) все примеры, кроме `sales-external`,
  продолжали читать данные «по умолчанию» — источник в шаблоне не был описан вовсе. Из-за этого
  нельзя было ни увидеть, куда идёт запрос, ни перенастроить пример на другую роль, а половина
  ревизии «источник в блоке» оставалась невыполненной.
- **Решение:** у всех 21 шаблона примеров появился явный источник `connections.main`; каждый
  набор данных и каждый справочник параметров ссылается на него полем `connection`. Поля
  `host`, `port`, `database`, `user`, `schema` допускают подстановку окружения вида `${PGHOST}` —
  целиком, не в составе строки. Значение берётся из окружения сервера; незаданная переменная —
  ошибка с её именем. Примеры читают данные под ролью `reporting_ro`
  (`user: ${REP_RO_DB_USER}`, `passwordEnv: REP_RO_DB_PASSWORD`), поэтому эксплуатационное
  разделение ролей (ADR-75) соблюдается и в примерах. На CI-стенде переменные указывают на
  основную учётную запись — отдельной роли чтения там нет.
- **Следствия:** все 21 отчёт открываются и отдают данные через `main`; проверено, что внутри
  сессии `current_user = reporting_ro`, `current_database = reporting`, а
  `default_transaction_read_only = on` (то есть источник открыт только на чтение). Валидаторы
  клиента и сервера принимают `${ИМЯ}` как целое значение поля и отклоняют смесь вроде
  `db-${ID}` — parity 67/67. Подстановка адреса делает шаблоны переносимыми: тот же файл
  работает на dev-базе и на CI без правок.
- **Ограничения:** подстановка — только одиночная ссылка на переменную (без `${A}${B}`,
  значений по умолчанию и подстановки в `passwordEnv`/`kind`); при отсутствии переменной
  источник недоступен целиком (нет fallback на localhost — так ошибка видна сразу); адреса и
  логины остаются в шаблоне (в админке), а публичный API их вырезает; примеры жёстко требуют
  роль чтения — на стенде без неё нужно задать `REP_RO_DB_USER`/`REP_RO_DB_PASSWORD`.

**ADR-76. Источники данных в шаблоне: блок connections (версия 1.49).**
- **Проблема:** параметры запросов к БД были размазаны: SQL жил в шаблоне, а адрес, база и учётная
  запись — в окружении сервера. Из-за этого один отчёт не мог читать второй PostgreSQL, а перенос
  отчёта на другой стенд требовал менять переменные процесса. Пароли в шаблон класть нельзя
  (правило проекта), а «просто разрешить» означало бы утечку секретов в БД и в админку.
- **Решение:** в шаблоне появился блок `connections`: `kind` (`postgres` | `rest`), `host`, `port`,
  `database`, `user`, `schema`, `sslmode`, `connectTimeout`, `statementTimeoutMs` и `passwordEnv` —
  **имя** переменной окружения с паролем. Наборы данных и справочники параметров ссылаются на источник
  полем `connection` (пусто или `default` — сервер из окружения). Клиенты создаются лениво и
  кэшируются по строке подключения (до 16 на процесс). Каждое внешнее соединение открывается с
  `default_transaction_read_only=on`, поэтому шаблон не может изменить данные источника. Работает
  во всех путях исполнения: `/api/report/data`, `aggregate`, `group`, `lookups`, серверный
  `.xlsx`/CSV и рассылка. Публичный `GET /api/reports/{id}` вырезает `connections`; админский
  отдаёт полностью. `rest` зарезервирован: структура валидируется, исполнение отвечает
  `422 CONNECTION_ERROR`.
- **Следствия:** один отчёт может соединять данные двух и более PostgreSQL — проверено на
  `sales-external` (продажи из БД сервера, отгрузки из `reporting_ext.warehouse`: «Восток»
  88 350 000, 1 315 заказов; сумма по регионам 410 450 000). Пароль в шаблоне — ошибка
  валидатора (`connections.<ключ>.password`), незаданная переменная — `422` с её именем.
  Клиент и сервер валят одинаково (parity 65/65). DDL на внешнем сервере не нужен: роль —
  только `SELECT`.
- **Ограничения:** один `passwordEnv` на источник, смена пароля требует перезапуска процесса
  (клиент кэшируется по строке подключения); `rest` пока только структура — ни заголовков, ни
  маппинга ответа; внешние источники не участвуют в `live`-обновлении по событиям (событие —
  публикация шаблона, а не изменение чужой БД), поэтому кэш в 60 с остаётся единственным
  ограничителем частоты; число источников ограничено 16 на процесс; `default` нельзя объявить
  как `rest`; реквизиты источника видны в админке любому автору — отдельного права на просмотр
  блока не вводилось.

**ADR-75. Эксплуатационные роли БД: owner, srv, ro (версия 1.48).**
- **Проблема:** сервер работал под одной ролью `rep_app`, которая была ещё и владельцем схем и таблиц:
  то есть могла выполнять DDL. Отчётность читалась под `reporting_ro`, но граница «кто владеет структурой»
  и «кто работает с данными» не была разведена. Требование эксплуатации — суперпользователь только для
  разработки и развёртывания; на практике же ничто не мешало поднять сервер под `postgres` или владельцем.
- **Решение:** три роли с разными правами. `reporting_owner` — владелец схем и таблиц, под ней идут DDL и
  миграции (`REP_OWNER_DB_*`, только на развёртывании). `reporting_srv` — под ней работает сам сервер
  (`PGUSER`): SELECT/INSERT/UPDATE/DELETE в `reports`, USAGE на последовательности ядра, чтение
  `reports_examples`; CREATE в схеме запрещён. `reporting_ro` — прежняя роль только-чтения, видит только
  `reports_examples`. Роль `rep_app` переименована в `reporting_owner`, чтобы владение объектами сохранилось
  без переназначения. Права выдаёт `db/roles.sql` (GRANT + ALTER DEFAULT PRIVILEGES), `db/init.sh` выполняет
  DDL под владельцем. При старте сервер проверяет `current_user`: под суперпользователем пишет WARN, а с
  `REP_STRICT_ROLE=1` — отказывается запускаться; `/api/health` отдаёт `dbUser` и `superuser`.
- **Следствия:** сервер под `reporting_srv` выполняет все админские операции — создание и публикацию
  шаблонов, пользователей, подписки, выгрузку журнала, удаление — проверено на живом стенде; попытка
  `CREATE TABLE` и запись в примеры упирается в права («нет доступа к схеме reports» / «нет доступа к
  таблице sales»). Под суперпользователем с `REP_STRICT_ROLE=1` сервер завершается с кодом 1 и понятным
  сообщением; без флага — работает с предупреждением (стенд).
- **Ограничения:** роль `reporting_srv` может читать всё, что читает приложение, и удалять данные ядра —
  разделение на «чтение» и «администрирование» внутри сервера не делается (это одна роль на процесс);
  `reporting_ro` не имеет доступа к ядру вовсе, поэтому у неё не работают админские запросы; владелец
  объектов не может быть удалён без переназначения владения (переименование безопасно, DROP — нет);
  пароль владельца лежит в `.env` рядом с паролем сервера — для эксплуатации его надо держать отдельно.

**ADR-74. Схемы `reports` (ядро) и `reports_examples` (примеры) (версия 1.47).**
- **Проблема:** в одной базе лежали и продукт, и демонстрация: `report_templates`, `users`, `sessions`,
  `audit_log`, `report_subscriptions` соседствовали с `sales`, `finance`, `ops`, `regions` в `public`.
  Из-за этого ядро нельзя было поставить на чистую базу без синтетики, а «где кончается продукт и начинаются
  примеры» определялось только по имени таблицы. Скрипт `db/schema.sql` был и ядром, и демо-данными сразу,
  миграции создавали таблицы ядра без схемы.
- **Решение:** ядро живёт в схеме `reports` (`db/core.sql`: шаблоны, история версий, пользователи, сессии,
  рассылка, журнал), примеры — в `reports_examples` (`db/examples/schema.sql` + `db/examples/seed.sql`).
  Приложение подключается с `search_path=reports` (`REP_DB_SCHEMA`), пул только-чтения — с
  `search_path=reports_examples` (`REP_RO_DB_SCHEMA`); psql-скрипты получают `PGOPTIONS=-c search_path=reports`
  из `scripts/env.sh`. SQL шаблонов указывает примеры явно: `reports_examples.sales`. `db/init.sh` умеет
  ставить только ядро (`--core-only`), только примеры (`--examples-only`) или всё вместе. Миграции
  квалифицированы схемой `reports` и остаются идемпотентными.
- **Следствия:** `./db/init.sh --core-only` на чистой базе даёт ровно семь таблиц ядра и ни одной таблицы
  примеров; сервер отвечает `db: true`, каталог пуст, отчёты примеров честно не находят данных. Полная
  установка даёт 4 таблицы примеров и 50 000/576/540 строк, 20 шаблонов загружаются через API, отчёт
  «Сводная таблица продаж» отдаёт 2 748 строк. Роль `reporting_ro` видит только `reports_examples`.
- **Ограничения:** шаблон, обращающийся к таблице без схемы, получает `relation does not exist` — это
  осознанно, но старые шаблоны и пользовательские копии надо править вручную; одна база по-прежнему содержит
  обе схемы (разделение логическое, не по базам); миграции рассчитаны на схему `reports`, базы, созданные до
  ADR-74, требуют переноса таблиц из `public` (в dev-базе проще пересоздать через `scripts/dev-db-init.sh`).

**ADR-73. Сборка под Windows/MSVC (версия 1.46).**
- **Проблема:** сервер собирался только под Linux: `main.cc` и `smtp.cc` напрямую звали POSIX-сокеты
  (`<sys/socket.h>`, `bind`, `close`, `ssize_t`), расписание подписок опиралось на `timegm`, а проверка
  порта использовала `sockaddr_in` из `<netinet/in.h>`. Под MSVC этого нет: сборка падала на первом же
  заголовке, а русский текст в строках без `/utf-8` превращался в мусор.
- **Решение:** платформенные различия собраны в `backend/src/net.h` и `net.cc`: тип `socket_t`
  (`SOCKET`/`int`), `create/valid/closeSocket`, `setIoTimeout` (DWORD против `timeval`), `portFree`,
  `lastError/errorText` (Winsock не пишет в `errno`), `startup()` (WSAStartup) и `timegmUtc`
  (`_mkgmtime` под MSVC). Остальной код о платформе не знает. В CMake: `ws2_32`, определения
  `WIN32_LEAN_AND_MEAN`/`NOMINMAX`/`_WIN32_WINNT`, флаги MSVC `/utf-8 /bigobj /permissive-` и CRT `MD/MDd`;
  `REP_SOURCE_DIR` для тестов прогоняется через `file(TO_CMAKE_PATH)`, иначе обратный слэш в пути ломает
  литерал. Добавлены `backend/CMakePresets.json` (пресеты `windows-msvc`, `windows-msvc-ninja`,
  `linux-release`), профиль Conan v1 `backend/conan/profiles/windows-msvc2022` и `scripts/build.ps1`.
- **Следствия:** под Windows достаточно `.\scriptsuild.ps1`: скрипт проверяет Conan v1, ставит
  зависимости, конфигурирует пресет, собирает и прогоняет ctest. На Linux сборка не изменилась:
  `cmake --preset linux-release` и прежний `scripts/build.sh` дают тот же бинарник, 68 тестов (340 проверок)
  зелёные, `net.cc` в POSIX-ветке сводится к обёрткам над системными вызовами.
- **Ограничения:** сборка MSVC не проверена прогоном — Windows-машины в проекте нет; инструкция
  `docs/build-windows.md` содержит типовые ошибки (Conan 2.x, отсутствие DLL в PATH, CRT MD/MDd, CP866 в
  консоли), но первый реальный прогон может потребовать правок. Windows-версия проверки порта и SMTP
  использует Winsock, поведение таймаутов задаётся миллисекундами; отдельной Windows-сборки в CI нет.

**ADR-72. Переход из цепочки уровней sankey (версия 1.45).**
- **Проблема:** drill у диаграмм подставлял `x` и `series` — для пары «источник → приёмник» этого хватало.
  У цепочки уровней (ADR-68) конец связи может быть категорией или товаром, и одинаковые подстановки означали
  разное на разных уровнях: клик по связи «категория → товар» отправлял категорию в параметр региона. Поэтому
  в примере `sales-path` перехода не было вовсе — диаграмма выглядела многоуровневой, но дальше не вела.
- **Решение:** модель sankey хранит у каждого узла `level`, `raw` и карту `levels`, а у каждой связи — карту
  значений двух её концов (`{region: 'Восток', category: 'Электроника'}`) и номера уровней. В `drill.params`
  появились ссылки `level.<поле>` (значение уровня) и `node` (значение кликнутого узла); прежние `x`/`series`
  и `param.<name>` работают как раньше. Сборка параметров вынесена в `engine/drill.js`: `drillAllowed()`
  проверяет, что в кликнутом элементе есть все требуемые уровни, `resolveDrill()` собирает пары «параметр —
  значение». Если уровня нет, переход не выполняется — ни в диаграмме, ни на втором рубеже в `ReportViewer`,
  чтобы в детали не уходил фильтр шире клика. Валидатор (клиентский и серверный) принимает `level.*` только
  у sankey с `levels` и проверяет, что поле есть в цепочке.
- **Следствия:** `sales-path` ведёт в «Продажи: детали по региону и категории»: клик по связи «Восток →
  Электроника» открывает 138 строк за 1–10 марта с заполненными регионом и категорией и сохранённым периодом.
  Клик по связи «категория → товар» или по узлу перехода не даёт — регион в них не участвует. Пять юнит-тестов
  закрепляют сборку параметров, включая случай отсутствующего уровня и нулевые значения.
- **Ограничения:** таблица переходов не поддерживает два drill'а с разными уровнями — один блок ведёт в один
  отчёт; переход по узлу возможен только если drill ссылается на один уровень (`node` или `level.<поле>` этого
  уровня); клик по ленте в браузере нельзя отличить от клика по узлу, когда лента нарисована поверх, поэтому
  запрет «не хватает уровня» проверяется юнитом, а не e2e; значения уровней уходят в URL как есть, длинные
  цепочки дают длинный адрес.

**ADR-71. Порядок деталей группы и полное раскрытие (версия 1.44).**
- **Проблема:** раскрытая группа шла в порядке, который выбирала база: если SQL набора не задавал `ORDER BY`,
  сервер сортировал строки по их тексту (`row_to_json`), чтобы страницы не пересекались. Пользователь видел
  «Аксессуары, 98 800, 23 300…» без смысла: полезные строки (самая крупная прибыль, свежая дата) могли оказаться
  на последней странице. Второе: «Развернуть всё» грузило только первую страницу каждой группы — кнопка
  обещала «всё», а в таблице оставалось по 200 строк и висели кнопки «ещё N».
- **Решение:** у табличного блока появилось поле `detailOrder: [{field, dir?}]` (1…4 поля, только вместе
  с `aggregate`); клиент передаёт его в `POST /api/report/group`, сервер проверяет каждое поле как идентификатор
  и `dir` как `asc|desc`, ставит `ORDER BY d.<поле> <dir>, … , row_to_json(d)::text` — текст остаётся последним
  ключом, чтобы строки с равными значениями не «плавали» между страницами. Если `detailOrder` нет, порядок
  по-прежнему берётся из набора, а при его отсутствии — по содержимому строки. «Развернуть всё» теперь тянет
  каждую группу до конца страницами, но с общим потолком 20 000 строк на операцию; что не влезло — остаётся
  кнопкой «ещё N».
- **Следствия:** `sales-aggregate` показывает детали по прибыли (24 400 → 23 800 → 23 300…), стык страниц
  200/201 не рвёт порядок, постраничная выборка совпадает с полной один-в-один. «Развернуть всё» на пяти
  группах (2 748 строк) — 16 запросов и около 2 секунд, после чего «0 свёрнуто» и ни одной кнопки «ещё».
- **Ограничения:** `detailOrder` ссылается только на колонки, которые выбирает набор данных — поле вне SELECT
  даст ошибку базы (422), это проверяется на первом же запросе; сортировка по неуникальному ключу опирается
  на текстовый tiebreak, то есть при равных значениях порядок произвольный, но стабильный; потолок 20 000 строк
  на «Развернуть всё» — на очень широком периоде часть групп останется с кнопкой «ещё»; сортировка выполняется
  базой, отдельного индекса под неё проект не создаёт.

**ADR-70. Порционная подгрузка деталей группы (версия 1.43).**
- **Проблема:** раскрытие группы забирало до 5000 строк одним запросом и одним куском в таблицу: на «Электронике»
  это 689 строк, на широком периоде — тысячи. Ответ ждать долго, браузер рендерит всё разом, а если строк больше
  предела, остаток просто отсутствует — «показано 5000 из 12 000» без способа добрать. Второй дефект увиделся на
  тестах: повторная загрузка того же набора (автовыбор параметров даёт два запроса подряд) сбрасывала раскрытие
  и кэш деталей, то есть только что открытая группа схлопывалась сама.
- **Решение:** маршрут `POST /api/report/group` принимает `offset` (по умолчанию 0) и `limit` (страница 200,
  потолок 5000) и возвращает `offset`, `limit`, `hasMore` рядом с `total`; `total` считается `count(*) OVER ()`
  по всему отфильтрованному набору, поэтому известен на любой странице. Страницы не должны пересекаться: если SQL
  набора не задаёт `ORDER BY`, сервер сортирует по содержимому строки (`row_to_json(d)::text`) — иначе LIMIT/OFFSET
  на разных планах мог бы вернуть строку дважды и потерять другую. Клиент просит по 200 строк, копит их в том же
  `details` и показывает в панели кнопку «ещё N · имя группы» на каждую недогруженную группу; подсказка
  «в группах показано N из M» обновляется. Сброс раскрытия и кэша теперь идёт по отпечатку набора (длина и крайние
  строки): пришёл тот же набор — состояние не трогаем.
- **Следствия:** группа «Электроника» (689 строк) открывается за один запрос 200 строк и добирается тремя кликами
  до 689; мультимножество четырёх страниц совпадает с полной выборкой — ни потерь, ни дублей. Свернуть и раскрыть
  снова — запросов нет (кэш). Повторная загрузка того же набора больше не сворачивает группу.
- **Ограничения:** сортировка по содержимому — не «естественный» порядок строк: если набор не задаёт `ORDER BY`,
  детали идут по тексту строки, а не по дате или id; при смене данных между страницами (параллельная вставка) строки
  могут сдвинуться — согласованность страниц ограничена моментом запроса; кэш живёт до смены набора строк или
  перезагрузки страницы, межвкладочного обмена нет; «Развернуть всё» по-прежнему грузит по одной странице на группу.

**ADR-69. Несколько коридоров в band (версия 1.42).**
- **Проблема:** полоса знала ровно две границы (ADR-58): `lowField` и `highField`. Для «время ответа: значение,
  разброс по сервисам, среднее ± σ» нужны два диапазона сразу — на одном графике они сравнимы глазами, а двумя
  графиками сравнивать приходится в голове. Обойти ограничение шаблоном было нельзя: второй коридор рисовать
  нечем.
- **Решение:** необязательное поле `bands: [{lowField, highField, color?, name?}]` (1…4 коридора) заменяет пару
  `lowField`/`highField`; пара остаётся рабочим вариантом. Каждый коридор рисуется своим стеком (`band-<i>`), иначе
  основание второго начиналось бы от верха первого; цвет берётся из `bands[].color` (токен палитры разрешается),
  без него — из прежнего `bandColor`, дальше — из встроенного набора. Узор остался прежним: невидимое основание
  плюс закрашенная разница «верх − низ» со прозрачностью 0.22, линия значения сверху. Подсказка перечисляет
  значение и все коридоры, под графиком появляется расшифровка цветов (при двух и более коридорах). Правила
  (1…4 коридора, границы разные и не совпадают со значением, `bands` только для band) продублированы на сервере,
  parity закреплена 7 фикстурами.
- **Следствия:** отчёт `ops-corridors` показывает 31 день сразу с двумя диапазонами: широкий (min…max по сервисам)
  и узкий (среднее ± стандартное отклонение, считается в SQL через `stddev_pop`); подсказка на 10 марта даёт
  «значение 319, разброс 244…394, среднее ± σ 267,8…370,2». Прежние шаблоны с одной полосой не изменились,
  кроме служебных имён рядов (`__band_low_0`).
- **Ограничения:** коридоров не больше четырёх (больше цветов не различить и легенда перестаёт читаться);
  коридоры не упорядочиваются по величине — порядок задаёт шаблон, и при пересечении диапазонов верхний закрашивается
  поверх нижнего; в Excel и печать полосы не попадают (диаграммы не экспортируются, ADR-28); `bands` с
  вычисляемыми колонками не работает — считаются только поля из SQL.

**ADR-68. Многоуровневый sankey (версия 1.41).**
- **Проблема:** sankey умел только пару «источник → приёмник» (ADR-56). Для «пути продажи» нужна цепочка
регион → категория → товар: без неё отчёт показывает один шаг, а остальное собирают в голове. Плюс узлов на
последнем уровне десятки, и на высоте 320 px подписи наезжают друг на друга — высоту диаграммы нельзя было
задать из шаблона.
- **Решение:** поле `levels: [поле, …]` (2…4) заменяет `sourceField`/`targetField`: связи строятся между
соседними уровнями, вес агрегируется по парам так же, как раньше (`sum|avg|min|max|count`), строки с пустым
уровнем отбрасываются. Узлы нумеруются префиксом уровня (`0\u0001Восток`), иначе одинаковые названия на разных
уровнях склеились бы в один узел и путь посчитался бы неверно; подпись и тултип показывают исходное значение.
Правила `sourceField`/`targetField`/`levels` (взаимоисключение, 2…4 уровня, уникальность полей) живут в
семантическом валидаторе и продублированы на сервере, parity закреплена 5 фикстурами. Добавлено поле
`height` (240…900 px) для блока диаграммы и `nodeAlign: justify` у sankey.
- **Следствия:** шаблон `sales-path` («Путь продажи: регион → категория → товар») рисует 49 узлов и 60 связей
на трёх уровнях; сумма на входе и на выходе совпадает (150 892 900), то есть поток не теряется; при 620 px
подписи читаются. Пара `source/target` продолжает работать без изменений.
- **Ограничения:** 4 уровня — предел, дальше цепочка не помещается в ширину; одинаковые названия внутри одного
уровня сливаются (это ожидаемо), но между уровнями не различить визуально, если имя повторяется — помогает
только смысл полей; drill в цепочке уровней настраивается на конкретную пару `x`/`series` и для средних
уровней подставляет не то, что ждёт получатель, поэтому в примере drill не настроен.

**ADR-67. Выгрузка журнала действий (версия 1.40).**
- **Проблема:** журнал `audit_log` живёт под ретеншеном (ADR-59) и чистится по сроку безвозвратно, а снять с
него архив было нечем: только `GET /api/admin/audit` со страницами по 50 записей. Внедрение, где журнал
нужен для разбора инцидента или передачи в SIEM, оставалось с «посмотрите в интерфейсе, пока не удалилось».
- **Решение:** `GET /api/admin/audit/export.csv` с теми же фильтрами, что у списка (`action`, `actor`), плюс
период `from`/`to` (даты ГГГГ-ММ-ДД) и предел `limit` (по умолчанию 100 000, максимум 200 000). Формат по
умолчанию — RFC 4180: UTF-8 **без BOM**, запятая, CRLF, ISO-8601 в UTC, порядок по возрастанию времени (так
файл удобно дописывать и сравнивать). `excel=1` переключает на BOM и `;` — для открытия двойным щелчком.
Если записей больше лимита — `422 AUDIT_LIMIT` с числом записей и подсказкой сузить период, а не молча
обрезанный архив. Сама выгрузка пишется в журнал действием `audit.export` с числом строк и фильтрами.
На странице журнала появились поля периода и две ссылки выгрузки, несущие текущие фильтры.
- **Следствия:** архив снимается до чистки и совпадает с тем, что видно на экране; факт выгрузки (кто, когда,
сколько записей, с какими фильтрами) остаётся в журнале; CSV читается и Excel, и парсером SIEM.
- **Ограничения:** файл собирается в памяти целиком, потоковой отдачи нет — для журналов в миллионы строк
нужен отдельный архиватор; автоматической отправки в SIEM (syslog/HTTP) нет, только скачивание; подписи и
контрольной суммы у файла нет; выгружать может только роль `admin`; удалённые ретеншеном записи выгрузка,
разумеется, не вернёт — только то, что ещё лежит в таблице.

**ADR-66. Подытоги и ИТОГО в серверном Excel (версия 1.39).**
- **Проблема:** серверный `.xlsx` (ADR-38/49) выгружал плоский список детальных строк с объединениями и
outline-уровнями, но без строк «Итого …» и общего итога: книгу нельзя было читать как отчёт — суммы
приходилось считать глазами, а письмо по расписанию отличалось от экрана. Хуже того, в коде жили **две**
сборки листа: отдельный обработчик `/api/report/export.xlsx` со своей копией и общий `buildSheet` для CSV
и рассылки, поэтому любое улучшение доставалось только одному пути.
- **Решение:** одна функция группировки листа `buildGroupedSheet` (модуль `group_rows`): строка «Итого <ключ>» на
уровне, объявленном в шаблоне (`columns[].subtotal`), общий итог последней строкой (`grandTotal`, по умолчанию
включён), суммы по колонкам с `aggregate`, предки сохраняют свои значения, пустой ключ — `(пусто)`.
Объединения считаются по правилу экрана: строка итога уровня L входит в объединения колонок-предков, но не
своей колонки. Строки итогов оформлены как зоны (жирный, светлый фон, у ИТОГО линия сверху). Обработчик
`/api/report/export.xlsx` переведён на общий `buildSheet`, вторая копия удалена; CSV (`dropSummaryRows`)
остаётся машинным — без строк итогов.
- **Следствия:** файл, письмо и экран совпадают по числам: «Сводная таблица продаж» 1–10 марта —
2 748 детальных строк, 6 подытогов (пять регионов и `(пусто)`), ИТОГО 150 977 000 / 31 013 250 — те же числа,
что в модели на экране; «Финансы: план и факт» — 6 подытогов по месяцам и ИТОГО 1 661 216 000. Outline
работает: детали на уровне глубины группировки, подытоги выше.
- **Ограничения:** суммы считаются по колонкам с `aggregate`; вычисляемые колонки (выражения) в итогах
остаются пустыми, как и раньше, — сервер их не считает. CSV сознательно без итогов: машинному потребителю
они мешают, а эквивалентный итог он получает своим `GROUP BY`. Подытоги выгружаются всегда раскрытыми
(состояние сворачивания в браузере на файл не влияет), а строки итогов не участвуют в автофильтре.

**ADR-65. Раскрытие группы серверной агрегации подгружает детали (версия 1.38).**
- **Проблема:** в отчёте «Продажи: агрегация на сервере» у каждой категории был шеврон, но раскрытие
ничего не показывало: сервер по ADR-37 отдаёт ОДНУ строку на группу (`GROUP BY`), деталей в модели нет,
и шеврон обещал то, чего интерфейс сделать не мог. Заодно нашлось, что роль `viewer` получала 403 на
`/api/report/aggregate` (и на экспорт, и на поток изменений): в матрице прав для чтения был перечислен
только `/api/report/data`, остальные маршруты чтения попадали в правило «неизвестный путь — admin»,
поэтому у зрителя агрегированный отчёт показывал одно ИТОГО.
- **Решение:** новый маршрут `POST /api/report/group` — детали одной группы из того же набора данных:
SQL набора идёт подзапросом (`SELECT count(*) OVER () AS __group_total, d.* FROM (<sql>) d WHERE d.<field> = $N`),
поле фильтра берётся из groupBy блока и проверяется как идентификатор, значение уходит параметром, `NULL`
превращается в `IS NULL`. Предел — 5000 строк, `total` приходит всегда. Клиент при раскрытии группы
(если у блока есть объект `aggregate`) грузит её строки, кладёт их в модель как детальные, а строку итога
строит из **серверной** строки, а не из загруженной части; при обрезке в панели блока появляется
«в группах показано N из M строк». Матрица прав: все `/api/report/*` — чтение для `viewer`.
- **Следствия:** в примере марта раскрытие «Аксессуаров» даёт 685 строк вместо одной, итог группы остаётся
37 634 100, общий ИТОГО — 150 977 000 (не пересчитан по загруженной части); зритель видит агрегированный
отчёт целиком. Один запрос идёт в момент клика, остальное — как раньше. Группы агрегата стартуют
**свёрнутыми** (▸): строк в браузере ещё нет, и показывать «раскрыто» при пустой группе — обещание без данных;
первый клик и подгружает строки, и раскрывает. «Развернуть всё» подгружает все группы (по лимиту на каждую).
- **Ограничения:** детали грузятся только по одной группе и не кэшируются на сервере (клиент помнит их до
перезагрузки данных); лимит 5000 строк на группу, при большем объёме видна подсказка, догрузки «ещё» нет;
итог группы всегда серверный, поэтому суммы в раскрытой группе и в её строке итога могут не совпадать,
если группа обрезана; сводные строки внутри группы (подуровни) не появляются — группировка остаётся
одноуровневой, как её отдал `GROUP BY`.

**ADR-64. Ширины колонок виртуализированной таблицы считаются по модели (версия 1.37).**
- **Проблема:** контрольные замеры дали два дефекта под шапкой у сгруппированных таблиц. Первый: на месте
разреза объединения (прозрачная ячейка + подпись) рисовалась горизонтальная линия — она читается как
граница группы, хотя группа продолжается, и при прокрутке линия «всегда сверху». Второй: при
`table-layout: auto` ширину колонки задаёт **набор строк, попавших в окно**: пока в окне детальные строки,
колонка узкая, но как только в окно входит строка итога с более длинной подписью («Итого 01.10.2025»),
колонка скачком расширяется, таблица выходит за контейнер и появляется горизонтальная прокрутка; при
уходе строки всё сжимается обратно. Окно меняется на каждом шаге прокрутки — таблица «дышит».
- **Решение:** ширины колонок вычисляются **по всей модели** (самые длинные тексты шапки и зон, измерение
через `canvas.measureText` с шрифтами зон), подставляются в `<colgroup>`, раскладка всегда `fixed`;
вычисленные ширины сжимаются пропорционально, если сумма не влезает в контейнер (явные ширины шаблона не
трогаются); ширина контейнера отслеживается `ResizeObserver`. Прозрачная ячейка разреза получила класс
`phantom` без нижней границы и без фона. Поле `layout.tableLayout` принимается, но на раскладку не влияет.
- **Следствия:** ширины не меняются ни при прокрутке (замер: одна и та же строка ширин на 90 позициях),
ни при попадании строки итога в окно; таблица не выезжает за контейнер; в 9 отчётах обрезанных ячеек — 0.
Два новых e2e закрепляют это и падают на прежней версии компонента.
- **Ограничения:** ширина считается по длине строк, а не по реальной отрисовке шрифта для каждой ячейки:
  самый длинный текст выбирается по числу символов из 12 кандидатов, поэтому редкий «широкий» символ может
  получить запас в 4 px, а не точную ширину. При экзотическом шрифте с широкими глифами возможен многоточие;
  ширина колонки не интерактивна — пользователь не может растянуть её мышью.

**ADR-63. Окно виртуализации и подпись группы при прокрутке (версия 1.36.1).**
- **Проблема:** у отчётов с объединёнными групповыми колонками при прокрутке между липкой шапкой и
первой строкой появлялась пустая полоса — от 30 до 48 px («Финансы: план и факт по центрам затрат»).
Причина: окно начиналось со строки, чей верх лежит НИЖЕ шапки, а предыдущая, частично видимая строка не
рендерилась; к этому добавлялся сдвиг на высоту шапки (`scrollTop + headerHeight`), который был нужен,
чтобы подпись группы не рисовалась под шапкой. Ещё один дефект того же узла: при свёртывании группы
модель сокращается, элемент прокрутки молча упирается в новый максимум, событие `scroll` не приходит —
окно остаётся посчитанным по прежнему `scrollTop`, и таблица показывает хвост с пустотой сверху.
- **Решение:** окно начинается со строки, которая пересекает верх окна (`lowerBound(offsets, scrollTop)`
и шаг на строку назад), поэтому видимый остаток предыдущей строки закрывает полосу. Подпись группы
переносится: объединение режется на две ячейки — прозрачную часть под шапкой (держит выравнивание
колонок) и подпись, начинающуюся на первой полностью видимой строке; текст берётся у головы серии,
потому что в остальных строках группы значение групповой колонки пустое. После изменения модели
`scrollTop` пересчитывается от элемента (`watch` + `nextTick`).
- **Следствия:** полоса исчезла (замер: 42 px → 0 при `scrollTop=400`), подпись и шеврон всегда видны
под шапкой, свёртывание после прокрутки возвращает окно к началу, e2e это проверяет (2 новых теста).
- **Ограничения:** строка, попавшая под шапку, видна частично и обрезана посередине — так ведёт себя и
обычная таблица без виртуализации; в печатном слое окно не используется, там рендерится вся модель.
Прокрутка остаётся по строкам, а не по пикселям: шапку нельзя «протащить» поверх первой строки.

**ADR-62. Заём подписки и устойчивость отправки (версия 1.36).**
- **Проблема:** «заём» подписки на время отправки был зашит в SQL двумя минутами: при медленной сборке
файла второй экземпляр успевал взяться за ту же подписку, а при быстрой — подписка оставалась занятой
дольше нужного. Кроме того, попытка попадала в журнал только после завершения: падение процесса
в середине отправки не оставляло следа, и никто не знал, ушло письмо или нет.
- **Решение:** длительность заёма задаётся `REP_SUBSCRIPTION_LEASE_SECONDS` (120 с по умолчанию,
10…3600), период планировщика — `REP_SCHEDULER_TICK_SECONDS` (30 с). Попытка пишется в
`subscription_runs` до отправки (`finished_at = NULL`), в конце та же строка обновляется результатом;
при старте незавершённые попытки старше заёма закрываются как прерванные. Журнал отправок показывает
только завершённые строки. Добавлен частичный индекс `subscription_runs_open_idx`.
- **Следствия:** обрыв процесса больше не «тихий»: в журнале есть прерванная попытка, подписка
освобождается через заём и отправка повторяется. Медленная сборка файла не приводит к двойной отправке,
если заём больше времени сборки.
- **Ограничения:** доставка — at-least-once: обрыв ровно в момент передачи письма может дать дубль,
избежать этого без транзакции на SMTP нельзя. Заём — время, а не сердцебиение: при сборке дольше заёма
второй экземпляр всё равно возьмётся за подписку, поэтому значение надо держать выше худшего времени
сборки. Прерванные попытки закрываются только при старте процесса — на живом экземпляре строка
с `finished_at = NULL` может висеть, если поток отправки завис.

**ADR-61. Повтор отправки рассылки при сбое SMTP (версия 1.34).**
- **Проблема:** Сбой почтового сервера не должен терять выпуск: раньше единственной попыткой дело и заканчивалось, в журнале оставался `ok=false`.
- **Решение:** Повтор планируется в БД (`retry_count`, `retry_at`), а не сном в потоке. Пауза растёт экспоненциально (60 → 120 → 240 с, настраивается). Повтор не сдвигает `next_run_at`. При выборе подписки планировщик ставит «заём»: `next_run_at` уезжает вперёд на 2 минуты и перезаписывается настоящим расписанием в конце отправки. Номер попытки — в `subscription_runs.attempt`, исчерпание — в журнал действий (`subscription.given_up`). Ручной запуск повторов не планирует.
- **Следствия:** Письмо не теряется при кратком сбое; при двух экземплярах не уходит дважды (заём закрывает окно на всё время отправки).
- **Ограничения:** Очередь не персистентна на уровне писем: падение процесса во время отправки не переотправит письмо; суммарная длительность серии повторов ограничена только числом попыток и задержкой.

### 5.2 Грамматика выражений (полностью закрытая)

```ebnf
expr    := add
add     := mul (('+' | '-') mul)*
mul     := unary (('*' | '/') unary)*
unary   := '-'? primary
primary := NUMBER | 'null' | 'true' | 'false'
         | field | agg
         | '(' expr ')'
field   := IDENT | '[' IDENT ']'      (* IDENT: [A-Za-z_][A-Za-z0-9_]* *)
agg     := ('sum'|'avg'|'min'|'max'|'count'|'countDistinct') '(' expr? ')'
```

Семантика:
1. Область действия выражения — строка, для которой оно вычисляется. Для детальной строки область = эта строка; для строки промежуточного итога — соответствующая группа; для общего итога — весь набор.
2. `field` в строке итога разрешается в значение группового ключа или в агрегат по этому полю, если поле не является ключом группировки.
3. `agg(e)` агрегирует `e` по детальным строкам текущей области; `count()` без аргумента — число детальных строк области.
4. Вычисляемые колонки пересчитываются на **каждом** уровне области (детальная строка, каждый уровень группировки, общий итог) — та же семантика, что Scope в SSRS.
5. `null`-операнд → `null`; `/0` → `null`; `NaN`/`Infinity` → `null`.
6. Сравнений, условий (`if`), строковых функций и ссылок между блоками в v1 нет — фиксируется в `docs/expressions.md` как известное ограничение; при необходимости такие поля считаются в SQL.

### 5.3 Контракт API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | живость + версия схемы шаблонов + пинг БД |
| GET | `/api/reports` | список `{id, title}` |
| GET | `/api/reports/{id}` | шаблон (провалидированный) |
| POST | `/api/report/data` | `{reportId, params:{...}}` → данные |

Ответ `/api/report/data`:
```json
{"columns":[{"name":"region","type":"string"},{"name":"amount","type":"int"}],
 "rows":[{"region":"Север","amount":1200}],
 "rowCount":1,"truncated":false}
```

Ошибки (единая форма): `{"error":{"code":"...","message":"...","details":{}}}`.
Коды: `REPORT_NOT_FOUND` (404), `QUERY_NOT_FOUND` (500), `INVALID_PARAMS` (422), `ROW_LIMIT` (422), `SQL_TIMEOUT` (504), `DB_UNAVAILABLE` (503), `TEMPLATE_INVALID` (500).

Лимиты: `maxRows=50000`, `statement_timeout=30s`, `Cache-Control: no-store`. Сжатие ответа — gzip/deflate (brotli отключён: баг рецепта Conan, ADR-13). Отмена — `AbortController` на клиенте; на сервере — закрытие соединения прерывает обработку.

### 6.1 Порядок и зависимости

```
Ф0 ──► Ф1 ──► Ф2a ──► Ф2b ──► Ф3 ──► Ф4
        │       │                  │
        └─ 1.1–1.2 (схема+API) ────┴─► 4.1 (примеры) можно готовить заранее на Ф2a
```

- Жёсткая последовательность: Ф0 → Ф1 → Ф2a → Ф2b. Причина: Ф2b зависит от плоской модели Ф2a; Ф1 даёт API и шаблон, без которых Ф2a нечего рендерить.
- Внутри Ф0 порядок: 0.0 → 0.2 → 0.3 обязательны первыми (без сборки и БД остальное не проверить); 0.4 (vxe-table) — независимо, можно параллельно с 0.3; 0.5 — после 0.2.
- Может идти параллельно: документация (4.2) и примеры (4.1) — с середины Ф2a; скриншот-инфраструктура (3.5) — с Ф1.
- 2a.2 (выражения) и 2a.3 (группировки) независимы по коду — можно вести одновременно.
- Ф8 (экспорт и печать, 1.4) идёт после Ф7; 8.1–8.3 (Excel) и 8.5 (печать) независимы.
- Ф7 (админка, 1.3) идёт после Ф6; 7.1–7.4 (бэкенд) и 7.5–7.7 (UI) можно вести параллельно, 7.8 — в конце.
  Блокирующая зависимость: перед выносом админки за пределы localhost нужна read-only роль БД (5.9).
- Ф6 (условное форматирование, 1.2) идёт после Ф5; 6.1–6.2 можно вести параллельно с 6.3.
- Ф5 (стили, 1.1) идёт после Ф4 и не блокирует версию 1.0; внутри Ф5 порядок 5.1 → 5.2 → 5.3 → 5.4, документация (5.6) — параллельно с 5.3.
- Итого: **52 чел.-дн.** по версии 1.0 + 6 чел.-дн. на стили (Ф5, версия 1.1) ≈ 11 недель календарно для одного разработчика; при исполнении агентом календарь короче, узкое место — ревью-гейты PO.

Почему оценка ниже первичной (12–16 недель): снят decimal-слой (ADR-8), зафиксирован потолок 50k (ADR-7), Этап 2 разделён на 2a/2b (риск перестал быть неделимым), схема и валидатор перенесены в начало, а не «параллельно в конце». Поправка +2 чел.-дн. против v1.0 — на настройку Conan v1 и создание БД/синтетики.

## 9. Управление изменениями

- Базовый объём = этот документ. Любое требование вне его — отдельная фаза с собственной оценкой и гейтом; в текущие 52 чел.-дн. не входит.
- Изменение ADR-1…ADR-19 допускается только с записью в `docs/adr.md` и переоценкой затронутых фаз.
- Вне объёма (ТЗ §6, подтверждено): визуальный конструктор, экспорт Excel/PDF, drill-through, планировщик/рассылка, аутентификация на уровне отчётов, не-реляционные источники, справочники параметров из БД, условия/`if` в выражениях, фильтры и пользовательская сортировка таблицы.
