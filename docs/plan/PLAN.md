## 1. Принятые архитектурные решения (ADR)

Каждое решение закрывает конкретное противоречие или пробел ТЗ. Изменение любого пункта — через раздел 9 (управление изменениями).

Формат записи единый — четыре части, чтобы решение читалось за минуту:

- **Проблема** — что было не так и какое противоречие закрывалось;
- **Решение** — что именно принято (поля, таблицы, маршруты, замеры);
- **Следствия** — что изменилось в коде, поведении и цифрах;
- **Ограничения** — чего решение не делает и где сломается.

Полный реестр с оглавлением и якорями — `docs/adr.md` (генерируется: `node scripts/adr.mjs`);
при добавлении ADR правится этот файл, реестр пересобирается, актуальность и наличие четырёх частей
проверяет `./scripts/check.sh` (`node scripts/adr.mjs --check`).

**ADR-1. Единственный источник истины для таблицы — плоская модель строк.**
- **Проблема:** `mergeCells` в vxe-table адресуется индексами строк и колонок, а сворачивание групп и вставка строк итогов эти индексы меняют. ТЗ называло риски для пар «`footerMethod` × `mergeCells`» и «`subtotals` × `mergeCells`», но не для третьей — «`collapsible` × `mergeCells`».
- **Решение:** Движок отдаёт `FlatRow[]`: `{ kind: 'detail' | 'subtotal' | 'grandtotal', level, groupPath: string[], groupId, visible, cells }`. Колонки, объединения и общий итог выводятся из этого массива, а не из состояния табличного компонента.
- **Следствия:** Все три риска снимаются конструктивно: рендер, объединения и итоги читают одну структуру.
- **Ограничения:** Модель плоская — иерархия живёт только в `groupPath` и `level`; строки отчёта целиком держатся в памяти клиента (до 50 000).

**ADR-2. Общий итог — последняя строка массива, `footerMethod` не используется.**
- **Проблема:** Подвал компонента и объединения ячеек могут разъехаться: подвал считался отдельным проходом (§3 ТЗ).
- **Решение:** Строка общего итога — последняя строка того же массива (ADR-1); `footerMethod` не применяется.
- **Следствия:** Выравнивание по листовым колонкам получается автоматически: итог строится тем же маппингом, что заголовки.
- **Ограничения:** Итог всегда в конце — вставить «промежуточный итог» посреди таблицы нельзя; отдельного API подвала нет.

**ADR-3. Группировка описывается только колонками, `groupBy` в шаблоне отсутствует.**
- **Проблема:** ТЗ содержало два источника истины: `groupBy: [...]` в шаблоне и `columns[].group: true`.
- **Решение:** Оставлен один: порядок колонок с `group: true` задаёт порядок группировки. Подытоги — `subtotal: true` на групповой колонке вместо массива `subtotals`.
- **Следствия:** Одна декларация вместо двух; валидатор требует, чтобы групповая колонка шла до обычных.
- **Ограничения:** Группировать можно только по отображаемым колонкам; скрытая группировка невозможна.

**ADR-4. Шаблоны и SQL живут на сервере.**
- **Проблема:** Шаблон в бандле дублировался бы, а SQL оказался бы в браузере.
- **Решение:** `backend/templates/<id>.json` и `backend/config/queries.json` в репозитории; Drogon валидирует оба на старте и не поднимается при ошибке (fail-fast). Фронтенд получает шаблон по `GET /api/reports/{id}`. В dev-режиме — горячая перезагрузка шаблонов.
- **Следствия:** Единый источник шаблонов и SQL; битый файл останавливает сервис, а не ломает отчёты на ходу.
- **Ограничения:** Хранение шаблонов в БД позже заменило ADR-21; горячая перезагрузка осталась только в режиме `REP_TEMPLATES_SOURCE=files`.

**ADR-5. Параметры — часть шаблона, состояние — в URL.**
- **Проблема:** Ссылку на построенный отчёт нужно передавать и воспроизводить.
- **Решение:** Шаблон объявляет `params: [{name, type, label, required, default, options?}]`; `ReportViewer` строит форму, значения уходят в API и в query-строку (`/reports/sales?from=2026-01-01&to=2026-03-31`).
- **Следствия:** Ссылка воспроизводима, перезагрузка страницы сохраняет выбор.
- **Ограничения:** В версиях 1.0–1.3 `select` брался из статического `options`; справочники из БД появились отдельно (ADR-22, ADR-24).

**ADR-6. SQL — только подготовленные выражения с именованными параметрами.**
- **Проблема:** Подстановка значений в текст SQL открывает инъекцию через параметр отчёта.
- **Решение:** `queries.json` хранит SQL с именованными параметрами (`:from::date`); значения передаются только через binding. Проверка — ревью плюс тест на попытку инъекции.
- **Следствия:** Значения параметров не попадают в текст запроса; `::` остаётся кастом типа.
- **Ограничения:** Сам SQL — доверенный ввод автора шаблона; его прикрывают guard «только SELECT» (ADR-26) и роль только-чтения (ADR-33).

**ADR-7. Агрегация только на клиенте; на сервере — лимиты вместо агрегатов.**
- **Проблема:** ТЗ §2 требует клиентскую агрегацию, но выборка может не влезть в браузер.
- **Решение:** Сервер не считает агрегатов: `maxRows = 50000` (превышение — 422 `ROW_LIMIT`), `statement_timeout` на соединении (сейчас по умолчанию 30 000 мс, `REP_STATEMENT_TIMEOUT_MS`), отмена запроса через `AbortController`. Запасной вариант ТЗ «кэш агрегатов на бэкенде» отклонён.
- **Следствия:** Одна реализация семантики агрегации; браузер защищён лимитом и таймаутом.
- **Ограничения:** 50 000 строк — жёсткий потолок клиентского режима; при росте объёмов нужен серверный `GROUP BY` (сделан в ADR-37).

**ADR-8. Числа: `int` (включая bigint), `float`, `string`, `date`, `bool`; без decimal-типа.**
- **Проблема:** Нужна арифметика денег без ошибок округления и без нового типа.
- **Решение:** Десятичного типа нет: деньги хранятся и агрегируются целыми минорными единицами, округление выполняется только при выводе.
- **Следствия:** `double` точен до 2^53 — при 50 000 строк и значениях в минорных единицах переполнение недостижимо (проверяется тестом-стражем).
- **Ограничения:** Копейки нельзя хранить во `float`; сумма в минорных единицах должна помещаться в 2^53.

**ADR-9. Ошибки и `null` в выражениях — типизированы.**
- **Проблема:** Без правил `null` и деление на ноль давали бы разный результат в разных местах.
- **Решение:** Любой `null`-операнд → `null`; деление на 0 → `null`; `NaN`/`Infinity` → `null`. В ячейке `null` рендерится как `nullText` (по умолчанию «—»), пустая группа или пустой ключ → «(пусто)».
- **Следствия:** Одинаковое поведение движка на клиенте и в тестах.
- **Ограничения:** Пользователь не отличает «нет данных» от «нечисловое значение» — оба показываются как `nullText`.

**ADR-10. vxe-table — только MIT-ядро, фиксированная версия.**
- **Проблема:** В README vxe-table (4.x) как enterprise помечены сводные данные, агрегатные функции, выделение/copy-paste/поиск и встроенные диаграммы — коммерческая лицензия.
- **Решение:** Разрешено только бесплатное ядро: многоуровневые заголовки, подвал, объединения, группировка, виртуальный скролл. Версия пинована, внесена в `THIRD_PARTY.md`, CI проверяет отсутствие enterprise-API регуляркой.
- **Следствия:** Лицензионная чистота подтверждается автоматически.
- **Ограничения:** Позже vxe-table выведен из зависимостей вовсе (ADR-20); проверка осталась стражем на случай возврата.

**ADR-11. Все агрегаты и выражения считает собственный движок.**
- **Проблема:** Библиотеки выражений (`expr-eval` и подобные) не знают областей действия и агрегатных функций.
- **Решение:** Движок выражений и агрегатов написан свой (TypeScript): области row / group / grand total, функции `sum`, `avg`, `min`, `max`, `count`, `countDistinct`.
- **Следствия:** Правила одинаковы во всех зонах; лишней зависимости нет.
- **Ограничения:** Грамматика закрытая: сложные условия выносятся отдельным шагом (ADR-25), `median` и перцентили не поддерживаются.

**ADR-12. Форматы — закрытый каталог.**
- **Проблема:** Произвольные шаблоны форматирования дают расхождения между экраном, Excel и письмом.
- **Решение:** Каталог: `number` (разделитель тысяч — неразрывный пробел, `decimals` 0), `percent` (вход 0..1, вывод ×100, `decimals` 1), `currency` (₽/$/€, `decimals` 2), `date` (dd.MM.yyyy), `integer`. Локаль ru-RU фиксирована.
- **Следствия:** Один код форматирования на экран, `.xlsx` и печать.
- **Ограничения:** Своих форматов нет; локаль не переключается.

**ADR-13. Conan v1 — единственный пакетный менеджер C++; вызов только из venv.**
- **Проблема:** В `PATH` (`~/.local/bin/conan`) стоит Conan 2.28.1 с кэшем `~/.conan2`, а нужен v1 (1.66.0) с кэшем `~/.conan`; смешивание кэшей недопустимо.
- **Решение:** Любой вызов — `~/python_venv/bin/conan` или обёртка `scripts/conan`; `check.sh` падает при версии ≠ 1.66.x. Опции drogon: `with_postgres=True`, `with_orm=True`, `with_boost=False`, `with_brotli=False`, `with_profile=False`.
- **Следствия:** Сборка воспроизводима; генератор `cmake_find_package_multi`, `libcxx=libstdc++11`.
- **Ограничения:** Первая сборка из исходников — 15–25 мин; Conan 2 не поддерживается; brotli выключен, потому что рецепт не прокидывает include-пути.

**ADR-14. Catch2 v3 — тесты C++.**
- **Проблема:** Ядро нужно тестировать без HTTP-слоя и без браузера.
- **Решение:** `catch2/3.7.1`, `Catch2::Catch2WithMain`, отдельная цель `rep_tests`, регистрация в `ctest`. Интеграционные тесты ходят в реальную БД и убирают за собой данные.
- **Следствия:** Парсинг, параметры, агрегация, миграции, валидация и экспорт проверяются за секунды.
- **Ограничения:** Тесты с БД требуют живого PostgreSQL; HTTP-контракт и рендер проверяются e2e, а не Catch2.

**ADR-15. Секреты — только через `.env`.**
- **Проблема:** Пароли БД и SMTP не должны попадать в репозиторий, логи и тексты ошибок.
- **Решение:** `backend/.env` (в `.gitignore`) плюс `.env.example` с плейсхолдерами; DSN и SMTP читаются из окружения, пароли не логируются.
- **Следствия:** Репозиторий чистый; на сервере используется `EnvironmentFile` systemd (путь меняется `REP_ENV_FILE`).
- **Ограничения:** Файл `.env` лежит рядом с бэкендом — при переносе артефактов его нужно положить отдельно.

**ADR-16. Синтетические данные — детерминированный SQL-генератор.**
- **Проблема:** Эталонам и тестам нужны воспроизводимые данные.
- **Решение:** `db/schema.sql` (таблицы `sales`, `finance`, `ops`) и `db/seed.sql` (`setseed()` + `generate_series`): 50 000 фактов, 3 иерархии, намеренные `null`-ключи, нулевые знаменатели, отрицательные суммы, строка-выброс. Экспорт эталонов — через `psql`. Python-генератор не заводится.
- **Следствия:** Один seed питает и стенд, и golden-тесты.
- **Ограничения:** Данные синтетические: 50 000 строк хватает для бюджета рендера, но это не «большие данные».

**ADR-17. PostgreSQL 18.6 на 192.168.0.3:32770 — общий инстанс, работаем только в своей БД.**
- **Проблема:** Инстанс общий: чужие базы и объекты трогать нельзя.
- **Решение:** Работаем в БД `reporting`, DDL — только в схеме `public`; база создаётся идемпотентно `db/init.sh`.
- **Следствия:** Чужие БД не читаются и не меняются; стенд поднимается с нуля одной командой.
- **Ограничения:** Сервер 18.6, клиент `psql` 15.14 — фичи PG18 в коде не используются; локальный Postgres в Docker — только резерв для тестов.

**ADR-18. Типы колонок объявляются рядом с SQL.**
- **Проблема:** Drogon не отдаёт OID и типы колонок результата — только имена.
- **Решение:** Типы перечисляются в описании набора (`columns: {имя: int|float|text|date|bool}`); если колонка не объявлена, тип выводится из первого непустого значения.
- **Следствия:** Фронтенд знает типы до прихода данных — это нужно для форматирования и группировки.
- **Ограничения:** Схема дублируется рядом с SQL; ошибка объявления даёт неверное форматирование, а не падение. После ADR-27 обязательные объявления ушли, осталось выведение по значению.

**ADR-19. (заменён ADR-20) Сгруппированные таблицы рендерятся постранично.**
- **Проблема:** Замер спайка S1: `mergeCells` с большими `rowspan` вместе с виртуальным скроллом блокирует главный поток (> 60 с на 20 000 строк).
- **Решение:** Сгруппированная таблица показывает 200 строк на страницу, объединения считаются в пределах страницы.
- **Следствия:** Страница перестала зависать: 200 строк — 861 мс, 1 000 — 2 690 мс, 2 000 — 4 818 мс.
- **Ограничения:** Объединение не переносится через границу страницы; узкое место оказалось в базовом рендере vxe-table (2,4–4 мс/строку), поэтому решение заменено ADR-20.

**ADR-20. Свой лёгкий рендерер таблиц на Vue вместо vxe-table.**
- **Проблема:** vxe-table рендерит 2,4–4 мс/строку, а `mergeCells` с виртуальным скроллом вешает страницу (ADR-19).
- **Решение:** Собственный компонент `ReportTable`: нативная `<table>`, `rowspan`/`colspan` из модели ADR-1, своя витрина по фиксированной высоте строки, sticky-подпись группы. Это отклонение от ТЗ §2 (там назван vxe-table), согласовано постановщиком.
- **Следствия:** 50 000 строк укладываются в бюджет 1,63–1,71 с; vxe-table выведен из зависимостей; лицензионный манифест сократился.
- **Ограничения:** Свой код вместо библиотеки — сопровождение на нас; печать потребовала отдельного слоя (вариант A, версия 1.4.4).

**ADR-21. Шаблоны отчётов хранятся в БД.**
- **Проблема:** Шаблоны в файлах не редактируются через админку и не имеют истории; кроме того, PO решил хранить их в базе.
- **Решение:** Таблица `report_templates(id, title, body jsonb, updated_at)`; файлы `backend/templates/*.json` остаются источником в репозитории, `scripts/templates-push.mjs` загружает их в БД (upsert, dollar-quoting). Сервис читает шаблоны из БД на старте (`REP_TEMPLATES_SOURCE=db`), валидирует и держит в памяти.
- **Следствия:** Правка шаблона идёт через БД и админку; `GET /api/reports/{id}` отдаёт исходный JSON.
- **Ограничения:** Загруженные скриптом шаблоны требуют перезапуска сервиса; правки через админку применяются без рестарта (ADR-26).

**ADR-23. Внешний вид таблицы задаётся шаблоном (версия 1.1).**
- **Проблема:** Оформление было зашито в CSS компонента: заказчик не мог задать шрифты, цвета, ширины и высоты без правки кода.
- **Решение:** Необязательная секция `styles` + `blocks[].styles` + `columns[].style`: шрифты, цвета, выравнивание, отступы, ширины, высоты зон, границы, зебра. Реализация — CSS-переменные на корне таблицы и классы зон, без inline-стилей на ячейках; виртуализация переведена с умножения на `rowHeight` на префиксные суммы с бинарным поиском.
- **Следствия:** Оформление переносится в шаблон; 50 000 строк сохраняют производительность.
- **Ограничения:** Переменная высота строки (перенос текста) и условное форматирование в 1.1 не входили — они появились отдельными решениями.

**ADR-24. SQL справочников параметров живёт в шаблоне.**
- **Проблема:** Справочники обслуживались реестром `queries.json`: чтобы добавить фильтр, нужно было править серверный файл (требование PO, заменяет часть ADR-22).
- **Решение:** `params[].source` с `kind: "lookup"` содержит `sql` и не содержит `queryId` (валидатор запрещает). `GET /api/reports/{reportId}/lookups/{param}` берёт SQL из шаблона, `GET /api/reports/{id}` вырезает его из публичного ответа.
- **Следствия:** Справочник добавляется вместе с отчётом; браузер SQL не видит; 6 шаблонов переведены на `source.sql`.
- **Ограничения:** Серверного кэша справочников нет (кэш только на клиенте); тяжёлый SQL прикрывают `statement_timeout` и роль только-чтения.

**ADR-25. Условное форматирование — декларативные правила в блоке таблицы (версия 1.2).**
- **Проблема:** Подсветку «плохих» значений нельзя было задать шаблоном, а только кодом.
- **Решение:** `blocks[].rules[]`: `when {column, op, value}`, `apply` (стиль-объект как у зон), `scope` (`cell`/`row`), `zones` (`detail`/`subtotal`/`grandtotal`), `priority`. Операторы `= != > >= < <= between empty notEmpty contains`.
- **Следствия:** Правила сравнивают сырые значения, поэтому работают и для вычисляемых колонок; форматирование чисел применяется после правил; считаются только для видимого окна.
- **Ограничения:** В модель строк правила не попадают — Excel и печать переносят лишь совпадения, пересчитанные на клиенте; сложные условия выражениями не описываются.

**ADR-26. Администрирование отчётов: запись через API с hot-reload (версия 1.3).**
- **Проблема:** Правка отчёта требовала правки файлов, коммита и перезапуска сервиса.
- **Решение:** `GET /api/admin/reports`, `POST /api/reports`, `PUT /api/reports/{id}`, `DELETE /api/reports/{id}`, `POST /api/reports/{id}/validate`; всё доступно при `REP_ADMIN=1`. После записи шаблон в памяти обновляется под мьютексом.
- **Следствия:** Правки из админки применяются без рестарта; история версий — `report_templates_history`, откат = запись прежней версии.
- **Ограничения:** Валидация двухуровневая (клиент — полная, сервер — структурный минимум; позже серверная стала полной, ADR-45); `templates-push.mjs` пишет в обход процесса и по-прежнему требует рестарта.

**ADR-27. SQL наборов данных живёт в шаблоне.**
- **Проблема:** Наборы данных ссылались на реестр `queries.json`: отчёт нельзя было завести без правки серверного файла (требование PO, заменяет ADR-4/ADR-21 в части запросов).
- **Решение:** `datasets.<key>` содержит `sql` (обязателен) и `params` (отображение «параметр SQL → параметр отчёта»); `queryId` запрещён на клиенте и на сервере. Публичный `GET /api/reports/{id}` вырезает `datasets.*.sql`, админский отдаёт полный шаблон.
- **Следствия:** Отчёт самодостаточен; 12 шаблонов переведены на `datasets.sql`; реестр `queries.json` сокращён до служебного `slow_probe`.
- **Ограничения:** SQL исполняется под ролью сервиса — его прикрывают guard «только SELECT» и роль только-чтения; тип параметра определяется кастом в SQL.

**ADR-28. Экспорт в Excel и печатный вид (версия 1.4).**
- **Проблема:** Пользователю нужен файл, совпадающий с экраном (группировка, подытоги, форматы, правила), и печать без потери шапки.
- **Решение:** Excel собирается на клиенте из модели витрины (ExcelJS, MIT, ленивый чанк): объединения шапки, подытоги, `numFmt`, цвета зон, совпадения правил, лист «Параметры». Печать — `@media print` + `window.print()`, шапка повторяется, группы не разрываются.
- **Следствия:** Файл и печать соответствуют экрану «по построению»; лимиты — 100 000 строк в Excel, 20 000 в печать (сейчас 5 000), сверх — отказ с сообщением.
- **Ограничения:** Диаграммы не переносятся ни в Excel, ни в печать; серверный экспорт (ADR-38) появился для объёмов и рассылки, но он плоский.

**ADR-29. Drill-through (версия 1.5).**
- **Проблема:** Из сводного отчёта нужно перейти к деталям по выбранной группе.
- **Решение:** Секция `drill: { report, label?, params }` в табличном блоке; значения — `group.<field>`, `param.<name>` или литерал. Ссылкой становится ячейка группы, параметры уходят в URL целевого отчёта.
- **Следствия:** Переход — обычное открытие отчёта с параметрами: без нового контракта, работает «назад» в браузере.
- **Ограничения:** Доступен только из групп таблицы; диаграммы получили drill отдельным решением (ADR-43), из подытогов и ИТОГО переход не настраивается.

**ADR-30. Каталог отчётов (версия 1.5).**
- **Проблема:** Отчёты находились только по прямой ссылке.
- **Решение:** Папка и теги объявляются в шаблоне (`folder`, `tags`); `GET /api/reports` отдаёт их вместе с описанием и параметрами. Экран списка: папки со счётчиками, фильтр по тегам, поиск по названию/описанию/id/тегам, избранное в `localStorage`.
- **Следствия:** Отдельной таблицы каталога нет: источник истины — сами шаблоны, перенос отчёта в другую папку не требует миграций.
- **Ограничения:** Избранное локальное — на другом браузере его нет; поиск и пагинация позже перенесены на сервер (ADR-41).

**ADR-31. Черновик и публикация (версия 1.6).**
- **Проблема:** Правка шаблона сразу меняла публичный отчёт; согласовать изменения было нельзя.
- **Решение:** Правка пишется в колонку `report_templates.draft`; публикация пишет снапшот прежней версии в историю, переносит черновик в `body` и обновляет память без рестарта. Создание отчёта сразу публикует его.
- **Следствия:** Публичный отчёт не меняется до явной публикации; откат — обычная запись прежней версии.
- **Ограничения:** Черновик один на отчёт — параллельная правка двумя авторами перетирается; метка «черновик от ДД.ММ» не защищает от конфликта.

**ADR-32. Кэш результатов (версия 1.7).**
- **Проблема:** Повторные запросы одного отчёта с теми же параметрами заново читали базу.
- **Решение:** Ответы `POST /api/report/data` кэшируются в памяти по ключу «отчёт + версия шаблонов + параметры»: TTL 60 с, `ETag`, `X-Cache`, поддержка `If-None-Match` (304). Публикация, правка, откат и удаление поднимают версию шаблонов и сбрасывают кэш.
- **Следствия:** Повторные открытия отвечают мгновенно; устаревшие данные не отдаются при правке шаблона.
- **Ограничения:** Кэш на процесс — у нескольких экземпляров свой; ответы больше 2 МБ и ошибки не кэшируются; TTL задерживает свежесть данных.

**ADR-33. Роль БД только-чтения (версия 1.8).**
- **Проблема:** SQL из шаблонов (ADR-27) исполняется под ролью сервиса — ошибка или злой умысел автора могла писать в базу.
- **Решение:** Данные и справочники читаются отдельным пулом под ролью `reporting_ro` (`REP_RO_DB_USER`/`REP_RO_DB_PASSWORD`), которую создаёт `scripts/db-ro.sh`; запись шаблонов и админка остаются на основной роли.
- **Следствия:** `INSERT` отклоняется самой СУБД; `/api/health` показывает `readOnlyRole`.
- **Ограничения:** Если переменные не заданы, чтение идёт основной ролью (совместимость сохранена); права нужно выдавать в каждой новой БД — ошибка, поймана в CI (ADR-47).

**ADR-34. Аутентификация и роли (версия 1.9).**
- **Проблема:** Админка и отчёты были доступны всем, кто открыл страницу.
- **Решение:** `users` (PBKDF2-HMAC-SHA256, 120 000 итераций, соль на пользователя) и `sessions` (токен 32 байта, TTL 12 ч); cookie `rep_session` — `HttpOnly`, `SameSite=Lax`, `Path=/`. Проверка одна, до маршрутизации: матрица «метод + путь → минимальная роль», неизвестные пути требуют admin.
- **Следствия:** Роли viewer/author/admin работают на всех маршрутах; отзыв сессии — удаление строки в БД.
- **Ограничения:** Нет ограничения попыток входа, нет `Secure` (пока нет HTTPS), нет 2FA и смены своего пароля.

**ADR-36. Несколько наборов данных в шаблоне (версия 1.10).**
- **Проблема:** Один шаблон описывал только один запрос, хотя отчёт часто требует разных гранулярностей.
- **Решение:** `datasets` — словарь; блок ссылается на набор через `dataKey`; клиент запрашивает каждый набор отдельно (`POST /api/report/data` с полем `dataset`), без поля сервер отдаёт первый набор.
- **Следствия:** Один шаблон = несколько независимых выборок; ключ кэша включает имя набора.
- **Ограничения:** JOIN через один запрос отклонён (разная гранулярность раздувает выборку); до версии 1.29 диаграммы игнорировали `dataKey` — дефект исправлен в ADR-56.

**ADR-37. Серверная агрегация (версия 1.11).**
- **Проблема:** На 50 000 строк клиентская агрегация упирается в лимит и трафик.
- **Решение:** Блок объявляет `aggregate: {groupBy, measures}`; сервер выполняет `GROUP BY` поверх SQL набора, имена и агрегаты проверяются как идентификаторы, параметры идут тем же компилятором.
- **Следствия:** Детализация не покидает базу; клиент получает уже сгруппированные строки.
- **Ограничения:** Функции только `sum|avg|min|max|count`; клиентская агрегация остаётся для WYSIWYG; существование колонок проверяется не валидатором, а базой (422 при построении).

**ADR-38. Серверный экспорт в Excel (версия 1.12).**
- **Проблема:** Excel нужен без браузера — для рассылки и больших объёмов.
- **Решение:** `POST /api/report/export.xlsx` собирает книгу на сервере (`libxlsxwriter`, BSD-2): шапка и форматы из табличного блока, данные из набора с применением `aggregate` блока, второй лист — параметры.
- **Следствия:** Экспорт работает без клиента; клиентский WYSIWYG (ADR-28) остаётся для точного совпадения с экраном.
- **Ограничения:** Плоская таблица: без подытогов/ИТОГО и без объединений (объединения добавлены в 1.21, ADR-49); диаграммы не экспортируются.

**ADR-39. Автообновление отчёта (версия 1.13).**
- **Проблема:** Экран с операционными показателями устаревал, пока его не перезагрузят.
- **Решение:** Шаблон задаёт `refreshSeconds` (0…3600, меньше 5 — предупреждение); страница перезапрашивает данные с сохранением параметров и состояния групп; тик пропускается в фоне и при активном запросе, есть пауза.
- **Следствия:** Данные обновляются без действий пользователя; сервер ничего не помнит о подписках.
- **Ограничения:** Кэш TTL может отдавать данные с задержкой; несколько открытых страниц дают несколько запросов.

**ADR-40. CSV на сервере (версия 1.14).**
- **Проблема:** CSV нужен для машинной обработки и как вложение письма.
- **Решение:** Отдельный маршрут `POST /api/report/export.csv` (а не параметр `format` у `.xlsx`); расчёт тот же, что у серверного XLSX. Формат: UTF-8 с BOM, `;`, CRLF, кавычки при спецсимволах, числа без форматирования.
- **Следствия:** Excel открывает файл двойным щелчком; CSV пригоден для машинной обработки.
- **Ограничения:** Разделитель `;` не настраивается; числа теряют форматирование шаблона — это осознанно.

**ADR-41. Поиск и пагинация каталога на сервере (версия 1.14).**
- **Проблема:** Каталог грузил все шаблоны и фильтровал на клиенте — при росте числа отчётов это лишний трафик.
- **Решение:** `GET /api/reports` принимает `q`, `folder`, `tag`, `limit`, `offset`; без `limit` отдаёт прежний массив (совместимость), с `limit` — `{items,total}`. Фильтрация по снимку шаблонов в памяти; страница грузит по 10, поиск с задержкой 250 мс.
- **Следствия:** Каталог масштабируется по числу отчётов; старые клиенты и e2e не ломаются.
- **Ограничения:** Избранное осталось в `localStorage`; полнотекстового поиска нет — только подстрока по полям.

**ADR-42. Обновление по событию (long-poll) — заменён ADR-44 (версия 1.14).**
- **Проблема:** Таймер опроса тратит запросы в простое и даёт задержку до периода.
- **Решение:** `GET /api/report/changes?report=<id>` держит запрос до 20 с и отвечает сразу после публикации или отката шаблона; шаблон включает режим полем `live: true`.
- **Следствия:** Нет опроса по таймеру; живёт на штатных таймерах Drogon, без WebSocket.
- **Ограничения:** Висящее соединение на каждого зрителя; заменено на SSE в ADR-44 из-за двух обменов на каждое событие.

**ADR-43. Drill-through с диаграмм (версия 1.15).**
- **Проблема:** Из точки диаграммы нельзя было перейти к деталям, хотя из таблицы уже можно (ADR-29).
- **Решение:** Та же секция `drill`, но ссылки другие: `x` — категория точки, `series` — имя серии; `group.<field>` отклоняется валидатором. Клик обрабатывает `ChartBlock`, решение о переходе принимает `ReportViewer`.
- **Следствия:** URL-схема перехода одна для таблицы и диаграмм.
- **Ограничения:** Круговая диаграмма отдаёт только `name`, поэтому для неё допустим лишь `x`/`param.`/литерал; из gauge подставлять нечего (ADR-56/57).

**ADR-44. SSE вместо long-poll (версия 1.16).**
- **Проблема:** Long-poll (ADR-42) требовал нового запроса после каждого ответа: два HTTP-обмена на событие и вечная ротация соединений в простое.
- **Решение:** Одно SSE-соединение `GET /api/report/events?report=<id>` на всё время работы страницы (`newAsyncStreamResponse` в Drogon); сервер пишет `event: change` после публикации и `: ping` раз в 15 с, отвалившиеся клиенты вычищаются на пульсе.
- **Следствия:** Событие доходит за доли секунды; в простое только пульс.
- **Ограничения:** Потоковые ответы буферизуют прокси — нужен `proxy_buffering off`; Vite-прокси отдавал SSE как `Content-Length: 0`, потребовался собственный проброс (`frontend/sse-proxy.js`).

**ADR-45. Полная серверная валидация (версия 1.17).**
- **Проблема:** Сервер делал «структурную» проверку, а семантика жила в клиентском `validate.js` — шаблон можно было сохранить в обход браузера.
- **Решение:** Правила перенесены в `backend/src/validate.cc` и возвращают список `{path, message}`; клиентский валидатор остался для мгновенной подсказки, истина — сервер. Parity закреплена фикстурами `docs/fixtures/validation-cases.json`, которые читают оба теста.
- **Следствия:** В обход браузера нельзя сохранить заведомо битый шаблон; сервер дополнительно проверяет `id`, уникальность параметров, `chartType`, размер и SQL-гард.
- **Ограничения:** Правила описаны дважды — фикстуры стали обязательной частью изменений; SQL-гард проверяет форму запроса, а не его смысл.

**ADR-46. Рассылка по расписанию (версия 1.18).**
- **Проблема:** Отчёт нужно получать на почту без участия человека; ручная отправка не масштабируется.
- **Решение:** Подписки лежат в БД (`report_subscriptions`), расписание — cron из пяти полей. Планировщик — отдельный поток с собственным соединением libpq: отправка блокирующая и не должна занимать цикл событий. Просроченные подписки забираются одним `UPDATE … FOR UPDATE SKIP LOCKED`. Почта — собственный минимальный SMTP-клиент (OpenSSL): STARTTLS, AUTH PLAIN/LOGIN, вложение base64. Журнал — `subscription_runs`.
- **Следствия:** Одно письмо не уходит дважды; результат каждой отправки виден в админке; файл собирается тем же кодом, что HTTP-экспорт.
- **Ограничения:** Изначально только CSV, без повторов и таймзон (закрыто в ADR-48, ADR-60, ADR-61); SMTP без проверки сертификата; per-user подписок нет.

**ADR-47. E2E в CI (версия 1.19).**
- **Проблема:** Сквозные тесты шли только вручную, регрессии ловились поздно.
- **Решение:** Job `e2e` в GH Actions на сервисе `postgres:16`; стенд поднимает `scripts/ci-e2e.sh` — тот же скрипт работает локально с отдельной БД (`reporting_ci`) и своими портами (8081/5174/1026), поэтому «у меня» и «в CI» проверяют одно и то же.
- **Следствия:** Каждый push проверяется сквозными сценариями; стенд изолирован от рабочей БД.
- **Ограничения:** Сервис Postgres в CI — контейнер с паролем по умолчанию (только внутри job'а); без кэша Conan job выходит за таймаут; первый прогон на раннере так и не наблюдался.

**ADR-48. XLSX в рассылке (версия 1.20).**
- **Проблема:** Письмо уходило только в CSV, хотя подписка может требовать книгу Excel.
- **Решение:** Лист собирает одна функция `buildSheet` (выборка, агрегация блока, колонки с форматами, заголовок, параметры), а форматы — тонкие обёртки: CSV (`toCsv`) и XLSX (`writeXlsx` во временный файл → байты в письмо). Формат — поле подписки (`csv`/`xlsx`), проверяется при сохранении.
- **Следствия:** Письмо, скачивание и экран считаются одним кодом — расхождение невозможно по построению.
- **Ограничения:** Серверный XLSX плоский: без подытогов и outline (подытоги по-прежнему только в браузерном экспорте).

**ADR-49. Объединения и outline в серверном XLSX (версия 1.21).**
- **Проблема:** Сводная книга в письме выглядела плоской таблицей — группировку приходилось восстанавливать глазами.
- **Решение:** `applyGrouping` считает по групповым колонкам вертикальные объединения одинаковых подряд идущих значений и уровни структуры; `writeXlsx` ставит `mergeCells`, `outlineLevel`, `summaryBelow=0`. Порядок строк не пересортировывается — он приходит из SQL и совпадает с экраном.
- **Следствия:** Книга читается как на экране; кириллица не ломает порядок, потому что сортировки по байтам нет.
- **Ограничения:** Сервер не строит подытоги и ИТОГО: в книге детальные строки с объединениями и структурой; полный WYSIWYG даёт только браузерный экспорт.

**ADR-50. Управление пользователями (версия 1.22).**
- **Проблема:** Пользователей заводил только скрипт на сервере (`scripts/auth-init.sh`), то есть человек с shell.
- **Решение:** Админка создаёт и правит пользователей; отключение (`enabled=false`) вместо удаления там, где нужна история: вход запрещён, сессии удаляются сразу. Защита от потери управления: нельзя удалить себя, отключить себя или снять роль с последнего включённого админа (`SELF_PROTECTED`, `LAST_ADMIN`).
- **Следствия:** Управление доступом не требует shell; история действий по пользователям видна в журнале.
- **Ограничения:** Нет смены своего пароля, нет 2FA, нет ограничения попыток входа.

**ADR-51. Версионирование шаблона и миграции (версия 1.23).**
- **Проблема:** `version` был константой «1» и ничего не означал: формат менялся, а старые шаблоны никто не проверял.
- **Решение:** `version` — версия формата: текущая 2, поддерживается 1…2, старые поднимаются цепочкой миграций, новые отклоняются с текстом «обновите сервер». Миграция выполняется на сервере (сохранение, публикация, загрузка в память) и в админке при открытии; логика продублирована на C++ и JS и сверяется общими фикстурами.
- **Следствия:** Шаблоны в БД всегда в актуальном формате; версия 2 сделала `chartType` обязательным (при миграции — `bar`).
- **Ограничения:** Миграции только вперёд и необратимы; шаблон с `queryId` (эпоха ADR-27) миграция не спасёт — SQL из удалённого реестра не восстановить.

**ADR-52. Аудит действий (версия 1.24).**
- **Проблема:** На вопрос «кто это сделал» не было ответа: журнал приложения — это grep по файлам.
- **Решение:** Отдельная таблица `audit_log` (когда, кто, действие, объект, детали `jsonb`, адрес). Событие пишется при успехе; неудачные попытки — только для входа (`auth.login_failed`). Детали — безопасный минимум (логин, роль, формат, число писем). API только на чтение, страница `audit.html`.
- **Следствия:** Разбор инцидента идёт по запросу, а не по логам; журнал нельзя подчистить через интерфейс.
- **Ограничения:** Нет выгрузки в файл/SIEM и нет записи чтения отчётов; ретеншен появился позже (ADR-59).

**ADR-53. Префикс приложения для реверс-прокси (версия 1.25).**
- **Проблема:** Сервер отчётов должен стоять не только в корне домена: у заказчика он живёт рядом с другими системами.
- **Решение:** База сборки задаётся `REP_BASE`, адрес API вычисляется на клиенте из расположения страницы (`/reports/report.html` → `/reports/api`); ассеты подключаются относительными путями (`base: './'`), поэтому `dist` переносим без пересборки. Прокси обязан снимать префикс, для SSE — отдельный блок с `proxy_buffering off`.
- **Следствия:** Одна сборка работает и в корне, и под любым префиксом; переезд не требует пересборки.
- **Ограничения:** Подпрефиксная проверка не входит в обычный `check.sh` (нужен отдельный прогон стенда); cookie живёт на `Path=/` и `Secure` появится только с HTTPS.

**ADR-54. Аутентификация на реверс-прокси (версия 1.26).**
- **Проблема:** В части внедрений вход выполняет прокси (basic, SSO, `auth_request`) — второй вход в приложении не нужен.
- **Решение:** `REP_AUTH=proxy`: логин из заголовка `X-Remote-User`, роль — из `users`, поэтому матрица viewer/author/admin общая для обоих режимов. Заголовок принимается только с адресов `REP_AUTH_PROXY_TRUSTED` и проверяется по безопасному набору символов. Вход и выход в этом режиме отвечают 400 `AUTH_ON_PROXY`.
- **Следствия:** Внешний вход без второго пароля; неизвестный логин — 403, а не «гость»; автосоздание возможно явным флагом и пишется в журнал.
- **Ограничения:** Доверие к заголовку защищено только адресом прокси (без mTLS/подписи); заголовок не несёт групп; роль кэшируется 60 с.

**ADR-55. Схема шаблона — контракт формата (версия 1.28).**
- **Проблема:** Сервер и шаблоны использовали у табличного блока `title` и `aggregate`, а схема их не объявляла — три рабочих шаблона считались невалидными. Причина живучести: в `check.sh` проверка стояла в `npm run … && echo`, левая часть `&&` не подпадает под `set -e`, и провал тонул в успешном выводе.
- **Решение:** Поля, которые реально работают, объявлены в `schema.js`, `docs/template.schema.json` перегенерируется; `check.sh` проверяет код возврата явно и падает с «шаблоны не проходят валидацию»; мёртвые поля из шаблонов убраны.
- **Следствия:** Машиночитаемая схема перестала врать: 15 из 15 шаблонов валидны.
- **Ограничения:** Валидатор проверяет структуру и допустимые значения, но не существование колонок в SQL — неверное имя даёт 422 при построении отчёта.

**ADR-56. Виды диаграмм gauge и sankey (версия 1.29).**
- **Проблема:** Заказчику нужны не только ряды, но и «одно число» и «потоки»: спидометр для KPI и sankey для распределения сумм между категориями и регионами.
- **Решение:** Оба вида — надстройка над блоком `chart`: у `gauge` поля `yField` + `aggregate` и шкала `min`/`max`/`unit`, у `sankey` — `sourceField`, `targetField`, `valueField`. Обязательность полей переехала в семантический валидатор и продублирована на клиенте и сервере с parity-фикстурами. Агрегация остаётся клиентской.
- **Следствия:** Новые виды без третьего типа блока; попутно исправлены два дефекта: диаграммы игнорировали `dataKey` и `aggregate`-строка принималась за серверную агрегацию (422).
- **Ограничения:** Диаграммы не экспортируются в Excel и не печатаются; sankey без промежуточных уровней; gauge показывает одно значение без порогов (зоны добавлены в ADR-57).

**ADR-57. Цветовые зоны gauge (версия 1.30).**
- **Проблема:** Для KPI мало одного числа: нужно «плохо/терпимо/хорошо».
- **Решение:** `thresholds` (2…8 строго возрастающих границ) и `zoneColors` (`thresholds.length + 1` цветов: hex, `transparent` или токен `styles.palette`). N границ дают N+1 зон; полоса прогресса при зонах отключается, чтобы цвета читались. Границы вне `min…max` обрезаются.
- **Следствия:** Шкала и указатель окрашиваются по зоне; при некорректных цветах рисуется шкала без зон, страница не падает.
- **Ограничения:** Пороговая логика только у `gauge` (у таблиц — `rules`, ADR-25); зоны не попадают в Excel; валидатор полей не видит данных.

**ADR-58. Диаграмма band: значение и коридор (версия 1.31).**
- **Проблема:** Для эксплуатационных отчётов нужен не только ряд значений, но и допустимый разброс: у точки три числа — значение, нижняя и верхняя границы.
- **Решение:** Отдельный `chartType: "band"` с полями `yField`, `lowField`, `highField`; заливка рисуется двумя невидимыми стековыми рядами (основание «низ» плюс разница «верх − низ»), значение — третьим рядом.
- **Следствия:** Работает на любых данных, включая отрицательные нижние границы; не нужны ни `custom`-серия, ни расчёт полигонов.
- **Ограничения:** Одна полоса на график; полоса не попадает в Excel и печать; при перепутанных границах вырождается в ноль — валидатор данных не видит.

**ADR-59. Ретеншен журналов (версия 1.32).**
- **Проблема:** `audit_log` и `subscription_runs` растут монотонно, а «чистить руками, когда станет много» — отложенный инцидент.
- **Решение:** Глубина хранения задаётся `REP_LOG_RETENTION_DAYS` (90 дней по умолчанию, `0` — бессрочно), одна настройка на оба журнала. Чистка живёт в отдельном потоке (не в планировщике рассылки), запускается при старте и раз в 6 часов; факт удаления пишется в журнал действием `logs.purge` только при ненулевых удалениях; `/api/health` показывает действующую глубину.
- **Следствия:** Журналы не растут бесконечно; настройка видна на развёрнутом экземпляре без догадок.
- **Ограничения:** Удаление необратимо (архивации в файл/SIEM нет); глубина считается по времени сервера, а не по поясу зрителя.

**ADR-60. Часовой пояс расписания в подписке (версия 1.34).**
- **Проблема:** «Каждый будний день в 9:00» — это 9:00 по месту работы, а не по UTC сервера: до этой версии cron считался в поясе процесса, и рассылка уходила на 3–7 часов позже или раньше ожидаемого.
- **Решение:** Пояс хранится в подписке (`timezone`, IANA-идентификатор), а не в переменной окружения: у подписок бывают разные получатели и регионы. Пересчёт «местное ↔ UTC» с переходами на летнее время выполняет PostgreSQL (`AT TIME ZONE`), в C++ остаётся календарный поиск следующей минуты. Неизвестный пояс отклоняется при сохранении (422).
- **Следствия:** Расписание совпадает с ожиданием получателя; DST обрабатывает база.
- **Ограничения:** Старые подписки получили `UTC` при миграции (их расписание не менялось); производственного календаря (праздников) нет — только дни недели.

**ADR-81. Приложение живёт под префиксом /reports (версия 1.56).**
- **Проблема:** после ADR-79/80 сервер отдаёт и API, и статику, но по корню: `http://host:8080/report.html`.
  На общем хосте приложение нужно вешать в подкаталог (`/reports/…`), а без внешнего прокси
  это было нечем: маршруты зарегистрированы без префикса, статика искалась от корня.
- **Решение:** `REP_BASE_PATH` (по умолчанию `/reports`) снимается с пути в pre-routing advice —
  **до** маршрутизации и **до** проверки прав. `HttpRequest::setPath` позволяет переписать путь,
  поэтому все обработчики, матрица прав (`requiredRole`), кэш и статика остаются на своих путях,
  а наружу всё видно как `/reports/...`: `/reports/report.html`, `/reports/api/health`,
  `/reports/assets/*`. Значение нормализуется (`reports` → `/reports`, хвостовой слэш убирается,
  пусто и `/` — работа без префикса). Корень `/` отвечает 302 на `/reports/`: иначе относительные
  ссылки на ассеты (`./assets/…`) ушли бы на уровень выше. Клиент ничего не знает о префиксе —
  он вычисляет базу API из расположения страницы (ADR-53), поэтому сборка та же.
- **Следствия:** полный адрес — `http(s)://host:port/reports/*`; проверено, что страницы, ассеты,
  `api/health` и защищённый `api/report/data` работают под префиксом, ассеты получают
  `immutable`-кэш, `/` отдаёт 302 на `/reports/`, отчёт открывается и показывает 2 748 строк.
  Старые пути без префикса продолжают работать (алиас): это сохраняет скрипты, e2e и внешние
  ссылки; при необходимости префикс отключается `REP_BASE_PATH=""`.
- **Ограничения:** префикс один и задаётся при старте (смена — перезапуск); алиас без префикса
  не выключается флагом (только пустым `REP_BASE_PATH`, что убирает и префикс); внутри префикса
  не поддерживаются вложенные приложения (`/reports/x/...` — это путь статики, не второй сервис);
  редирект с `/` — 302, а не 301, чтобы после смены префикса браузер не запомнил старый адрес
  навсегда; TLS и внешний домен по-прежнему требуют прокси, но путь он уже не переписывает.

**ADR-149. Синхронизация шаблонов с БД (версия 2.22.0).**
- **Проблема:** шаблоны читаются из БД один раз на старте, поэтому отчёт, удалённый прямо в базе
  (или из другого экземпляра сервера), продолжал отдаваться в `/api/reports` и открываться по прямой
  ссылке до перезапуска. На e2e это проявилось «мусорным» шаблоном, который валил тест.
- **Решение:** после загрузки шаблонов запускается периодическая сверка с БД
  (`app().getLoop()->runEvery`): раз в `REP_TEMPLATES_SYNC_SECONDS` (по умолчанию 30, минимум 5)
  читается список `report_templates`; новые шаблоны добавляются в память, отсутствующие в БД —
  удаляются из `templates`/`templatesRaw`, вместе с их черновиками (`draftsParsed`/`draftsRaw`/
  `draftsErrors`). Удаление пишется в журнал событием `change_template`. Ошибка БД не роняет сервер:
  пишется предупреждение, следующая попытка — через интервал.
- **Следствия:** удаление `manual-load` прямо в БД убирает отчёт из выдачи (43 → 42) за один интервал
  синхронизации; в журнале — «шаблон удалён из БД и убран из выдачи: manual-load».
- **Ограничения:** изменение существующего шаблона в БД синк не подхватывает (только появление и
  удаление) — правки тела идут через админку; `REP_TEMPLATES_SOURCE=files` синк не делает (файлы
  читаются на старте); при интервале 30 с удалённый отчёт остаётся доступным до полуминуты; синк
  делает два синхронных запроса в цикле drogon, то есть на время запроса обработчик блокируется.

**ADR-148. Сброс карантина по одному источнику (версия 2.21.0).**
- **Проблема:** карантин снимался только целиком (`POST /api/admin/datasources/reset`), поэтому при
  одном неисправном источнике перепроверялись все, а admin не видел, какие именно источники в карантине.
- **Решение:** `markFailed` принимает человекочитаемую метку (`source · host/database`), реестр хранит
  её рядом с ошибкой (DSN наружу не отдаётся — в нём пароль). `GET /api/admin/datasources` возвращает
  `{items: [{label, error}]}`, `POST …/reset` с `{label}` снимает карантин с одного источника
  (`clearFailure`), без тела — со всех. В админке под кнопкой «Проверить источники данных» появился
  список источников в карантине с кнопкой «Сбросить» у каждого.
- **Следствия:** в админке видно `main · ${PGHOST}/no_such_db` и кнопку «Сбросить»; сброс одного
  источника возвращает `{"cleared":1}`, после него список пуст, остальные источники не затрагиваются.
- **Ограничения:** метка строится из шаблона и может повторяться у двух отчётов с одинаковыми
  host/database и именем источника — тогда сброс снимет карантин с обоих; метка не содержит порт, при
  двух базах на одном хосте с разными портами подписи совпадут; список показывает только активный
  карантин (истёкшие записи не видны).


**ADR-147. Устойчивый e2e «все шаблоны из списка» (версия 2.21.0).**
- **Проблема:** тест падал через раз (2,1 с против обычных 20+): он ждал `.meta` с числом строк, но
  сразу после этого считал ячейки и диаграммы, а виртуализированная таблица рисуется на следующем
  кадре — проверка `cells + charts > 0` получала 0.
- **Решение:** проверка заменена на `expect.poll(..., {timeout: 10000})` — тест ждёт, пока появится
  либо строка таблицы, либо холст диаграммы, и в сообщении об ошибке называет отчёт.
- **Следствия:** полный прогон перестал быть флаки: тест проходит и при быстром прогоне (2,1 с
  больше не ошибка), и отдельно (20,7 с).
- **Ограничения:** тест по-прежнему последовательный (43 отчёта, ~20 с) и зависит от живых REST- и
  Kerberos-сервисов: при погашенном демо падает по другой причине — ошибка данных, а не отрисовки.

**ADR-146. Сообщение «Строка не найдена» (версия 2.20.2).**
- **Проблема:** если запрос не находился, поиск молча ничего не делал — автор не понимал, ошибся он в
  тексте или совпадений действительно нет; при переборе совпадений тоже не было видно, что они
  закончились (перебор шёл по кругу бесконечно).
- **Решение:** состояние поиска получило `message`; `ParamsForm` показывает его рядом с кнопкой
  (красным). Сообщение выставляется, когда совпадений нет, и когда нажали «Найти» после последнего
  совпадения; в последнем случае индекс сбрасывается в -1, поэтому следующее нажатие снова начинает
  с первого совпадения. При успешном переходе сообщение очищается.
- **Следствия:** «абракадабра» → «Строка не найдена» сразу; в отчёте `crm-filtered` запрос «Мебель»
  (единственное совпадение): 1-е нажатие — без сообщения, 2-е — «Строка не найдена», 3-е — снова
  первое совпадение.
- **Ограничения:** сообщение не озвучивается скринридером (нет `role="alert"`), показывается только
  при нажатии кнопки, а не при вводе; счётчика «найдено N» нет — автор видит лишь факт отсутствия;
  после сброса индекса в -1 подсветка активного совпадения снимается не всегда (остаётся последнее
  выделенное).

**ADR-145. Поиск по отображаемому тексту и неразрывные пробелы (версия 2.20.1).**
- **Проблема:** поиск сравнивал сырые значения строк, поэтому «15 000,00» из колонки «Прибыль» не
  находился — в модели лежит `15000`, а на экране формат даёт `15 000,00 ₽`; вдобавок разделитель
  тысяч в `toLocaleString('ru-RU')` — неразрывный пробел (U+00A0), который не равен обычному.
- **Решение:** `collectMatches` сравнивает и сырое значение, и текст «как на экране»
  (`displayText`: `columnFormat` + `formatCell` с учётом `styles.columns.<field>.format`); перед
  сравнением неразрывные пробелы (U+00A0/U+202F) в запросе и в тексте заменяются обычными — замена
  не меняет длину, поэтому индексы годятся и для подсветки в `ReportTable.cellParts`.
- **Следствия:** «15 000,00» в `bench-50k` находится: первое совпадение — строка 50 (`scrollTop 1084`),
  второе нажатие — строка 500 (`scrollTop 12784`), подсвечен фрагмент `15 000,00`; «Запад» работает
  как прежде.
- **Ограничения:** совпадение проверяется по формату колонки того блока, где ищется, поэтому одно и
  то же значение в блоке с другим форматом ищется по своему тексту; поиск по строке с валютным знаком
  («15 000,00 ₽») сработает только если знак есть в отформатированном тексте (в шаблоне он добавляется
  стилем зоны, а не форматом колонки); для нечисловых форматов (даты по pattern) сравнение идёт по
  отформатированной дате.

**ADR-144. Поиск по всему набору, а не по видимым строкам (версия 2.20.0).**
- **Проблема:** поиск (ADR-143) обходил DOM и находил только отрисованные строки: в отчёте на 50 000
  строк окно виртуализации — несколько десятков, и всё остальное не находилось.
- **Решение:** совпадения собираются по модели данных (`collectMatches`): перебираются все табличные
  блоки шаблона и все их строки/колонки, регистронезависимо. В `ReportTable` передаются `searchTerm`
  и `searchRow`/`searchCol`; таблица подсвечивает совпадения в видимых ячейках (текст делится на части,
  совпадения оборачиваются в `mark.find-hit`) и по `watch(searchRow)` прокручивается к строке
  активного совпадения через префиксные суммы (`scrollTop = offset - clientHeight/2`). Повторное
  нажатие переводит активное совпадение на следующее по модели.
- **Следствия:** в `bench-50k` поиск «Товар-9» (первое вхождение — строка 32, вне начального окна)
  прокручивает таблицу (`scrollTop 616`) и подсвечивает ячейку; «Запад» перебирает совпадения по
  модели, а не только по видимым.
- **Ограничения:** подсвечиваются только видимые ячейки (виртуализация не рисует остальные) — при
  прокрутке подсветка появляется заново по термину; поиск идёт по сырым значениям строк, поэтому
  отформатированные числа с пробелами (`12 500`) ищутся без пробелов; поиск по агрегированным
  подытогам и группам, которых нет в исходных строках, не выполняется; совпадения считаются заново
  при каждом новом термине — для больших наборов это заметная работа в главном потоке (50k строк ×
  8 колонок ≈ 400 тыс. проверок).

**ADR-139. Подсказка с полным текстом ячейки (версия 2.17.0).**
- **Проблема:** длинный текст в ячейке обрезается многоточием (`overflow: hidden; text-overflow:
  ellipsis; white-space: nowrap`), и прочитать его было нельзя ни на экране, ни без экспорта.
- **Решение:** в `ReportTable.vue` на ячейки данных навешаны `mouseenter`/`mouseleave`; через 350 мс

  помещается (`scrollWidth > clientWidth + 1`) и скрывается при уходе курсора, прокрутке таблицы и
  изменении размера окна.
- **Следствия:** наведение на обрезанную ячейку показывает полный текст; для коротких значений
  подсказки нет — она не дублирует видимое. Проверено в браузере: у ячейки с `scrollWidth 591` при
  `clientWidth 166` подсказка появляется.
- **Ограничения:** текст берётся из модели строки (`cellTextOf`), а не из DOM, поэтому подмена текста
  в DevTools даёт старую подсказку; подсказка не показывается в печати и в Excel (там текст целиком);
  для ячеек с `rowspan`/`colspan` координаты берутся по самой ячейке, поэтому у высоких объединённых
  ячеек подсказка появляется над верхней границей; на сенсорных экранах наведения нет — механизм не
  работает.

**ADR-136. «Проверить SQL» в панели наборов (версия 2.16.0).**
- **Проблема:** автор правил запрос в панели «Наборы данных» и узнавал о его ошибке только после
  сохранения черновика и запроса данных — то есть через две операции и без указания, что именно не так.
- **Решение:** эндпоинт `POST /api/admin/datasets/check` и кнопка «Проверить SQL» рядом с «Применить».
  Сервер проверяет, что запрос только на чтение (`isReadOnlySql`), компилирует именованные параметры
  (`compileDataset`) и выполняет `SELECT * FROM (<sql>) AS rep_check LIMIT 21` под ролью сервера
  (сессия только-чтения) с таймаутом 5 с; соединение берётся из тела запроса (`connections` +
  `connection`), потому что проверяемый SQL ещё не сохранён в шаблоне. Ответ — `{columns, rows,
  truncated, tookMs}` или `422` с текстом PostgreSQL. Панель показывает таблицу первых 20 строк
  (с прокруткой и закреплённой шапкой) и время выполнения; ошибки БД и запрет не-SELECT выводятся
  плашкой.
- **Следствия:** проверка рабочего запроса в панели — «строк: 20 (показаны первые 20) · 1 мс» с
  колонками `id, order_date, region, category, product, amount, qty, profit`; запрос с опечаткой
  возвращает `QUERY_FAILED: столбец "nope" не существует`; `DELETE` — `SQL_FORBIDDEN`.
- **Ограничения:** параметры не подставляются автоматически — если в SQL есть `$имя`, проверка вернёт
  ошибку «не передан параметр» (автор увидит это как обычную ошибку); лимит 20 строк и таймаут 5 с
  нельзя изменить из интерфейса; запрос всё равно выполняется на реальных данных, поэтому тяжёлый
  `SELECT` без индексов может занять до 5 с и нагрузить БД; проверка доступна только администратору.

- **Ограничения:** `Tab` больше не уводит фокус с редактора — выйти из него клавиатурой можно
  `Escape` (CodeMirror снимает фокус), остальные поля доступны мышью; поведение одинаково для всех
  полей CodeMirror (сейчас это только редактор шаблона).

**ADR-132. Список ошибок черновика, переход к месту ошибки, статус источников в health (2.15.1).**
- **Проблема:** сохранение черновика возвращало одну ошибку строкой, автор исправлял шаблон по одной
  итерации; в редакторе место ошибки не подсвечивалось. О карантине внешних источников можно было
  узнать только из журнала.
- **Решение:** `PUT …/draft` возвращает `errors` массивом `[{path, message}]` (полный результат
  `validateTemplateFull`); панель проблем редактора показывает весь список, а первая ошибка
  подсвечивается и прокручивается в тексте (`focusProblem`: последний сегмент пути, например
  `blocks.0.span` → ключ `span`). `/api/health` получил поле `datasourcesInQuarantine`.
- **Следствия:** сохранение шаблона с двумя ошибками отдаёт массив из двух элементов и статус
  «черновик сохранён с ошибками: 2»; health показывает `datasourcesInQuarantine: 0` в норме.
- **Ограничения:** подсветка ищет первое вхождение ключа по тексту, а не по настоящему пути в JSON —
  при повторяющихся ключах (`span` в двух блоках) подсветится первый; список ошибок приходит только
  при сохранении, отдельного эндпоинта «проверить черновик» нет; `datasourcesInQuarantine` — счётчик
  без имён источников.

**ADR-131. Черновик сохраняется с ошибками, но не исполняется (версия 2.15.0).**
- **Проблема:** `PUT /api/admin/reports/{id}/draft` отклонял сохранение при любой ошибке проверки, поэтому
  автор не мог оставить работу на середине: недописанный блок или временно неверный `span` терялись.
  При этом обратная ошибка тоже опасна — исполнять невалидный шаблон нельзя.
- **Решение:** сохранение черновика больше не валидируется «на отказ»: тело пишется в БД и память,
  ответ содержит `{draft: true, valid: bool, errors?}` с первой ошибкой проверки; редактор показывает
  «черновик сохранён с ошибками … — просмотр и публикация недоступны». Исполнение запрещено на трёх
  уровнях: `resolveDataset` при `draft: true` возвращает `422 TEMPLATE_INVALID` «черновик содержит
  ошибки: …», публикация получает `422` из `prepareTemplate`, а невалидный черновик не попадает в
  `draftsParsed` (после исправления — попадает). При старте невалидные черновики из БД тоже
  сохраняются в памяти с признаком ошибки, чтобы автор увидел их после перезапуска сервера.
- **Следствия:** сохранение невалидного черновика — `200` с `valid:false`; данные по нему — `422`;
  публикация — `422`; тело черновика для редактора по-прежнему отдаётся (`GET …/draft`), и после
  исправления всё работает. e2e: 106 тестов.
- **Ограничения:** в ответе только первая ошибка (строкой), а не список; признак «валиден» не хранится
  в БД — вычисляется при загрузке; предпросмотр в редакторе использует тот же `draft: true` и тоже
  получает `422`, то есть посмотреть отчёт с ошибками нельзя даже в предпросмотре (так и задумано,
  но автор видит только текст ошибки, а не место в шаблоне).

**ADR-130. Сброс карантина из админки, 403 с логином, e2e на сбой источника (версия 2.14.6).**
- **Проблема:** три незакрытых места. (1) Карантин источника жил 30 с и снимался только перезапуском,
  хотя после правки шаблона он не нужен. (2) Отказы `403`, формируемые в pre-routing advice
  (`недостаточно прав`, `не доверенный прокси`), писались в журнал без логина, хотя он уже известен;
  `401` вообще не логировался. (3) Поведение «неверная база → понятная ошибка без зависания» не имело
  автотеста: проверялось вручную.
- **Решение:** (1) `POST /api/admin/datasources/reset` → `ConnRegistry::clearFailures()` снимает
  карантин и признаки проверки, в админке появилась кнопка «Проверить источники данных» с сообщением
  о результате. (2) лямбды `unauthorized`/`forbidden` пишут запись в журнал: `403` — `warning`
  с логином из `currentActor`, `401` — `debug`. (3) e2e-тест `сбой источника`: создаёт отчёт с
  `database: no_such_db_e2e`, ждёт `503` с текстом PostgreSQL менее чем за 3 с, проверяет запись
  уровня `error` в `/api/admin/audit` и ответ сброса карантина.
- **Следствия:** после правки шаблона источник проверяется заново по кнопке; в журнале появились
  строки `403 FORBIDDEN` с логином и `401 UNAUTHORIZED` (уровень `debug`); e2e 105 тестов.
- **Ограничения:** сброс действует на весь реестр сразу — снять карантин с одного источника нельзя;
  `401` пишется без логина (его ещё нет) и не виден в stdout при `REP_LOG_LEVEL=info`;
  e2e-тест требует прав `reporting_ro` и переменной `REP_RO_DB_PASSWORD` в окружении сервера.

**ADR-129. Логин во всех ошибках API (версия 2.14.5).**
- **Проблема:** ADR-128 проставлял пользователя только в обработчиках данных и агрегации; ошибки
  экспорта, справочников и остальных маршрутов писались с пустым `user`, и по журналу нельзя было
  понять, кто их получил.
- **Решение:** `currentActor = actorOf(req)` проставлен в начале всех обработчиков, которые формируют
  ответ с ошибкой (14 обычных маршрутов и обработчик справочников с параметрами пути), а не только в
  двух исходных. Механика прежняя: `sendError` читает логин из `thread_local`.
- **Следствия:** `POST /api/report/export.csv` без `reportId` → `user=admin`, `GET
  /api/reports/nope/lookups/x` → `user=admin`; поведение ответов не изменилось (422/404 те же).
- **Ограничения:** отказы, которые формируются в pre-routing advice (401/403 до вызова обработчика),
  по-прежнему пишутся с пустым пользователем — там нет `sendError`; `thread_local` сохраняется, пока
  обработчик и колбэк выполняются в одном потоке drogon.

**ADR-128. Логин в ошибках API, перепроверка источника, Kerberos в check.sh (версия 2.14.4).**
- **Проблема:** три хвоста предыдущих решений. (1) Записи об ошибках API писались с пустым
  пользователем: `sendError` не получает запрос (181 вызов), и по журналу нельзя понять, кто получил
  отказ. (2) После истечения 30-секундного карантина источник оставался помеченным как проверенный,
  поэтому вернувшийся к жизни источник сначала снова ждал общий таймаут 6 с. (3) `dev-kerberos.sh`
  мог зависнуть без вывода (утилиты MIT ждут ввод), а `check-kerberos.sh` не входил в `check.sh` —
  Kerberos проверялся только вручную.
- **Решение:** (1) `thread_local currentActor` заполняется из `actorOf(req)` в начале обработчиков
  данных и агрегации; `sendError` пишет его в поле `user`. (2) при истечении карантина `resolve`
  снимает и признак «проверен», так что следующий запрос делает новую проверку соединения.
  (3) в `dev-kerberos.sh` все вызовы `kdb5_util`/`kadmin.local`/`kinit` обёрнуты в `timeout` с
  понятными сообщениями и шагами; в `check.sh` добавлен необязательный шаг «Kerberos», который
  пропускается, если нет SPNEGO на :8098 или тикета.
- **Следствия:** запись об ошибке содержит `"user":"admin"`; после карантина живой источник
  обслуживается без 6-секундного ожидания; `./scripts/dev-kerberos.sh` завершается за 1,5 с при уже
  поднятом KDC и не висит молча; полный `check.sh` печатает либо результат Kerberos-проверки, либо
  «пропуск».
- **Ограничения:** логин проставляется только в обработчиках данных и агрегации — ошибки остальных
  маршрутов (экспорт, админка) по-прежнему пишутся с пустым пользователем; `thread_local` работает,
  пока обработчик и колбэк выполняются в одном потоке drogon (при смене потока логин потеряется);
  шаг Kerberos в `check.sh` необязателен, поэтому в CI Kerberos по-прежнему не проверяется.

**ADR-127. Каждая ошибка API — в журнале (версия 2.14.2).**
- **Проблема:** после ADR-126 отказ подключения обрабатывался до drogon, поэтому в журнале не
  оставалось вообще ничего: `PQconnectdb` вернул ошибку, мы ответили пользователю, а в
  `REP_LOG_FILE` — ни строки. Общее требование «все ошибки фиксируются в лог-файле» не выполнялось
  и для остальных отказов: 422 `INVALID_PARAMS`, 404, 403 в журнал не попадали.
- **Решение:** `sendError()` — единственная точка формирования ответа с ошибкой — пишет запись в
  `rep::log` с кодом и текстом: `5xx` → `error`, `401` → `debug` (нет сессии — обычное дело при
  первом открытии страницы), остальные → `warning`. Отказ проверки источника пишется отдельной
  записью `error` с контекстом `{source, host, database}` (пароль не попадает).
- **Следствия:** неверная база даёт в файле две строки — «источник не подключается: … база данных
  "no_such_db" не существует» с контекстом и «ошибка API 503 DB_UNAVAILABLE: …»; `422
  INVALID_PARAMS` — строку уровня `warning`; уровень задаётся `REP_LOG_LEVEL`/`REP_LOG_FILE_LEVEL`.
- **Ограничения:** запись не содержит логина пользователя (у `sendError` нет доступа к запросу) —
  по строке не видно, кто ошибся; 401 пишется в файл, но не в stdout (уровень `info`); объём журнала
  растёт вместе с числом ошибочных запросов, дедупликации для них нет; чувствительные значения в
  сообщениях не фильтруются, поэтому в текстах ошибок по-прежнему нельзя печатать секреты.

**ADR-126. Проверка соединения до запроса и карантин по DSN (версия 2.14.1).**
- **Проблема:** после ADR-125 первый запрос всё равно ждал 6 с и отвечал «источник не ответил за
  6000 мс», хотя PostgreSQL уже сказал «база данных не существует»: таймаут срабатывал раньше, чем
  мы узнавали причину, и drogon успевал сделать несколько попыток подключения. Кроме того, карантин
  был привязан к имени источника (`main`), поэтому сбой одного шаблона отравлял все остальные с тем
  же именем, даже если они ведут в другую базу.
- **Решение:** перед первым запросом к внешнему источнику выполняется одна проверка соединения
  `PQconnectdb` в отдельном потоке (`pg_probe.{h,cc}`), результат возвращается в loop drogon. Успех —
  источник помечается проверенным (`markProbed`) и запрос идёт обычным путём; отказ — `503
  DB_UNAVAILABLE` с текстом PostgreSQL и карантин на 30 с. Ключом карантина и проверки стал DSN, а не
  имя источника. Общий таймаут `REP_DATASET_TIMEOUT_MS` остаётся страховкой для медленных, но живых
  источников.
- **Следствия:** неверная база — `503` за **0,018 с** с сообщением «connection to server at
  "127.0.0.1", port 5432 failed: ВАЖНО: база данных "no_such_db" не существует (повтор через 30 с)»;
  в журнале ни одной строки drogon про повторные подключения; `sales-crm` (другая база, то же имя
  источника `main`) по-прежнему отвечает `200` и 24 723 строки. Проверено в браузере: плашка
  `DB_UNAVAILABLE` с тем же текстом.
- **Ограничения:** проверка — синхронный `PQconnectdb` в отдельном потоке: при недоступном хосте она
  ждёт `connect_timeout` (5 с), но не блокирует event loop; на каждый DSN проверка одна, дальше
  запросы идут без неё, поэтому «оживший» источник подхватывается только при новом DSN или после
  перезапуска; libpq линкуется статически из Conan (`libpq.a`), то есть версия клиента фиксирована
  сборкой; пароль участвует в ключе DSN и остаётся в памяти процесса (в журнал не попадает).

**ADR-125. Сбой внешнего источника: ошибка вместо зависания (версия 2.14).**
- **Проблема:** при неверных параметрах подключения в `connections` (например, несуществующая
  `database`) запрос данных висел бесконечно: drogon создавал клиент, не мог подключиться и
  переподключался в своём цикле, колбэки запроса не вызывались никогда. Пользователь видел пустой
  экран, в `REP_LOG_FILE` не было ни строки (сообщения drogon «!!!Pg connection failed» шли только
  в stdout, которого у службы нет), а консоль заполнялась одними и теми же строками.
- **Решение:** три части. (1) `rep::log::installFrameworkSink()` перехватывает вывод drogon/trantor
  через `Logger::setOutputFunction` и пишет его в общий журнал (stdout JSON + файл + аудит) с
  уровнем из строки; повторяющиеся строки склеиваются: не чаще раза в 5 с, с числом подавленных.
  (2) Для внешних источников (`datasets.<ключ>.connection` ≠ default) запрос ограничен по времени
  `REP_DATASET_TIMEOUT_MS` (по умолчанию 6000); по истечении — `504 SQL_TIMEOUT` с подсказкой
  «проверьте host, port и database». (3) `ConnRegistry::markFailed` запоминает сбой на 30 с:
  следующие запросы получают `422 CONNECTION_ERROR` сразу, без ожидания и без создания клиента;
  клиент с мёртвым соединением выбрасывается из кэша, что прекращает переподключения drogon.
- **Следствия:** первый запрос с неверной базой отвечает за 6 с `504` с текстом ошибки, повторные —
  мгновенно `422`; в журнале появляется одна запись `drogon: !!!Pg connection failed: база данных
  "no_such_db" не существует (повторов подавлено: N)`; интерфейс показывает плашку с кодом и
  текстом. Проверено в браузере: `SQL_TIMEOUT … (повтор через 30 с)`.
- **Ограничения:** обновление исправленного шаблона не сбрасывает карантин — до 30 с источник
  считается недоступным (перезапуск сервера снимает); сам drogon по-прежнему пытается
  переподключиться, мы лишь не даём этому длиться дольше; `REP_DATASET_TIMEOUT_MS` — общий для всех
  внешних источников, отдельного значения на источник нет; таймаут считается от постановки запроса,
  а не от установления соединения, поэтому медленный, но живой источник с большим запросом тоже
  получит `504`.

**ADR-124. Тесты помощников Kerberos и защита заголовка (версия 2.13.3).**
- **Проблема:** `negotiate.cc` — единственный новый модуль после ADR-114 без unit-тестов: разбор
  base64 из `WWW-Authenticate: Negotiate` и текст ошибки с подсказкой `kinit` проверялись только
  вручную через стенд, то есть в CI не проверялись вовсе. При вынесении текста обнаружилось, что
  в `negotiate.h` вместо `#pragma once` стояла строка `*** once` — заголовок собирался лишь потому,
  что включался один раз.
- **Решение:** `describe()` получил публичную обёртку `kerbErrorText(major, minor)`; добавлен
  `tests/negotiate_test.cc` (8 TEST_CASE): base64 с padding и без, с пробелом-разделителем, с
  мусорными символами (base64url отбрасываются — поведение зафиксировано тестом), пустая строка;
  подсказки для `GSS_S_NO_CRED` и `GSS_S_CREDENTIALS_EXPIRED` и их отсутствие для `GSS_S_BAD_NAME`;
  при сборке без GSSAPI проверяется текст «сервер собран без GSSAPI». В `negotiate.h` — `#pragma once`.
- **Следствия:** ctest 139 кейсов / 760 assertion (было 131 / 745); Windows-проверка проходит.
  Обмен с KDC по-прежнему проверяется скриптом `scripts/check-kerberos.sh`, а не тестами.
- **Ограничения:** тесты не поднимают KDC и не проверяют реальное рукопожатие — это интеграционный
  сценарий, для CI нужен KDC, которого там нет; `base64Decode` терпима к мусору, то есть на битом
  токене ошибка придёт от GSSAPI, а не от разбора.

**ADR-123. Подсказки при ошибках Kerberos и пример окружения (версия 2.13.2).**
- **Проблема:** при отсутствующем или истёкшем тикете REST-источник отвечал `422 REST_AUTH` с текстом
  GSSAPI «No credentials were supplied, or the credentials were unavailable or inaccessible» — что
  делать, из него не следовало; `backend/.env.example` не содержал `CRM_BASE_URL`, `CRM_USER`,
  `CRM_PASSWORD`, `SPNEGO_BASE_URL`, из-за чего на чистой машине отчёты `crm-*` падали с `REST_ERROR`
  (у нас это стоило шести упавших e2e).
- **Решение:** `describe()` в `negotiate.cc` распознаёт `GSS_S_NO_CRED` и `GSS_S_CREDENTIALS_EXPIRED`
  и дописывает действие: «получите тикет: kinit <пользователь>@<REALM>» или «тикет истёк, обновите
  его», а сообщение `start()` добавляет путь ccache. В `.env.example` добавлен блок переменных стенда
  с пояснением, что `ccache`/`krb5.conf` задаются в шаблоне, а `KRB5_*` в окружении сервера ломают
  подключение к PostgreSQL. Статус в `docs/plan/plan-rest-auth.md` приведён к реальности.
- **Следствия:** с пустым ccache отчёт отдаёт `422 REST_AUTH` и текст «… — нет тикета Kerberos,
  получите его: kinit <пользователь>@<REALM> (ccache: FILE:/tmp/rep-krb/empty.ccache)»; на чистой
  машине достаточно скопировать `.env.example` в `.env`, чтобы `crm-*` заработали.
- **Ограничения:** подсказка не знает фактического имени пользователя и realm — подставляет шаблон
  `<пользователь>@<REALM>`; сервер по-прежнему не обновляет тикеты сам (нужен `kinit` извне);
  `.env.example` — пример, а не рабочая конфигурация: в нём тестовые `demo`/`demo-pass`.

**ADR-122. Kerberos/SPNEGO для REST-источников (версия 2.13).**
- **Проблема:** оценка в `docs/plan/plan-rest-auth.md` показала, что BASIC закрывает парольные
  сервисы, но не корпоративный вход: в домене REST-сервис ждёт `Authorization: Negotiate`, а
  `drogon::HttpClient` такого не умеет.
- **Решение:** реализован GSSAPI-клиент `negotiate.{h,cc}`: `gss_init_sec_context` по SPN, разбор
  `401` + `WWW-Authenticate: Negotiate` с продолжением контекста (до трёх раундов), токены в
  base64, ничего не логируется. Конфиг: `auth: {type: "kerberos", spn, ccache, krb5Config}`.
  Пути `ccache`/`krb5Config` передаются в GSSAPI через временную установку окружения
  (`KRB5CCNAME`/`KRB5_CONFIG`) только на время вызова: глобальные переменные ломают старт — libpq
  видит их и пытается GSSAPI-аутентификацию к PostgreSQL, сервер зависает. CMake ищет `libgssapi_krb5`
  и включает механизм только при её наличии; без GSSAPI — `422 REST_AUTH`.
- **Следствия:** поднят изолированный KDC без root (`/tmp/rep-krb`, realm `REP.LOCAL`, порт 10088),
  principals `HTTP/localhost` (keytab) и `demo`; SPNEGO-демо `scripts/rest-spnego-demo.py` на :8098
  отвечает `401` без токена и `200` с `Negotiate` (проверено `curl --negotiate`). Отчёт
  `crm-kerberos` возвращает строку `demo@REP.LOCAL / 42`; `scripts/check-kerberos.sh` подтверждает
  это на живом стенде. Parity — 115 фикстур (SPN неверного формата).
- **Ограничения:** только Linux (Windows-ветка не делалась, NTLM/SSPI — отдельная задача);
  делегирования нет — сервер ходит под своей учётной записью из ccache, а не под учёткой смотрящего;
  KDC/тикеты должны быть получены до запроса (`kinit`), сам сервер тикеты не обновляет; чувствительность
  к времени (5 минут); e2e в CI не добавлен — инфраструктуры Kerberos там нет, проверка ручная;
  при истёкшем тикете ошибка приходит как `422 REST_AUTH` без подсказки «обновите kinit».

**ADR-121. BASIC-аутентификация REST-источников (версия 2.12).**
- **Проблема:** REST-источник (ADR-104) ходил без аутентификации. Единственный способ передать
  логин и пароль — положить готовый `Authorization: Basic …` в `connections.headers` через `${ENV}`,
  то есть держать base64 в окружении и не иметь ни проверки, ни понятной ошибки при опечатке.
- **Решение:** у rest-источника появился блок `auth: {type: "basic", userEnv, passwordEnv}`. Сервер
  читает переменные окружения, собирает `Authorization: Basic base64(логин:пароль)` и добавляет
  заголовок к каждому запросу (включая страницы пагинации и POST); значения не логируются и не
  попадают в текст ошибок. Пустая переменная — `422 REST_AUTH` с её именем; `auth` у postgres —
  ошибка валидатора. Проверки продублированы в `validate.js` и `validate.cc`; демо-сервис
  `scripts/rest-demo.mjs` теперь требует BASIC (`demo`/`demo-pass`).
- **Следствия:** все `crm-*` отчёты и `sales-crm` работают через демо только с заголовком: без него
  демо отвечает `401` + `WWW-Authenticate: Basic`, отчёт — `422 REST_ERROR`; с ним — 4 строки цен.
  Parity вырос до 114 фикстур (пустой `userEnv`, `auth` у postgres, неизвестный тип).
- **Ограничения:** поддержан только BASIC — NTLM/SPNEGO и Kerberos требуют отдельного клиента
  (оценка в `docs/plan/plan-rest-auth.md`); нет обновления токенов и Digest; логин и пароль читаются
  при каждом запросе, но проверить их до отправки нельзя — сервис отвечает `401`, и это приходит как
  `REST_ERROR`; базовый заголовок целиком виден в памяти процесса и в отладчике.

**ADR-119. История ротации журнала и миграция старых записей (версия 2.11.1).**
- **Проблема:** файловый приёмник (ADR-111) при ротации держал ровно один архив `<файл>.1`:
  предыдущий архив терялся при каждом срабатывании, разобрать инцидент за два периода было нельзя.
  Плюс в `audit_log` оставались записи `open_report`/`export_report` с `object_type = 'log'` —
  они писались до ADR-111, и колонка «Объект» в админке показывала для них не то, что для новых.
- **Решение:** ротация стала кольцевой: `<файл>` → `.1` → `.2` … → `.N`, самый старый удаляется;
  число архивов задаётся `REP_LOG_FILE_KEEP` (по умолчанию 5, `0` — без архивов, файл начинается
  заново). Данные журнала приведены миграцией `db/migrations/2026-11-12-audit-object-type.sql`
  (идемпотентно; обёртка `db/migrate-audit-object-type.sh` для уже развёрнутой базы).
- **Следствия:** при `REP_LOG_FILE_MAX_BYTES=1200` и `REP_LOG_FILE_KEEP=3` после 12 неудачных входов
  на диске `rot.log` (880 байт) и архивы `.1` (1100), `.2` (1070), `.3` (1111) — старый архив
  сдвигается, а не пропадает; в `audit_log` не осталось строк `object_type='log'` с действиями
  `open_report`/`export_report`.
- **Ограничения:** архивы не сжимаются, ротация только по размеру (нет деления по времени); при
  `keep = 0` история теряется сразу; миграция не трогает технические события с `object_type='log'`
  (старт, SQL, REST) — у них нет объекта отчёта; `REP_LOG_FILE_KEEP` читается один раз при старте.

**ADR-118. Плейсхолдеры в пути и заголовках, глубина цепочек (версия 2.11).**
- **Проблема:** подстановка из наборов (ADR-117) работала только в `query` и `body`. Сервисы с
  `GET /api/prices/{category}` или с обязательным заголовком (`X-Tenant`) выразить было нельзя.
  Цепочка `dependsOn` при этом выполнялась рекурсивно без ограничения: шаблон из десяти REST-наборов
  давал десять последовательных вызовов, и ничто не мешало сделать больше.
- **Решение:** `rest.path` и `rest.headers` принимают `$набор.колонка` внутри строки (значение первой
  строки, в пути — urlencode), `rest.headers` перекрывают заголовки источника; в контексте REST
  заголовки набора попадают в хеш кеша. Глубина цепочки наборов ограничена 8 (`kMaxDatasetDepth`),
  считаются и `dependsOn`, и объединения; глубже — `422 DATASET_DEPTH`. Валидаторы (клиент и сервер)
  ищут плейсхолдеры внутри `path`/`headers` и отклоняют цикл по `dependsOn`
  (`datasets.<key>.rest.dependsOn.<i>`, «цикл зависимостей»). Пример `crm-filter-path`: путь
  `/api/prices/$category.category`, заголовок `X-Tenant: $settings.tenant`.
- **Следствия:** `crm-filter-path` возвращает строку `Мебель / 43000 / RUB / demo-tenant`; в логе
  видно `rest: 127.0.0.1:8099/api/prices/%D0%9C%D0%B5%D0%B1%D0%B5%D0%BB%D1%8C — запрос (miss)`;
  parity-фикстуры — 111, цикл и плейсхолдер в пути ловятся на клиенте и сервере одинаково.
- **Ограничения:** значение для пути берётся только из первой строки набора (несколько значений в
  пути не выразить); заголовки набора не поддерживают `${ENV}` — секреты остаются в
  `connections.headers`; лимит глубины считает все переходы, включая объединения, поэтому глубокий
  join может упереться в тот же порог; кодирование пути выполняется один раз, повторно
  закодированный путь (двойное `%25`) сервис должен разбирать сам.

**ADR-117. REST-запрос с параметрами из другого набора (версия 2.10).**
- **Проблема:** REST-набор (ADR-104) умел только статический `query` с литералами: чтобы отправить
  в сервис список категорий, выбранных в БД по параметрам отчёта, приходилось либо дублировать SQL
  в REST-вызове, либо вообще не делать такой отчёт. Объединение `join` тоже не помогало — сервису
  нужно тело запроса, а не таблица.
- **Решение:** согласовано с PO до реализации — в `rest` появились `method` (`GET`/`POST`), `body`
  (произвольный JSON с плейсхолдерами) и `dependsOn` (наборы-источники значений). Плейсхолдер —
  `$ключ.колонка`, имя набора указано явно. В массиве из одного элемента с плейсхолдерами значения
  разворачиваются по строкам набора (объект → массив объектов, скаляр → массив значений); в остальных
  местах берётся первая строка. Типы сохраняются (int/float — числом, bool — логическим, пусто —
  `null`). Пустой набор-источник: REST не вызывается, отдаётся пустой результат с колонками набора.
  Проверки дублированы в `validate.js` и `validate.cc` (ключ в `dependsOn`, формат плейсхолдера,
  колонка существует), parity растёт до 109 фикстур. Пример `crm-filtered`: категории из PostgreSQL,
  цены из REST `POST /api/prices`, тело собирается подстановкой.
- **Следствия:** `crm-filtered` возвращает 4 строки цен по категориям из БД; POST уходит с типизированным
  телом, кеш REST учитывает тело в ключе (разные фильтры — разные записи кеша); пустой источник
  виден в логе строкой «набор пуст — запрос не отправлен».
- **Ограничения:** `dependsOn` не создаёт циклов (валидатор проверяет только самоссылку и объявление
  набора — цепочки REST→REST допускаются и выполняются рекурсивно); плейсхолдеры не работают в
  `path` и `headers` (только `query`/`body`); в массиве с плейсхолдерами из разных наборов ошибка —
  разворот по строкам неоднозначен; значения подставляются как есть, без экранирования SQL (это
  JSON, а не SQL); `rest.method: POST` не поддержан серверным экспортом — экспорт читает те же строки,
  поэтому данные выгружаются, но запрос при экспорте выполняется заново.

**ADR-116. Статическая проверка готовности к MSVC (версия 2.9.1).**
- **Проблема:** сборка под Windows не проверена — Windows-машины нет, CI-job `backend-windows`
  отключён. Платформенный слой (`net.{h,cc}`, `env.cc`, `logging.cc`) написан, но ничто не мешало

- **Решение:** `scripts/check-windows.sh` (шаг в `scripts/check.sh`) статически проверяет границу
  платформы: POSIX-вызовы разрешены только в четырёх файлах-обёртках, каждый из них обязан содержать
  ветку `_WIN32`, в `CMakeLists.txt` должны быть `ws2_32`/`WIN32_LEAN_AND_MEAN`/`NOMINMAX`, а
  `execinfo.h` в `main.cc` — внутри `#if !defined(_WIN32)`; проверяется наличие профиля Conan

  в `backend/src`) валит скрипт и печатает имя файла. Регрессии платформенного слоя теперь видны
  на Linux, до отправки на Windows.
- **Ограничения:** проверка статическая и синтаксическая — она не заменяет сборку MSVC (типы `SOCKET`
  против `int`, `DWORD`, порядок include, `/utf-8`, линковка CRT): реальная приёмка возможна только
  на Windows; `build.ps1` и пресеты по-прежнему не исполнялись; правила не ловят платформенные
  различия внутри стандартной библиотеки и заголовков drogon.

**ADR-115. Файл `.env` приоритетнее окружения процесса (версия 2.9).**
- **Проблема:** `loadDotEnv` не перетирал уже заданные переменные (`setenv(..., 0)`), поэтому
  окружение процесса было важнее файла: запуск из оболочки с унаследованным `PGPORT`/`PGDATABASE`
  или из systemd с чужим `REP_DB_SCHEMA` молча подключал сервер не к той базе, а `.env` —
  документированный источник настроек стенда — не применялся. Расхождение проявлялось как «в .env
  одно, а сервер ходит в другое».
- **Решение:** файл читается после разбора `REP_ENV_FILE`, и каждая его строка применяется с
  перезаписью (`setenv(..., 1)`, `_putenv_s`). Порядок: **`.env` → окружение → значение по
  умолчанию**; путь к файлу по-прежнему задаётся только из окружения (`REP_ENV_FILE`), иначе
  получился бы цикл. Документация в `docs/configuration.md` приведена к этому порядку.
- **Следствия:** при заведомо неверных `PGPORT=5999`, `PGDATABASE=нет-такой-базы`,
  `REP_DB_SCHEMA=нет-схемы` в окружении сервер стартует и работает с базой из `.env`
  (`db: true`, `dbUser: reporting_srv`). Тесты: 3 кейса на приоритет, отсутствие файла и снятие
  кавычек.
- **Ограничения:** перекрыть значение из `.env` одной переменной окружения больше нельзя — для
  точечного переопределения правят файл или указывают другой `REP_ENV_FILE`; в CI, где `.env` нет,
  поведение прежнее (всё из окружения); секреты из `.env` теперь гарантированно применяются, поэтому
  файл должен быть закрыт правами (chmod 600, так его и создают скрипты).

**ADR-114. Компактный формат ответа набора: строки-массивы (версия 2.8).**
- **Проблема:** полный цикл 50 000 строк не укладывался в бюджет 2 с (1 982–2 273 мс, ADR-113).
  Половину времени занимал сервер: 11,9 МБ JSON, где на каждую строку создавался `Json::Value`
  с именем поля на каждое значение, затем сериализовался общим `Json::StreamWriter`.
- **Решение:** `/api/report/data` и `/api/report/aggregate` отдают компактный вид —
  `{"columns":[{name,type,title?}],"rows":[[v1,v2,…]],"rowCount":N,"layout":"compact"}`, собираемый
  строкой (`datasetJsonFast`): без `Json::Value` на строку, числа пишутся как есть (проверка формата),
  пустые значения — `null`, строки экранируются вручную. Клиент приводит массивы к объектам в одном
  месте (`normalizeDataset` в `src/api/normalize.js`), поэтому движок, шаблоны и e2e не знают о
  формате. Прежний вид (объекты на строку) клиент по-прежнему принимает.
- **Следствия:** ответ 11,9 МБ → 4,3 МБ, сервер 872–1 023 мс → 358–399 мс, полный цикл 1 982–2 273 →
  **1 526–1 859 мс** (бюджет 2 000 мс выполнен, запас 141–474 мс). Клиент подорожал на ~90–210 мс
  (`renderMs` 839–1 084 мс) за приведение строк, но суммарно выигрыш 400–750 мс.
- **Ограничения:** формат меняет разбор ответа, поэтому старый код, читающий `rows[i].field` напрямую
  с сервера, должен вызывать `normalizeDataset`; `layout` в ответе предусмотрен для будущего
  «нулевого» режима без приведения; числа с ведущими нулями или `+` уходят строкой (в JSON это
  не число), и это проверено правилом `isJsonNumber`.

**ADR-113. Методика измерения бюджета рендера 50 000 строк (версия 2.7.1).**
- **Проблема:** в DoD бюджет «2 с» соседствовал с цифрами 1,63 / 1,71 / 1,47 с, но границы
  измерения не были заданы: прежние замеры считали рендер без сети и без полного цикла, новый
  воспроизводимый замер дал 2 248–2 385 мс от навигации. Сравнивать такие числа нельзя, а
  приёмка опиралась на несопоставимые величины.
- **Решение:** закреплены три метрики в `frontend/scripts/bench-render.mjs` и `docs/bench-50k.md`:
  `fullMs` (навигация → первая строка в DOM) — критерий приёмки 2 000 мс; `renderMs` (конец ответа
  данных → первая строка) — здоровье клиента, разбор JSON и нормализация; `apiMs` — запрос и ответ
  сервера. Исторические цифры в `docs/dod.md` оставлены как протокол фаз, рядом добавлено
  действующее определение.
- **Следствия:** `renderMs` 750–871 мс — бюджет рендера выполнен с запасом; `fullMs` 1 982 / 2 000 /
  2 273 мс — бюджет не подтверждён, разброс 291 мс, узкое место — серверная часть (~0,9–1,0 с),
  а не таблица. Виртуализация подтверждена: 28 строк в DOM, прокрутка 0,4 с.
- **Ограничения:** замер на локальной машине без сетевой задержки; `fullMs` зависит от прогрева
  сервера (холодный прогон 3 304 мс), поэтому приёмка требует трёх прогонов и медианы; целевой

**ADR-111. Журнал по объектам и уровням, файловый приёмник, глубина цепочек (версия 2.6).**
- **Проблема:** события действий писались в `audit_log` с `object_type = "log"`, а уровень лежал только
  внутри `details` — журнал не показывал уровень и не фильтровал по нему, объект в списке выглядел как
  «log». Единственным приёмником была БД: файла для разбора инцидентов не было. Глубина цепочки
  объединений `A⋈B⋈C⋈…` формально не ограничивалась — сдерживал только `REP_JOIN_MAX_ROWS`.
- **Решение:** события отчётов передают `object_type = "report"`, `object_id = <id отчёта>`; API
  `/api/admin/audit` принимает `level` (`trace|debug|info|warning|error`) и отдаёт `level` в элементах;
  страница журнала получила колонку «Уровень» и фильтр, выгрузка CSV идёт по тем же фильтрам.
  В `logging` добавлен файловый приёмник: `REP_LOG_FILE` (JSON-строки, дописывание), отдельный порог
  `REP_LOG_FILE_LEVEL` (по умолчанию `debug`) и ротация по размеру `REP_LOG_FILE_MAX_BYTES`
  (по умолчанию 10 МБ, архив — `<файл>.1`). Глубина цепочки объединений ограничена 8 наборами:
  `MAX_JOIN_DEPTH` в `validate.js` и `kMaxJoinDepth` в `validate.cc`, ошибка
  `datasets.<key>.join` «глубина цепочки объединений N больше допустимой 8».
- **Следствия:** `open_report` в журнале — `objectType=report`, `objectId=crm-paged-offset`, уровень
  `info`; фильтр `level=warning` отдаёт только неудачные входы; файл `/tmp/rep-audit.log` получает те же
  строки JSON, что stdout, но с более подробным порогом. Parity вырос до 106 фикстур (цепочка из десяти
  наборов даёт ошибки на `chain8` и `chain9`). Добавлен e2e на `rest.page.mode: offset` — 2500 строк
  тремя страницами по 1000.
- **Ограничения:** ротация хранит один архив (`<файл>.1`), без сжатия и почасового деления; старые
  записи журнала остались с `object_type = "log"` (миграция данных не делалась); глубина считается по
  максимальной ветке, а не по числу узлов; порог файла сравнивается по перечислению, порядок уровней
  фиксирован (`trace < debug < info < warning < error`).

**ADR-110. Админские действия в едином журнале, ip и уровень (версия 2.5).**
- **Проблема:** после ADR-109 события действий шли через `log::event`, но админские (`template.*`,
  `user.*`, `role.*`, `subscription.*`, вход) писались прежней `auditEvent` — два механизма
  сосуществовали, в stdout JSON этих событий не было, `ip` в журнал не попадал, а фильтра по уровню
  не было вовсе.
- **Решение:** `auditEvent` стал адаптером: старая строка действия (`template.create`, `user.update`,
  …) переводится в enum (`change_template`, `change_user`, …), `object_type`/`object_id`/`ip` уходят
  в контекст, сообщение — исходная строка, уровень `warning` для неудачного входа и отказа от рассылки.
  Запись в БД вынесена в `writeAuditRow` — её вызывает приёмник логов, поэтому рекурсии нет. Добавлены
  `REP_LOG_LEVEL` (trace/debug/info/warning/error, по умолчанию info) и `parseLevel`.
- **Следствия:** вход (`login`, `auth.login`/`auth.login_failed`) виден и в stdout JSON, и в
  `audit_log` с `ip='127.0.0.1'` и `object_id='admin'`; неудачный вход — уровень `warning`; при
  `REP_LOG_LEVEL=error` информационные события не пишутся ни в stdout, ни в журнал (проверено тестом).
- **Ограничения:** `object_type`/`object_id` остаются в контексте, а не отдельными колонками (они есть
  в `audit_log` только у старых записей); уровень `debug`/`trace` пока никем не используется; фильтр
  общий для stdout и журнала — раздельных порогов нет.

**ADR-109. Единая функция логирования (версия 2.4).**
- **Проблема:** логи писались напрямую через `LOG_INFO/LOG_WARN/LOG_ERROR` drogon: свободный текст,
  без типа действия и пользователя, в разных местах по-разному. Журнал аудита (`reports.audit_log`,
  ADR-52) заполнялся отдельной функцией только для админских действий, поэтому «кто открыл отчёт» и
  «кто выгрузил Excel» в журнале не было. Для будущей отправки в SIEM структуры тоже не было.
- **Решение:** модуль `logging.{h,cc}` с одной точкой записи:
  `rep::log::event(level, action, user, message, context)`, где `level` — `trace|debug|info|warning|error`,
  `action` — значение enum (`open_report`, `export_report`, `print_report`, `login`, `logout`,
  `create_user`, `change_user`, `delete_user`, `change_roles`, `change_template`, `publish_template`,
  `run_subscription`, `access_denied` + технические `server_start`, `server_stop`, `sql_slow`,
  `sql_error`, `connection_error`, `rest_error`, `audit_failed`, `other`), `user` — логин (пусто для
  системных и анонимных событий), метка времени берётся в момент события (ISO-8601 UTC с мс), `context` —
  произвольные поля (reportId, rows, bytes, format). Событие уходит одной строкой JSON в stdout и в
  сменный приёмник (`setSink`), который пишет `reports.audit_log` (`actor` — логин или `system`,
  `action` — имя enum, `details` — уровень, текст, метка, контекст). Для привычной записи добавлены
  макросы `REP_LOG_INFO/WARN/ERROR(action, user) << …`; ими заменены все прежние `LOG_*` в `main.cc`.
- **Следствия:** в stdout видно `{"action":"open_report","context":{"dataset":"orders_by_region",
  "reportId":"sales-crm","rows":550},"level":"info","message":"открыт отчёт sales-crm",
  "ts":"2026-11-14T07:26:43.831Z","user":"admin"}` и такая же запись появляется в `audit_log`;
  выгрузка даёт `export_report` с `bytes` и `format`; технические сообщения (старт, порт, БД, рассылка)
  идут тем же путём. Приёмник можно заменить на файл или SIEM, не трогая места вызовов.
- **Ограничения:** админские действия (`user.*`, `template.*`, `subscription.*`) пока пишутся прежней
  `auditEvent` с `object_type/object_id` — два механизма сосуществуют, сведение в один — следующий шаг;
  в `audit_log` из лога не передаётся `ip`; действие `print_report` объявлено, но серверного события
  печати нет (печать выполняется в браузере); уровень `trace/debug` используется только явными
  вызовами — фильтра уровня в конфигурации пока нет.

**ADR-108. Цепочки объединений, типы ключей и пагинация по смещению (версия 2.3).**
- **Проблема:** объединение допускало ровно один уровень (join→join запрещался), тип ключа не сверялся
  с типом колонки REST-стороны (ключи молча не совпадали), а пагинация REST умела только номер
  страницы — сервисы, отдающие `offset`, не поддерживались.
- **Решение:** цепочки `A⋈B⋈C` разрешены с защитой от циклов (обход по ссылкам в `parseTemplate` и в
  валидаторах); `join.on[].type` сверяется с типом колонки, если сторона — REST-набор (несовпадение —
  ошибка валидации); в `rest.page` добавлен `mode: "page" | "offset"` — при `offset` значение
  параметра считается как `start + страница × size` (для offset-источников `start: 0`).
- **Следствия:** пример `crm-paged-offset` (`/api/rows-offset`) собирает 2 500 строк тремя запросами
  `offset=0`, `1000`, `2000`; отчёт `sales-crm` продолжает работать; цикл `A→B→A` отклоняется при
  загрузке шаблона, а не в рантайме.
- **Ограничения:** глубина цепочки не ограничена формально (защита — только от циклов), поэтому
  длинная цепочка может съесть память — её сдерживает `REP_JOIN_MAX_ROWS` на каждой стороне;
  проверка типов работает только для REST-сторон (типы колонок SQL-наборов неизвестны до выполнения);
  offset-режим требует явного `start: 0` в шаблоне.

**ADR-107. Серверный экспорт и рассылка для rest/join (версия 2.2).**
- **Проблема:** для наборов `rest`/`join` серверный `.xlsx`, `.csv` и рассылка отвечали
  `EXPORT_UNSUPPORTED`. Две попытки включить их кончались падением процесса: причина — лямбда `take`
  в `fetchDatasetRows` захватывала окружение по ссылке и вызывалась асинхронно из колбэка REST, когда
  локальные переменные уже уничтожены (SIGSEGV, найдено по backtrace).
- **Решение:** захват переведён на значения; лист для не-SQL набора собирается из тех же `DatasetRows`,
  что и таблица на экране (`leaves` блока, подытоги и ИТОГО — через общий `buildGroupedSheet`);
  попутно восстановлен потерянный цикл `walk` по колонкам блока — без него лист выходил пустым у всех
  наборов. `EXPORT_UNSUPPORTED` убран.
- **Следствия:** `sales-crm` (join PostgreSQL + REST) выгружается в CSV (заголовки «Регион;Менеджер;
  Дата;Сумма;Кол-во») и в xlsx (лист A1:E552 — 550 строк, шапка, ИТОГО; отдельный лист «Параметры»);
  SQL-экспорт не изменился (`sales-summary` — 505 КБ); рассылка использует тот же `buildSheet`, значит
  подписка на такой отчёт теперь отправляется.
- **Ограничения:** серверный лист не содержит диаграмм (как и раньше); порядок строк — как в наборе,
  без клиентской виртуализации; при недоступном REST экспорт отвечает `REST_ERROR`, а не пустым файлом.

**ADR-106. Постраничный REST и предел стороны объединения (версия 2.1).**
- **Проблема:** REST-сервисы часто отдают данные страницами (`?page=2&limit=1000`), а набор читал
  только первый ответ — большой справочник молча обрезался. Одновременно объединение тянуло в память
  обе стороны целиком без ограничения: при 50k × 50k это ~73 МБ и 84 мс, но при большем объёме
  процесс мог упасть по памяти вместо понятной ошибки.
- **Решение:** в `rest` появился блок `page { param, sizeParam, size, maxPages, start }`: набор
  последовательно запрашивает страницы, накапливает строки и останавливается на неполной странице или
  на `maxPages`; кеш REST работает по каждой странице отдельно. Для объединения введён
  `REP_JOIN_MAX_ROWS` (по умолчанию 200 000): если любая сторона больше, ответ — `422 ROW_LIMIT` с
  числами и подсказкой сузить параметры.
- **Следствия:** пример `crm-paged` (`/api/rows`, 2 500 записей) собирается тремя запросами
  (1000 + 1000 + 500) и отдаёт `rowCount: 2500`; в логе видно каждую страницу. При
  `REP_JOIN_MAX_ROWS=100` отчёт `crm-public-filter` отвечает `ROW_LIMIT` с «сторона объединения 8290
  строк», а SQL-наборы работают как раньше.
- **Ограничения:** пагинация только по номеру страницы (cursor/offset-режимы не поддержаны); общий
  лимит строк `REP_MAX_ROWS` по-прежнему проверяется на результат; `maxPages` — предохранитель, а не
  «взять всё»: при большем числе страниц набор обрежется молча, поэтому значение задаётся в шаблоне
  осознанно.

**ADR-105. Один выбор шаблона и набора на все обработчики (версия 2.0.1).**
- **Проблема:** `data`, `aggregate`, `group`, `text` и серверный экспорт держали по копии кода
  «взять шаблон (или черновик), найти набор, проверить вид». При правке одной копии остальные
  расходились: в 2.0.0 `/text` отвечал 422 «нет datasets.<key>.sql» для join-набора, хотя данные
  и агрегация уже работали; правки через текстовые маркеры дважды ломали файл.
- **Решение:** тип `ResolvedDataset` и одна лямбда `resolveDataset(body, wantDraft, out)` рядом с
  кешем результатов: она выбирает шаблон, набор (по `dataset` или первый), возвращает `kind`, `sql`,
  `params`, `connection` и готовую копию шаблона (`shared_ptr` для async), либо статус/код/текст
  ошибки (`DRAFT_NOT_FOUND`, `REPORT_NOT_FOUND`, `DATASET_NOT_FOUND`, `TEMPLATE_INVALID`).
  Все пять обработчиков вызывают её и работают с `rds.*`.
- **Следствия:** выбор шаблона и набора теперь в одном месте; `/text` для join/rest отвечает по
  назначению (одна строка или `TEXT_ROW_MULTIPLE`); новый пример `crm-public-filter` (публичный
  отчёт, параметр-список из REST) открывается без входа: справочник — 5 регионов, шаблон и данные —
  200, SQL и заголовки источников в публичном JSON отсутствуют; e2e закрепляет это поведение.
- **Ограничения:** серверный экспорт и рассылка для rest/join по-прежнему отвечают
  `EXPORT_UNSUPPORTED` — попытка собрать лист из `DatasetRows` в этой версии приводила к зависанию
  обработчика, поэтому она отложена отдельной задачей; `resolveDataset` не валидирует шаблон (это
  делает валидатор при сохранении), только выбирает.

**ADR-104. Объединение наборов из разных источников: REST и join (версия 2.0).**
- **Проблема:** набор данных умел быть только SQL; отчёт, где факты лежат в PostgreSQL, а
  справочник регионов/менеджеров — в REST-сервисе, собрать было нечем. `kind: rest` был
  зарезервирован с ADR-76, но не реализован.
- **Решение:** два новых вида набора — REST и объединение. REST: `connection` с `kind: "rest"`
  (`baseUrl`, `headers` только через `${ENV}`, `timeoutMs`, `cacheSeconds`), набор `rest { path,
  query, rowsPath, columns[] }`; колонки обязательны, потому что типы JSON неоднозначны.
  Объединение: `join { left, right, on[], type, columns[] }` — hash join в прокси по 1–4 ключам с
  нормализацией по типу, `inner`/`left`, правые колонки переименовываются через `as`. Все три вида
  приводятся к одному контейнеру строк (`DatasetRows`), поэтому `/data`, `/aggregate`, `/group`,
  `/text`, клиентский Excel и печать работают одинаково; серверный xlsx/csv для rest/join отвечает
  `EXPORT_UNSUPPORTED`. Защита: `REP_REST_ALLOW_HOSTS` (без него REST выключен), запрет редиректов,
  лимит размера ответа, секреты только через окружение, лимит строк `REP_MAX_ROWS`.
- **Следствия:** `sales-crm` соединяет 24 723 заказа из PostgreSQL с 5 регионами из REST
  (`scripts/rest-demo.mjs`): на экране таблица с колонками «Регион»/«Менеджер» и ИТОГО, агрегация
  по объединённому набору даёт 5 регионов плюс группу без пары (left join), `/group` отдаёт детали
  с `detailOrder` и пагинацией. Замер join 50 000 × 5 000 — 36–38 мс, память ~43 МБ peak: узкое
  место — сеть до REST, а не соединение.
- **Ограничения:** один уровень join (без цепочек); REST только GET+JSON, без пагинации и вложенных
  объектов; материализация в temp-таблицу PostgreSQL и ETL-staging не делались; серверный экспорт и
  рассылка для rest/join не поддержаны (`EXPORT_UNSUPPORTED`) — работает клиентский Excel и печать;
  REST-ответы кешируются по `cacheSeconds` (по умолчанию 0 — без кеша); при недоступном REST отчёт
  показывает ошибку, а не пустые колонки; allowlist обязателен, поэтому в новом окружении REST нужно
  включать явно.

**ADR-103. Отчёт можно открыть без входа (public: true) (версия 1.78).**
- **Проблема:** доступ к любому отчёту требовал входа, даже если отчёт нужен «просто посмотреть по
  ссылке» — партнёру, коллеге без учётной записи, на большом экране. Роли (ADR-102) эту задачу не
  решают: они про группы внутри справочника пользователей, а не про анонимный доступ.
- **Решение:** флаг шаблона `public: true`. В pre-routing advice авторизации (одна точка на все
  данные) до проверки системной роли определяется отчёт по запросу (`reportId` из тела для
  `/api/report/data|aggregate|group|text|export.*`, из пути для `/api/reports/{id}` и
  `/api/reports/{id}/lookups/*`) и, если шаблон публичный, запрос пропускается без сессии; advice
  ролей (ADR-102) тоже пропускает публичный отчёт. Публичный JSON шаблона отдаётся как обычно (без
  SQL/connections). Клиент при открытии `report.html?report=<id>` сначала запрашивает шаблон: если
  он `public: true`, страница монтируется без сессии, иначе — обычный `ensureSession()` с переходом
  на вход. `public` важнее `accessRoles`: валидатор даёт предупреждение, роли игнорируются.
- **Следствия:** `public-demo` открывается анонимно (шаблон 200, данные 200, экспорт 200), закрытые
  отчёты и каталог без входа дают 401, обычный отчёт по ссылке без входа уводит на `login.html`;
  в анонимном окне строятся параметры и таблица на 5 регионов с ИТОГО.
- **Ограничения:** каталог остаётся закрытым — публичный отчёт доступен только по прямой ссылке;
  черновик публичного отчёта по-прежнему только для автора/администратора; анонимные запросы не
  попадают в аудит входа (сессии нет), но выполняются под ролью только-чтения PostgreSQL; секреты
  шаблона по-прежнему не отдаются (SQL и `connections` вырезаются из публичного JSON); отозвать
  публичность можно только правкой шаблона — отдельного «срока действия» ссылки нет.

**ADR-102. Доступ к отчётам по ролям (версия 1.77).**
- **Проблема:** права были только системные (`viewer`/`author`/`admin`): любой viewer видел все 32
  отчёта, включая финансовые. Ограничить доступ к отдельному отчёту было нечем — приходилось либо
  скрывать отчёт из каталога вручную, либо заводить отдельный экземпляр сервера.
- **Решение:** отдельный список ролей доступа (`reports.access_roles`: ключ + название) и связь
  «пользователь → роли» (`reports.user_roles`). В шаблоне отчёта объявляется `accessRoles` — массив
  ключей. Проверка одна на все запросы: pre-routing advice после сессии смотрит шаблон и роли
  пользователя и отдаёт `403 REPORT_FORBIDDEN`; каталог `/api/reports` фильтрует недоступные
  отчёты. Пустой `accessRoles` — доступ всем авторизованным (совместимость с существующими
  шаблонами), администратор видит всё. Роли и связи кэшируются в памяти и перечитываются после
  изменений в админке (`POST/PUT/DELETE /api/admin/access-roles`, `roles` в пользователе).
  В админке на странице «Пользователи» появились справочник ролей и галочки ролей у каждого;
  валидаторы (клиент и сервер) проверяют формат ключей и повторы.
- **Следствия:** `finance-plan-fact` (роль `finance`) и `ops-events` (`ops`) не видны пользователю
  с ролью `sales` — ни в каталоге, ни по прямой ссылке; после выдачи второй роли отчёт
  открывается без перезапуска; `sales-summary` с ролью `sales` виден, а отчёты без `accessRoles`
  (`sales-drill` и др.) остаются общими.
- **Ограничения:** роли не связаны с системными (`admin` всегда видит всё, `author` не получает
  доступа к чужим черновикам автоматически); проверка идёт по логину из сессии, поэтому смена
  ролей действует со следующего запроса, а кэш прокси-ролей (ADR-54) на доступ к отчётам не влияет;
  удаление роли делает отчёты с ней недоступными для всех, кроме администратора; в каталоге
  недоступные отчёты не видны, но их id по-прежнему возвращает 403 — существование отчёта не
  скрывается; справочник ролей плоский, без иерархии и групп.

**ADR-101. Текстовый блок берёт данные из запроса и умеет ссылки (версия 1.76).**
- **Проблема:** текстовый блок печатал только статический текст с подстановками параметров. Сводка
  «заказов N на сумму S» требовала отдельной таблицы-однострочника с колонками вместо фразы, а
  ссылки на другие отчёты и внешние документы вставить было нечем.
- **Решение:** блок `text` получил `dataKey` — набор из `datasets`, чей запрос обязан вернуть не
  более одной строки; колонки подставляются как `{{data.<колонка>}}` (отдельный префикс, чтобы не
  путать с параметрами). Новый эндпоинт `POST /api/report/text {reportId, dataset, params, draft?}`
  отдаёт `{row}` (0 строк → `null`, больше одной → `422 TEXT_ROW_MULTIPLE`); клиент запрашивает
  строки только блоков с `dataKey`, при открытии и по кнопке «Обновить» (при `autoLoad: false` —
  только по кнопке). В тексте появилась markdown-разметка ссылок `[текст](адрес)`: разрешены
  `http/https/mailto`, якоря и внутренние пути, `target="_blank"` и `rel="noopener noreferrer"`;
  активные схемы (`javascript:`, `data:`, `vbscript:`, `file:`) остаются текстом. Рендер — не
  `v-html`: текст и подстановки выводятся как значения Vue, ссылки строятся как `<a>`.
- **Следствия:** сводку можно написать фразой («заказов 24 723 на сумму …») с переходом в детальный
  отчёт; валидаторы (клиент и сервер) проверяют, что `dataKey` объявлен, а `{{data.*}}` без `dataKey`
  — ошибка; пример `text-data` показывает и подстановки, и обе разновидности ссылок.
- **Ограничения:** одна строка на блок — многострочные списки по-прежнему выводятся таблицей; значения
  подставляются строкой без форматирования чисел (разделители — в SQL); колонки `{{data.*}}`
  статически не проверяются (ошибка видна как пустая подстановка); HTML не поддерживается; при
  `autoLoad: false` до нажатия «Обновить» подстановки пустые; текст блока по-прежнему не попадает в
  Excel, но печатается; ссылки открываются в новой вкладке — параметры отчёта в новом окне
  подставляются по URL ссылки.

**ADR-100. Условное форматирование доходит до печати и Excel (версия 1.75).**
- **Проблема:** в `sales-rules` при печати был виден цвет шрифта, но не фон, а в Excel не было ни
  фона, ни цвета. Причины разные. В печати фон вычислялся и попадал в inline-стиль, но браузер по
  умолчанию не печатает фоны (`print-color-adjust: economy`), а текст печатается всегда — отсюда
  «красный есть, жёлтого нет». В книге `buildWorkbook` передавал в правила зону `body` (её имя
  используют стили зон), а шаблоны адресуют правила зоне `detail` — условие `zones.includes(zone)`
  не срабатывало, и ни одно правило не применялось.
- **Решение:** печатный слой просит `print-color-adjust: exact` (и `-webkit-` вариант) на
  `.rt-print`, таблице и ячейках — фоны печатаются без ручной настройки браузера. В книге зона
  стилей и зона правил разделены: `styleZoneOf` отдаёт `body`/`subtotal`/`grandtotal` для
  оформления, `ruleZoneOf` — `detail`/`subtotal`/`grandtotal` для правил; правила применяются как
  раньше (фон, цвет шрифта, начертание), значения берутся по `priority`.
- **Следствия:** в печати `sales-rules` 8801 ячейка с фоном всей строки, 1135 с жёлтым фоном маржи,
  66 с красным текстом (проверено computed-стилями в печатной медиа и PDF без `printBackground`);
  в книге появились `fill.fgColor` (`#fff7e6`, `#fff4d6`, `#dfe8f5`) и `font.color` (`#b42318`),
  проверено разбором `styles.xml`.
- **Ограничения:** `print-color-adjust` поддерживают Chrome/Edge и Firefox; в Safari фоны могут
  не печататься без галочки «Печать фонов»; в Excel цвет задаётся статично на момент выгрузки, а
  не формулой условного форматирования Excel — при правке значений в файле цвет не пересчитается;
  правила действуют на зоны, но не на объединённые ячейки групп (заливка остаётся у первой ячейки
  диапазона); печать по-прежнему ограничена 5000 строк модели.

**ADR-99. При печати шапка таблицы стоит только вверху страницы (версия 1.74).**
- **Проблема:** в `sales-detail` на второй странице печати шапка колонок появлялась ещё и в
  середине: примерно 15 строк, шапка, ещё 8 строк. Печатный слой резал таблицу на куски ровно по
  660 px, а браузер, встретив кусок, который не влезал в остаток страницы, разрывал саму
  таблицу-кусок и повторял её `thead` на текущей странице перед продолжением. Требование —
  шапка только вверху каждой страницы.
- **Решение:** для таблиц без групповых колонок печатный слой больше не режет на куски: печатается
  одна таблица, и браузер сам разрывает её по страницам, повторяя `thead` только сверху
  (`display: table-header-group`). Для сгруппированных таблиц нарезка остаётся (нужна для
  пересчёта объединений), но каждый кусок получает класс `no-break` и `break-inside: avoid`:
  кусок либо влезает в страницу целиком, либо переносится на следующую — разрыва внутри куска и
  «шапки посередине» не остаётся. Расчёт размера куска (ADR-98) гарантирует, что он укладывается
  в 660 px полосы.
- **Следствия:** `sales-detail` — одна таблица в печатном слое, 108 страниц вместо 112, шапка
  только вверху каждой страницы; `finance-print` — 23 куска по 23 страницам, каждый кусок на своей
  странице, шапка сверху (внизу возможен остаток полосы); `layout-horizontal` — по одной таблице на
  блок.
- **Ограничения:** у сгруппированной таблицы из-за `no-break` внизу страницы может оставаться
  незаполненное место до одной высоты куска (≈40 px в текущих шаблонах); при огромной высоте
  строки (больше полосы) кусок всё равно разорвётся, и шапка повторится — валидатор такие высоты
  не отсекает; нумерация страниц/колонтитулы в печать не добавляются.

**ADR-98. При печати таблица начинается на первой странице (версия 1.73).**
- **Проблема:** в `finance-print` первая страница печати содержала только заголовок и текст, а
  таблица начиналась со второй. Печатный слой режет таблицу на куски по `PRINT_PAGE_PX = 660` и
  считает строки только от высоты шапки, не зная, сколько места уже занято заголовком отчёта и
  текстовыми блоками. В finance-print над таблицей ~90 px: кусок 26 строк (658 px) переставал
  влезать в остаток полосы, и браузер переносил его на следующую страницу целиком — первая
  оставалась почти пустой.
- **Решение:** перед печатью измеряется позиция таблицы в потоке (`printTop` — от верха `.page` до
  скроллера таблицы) и первая порция строк считается от остатка: `fit((660 − printTop))`; остальные
  порции — как раньше. Для таблиц ниже первой страницы (`printTop ≥ 660`) считается, что они
  начинаются с новой страницы, поэтому порция полная. Замер делается при включении печати, пока
  экранный слой ещё виден (он скрывается только в `@media print`) и стоит там же, где печатный.
- **Следствия:** в `finance-print` первая страница содержит заголовок, текст и 16 строк таблицы
  (418 px), дальше по 26 строк, всего 23 страницы вместо 24 с пустой первой; `layout-horizontal`
  печатается с таблицы на первой странице.
- **Ограничения:** 660 px — эмпирическая полоса для A4 landscape с полями 10×8 мм; при других
  размерах бумаги и масштабе «по размеру страницы» остаток может отличаться (запас в 58 px это
  покрывает, но не гарантирует при нестандартных полях); измерение делается один раз перед печатью
  — при изменении размера окна во время печати порции не пересчитываются; шапка таблицы
  повторяется на каждой странице, но строка-заголовок блока (`title`) печатается один раз.

**ADR-97. В Excel каждая таблица отчёта — на своём листе (версия 1.72).**
- **Проблема:** `exportExcel` брал первый табличный блок (`tableBlock`) и передавал в
  `buildWorkbook` одну пару «блок + строки». В отчёте с двумя таблицами (например,
  `two-sets-styles`, `layout-horizontal`) в книгу попадала только первая — вторая молча
  терялась, хотя на экране обе видны.
- **Решение:** `buildWorkbook` принимает `sheets: [{block, rows, styles}]` (прежний вызов с
  `block`/`rows` остался совместимым); `exportExcel` собирает **все** блоки типа `table` и для
  каждого берёт строки своего `dataKey` (`rowsFor`) и свои стили (`stylesFor`, ADR-91). Имена
  листов — из `title`: без него «Таблица N»; повторы (без учёта регистра, как в Excel) получают
  суффикс « (2)», « (3)»; длиннее 31 символа имя обрезается и помечается «…»; запрещённые
  `* ? : \ / [ ]` заменяются на «·». Лист «Параметры» один на книгу и идёт последним.
- **Следствия:** `two-sets-styles` даёт три листа — «Продажи по регионам — светлая…» (8 строк),
  «Сервисы — тёмная тема» (8), «Параметры»; `layout-horizontal` — два листа данных;
  `sales-summary` с одной таблицей — как раньше, один лист отчёта и «Параметры».
- **Ограничения:** диаграммы и текстовые блоки в книгу не попадают (ADR-36); серверный
  `POST /api/report/export.xlsx` по-прежнему выгружает один набор (один лист) — он используется
  рассылкой, где формат задан подпиской; лимит Excel в 1 048 576 строк и 31 символ в имени листа
  не обходится, а соблюдается обрезкой; порядок листов = порядок блоков в шаблоне.

**ADR-96. Блоки раскладываются по 12-колоночной сетке (версия 1.71).**
- **Проблема:** блоки всегда шли друг под другом. В шаблоне был `width: full|half`, но CSS задавал
  половине только `max-width: 680px` — два блока не вставали в ряд, и «две таблицы рядом» или
  «таблица и диаграмма рядом» выразить было нельзя. Диаграммы и таблицы в отчётах шли длинной
  вертикальной лентой.
- **Решение:** блоки лежат в CSS-grid из 12 колонок; ширина — `blocks[].span` (1…12), ряды
  собираются автоматически (`grid-auto-flow: row`, `align-items: start`). Старый `width`
  поддерживается как алиас: `full` → 12, `half` → 6, `span` главнее. Высота блоков в ряду не
  выравнивается — у каждого своя (`height`, ADR-85), выравнивание по верхнему краю. На окне уже
  900 px и в печати сетка выключается: одна колонка на всю ширину. Валидация `span` (1…12) — на
  клиенте (JSON-схема) и на сервере (`validate.cc`), пути ошибок совпадают (parity).
- **Следствия:** таблица 7 + диаграмма 5 встают в один ряд, две половины — по 6; существующие
  шаблоны с `width: half` (их восемь) теперь показывают пары в ряд; пример `layout-horizontal`
  показывает оба ряда и полную строку текста.
- **Ограничения:** сетка не переносится на печать и не влияет на Excel/CSV (там данные блока, а не
  раскладка); при `span`, не кратном 12, последний блок ряда может оставить пустое место — сетка
  не растягивает блоки; минимальная ширина блока не проверяется (span 1 с таблицей из 8 колонок
  будет прокручиваться горизонтально); перестановки блоков мышью нет — порядок задаётся массивом
  `blocks`.

**ADR-95. Плоская таблица выгружается в Excel всеми строками (версия 1.70).**
- **Проблема:** `sales-drill` (таблица без групповых колонок) в Excel содержал только шапку и пустую
  строку итога. Причина — `buildTableModel` обходил `root.children`, а при пустом списке групповых
  полей все строки лежали в `root.details`, и в модель не попадала ни одна деталь. Экран это
  скрывал: `TableView` для таблиц без `group` идёт другой веткой (`flatView`), а экспорт — нет.
  Серверный `export.xlsx` строки отдавал, но подпись «ИТОГО» ставилась в первую групповую колонку,
  которой нет, — строка итога была безымянной.
- **Решение:** `buildTableModel` при отсутствии групповых колонок строит плоский список детальных
  строк в порядке набора, а строку общего итога формирует с подписью «ИТОГО» в первой колонке
  (раньше подпись ставилась только при наличии групп). `summaryRow` в `group_rows.cc` делает то же
  для серверного экспорта. Один путь — одна модель: экран, кнопка «Excel» и `POST
  /api/report/export.xlsx` дают одинаковый набор строк.
- **Следствия:** `sales-drill` выгружается 2748 строками (шапка + 2746 данных + ИТОГО),
  `ops-events` — 8 (6 + шапка + ИТОГО), `date-formats` (без `grandTotal`) — 7 (шапка + 6); суммы в
  ИТОГО считаются по `aggregate`-колонкам, вычисляемые колонки — по строке.
- **Ограничения:** Excel-выгрузка по-прежнему без диаграмм (ADR-36) и без серверной пагинации —
  выгружается весь набор в пределах `maxRows`; для плоской таблицы `outlineLevel` не пишется, так
  как группировки нет; печать не изменилась (свой лимит 5000 строк).

**ADR-94. `collapsible: false` действует и на Excel (версия 1.69).**
- **Проблема:** `collapsible: false` отключал сворачивание на экране (ADR-90), но выгрузка в Excel
  строила outline-структуру всегда: `buildGroupedSheet` выставлял `rowLevels`, а писатель книги —
  `outlineLevel` и `summaryBelow`. В итоге отчёт с запрещённым сворачиванием всё равно давал в книге
  кнопки «+/-» и группировку строк, то есть шаблон обещал разное поведение на экране и в файле.
- **Решение:** `GroupLayout::collapsible` (по умолчанию `true`) заполняется из
  `blocks[].collapsible` в `buildSheet`. `rebuildMergesAndLevels` теперь считает уровень строки
  дважды: внутренний (для объединений и подытогов) и `sheet.rowLevels` для структуры книги — при
  `collapsible: false` уровни в книгу не попадают (все 0, `outlineLevel` не пишется). Клиентский
  экспорт (`report/export/xlsx.js`) обёрнут тем же условием: без `outlineProperties` и без
  `outlineLevel` у строк. Подытоги, ИТОГО и объединения групповых колонок сохраняются в обоих путях.
- **Следствия:** оба пути выгрузки (кнопка «Excel» через ExcelJS и серверный `POST
  /api/report/export.xlsx` для рассылки) ведут себя одинаково; в книге `fixed-groups` нет ни одной
  строки с `outlineLevel`, а `sales-summary` по-прежнему даёт 24 723 строки с уровнями до 2.
- **Ограничения:** в серверном файле остаётся `outlinePr` без строк-уровней — Excel не показывает
  кнопок, но атрибут листа безвреден; свернуть группы в книге нельзя, однако пользователь может
  вручную применить «Группировать» в Excel — это уже его действие, а не шаблон; фильтры автофильтра
  по-прежнему в шапке.

**ADR-93. Доменные учётные записи в администрировании пользователей (версия 1.68).**
- **Проблема:** прокси-аутентификация принимала в заголовке любое имя (`isValidProxyLogin` разрешал
  заглавные буквы и «`\`»), но завести такого пользователя в админке было нельзя: логин
  ограничивался строчными латинскими буквами, цифрами и `_ . -` длиной 3…32, а пароль был
  обязателен при создании. Доменный пользователь `CORP\ivanov` либо не создавался, либо
  автосоздавался без роли и потом не находился из-за регистра.
- **Решение:** в администрировании пользователей логин принимает латинские буквы в любом регистре,
  цифры, `_`, `.`, `-`, `\`, `@` (длина 3…128); сравнение логинов и уникальность — без учёта
  регистра (уникальный индекс `users_login_lower_key`, поиск `lower(login) = lower($1)` в прокси,
  входе по паролю и автосоздании), сам логин хранится как задан. Пароль при создании может быть
  пустым: такая учётная запись имеет пустые `password_salt`/`password_hash` и входит только через
  доверенный прокси — вход по паролю возвращает 401, пока пароль не зададут. Кэш «логин → роль»
  ключуется в нижнем регистре, автосоздание использует `ON CONFLICT DO NOTHING` и берёт уже
  существующую запись, а не создаёт двойника.
- **Следствия:** доменные учётные записи заводятся в админке и работают через прокси независимо от
  регистра в заголовке; пароль доменной учётной записи хранится только если он явно задан;
  `scripts/check-proxy-auth.sh` проверяет доменный логин, другой регистр и пустой хеш.
- **Ограничения:** домен не проверяется по справочнику каталога — доверяем прокси (как и раньше,
  ADR-54); кириллица и пробелы в логине по-прежнему запрещены; `\` в логине требует экранирования
  при поиске в SQL и CSS-селекторах (в UI поиск идёт по тексту); смена логина не предусмотрена —
  учётную запись пересоздают.

**ADR-92. Арифметика дат в `default` параметров (версия 1.66).**
- **Проблема:** `default` у `date`/`datetime` был константой, поэтому «период по умолчанию — текущий
  месяц» приходилось переписывать в каждом шаблоне каждый месяц или оставлять пустым и просить
  пользователя вводить даты руками. Для отчётов «за последние сутки», «с начала месяца», «на момент
  пять часов назад» это означало постоянное сопровождение шаблонов.
- **Решение:** у `date`/`datetime` значение `default` может быть выражением от текущего момента:
  `*` (сейчас), `today(*)`, `week(*)`, `month(*)`, `quarter(*)`, `year(*)` — все с 00:00, плюс
  цепочка смещений `±N` с единицами `h`/`d`/`m`/`y` (`*-5h`, `*-30d`, `month(*)-1m`, `*-1d+2h`).
  Считается в локальном поясе браузера. Выражения пересчитываются при каждой загрузке данных:
  «Обновить», автообновление, смена параметров. Значение, выбранное вручную или пришедшее из URL,
  выражение не перезаписывает. Опечатка (`month2(*)`, `*+5x`) — ошибка валидации шаблона с указанием
  места, и на клиенте (`frontend/src/template/dates.js`), и на сервере (`backend/src/dates_expr.cc`).
- **Следствия:** шаблон не надо править при смене месяца; «период с начала года по сегодня» —
  `year(*)` и `*`; пример `period-defaults` показывает и `date`, и `datetime` (`*-5h`).
- **Ограничения:** единиц меньше часа и больше года нет (минуты и секунды не смещаются; `m` — месяц,
  а не минута); считает браузер, поэтому у пользователя в другом поясе граница месяца «своя»;
  сервер синтаксис проверяет, но значение не вычисляет — рассылка подставляет то, что записано в
  подписке (у подписок параметры задаются явно), поэтому выражения в рассылке не поддерживаются;
  в текстовом блоке `{{param}}` по-прежнему печатается подпись, а не вычисленная дата.

**ADR-91. Стили можно задавать у набора данных (версия 1.65).**
- **Проблема:** оформление задавалось только глобально (`styles`) или у блока (`blocks[].styles`).
  В отчёте с несколькими наборами у каждого блока своя тема — приходилось копировать один и тот же
  объект `styles` в каждый блок, а при правке забывать одну копию. Привязки «набор → вид» не было,
  хотя логически тема принадлежит набору: продажи светлые, сервисы тёмные.
- **Решение:** `datasets.<ключ>.styles` — те же ключи, что у глобальных и блочных стилей (шрифт,
  цвета, зоны, раскладка, `columns.<поле>`). `resolveStyles` собирает слои
  `пресет → styles → styles.<зона> → datasets[dataKey].styles → blocks[].styles → columns.<поле>`;
  блок берёт стили набора по своему `dataKey` и может перекрыть любое поле своими `styles`,
  остальные наследуются. Валидаторы (клиент и сервер) проверяют стиль набора так же, как блочный:
  цвета — hex или из `styles.palette`, `format` — по правилам дат, `columns.<поле>` — только для
  полей, объявленных в блоках этого набора.
- **Следствия:** одна тема на набор вместо копий в блоках; блок без `styles` выглядит согласно
  своему набору; пример `two-sets-styles` («Два набора — два стиля») — светлая таблица продаж и
  тёмная таблица сервисов из одного шаблона.
- **Ограничения:** стиль набора действует только на блоки, у которых `dataKey` совпадает с ключом
  набора (у текстовых блоков `dataKey` нет — они видят глобальные стили); `palette` на уровне
  набора не задаётся — слова палитры берутся из `styles.palette` шаблона; диаграммы берут из стилей
  только `font`/`colors` осей и легенды, цвета серий по-прежнему из `colors` графика.

**ADR-90. `collapsible: false` действительно фиксирует группы раскрытыми (версия 1.64).**
- **Проблема:** поле `blocks[].collapsible` было объявлено в схеме и использовалось в восьми
  примерах, но рендерер его не читал. `TableView` показывал панель «Свернуть всё / Развернуть всё»
  при любой группировке (`v-if="isGrouped"`), `ReportTable` всегда рисовал шеврон у подытога и
  всегда отправлял `toggle` при клике. Поэтому `collapsible: false` не давал ничего: группы
  сворачивались, счётчик «свёрнуто» менялся.
- **Решение:** флаг проброшен в рендерер. `TableView` считает `collapsible = block.collapsible !== false`,
  прячет кнопки и счётчик, не рендерит пустую панель (если в ней не осталось «ещё N» или заметки о
  подгрузке), и блокирует `collapseAll`/`expandAll`/`toggle`. `ReportTable` получил prop
  `collapsible` (по умолчанию `true`): при `false` у ячеек нет `toggle`, шеврон не рисуется,
  `handleToggle` выходит сразу. Пример `fixed-groups` — группировка по региону и категории без
  сворачивания.
- **Следствия:** `collapsible: false` теперь означает именно то, что написано: группы раскрыты,
  кнопок нет, щелчок по подписи группы не меняет таблицу; объединение ячеек и подытоги работают
  как раньше. Поведение по умолчанию (`true`) не изменилось.
- **Ограничения:** флаг действует на блок целиком — отдельную группу свернуть нельзя; при
  `collapsible: false` состояние `collapsed` не используется, но и не сбрасывается при смене
  шаблона на лету (перезагрузка отчёта возвращает всё раскрытым); в печатном виде разницы нет —
  печать и так разворачивает группы.

**ADR-89. Отчёт может требовать явной загрузки данных (версия 1.63).**
- **Проблема:** отчёт всегда запрашивал данные при открытии: столько, сколько нужно блоку. Для
  тяжёлых отчётов (50 000 строк, несколько наборов) открытие ссылки с чужой машины означало
  долгий запрос, которого пользователь не просил и не мог отменить; при этом сам процесс
  визуально не отличался от «пусто» — кнопка «Обновить» показывала «загрузка…» только в момент
  клика, а первый автоматический запрос шёл до появления формы.
- **Решение:** флаг шаблона `autoLoad` (по умолчанию `true`). При `autoLoad: false` отчёт при
  открытии загружает только шаблон и справочники: `/api/report/data` не вызывается, блоки таблиц и
  диаграмм скрыты, показывается подсказка «Данные не загружены — нажмите «Обновить». Единственный
  триггер загрузки — кнопка «Обновить»: изменения параметров и URL данные не перезапрашивают.
  `refreshSeconds` и `live` с выключенной автозагрузкой не включаются (валидатор предупреждает).
  Индикатор загрузки усилен для всех отчётов: текст кнопки меняется на «Загрузка…», кнопка
  неактивна, в шапке появляется «загрузка…».
- **Следствия:** тяжёлый отчёт не начинает запрос без команды; видно, что идёт загрузка, а не
  «ничего не происходит»; пример `manual-load` (50 000 строк, ~2,5 с) показывает оба состояния.
- **Ограничения:** пока идёт загрузка, отменить её из интерфейса нельзя (только уход со страницы —
  запрос прерывается вместе с компонентом); `autoLoad: false` отключает и автообновление, и live —
  их сочетание валидатор помечает предупреждением, но не ошибкой; кнопка «Обновить» живёт в форме
  параметров, поэтому при скрытой форме (нет параметров) загрузка запускается первым же событием
  `ready` — такие шаблоны с `autoLoad: false` бессмысленны, но не отклоняются.

**ADR-88. Шаблон даты для колонок (version 1.62).**
- **Проблема:** формат `date` был жёстким: `formatCell` отдавал ровно `ДД.ММ.ГГГГ` (и `ЧЧ:ММ`, если
  время есть), параметров у него не было. Отчёт не мог показать дату в ISO для сверки с базой, без
  года в компактной сводке или со временем в журнале. Дополнительно `ReportTable.pretty()`
  переписывал **любую** ISO-дату в тексте ячейки в `ДД.ММ.ГГГГ`, поэтому даже добавленный формат
  `YYYY-MM-DD` не отображался — ячейка возвращалась к «привычному» виду.
- **Решение:** у объекта формата появилось поле `pattern` — шаблон из токенов `YYYY`, `YY`, `MM`, `M`,
  `DD`, `D`, `HH`, `H`, `mm`, `ss` и разделителей. Наличие `pattern` без `style` включает формат
  даты. `pattern` допустим у колонки и у `styles.columns.<field>.format` (стиль сильнее). Валидаторы
  (схема, клиент, сервер) отклоняют неизвестные буквы, пустой шаблон и `pattern` у числового
  формата. `pretty()` в `ReportTable` теперь применяется только к подытогам и ИТОГО (там подписи
  формирует движок, например «Итого 2025-10-01»), а ячейки детальных строк печатаются как есть —
  их уже отформатировал `TableView`. Клиентский Excel получает шаблон как числовой формат.
- **Следствия:** одна дата показывается по-разному в разных колонках (`DD.MM.YYYY HH:mm`,
  `YYYY-MM-DD`, `DD.MM`, `DD/MM/YYYY`), формат из `styles.columns` работает наравне с колонкой;
  регрессия «ISO-дата в ячейке всегда превращается в ДД.ММ.ГГГГ» устранена.
- **Ограничения:** шаблон не локализуется (названий месяцев нет — только цифры); секунды выводятся,
  только если они есть в значении; шаблон не влияет на серверный `.xlsx` (libxlsxwriter пишет дату
  строкой — существующее ограничение); часы/минуты не пересчитываются между таймзонами.

**ADR-87. Параметры даты и времени и разбор SQL без ложных плейсхолдеров (версия 1.61).**
- **Проблема:** `type: "datetime"` был в схеме, но ни в одном шаблоне не использовался, и пройти
  этот путь целиком не удавалось. Три дефекта вскрылись сразу, как только понадобился фильтр по
  времени: (1) параметр `type: "datetime"` без `source` рендерился как **текстовое поле** — функция
  `kind()` в `ParamsForm.vue` знала только `date`/`select`; (2) SQL с форматированием времени
  `to_char(ts, 'DD.MM.YYYY HH24:MI')` падал с `INVALID_PARAMS: не передан параметр 'MI'` —
  парсер `:name` не отличал плейсхолдер от двоеточия в строковом литерале; (3) тип колонки
  угадывался по подстроке, и значение «01.03.2026 00:43» превращалось в число `1.03`.
- **Решение:** параметр времени — `input[type=datetime-local]` (`type` и `source.kind` = `datetime`),
  значение `ГГГГ-ММ-ДДTЧЧ:ММ`, в SQL — каст `::timestamp` с проверкой формата (422). Разбор
  плейсхолдеров вынесен в `rep::compileNamedParams` (`dataset.cc`) и пропускает строковые
  литералы, идентификаторы в двойных кавычках, dollar-quoted `$$…$$` и комментарии `--` / `/* */`;
  `main.cc` использует ту же функцию, дублирующий разбор удалён. Определение типа колонки
  вынесено в `rep::inferColumnType` и сравнивает значение целиком, а не подстроку. В демо-данные
  добавлена колонка `reports_examples.ops.logged_at` (время внутри дня), появился пример
  `ops-events` — «Журнал сервиса: выбор даты и времени», с ИТОГО по выбранному интервалу.
- **Следствия:** отчёт фильтруется по интервалу с точностью до минуты (1 марта 00:00–23:59 —
  6 событий, 31 марта — свои 6), ИТОГО считается по тем же строкам; в шаблонах теперь можно писать
  `to_char(..., 'HH24:MI')` и любые литералы с двоеточием; текстовые колонки больше не портятся
  эвристикой типов.
- **Ограничения:** `datetime-local` не содержит таймзоны — время трактуется как локальное для
  сервера и БД (для `timestamptz` нужен отдельный тип параметра); секунды не вводятся (шаг
  минуты), в тексте `{{dt_from}}` печатается ISO-строкой; `::timestamptz` отдельно не
  проверяется — только `::date`, `::int`, `::timestamp`.

**ADR-86. Текст отчёта печатает подпись параметра, включая пустой пункт (версия 1.59.1).**
- **Проблема:** в текстовом блоке `{{param}}` должен печатать подпись (`label`), а не значение.
  Для дат и наборов это работало, а после ADR-84 появился разрыв: пустой пункт списка
  (`emptyOption`) рисуется отдельным `<option>` и в список опций не попадал, поэтому
  `{{cost_center}}` при выбранном «Все центры» печатал **пустую строку** — во фразах вида
  `{{cost_center}}. Период: …` получалось «. Период: …». Список подписей собирался без пустого
  пункта, и значение `""` не находило своей метки.
- **Решение:** подписи собираются из отдельного списка `labelOptions` — `emptyOption` плюс
  значения справочника; для значения `""` берётся подпись пустого пункта (`[emptyOption].label`),
  для выбранных значений — `label` из списка, а `value` остаётся только запасным вариантом, когда
  метки нет (значение пришло из URL и отсутствует в справочнике). Подписи для множественного
  выбора по-прежнему склеиваются через запятую.
- **Следствия:** `{{cost_center}}` печатает «Все центры», `{{service}}` — «Все сервисы»,
  `{{scope}}` — «Все строки»; при выборе конкретной строки печатается её подпись из справочника
  (`{{region}}` → «Восток», а не `4`); фраза в тексте не начинается с точки.
- **Ограничения:** подпись известна только после загрузки справочника — до ответа `/lookups`
  в тексте может мелькнуть значение или пустота; для значения, которого нет в справочнике
  (устаревшая ссылка), печатается само значение; форматирование подписи (регистр, сокращения)
  задаётся SQL справочника, текст шаблона его не меняет.

**ADR-85. Высота блока задаётся в шаблоне — пиксели или процент от окна (версия 1.59).**
- **Проблема:** высота блока не была частью описания отчёта: таблица всегда рисовалась в 460 px
  (`:height="460"` в `ReportViewer.vue`), диаграмма — 320 px, и только у диаграммы было поле
  `height` (240…900 px), причём проверялось оно лишь у sankey. На большом экране таблица занимала
  четверть высоты, на маленьком — половину; подогнать отчёт под экран можно было только правкой
  кода.
- **Решение:** поле `height` у блоков `table` и `chart`: целое число — пиксели (160…2000),
  строка `"60%"` — процент от высоты окна (10…100). Клиент переводит значение в пиксели
  (`engine/layout.js`: `parseBlockHeight` → `resolveBlockHeight`) и пересчитывает процент при
  изменении размера окна; виртуализация таблицы и ECharts по-прежнему получают число. У таблицы
  действует прежнее правило «не выше содержимого», у диаграммы высота ровно заданная. У
  текстового блока `height` отклоняется. Ограничения закреплены в схеме, клиентском и серверном
  валидаторах и parity-фикстурах. Пример — шаблон `layout-heights` (таблица `"60%"`, диаграмма
  `320`, таблица `240`).
- **Следствия:** вёрстка отчёта стала частью шаблона; на экране высотой 900 px таблица `"60%"`
  занимает 540 px, при сжатии окна до 700 px — 420 px, а пиксельные блоки не меняются; диаграммы
  всех видов проверяют высоту одинаково.
- **Ограничения:** процент считается от высоты окна, а не от контейнера — вложенных областей
  прокрутки нет; единицы только px и %, `vh`/`rem`/`calc()` не принимаются; при печати процент
  берётся от текущего окна, то есть зависит от размера окна браузера в момент печати; `height`
  у текстового блока не поддерживается.

**ADR-84. Пустой пункт списка объявляется шаблоном (версия 1.58).**
- **Проблема:** пустой пункт параметра-справочника собирался из двух источников. Интерфейс
  подставлял `—` с `value=""` и `disabled`, а «Все центры» / «Все сервисы» добавлял сам SQL
  шаблона через `UNION ALL SELECT '' AS value, 'Все …' AS label`. Из-за этого пустой пункт нельзя
  было ни назвать осмысленно, ни задать ему другое значение (`all`, `0`), первый пункт зависел от
  сортировки SQL, а выбранное по умолчанию значение определялось случайно — браузер показывал
  первое, хотя в запрос уходила пустая строка.
- **Решение:** поле параметра `emptyOption: {value, label}`. Интерфейс рисует его первым пунктом
  списка и **не добавляет** `—` сам; нет `emptyOption` — нет и пустого пункта, выбирается значение
  из данных. `default` задаёт `value` пункта, выбранного по умолчанию; порядок применения —
  `default` → `emptyOption` → первое значение списка. Дубликат (`value` уже вернул справочник)
  не выводится дважды. Валидатор (фронт и сервер, parity-фикстуры) требует `value` и непустой
  `label` и разрешает `emptyOption` только у `source.kind=lookup` без `multiple`. Шесть шаблонов
  (`finance-plan-fact`, `finance-print`, `ops-sla`, `ops-dark`, `ops-band`, `ops-corridors`)
  переведены на декларативный пустой пункт, `UNION ALL SELECT ''` из их SQL убран.
- **Следствия:** пустой пункт виден одинаково во всех отчётах и не зависит от сортировки данных;
  его значение — часть контракта шаблона, а не догадка интерфейса; «—» из формы исчез; выбор по
  умолчанию задаётся явно (`default`), а не первым элементом.
- **Ограничения:** пустой пункт один (это не произвольный список служебных опций); только
  одиночный выбор — с `multiple` `emptyOption` отклоняется; согласованность `value` с SQL
  (например, `''` против `IS NULL`) валидатор не проверяет — это ответственность шаблона;
  `default` не сверяется с данными, поэтому несуществующее значение даст пустой отчёт или 422.

**ADR-83. CI собирает на фиксированном компиляторе (версия 1.57.1).**
- **Проблема:** `ubuntu-latest` принёс gcc 15, а Conan 1.66 знает `settings.compiler.version`
  только до 14.1. Профиль создавался автоматическим `detect`, поэтому в него попадало
  `compiler.version=15`, и `conan install` падал с
  `ERROR: Invalid setting '15' is not a valid 'settings.compiler.version' value` — job `backend`
  и `e2e` не доходили до сборки. Заодно сборка зависимостей зависела от того, какой компилятор
  окажется в образе: одинаковый коммит собирался бы по-разному.
- **Решение:** образ и компилятор фиксируются. Job'ы `backend` и `e2e` работают на
  `ubuntu-24.04` и ставят `g++-13`; профиль Conan пишется явно в
  `$CONAN_USER_HOME/.conan/profiles/default` (`compiler=gcc`, `compiler.version=13`,
  `libstdc++11`, `env.CC/CXX=/usr/bin/gcc-13`), а `detect` для сборки не используется.
  В ключ кэша Conan добавлен `gcc13`, чтобы не смешивать пакеты, собранные другим компилятором.
- **Следствия:** ошибка `Invalid setting` устранена — локальная проверка `conan install -pr`
  с этим профилем проходит валидацию и упирается только в `Missing binary`, которые в CI
  собирает `--build missing`; версия компилятора больше не зависит от образа; одинаковый коммит
  даёт одинаковый ABI.
- **Ограничения:** gcc 13 закреплён в двух местах (workflow и профиль) — при обновлении
  компилятора править оба; Conan остаётся 1.66 (v2 не используется), поэтому новые версии
  компиляторов требует правки `settings.yml` или такого же пина; реальный прогон CI
  проверяется только после пуша — локально GitHub Actions не запускается.

**ADR-82. Просмотр черновика исполняет тело черновика (версия 1.57).**
- **Проблема:** новый отчёт создаётся в админке каркасом — `{version: 1, blocks: [{type: "text"}]}`,
  без `datasets` и `params`. Пока черновик не опубликован, серверные запросы считались по
  **опубликованному** телу, то есть по каркасу: экран просмотра черновика
  (`report.html?report=X&draft=1`) подставлял тело черновика только в браузере, а `/api/report/data`
  отвечал `TEMPLATE_INVALID: в шаблоне не задан datasets.<key>.sql`, справочник —
  `LOOKUP_NOT_FOUND: у параметра 'cost_center' нет source.dataset`. Публикация «лечила» оба
  экрана, потому что переключала исполнение на новое тело.
- **Решение:** серверный режим черновика. Запросы данных, агрегации, деталей групп и экспорта
  принимают `draft: true` в теле, справочники — `?draft=1`; исполняется тело `report_templates.draft`
  (оно уже прошло валидацию при сохранении). Черновики загружаются в память при старте и
  обновляются при сохранении/удалении/публикации, поэтому просмотр видит последнюю правку без
  рестарта. Кэш результатов получает отдельный ключ (`|draft`), иначе данные черновика и
  опубликованной версии смешались бы. Доступ — только автору и администратору: зрителю `403
  DRAFT_FORBIDDEN`; после публикации черновик выгружается из памяти и `draft: true` даёт `404
  DRAFT_NOT_FOUND`. Клиент просмотра передаёт флаг во все запросы и, если `localStorage` пуст
  (другой браузер, новая вкладка), берёт тело из `GET /api/admin/reports/{id}/draft`.
- **Следствия:** просмотр черновика совпадает с публикацией — в том числе для нового отчёта;
  сообщения `TEMPLATE_INVALID`/`LOOKUP_NOT_FOUND` на неопубликованном отчёте исчезли; зритель
  по-прежнему видит только опубликованное; рассылка всегда считает по опубликованной версии.
  Проверено e2e: каркас → черновик с набором и справочником → `?draft=1` показывает 5 строк и
  регион «Восток»; `POST /api/report/data` без `draft` возвращает 422 (каркас), зрителю — 403.
- **Ограничения:** черновик исполняется в памяти процесса: при нескольких экземплярах сервера
  правка, сохранённая на одном, не видна другому до рестарта; правка `draft` напрямую в БД
  требует рестарта; кэш черновика живёт в общем TTL (60 с) и не сбрасывается при сохранении
  нового черновика — до истечения TTL можно увидеть предыдущий результат того же ключа.

**ADR-79. Один процесс отдаёт и API, и фронтенд (версия 1.53).**
- **Проблема:** статику раздавали снаружи — `vite preview` на стенде и nginx в эксплуатации.
  Для демонстрации это два процесса и node, для установки — обязательный веб-сервер, хотя
  приложение маленькое и уже целиком умеет работать под одним доменом. Вопрос «где должны
  лежать файлы фронтенда относительно бинарника» не имел ответа: сервер их вообще не искал.
- **Решение:** drogon отдаёт статику сам. Каталог ищется по порядку: `REP_WEB_ROOT` (если задан —
  только он), `./web`, `../web`, `<каталог бинарника>/web`, `<каталог бинарника>/../../frontend/dist`
  (раскладка репозитория). `build.sh` кладёт собранный фронтенд в `backend/build/web`, поэтому
  комплект — это два объекта: `rep` и `web/`. Маршрут регистрируется через
  `registerHandlerViaRegex("/.*")`: обычный `registerHandler` считает строку без `{…}` литералом,
  и «/.*» молча становился маршрутом с таким именем (первая версия отдавала 404 на всё).
  Правила: файл существует — отдаётся с `Cache-Control` (`no-cache` для html, `immutable` для
  `/assets/*`, час для остального); путь без расширения — `index.html` (SPA); путь с расширением
  и без файла — честный 404; `/api/*` — JSON-ошибка; `..` и `%2e%2e` отклоняются. В матрице прав
  не-`/api` пути стали `Public`: иначе страница входа не загружалась (401 на html), при этом все
  `/api`-маршруты остаются под ролью.
- **Следствия:** `./scripts/demo.sh` поднимает один процесс — `http://127.0.0.1:8080/report.html?report=…`
  работает без node; `REP_WEB_PORT=5173` оставлен для сверки с внешним preview. Проверено:
  `/` и `/report.html` — 200 `text/html`, `assets/*.js` — 200 `text/javascript` с `immutable`,
  `/api/health` — 200 без входа, `POST /api/report/data` без сессии — 401, `/api/nope` с админской
  сессией — 404 JSON, `/portal/x` — 200 html, `/assets/nope.js` — 404, `../../etc/passwd` — 404.
  Отчёт через сервер отдаёт 2 748 строк; сборка — `backend/build/web` 2,8 МБ.
- **Ограничения:** статика отдаётся файлом на каждый запрос без gzip/brotli и без кэша в памяти —
  для небольшой сборки это нормально, но при росте стоит включить сжатие drogon; имена ассетов
  в index.html относительные (`./assets/…`), поэтому SPA-маршруты с несколькими сегментами
  (`/portal/x`) получат страницу, но ассеты по относительным путям не загрузятся — приложение
  многостраничное, страницы лежат в корне; список MIME фиксирован в `static_web.cc` (html, js,
  css, json, map, svg, png/jpg/gif/webp, ico, шрифты, wasm, txt), новый тип нужно добавлять там;
  TLS и префикс `/reports` по-прежнему требуют внешнего прокси; при `REP_AUTH=proxy` заголовок
  `X-Remote-User` проверяется только на `/api` — оболочка страницы отдаётся без него.

**ADR-78. Справочники параметров — это наборы данных (версия 1.51, без обратной совместимости).**
- **Проблема:** после ADR-76 все запросы к БД получили единое место — блок `connections`, — но SQL
  справочников продолжал жить в `params[].source.sql`. В админке шаблон выглядел разорванным:
  данные отчёта описаны в `datasets` (с соединением), а запрос «Центр затрат» — в параметре,
  рядом с которым нет ни соединения, ни набора. Найти все запросы шаблона в одном месте было нельзя.
- **Решение:** справочник становится обычным набором данных: `datasets.<ключ>` с `sql` и
  `connection`, а параметр ссылается на него полем `source.dataset`. `source.sql` и
  `source.connection` удалены из формата и считаются ошибкой валидатора с подсказкой, куда
  переносить (`SQL справочника задаётся набором datasets.<ключ>: source.sql больше не
  поддерживается`). Обратная совместимость сознательно не вводится (решение PO): формат шаблона
  остаётся версии 2, но старые шаблоны не принимаются. Все 21 шаблон репозитория переведены:
  11 справочников в 8 файлах стали наборами (`cost_center_lookup`, `region_lookup`,
  `category_lookup`, `service_lookup`). Справочный набор отличается от отчёточного только
  использованием: блоки на него не ссылаются, а эндпоинт `lookups` берёт из него SQL и соединение.
- **Следствия:** в каждом шаблоне все SQL и все соединения теперь в одном блоке `datasets` —
  это видно и в JSON, и в админке (панель параметров показывает «набор: …» и «источник: …»,
  а сам SQL — из набора). Справочники работают через тот же механизм соединений, что и данные
  (ADR-76): подстановка `${PGHOST}`, read-only сессия, кэш. Каскад (`dependsOn`) сохранён:
  `:region` из query-строки подставляется в SQL набора. Проверено: `cost_center` отдаёт
  «Все центры» + ЦФ-1…ЦФ-N, `region → category` фильтруется, все 21 отчёт отдают данные,
  старый формат отклоняется с `422 TEMPLATE_INVALID` и путём `params.0.source.sql`.
- **Ограничения:** набор-справочник обязан возвращать ровно две колонки `value`/`label` —
  валидатор этого проверить не может (SQL исполняется на сервере), ошибка видна при открытии
  отчёта; один справочник — один набор, повторное использование набора двумя параметрами
  допустимо, но разных списков в одном наборе быть не может; шаблоны, сохранённые до версии
  1.51, нужно перевести вручную (автомиграции нет по решению PO); наборы-справочники попадают
  в общий список `datasets` и видны в админке как наборы — отдельного признака `role: lookup`
  не вводилось.

**ADR-77. Источники в шаблонах примеров: явный блок main и подстановка окружения (версия 1.50).**
- **Проблема:** после появления блока `connections` (ADR-76) все примеры, кроме `sales-external`,
  продолжали читать данные «по умолчанию» — источник в шаблоне не был описан вовсе. Из-за этого
  нельзя было ни увидеть, куда идёт запрос, ни перенастроить пример на другую роль, а половина
  ревизии «источник в блоке» оставалась невыполненной.
- **Решение:** у всех 21 шаблона примеров появился явный источник `connections.main`; каждый
  набор данных и каждый справочник параметров ссылается на него полем `connection`. Поля
  `host`, `port`, `database`, `user`, `schema` допускают подстановку окружения вида `${PGHOST}` —
  целиком, не в составе строки. Значение берётся из окружения сервера; незаданная переменная —
  ошибка с её именем. Примеры читают данные под ролью `reporting_ro`
  (`user: ${REP_RO_DB_USER}`, `passwordEnv: REP_RO_DB_PASSWORD`), поэтому эксплуатационное
  разделение ролей (ADR-75) соблюдается и в примерах. На CI-стенде переменные указывают на
  основную учётную запись — отдельной роли чтения там нет.
- **Следствия:** все 21 отчёт открываются и отдают данные через `main`; проверено, что внутри
  сессии `current_user = reporting_ro`, `current_database = reporting`, а
  `default_transaction_read_only = on` (то есть источник открыт только на чтение). Валидаторы
  клиента и сервера принимают `${ИМЯ}` как целое значение поля и отклоняют смесь вроде
  `db-${ID}` — parity 67/67. Подстановка адреса делает шаблоны переносимыми: тот же файл
  работает на dev-базе и на CI без правок.
- **Ограничения:** подстановка — только одиночная ссылка на переменную (без `${A}${B}`,
  значений по умолчанию и подстановки в `passwordEnv`/`kind`); при отсутствии переменной
  источник недоступен целиком (нет fallback на localhost — так ошибка видна сразу); адреса и
  логины остаются в шаблоне (в админке), а публичный API их вырезает; примеры жёстко требуют
  роль чтения — на стенде без неё нужно задать `REP_RO_DB_USER`/`REP_RO_DB_PASSWORD`.

**ADR-76. Источники данных в шаблоне: блок connections (версия 1.49).**
- **Проблема:** параметры запросов к БД были размазаны: SQL жил в шаблоне, а адрес, база и учётная
  запись — в окружении сервера. Из-за этого один отчёт не мог читать второй PostgreSQL, а перенос
  отчёта на другой стенд требовал менять переменные процесса. Пароли в шаблон класть нельзя
  (правило проекта), а «просто разрешить» означало бы утечку секретов в БД и в админку.
- **Решение:** в шаблоне появился блок `connections`: `kind` (`postgres` | `rest`), `host`, `port`,
  `database`, `user`, `schema`, `sslmode`, `connectTimeout`, `statementTimeoutMs` и `passwordEnv` —
  **имя** переменной окружения с паролем. Наборы данных и справочники параметров ссылаются на источник
  полем `connection` (пусто или `default` — сервер из окружения). Клиенты создаются лениво и
  кэшируются по строке подключения (до 16 на процесс). Каждое внешнее соединение открывается с
  `default_transaction_read_only=on`, поэтому шаблон не может изменить данные источника. Работает
  во всех путях исполнения: `/api/report/data`, `aggregate`, `group`, `lookups`, серверный
  `.xlsx`/CSV и рассылка. Публичный `GET /api/reports/{id}` вырезает `connections`; админский
  отдаёт полностью. `rest` зарезервирован: структура валидируется, исполнение отвечает
  `422 CONNECTION_ERROR`.
- **Следствия:** один отчёт может соединять данные двух и более PostgreSQL — проверено на
  `sales-external` (продажи из БД сервера, отгрузки из `reporting_ext.warehouse`: «Восток»
  88 350 000, 1 315 заказов; сумма по регионам 410 450 000). Пароль в шаблоне — ошибка
  валидатора (`connections.<ключ>.password`), незаданная переменная — `422` с её именем.
  Клиент и сервер валят одинаково (parity 65/65). DDL на внешнем сервере не нужен: роль —
  только `SELECT`.
- **Ограничения:** один `passwordEnv` на источник, смена пароля требует перезапуска процесса
  (клиент кэшируется по строке подключения); `rest` пока только структура — ни заголовков, ни
  маппинга ответа; внешние источники не участвуют в `live`-обновлении по событиям (событие —
  публикация шаблона, а не изменение чужой БД), поэтому кэш в 60 с остаётся единственным
  ограничителем частоты; число источников ограничено 16 на процесс; `default` нельзя объявить
  как `rest`; реквизиты источника видны в админке любому автору — отдельного права на просмотр
  блока не вводилось.

**ADR-75. Эксплуатационные роли БД: owner, srv, ro (версия 1.48).**
- **Проблема:** сервер работал под одной ролью `rep_app`, которая была ещё и владельцем схем и таблиц:
  то есть могла выполнять DDL. Отчётность читалась под `reporting_ro`, но граница «кто владеет структурой»
  и «кто работает с данными» не была разведена. Требование эксплуатации — суперпользователь только для
  разработки и развёртывания; на практике же ничто не мешало поднять сервер под `postgres` или владельцем.
- **Решение:** три роли с разными правами. `reporting_owner` — владелец схем и таблиц, под ней идут DDL и
  миграции (`REP_OWNER_DB_*`, только на развёртывании). `reporting_srv` — под ней работает сам сервер
  (`PGUSER`): SELECT/INSERT/UPDATE/DELETE в `reports`, USAGE на последовательности ядра, чтение
  `reports_examples`; CREATE в схеме запрещён. `reporting_ro` — прежняя роль только-чтения, видит только
  `reports_examples`. Роль `rep_app` переименована в `reporting_owner`, чтобы владение объектами сохранилось
  без переназначения. Права выдаёт `db/roles.sql` (GRANT + ALTER DEFAULT PRIVILEGES), `db/init.sh` выполняет
  DDL под владельцем. При старте сервер проверяет `current_user`: под суперпользователем пишет WARN, а с
  `REP_STRICT_ROLE=1` — отказывается запускаться; `/api/health` отдаёт `dbUser` и `superuser`.
  Роли `reporting_srv` и `reporting_ro` создаёт и обновляет `scripts/db-users.sh`: пароли из
  `backend/.env` или генерация, права — владельцем объектов через `db/roles.sql`, затем проверка
  (вход по паролю, DML в ядре, запрет записи в примеры и `CREATE` для сервера, закрытое ядро
  для зрителя). `--rotate` меняет оба пароля и обновляет `.env`, `--password-stdin` берёт
  пароли из stdin — сами пароли в лог не попадают.
- **Следствия:** сервер под `reporting_srv` выполняет все админские операции — создание и публикацию
  шаблонов, пользователей, подписки, выгрузку журнала, удаление — проверено на живом стенде; попытка
  `CREATE TABLE` и запись в примеры упирается в права («нет доступа к схеме reports» / «нет доступа к
  таблице sales»). Под суперпользователем с `REP_STRICT_ROLE=1` сервер завершается с кодом 1 и понятным
  сообщением; без флага — работает с предупреждением (стенд).
- **Ограничения:** роль `reporting_srv` может читать всё, что читает приложение, и удалять данные ядра —
  разделение на «чтение» и «администрирование» внутри сервера не делается (это одна роль на процесс);
  `reporting_ro` не имеет доступа к ядру вовсе, поэтому у неё не работают админские запросы; владелец
  объектов не может быть удалён без переназначения владения (переименование безопасно, DROP — нет);
  пароль владельца лежит в `.env` рядом с паролем сервера — для эксплуатации его надо держать отдельно.

**ADR-74. Схемы `reports` (ядро) и `reports_examples` (примеры) (версия 1.47).**
- **Проблема:** в одной базе лежали и продукт, и демонстрация: `report_templates`, `users`, `sessions`,
  `audit_log`, `report_subscriptions` соседствовали с `sales`, `finance`, `ops`, `regions` в `public`.
  Из-за этого ядро нельзя было поставить на чистую базу без синтетики, а «где кончается продукт и начинаются
  примеры» определялось только по имени таблицы. Скрипт `db/schema.sql` был и ядром, и демо-данными сразу,
  миграции создавали таблицы ядра без схемы.
- **Решение:** ядро живёт в схеме `reports` (`db/core.sql`: шаблоны, история версий, пользователи, сессии,
  рассылка, журнал), примеры — в `reports_examples` (`db/examples/schema.sql` + `db/examples/seed.sql`).
  Приложение подключается с `search_path=reports` (`REP_DB_SCHEMA`), пул только-чтения — с
  `search_path=reports_examples` (`REP_RO_DB_SCHEMA`); psql-скрипты получают `PGOPTIONS=-c search_path=reports`
  из `scripts/env.sh`. SQL шаблонов указывает примеры явно: `reports_examples.sales`. `db/init.sh` умеет
  ставить только ядро (`--core-only`), только примеры (`--examples-only`) или всё вместе. Миграции
  квалифицированы схемой `reports` и остаются идемпотентными.
- **Следствия:** `./db/init.sh --core-only` на чистой базе даёт ровно семь таблиц ядра и ни одной таблицы
  примеров; сервер отвечает `db: true`, каталог пуст, отчёты примеров честно не находят данных. Полная
  установка даёт 4 таблицы примеров и 50 000/576/540 строк, 20 шаблонов загружаются через API, отчёт
  «Сводная таблица продаж» отдаёт 2 748 строк. Роль `reporting_ro` видит только `reports_examples`.
- **Ограничения:** шаблон, обращающийся к таблице без схемы, получает `relation does not exist` — это
  осознанно, но старые шаблоны и пользовательские копии надо править вручную; одна база по-прежнему содержит
  обе схемы (разделение логическое, не по базам); миграции рассчитаны на схему `reports`, базы, созданные до
  ADR-74, требуют переноса таблиц из `public` (в dev-базе проще пересоздать через `scripts/dev-db-init.sh`).

**ADR-73. Сборка под Windows/MSVC (версия 1.46).**
- **Проблема:** сервер собирался только под Linux: `main.cc` и `smtp.cc` напрямую звали POSIX-сокеты
  (`<sys/socket.h>`, `bind`, `close`, `ssize_t`), расписание подписок опиралось на `timegm`, а проверка
  порта использовала `sockaddr_in` из `<netinet/in.h>`. Под MSVC этого нет: сборка падала на первом же
  заголовке, а русский текст в строках без `/utf-8` превращался в мусор.
- **Решение:** платформенные различия собраны в `backend/src/net.h` и `net.cc`: тип `socket_t`
  (`SOCKET`/`int`), `create/valid/closeSocket`, `setIoTimeout` (DWORD против `timeval`), `portFree`,
  `lastError/errorText` (Winsock не пишет в `errno`), `startup()` (WSAStartup) и `timegmUtc`
  (`_mkgmtime` под MSVC). Остальной код о платформе не знает. В CMake: `ws2_32`, определения
  `WIN32_LEAN_AND_MEAN`/`NOMINMAX`/`_WIN32_WINNT`, флаги MSVC `/utf-8 /bigobj /permissive-` и CRT `MD/MDd`;
  `REP_SOURCE_DIR` для тестов прогоняется через `file(TO_CMAKE_PATH)`, иначе обратный слэш в пути ломает
  литерал. Добавлены `backend/CMakePresets.json` (пресеты `windows-msvc`, `windows-msvc-ninja`,
  `linux-release`), профиль Conan v1 `backend/conan/profiles/windows-msvc2022` и `scripts/build.ps1`.
- **Следствия:** под Windows достаточно `.\scriptsuild.ps1`: скрипт проверяет Conan v1, ставит
  зависимости, конфигурирует пресет, собирает и прогоняет ctest. На Linux сборка не изменилась:
  `cmake --preset linux-release` и прежний `scripts/build.sh` дают тот же бинарник, 68 тестов (340 проверок)
  зелёные, `net.cc` в POSIX-ветке сводится к обёрткам над системными вызовами.
- **Ограничения:** сборка MSVC не проверена прогоном — Windows-машины в проекте нет; инструкция
  `docs/build-windows.md` содержит типовые ошибки (Conan 2.x, отсутствие DLL в PATH, CRT MD/MDd, CP866 в
  консоли), но первый реальный прогон может потребовать правок. Windows-версия проверки порта и SMTP
  использует Winsock, поведение таймаутов задаётся миллисекундами; отдельной Windows-сборки в CI нет.

**ADR-72. Переход из цепочки уровней sankey (версия 1.45).**
- **Проблема:** drill у диаграмм подставлял `x` и `series` — для пары «источник → приёмник» этого хватало.
  У цепочки уровней (ADR-68) конец связи может быть категорией или товаром, и одинаковые подстановки означали
  разное на разных уровнях: клик по связи «категория → товар» отправлял категорию в параметр региона. Поэтому
  в примере `sales-path` перехода не было вовсе — диаграмма выглядела многоуровневой, но дальше не вела.
- **Решение:** модель sankey хранит у каждого узла `level`, `raw` и карту `levels`, а у каждой связи — карту
  значений двух её концов (`{region: 'Восток', category: 'Электроника'}`) и номера уровней. В `drill.params`
  появились ссылки `level.<поле>` (значение уровня) и `node` (значение кликнутого узла); прежние `x`/`series`
  и `param.<name>` работают как раньше. Сборка параметров вынесена в `engine/drill.js`: `drillAllowed()`
  проверяет, что в кликнутом элементе есть все требуемые уровни, `resolveDrill()` собирает пары «параметр —
  значение». Если уровня нет, переход не выполняется — ни в диаграмме, ни на втором рубеже в `ReportViewer`,
  чтобы в детали не уходил фильтр шире клика. Валидатор (клиентский и серверный) принимает `level.*` только
  у sankey с `levels` и проверяет, что поле есть в цепочке.
- **Следствия:** `sales-path` ведёт в «Продажи: детали по региону и категории»: клик по связи «Восток →
  Электроника» открывает 138 строк за 1–10 марта с заполненными регионом и категорией и сохранённым периодом.
  Клик по связи «категория → товар» или по узлу перехода не даёт — регион в них не участвует. Пять юнит-тестов
  закрепляют сборку параметров, включая случай отсутствующего уровня и нулевые значения.
- **Ограничения:** таблица переходов не поддерживает два drill'а с разными уровнями — один блок ведёт в один
  отчёт; переход по узлу возможен только если drill ссылается на один уровень (`node` или `level.<поле>` этого
  уровня); клик по ленте в браузере нельзя отличить от клика по узлу, когда лента нарисована поверх, поэтому
  запрет «не хватает уровня» проверяется юнитом, а не e2e; значения уровней уходят в URL как есть, длинные
  цепочки дают длинный адрес.

**ADR-71. Порядок деталей группы и полное раскрытие (версия 1.44).**
- **Проблема:** раскрытая группа шла в порядке, который выбирала база: если SQL набора не задавал `ORDER BY`,
  сервер сортировал строки по их тексту (`row_to_json`), чтобы страницы не пересекались. Пользователь видел
  «Аксессуары, 98 800, 23 300…» без смысла: полезные строки (самая крупная прибыль, свежая дата) могли оказаться
  на последней странице. Второе: «Развернуть всё» грузило только первую страницу каждой группы — кнопка
  обещала «всё», а в таблице оставалось по 200 строк и висели кнопки «ещё N».
- **Решение:** у табличного блока появилось поле `detailOrder: [{field, dir?}]` (1…4 поля, только вместе
  с `aggregate`); клиент передаёт его в `POST /api/report/group`, сервер проверяет каждое поле как идентификатор
  и `dir` как `asc|desc`, ставит `ORDER BY d.<поле> <dir>, … , row_to_json(d)::text` — текст остаётся последним
  ключом, чтобы строки с равными значениями не «плавали» между страницами. Если `detailOrder` нет, порядок
  по-прежнему берётся из набора, а при его отсутствии — по содержимому строки. «Развернуть всё» теперь тянет
  каждую группу до конца страницами, но с общим потолком 20 000 строк на операцию; что не влезло — остаётся
  кнопкой «ещё N».
- **Следствия:** `sales-aggregate` показывает детали по прибыли (24 400 → 23 800 → 23 300…), стык страниц
  200/201 не рвёт порядок, постраничная выборка совпадает с полной один-в-один. «Развернуть всё» на пяти
  группах (2 748 строк) — 16 запросов и около 2 секунд, после чего «0 свёрнуто» и ни одной кнопки «ещё».
- **Ограничения:** `detailOrder` ссылается только на колонки, которые выбирает набор данных — поле вне SELECT
  даст ошибку базы (422), это проверяется на первом же запросе; сортировка по неуникальному ключу опирается
  на текстовый tiebreak, то есть при равных значениях порядок произвольный, но стабильный; потолок 20 000 строк
  на «Развернуть всё» — на очень широком периоде часть групп останется с кнопкой «ещё»; сортировка выполняется
  базой, отдельного индекса под неё проект не создаёт.

**ADR-70. Порционная подгрузка деталей группы (версия 1.43).**
- **Проблема:** раскрытие группы забирало до 5000 строк одним запросом и одним куском в таблицу: на «Электронике»
  это 689 строк, на широком периоде — тысячи. Ответ ждать долго, браузер рендерит всё разом, а если строк больше
  предела, остаток просто отсутствует — «показано 5000 из 12 000» без способа добрать. Второй дефект увиделся на
  тестах: повторная загрузка того же набора (автовыбор параметров даёт два запроса подряд) сбрасывала раскрытие
  и кэш деталей, то есть только что открытая группа схлопывалась сама.
- **Решение:** маршрут `POST /api/report/group` принимает `offset` (по умолчанию 0) и `limit` (страница 200,
  потолок 5000) и возвращает `offset`, `limit`, `hasMore` рядом с `total`; `total` считается `count(*) OVER ()`
  по всему отфильтрованному набору, поэтому известен на любой странице. Страницы не должны пересекаться: если SQL
  набора не задаёт `ORDER BY`, сервер сортирует по содержимому строки (`row_to_json(d)::text`) — иначе LIMIT/OFFSET
  на разных планах мог бы вернуть строку дважды и потерять другую. Клиент просит по 200 строк, копит их в том же
  `details` и показывает в панели кнопку «ещё N · имя группы» на каждую недогруженную группу; подсказка
  «в группах показано N из M» обновляется. Сброс раскрытия и кэша теперь идёт по отпечатку набора (длина и крайние
  строки): пришёл тот же набор — состояние не трогаем.
- **Следствия:** группа «Электроника» (689 строк) открывается за один запрос 200 строк и добирается тремя кликами
  до 689; мультимножество четырёх страниц совпадает с полной выборкой — ни потерь, ни дублей. Свернуть и раскрыть
  снова — запросов нет (кэш). Повторная загрузка того же набора больше не сворачивает группу.
- **Ограничения:** сортировка по содержимому — не «естественный» порядок строк: если набор не задаёт `ORDER BY`,
  детали идут по тексту строки, а не по дате или id; при смене данных между страницами (параллельная вставка) строки
  могут сдвинуться — согласованность страниц ограничена моментом запроса; кэш живёт до смены набора строк или
  перезагрузки страницы, межвкладочного обмена нет; «Развернуть всё» по-прежнему грузит по одной странице на группу.

**ADR-69. Несколько коридоров в band (версия 1.42).**
- **Проблема:** полоса знала ровно две границы (ADR-58): `lowField` и `highField`. Для «время ответа: значение,
  разброс по сервисам, среднее ± σ» нужны два диапазона сразу — на одном графике они сравнимы глазами, а двумя
  графиками сравнивать приходится в голове. Обойти ограничение шаблоном было нельзя: второй коридор рисовать
  нечем.
- **Решение:** необязательное поле `bands: [{lowField, highField, color?, name?}]` (1…4 коридора) заменяет пару
  `lowField`/`highField`; пара остаётся рабочим вариантом. Каждый коридор рисуется своим стеком (`band-<i>`), иначе
  основание второго начиналось бы от верха первого; цвет берётся из `bands[].color` (токен палитры разрешается),
  без него — из прежнего `bandColor`, дальше — из встроенного набора. Узор остался прежним: невидимое основание
  плюс закрашенная разница «верх − низ» со прозрачностью 0.22, линия значения сверху. Подсказка перечисляет
  значение и все коридоры, под графиком появляется расшифровка цветов (при двух и более коридорах). Правила
  (1…4 коридора, границы разные и не совпадают со значением, `bands` только для band) продублированы на сервере,
  parity закреплена 7 фикстурами.
- **Следствия:** отчёт `ops-corridors` показывает 31 день сразу с двумя диапазонами: широкий (min…max по сервисам)
  и узкий (среднее ± стандартное отклонение, считается в SQL через `stddev_pop`); подсказка на 10 марта даёт
  «значение 319, разброс 244…394, среднее ± σ 267,8…370,2». Прежние шаблоны с одной полосой не изменились,
  кроме служебных имён рядов (`__band_low_0`).
- **Ограничения:** коридоров не больше четырёх (больше цветов не различить и легенда перестаёт читаться);
  коридоры не упорядочиваются по величине — порядок задаёт шаблон, и при пересечении диапазонов верхний закрашивается
  поверх нижнего; в Excel и печать полосы не попадают (диаграммы не экспортируются, ADR-28); `bands` с
  вычисляемыми колонками не работает — считаются только поля из SQL.

**ADR-68. Многоуровневый sankey (версия 1.41).**
- **Проблема:** sankey умел только пару «источник → приёмник» (ADR-56). Для «пути продажи» нужна цепочка
регион → категория → товар: без неё отчёт показывает один шаг, а остальное собирают в голове. Плюс узлов на
последнем уровне десятки, и на высоте 320 px подписи наезжают друг на друга — высоту диаграммы нельзя было
задать из шаблона.
- **Решение:** поле `levels: [поле, …]` (2…4) заменяет `sourceField`/`targetField`: связи строятся между
соседними уровнями, вес агрегируется по парам так же, как раньше (`sum|avg|min|max|count`), строки с пустым
уровнем отбрасываются. Узлы нумеруются префиксом уровня (`0\u0001Восток`), иначе одинаковые названия на разных
уровнях склеились бы в один узел и путь посчитался бы неверно; подпись и тултип показывают исходное значение.
Правила `sourceField`/`targetField`/`levels` (взаимоисключение, 2…4 уровня, уникальность полей) живут в
семантическом валидаторе и продублированы на сервере, parity закреплена 5 фикстурами. Добавлено поле
`height` (240…900 px) для блока диаграммы и `nodeAlign: justify` у sankey.
- **Следствия:** шаблон `sales-path` («Путь продажи: регион → категория → товар») рисует 49 узлов и 60 связей
на трёх уровнях; сумма на входе и на выходе совпадает (150 892 900), то есть поток не теряется; при 620 px
подписи читаются. Пара `source/target` продолжает работать без изменений.
- **Ограничения:** 4 уровня — предел, дальше цепочка не помещается в ширину; одинаковые названия внутри одного
уровня сливаются (это ожидаемо), но между уровнями не различить визуально, если имя повторяется — помогает
только смысл полей; drill в цепочке уровней настраивается на конкретную пару `x`/`series` и для средних
уровней подставляет не то, что ждёт получатель, поэтому в примере drill не настроен.

**ADR-67. Выгрузка журнала действий (версия 1.40).**
- **Проблема:** журнал `audit_log` живёт под ретеншеном (ADR-59) и чистится по сроку безвозвратно, а снять с
него архив было нечем: только `GET /api/admin/audit` со страницами по 50 записей. Внедрение, где журнал
нужен для разбора инцидента или передачи в SIEM, оставалось с «посмотрите в интерфейсе, пока не удалилось».
- **Решение:** `GET /api/admin/audit/export.csv` с теми же фильтрами, что у списка (`action`, `actor`), плюс
период `from`/`to` (даты ГГГГ-ММ-ДД) и предел `limit` (по умолчанию 100 000, максимум 200 000). Формат по
умолчанию — RFC 4180: UTF-8 **без BOM**, запятая, CRLF, ISO-8601 в UTC, порядок по возрастанию времени (так
файл удобно дописывать и сравнивать). `excel=1` переключает на BOM и `;` — для открытия двойным щелчком.
Если записей больше лимита — `422 AUDIT_LIMIT` с числом записей и подсказкой сузить период, а не молча
обрезанный архив. Сама выгрузка пишется в журнал действием `audit.export` с числом строк и фильтрами.
На странице журнала появились поля периода и две ссылки выгрузки, несущие текущие фильтры.
- **Следствия:** архив снимается до чистки и совпадает с тем, что видно на экране; факт выгрузки (кто, когда,
сколько записей, с какими фильтрами) остаётся в журнале; CSV читается и Excel, и парсером SIEM.
- **Ограничения:** файл собирается в памяти целиком, потоковой отдачи нет — для журналов в миллионы строк
нужен отдельный архиватор; автоматической отправки в SIEM (syslog/HTTP) нет, только скачивание; подписи и
контрольной суммы у файла нет; выгружать может только роль `admin`; удалённые ретеншеном записи выгрузка,
разумеется, не вернёт — только то, что ещё лежит в таблице.

**ADR-66. Подытоги и ИТОГО в серверном Excel (версия 1.39).**
- **Проблема:** серверный `.xlsx` (ADR-38/49) выгружал плоский список детальных строк с объединениями и
outline-уровнями, но без строк «Итого …» и общего итога: книгу нельзя было читать как отчёт — суммы
приходилось считать глазами, а письмо по расписанию отличалось от экрана. Хуже того, в коде жили **две**
сборки листа: отдельный обработчик `/api/report/export.xlsx` со своей копией и общий `buildSheet` для CSV
и рассылки, поэтому любое улучшение доставалось только одному пути.
- **Решение:** одна функция группировки листа `buildGroupedSheet` (модуль `group_rows`): строка «Итого <ключ>» на
уровне, объявленном в шаблоне (`columns[].subtotal`), общий итог последней строкой (`grandTotal`, по умолчанию
включён), суммы по колонкам с `aggregate`, предки сохраняют свои значения, пустой ключ — `(пусто)`.
Объединения считаются по правилу экрана: строка итога уровня L входит в объединения колонок-предков, но не
своей колонки. Строки итогов оформлены как зоны (жирный, светлый фон, у ИТОГО линия сверху). Обработчик
`/api/report/export.xlsx` переведён на общий `buildSheet`, вторая копия удалена; CSV (`dropSummaryRows`)
остаётся машинным — без строк итогов.
- **Следствия:** файл, письмо и экран совпадают по числам: «Сводная таблица продаж» 1–10 марта —
2 748 детальных строк, 6 подытогов (пять регионов и `(пусто)`), ИТОГО 150 977 000 / 31 013 250 — те же числа,
что в модели на экране; «Финансы: план и факт» — 6 подытогов по месяцам и ИТОГО 1 661 216 000. Outline
работает: детали на уровне глубины группировки, подытоги выше.
- **Ограничения:** суммы считаются по колонкам с `aggregate`; вычисляемые колонки (выражения) в итогах
остаются пустыми, как и раньше, — сервер их не считает. CSV сознательно без итогов: машинному потребителю
они мешают, а эквивалентный итог он получает своим `GROUP BY`. Подытоги выгружаются всегда раскрытыми
(состояние сворачивания в браузере на файл не влияет), а строки итогов не участвуют в автофильтре.

**ADR-65. Раскрытие группы серверной агрегации подгружает детали (версия 1.38).**
- **Проблема:** в отчёте «Продажи: агрегация на сервере» у каждой категории был шеврон, но раскрытие
ничего не показывало: сервер по ADR-37 отдаёт ОДНУ строку на группу (`GROUP BY`), деталей в модели нет,
и шеврон обещал то, чего интерфейс сделать не мог. Заодно нашлось, что роль `viewer` получала 403 на
`/api/report/aggregate` (и на экспорт, и на поток изменений): в матрице прав для чтения был перечислен
только `/api/report/data`, остальные маршруты чтения попадали в правило «неизвестный путь — admin»,
поэтому у зрителя агрегированный отчёт показывал одно ИТОГО.
- **Решение:** новый маршрут `POST /api/report/group` — детали одной группы из того же набора данных:
SQL набора идёт подзапросом (`SELECT count(*) OVER () AS __group_total, d.* FROM (<sql>) d WHERE d.<field> = $N`),
поле фильтра берётся из groupBy блока и проверяется как идентификатор, значение уходит параметром, `NULL`
превращается в `IS NULL`. Предел — 5000 строк, `total` приходит всегда. Клиент при раскрытии группы
(если у блока есть объект `aggregate`) грузит её строки, кладёт их в модель как детальные, а строку итога
строит из **серверной** строки, а не из загруженной части; при обрезке в панели блока появляется
«в группах показано N из M строк». Матрица прав: все `/api/report/*` — чтение для `viewer`.
- **Следствия:** в примере марта раскрытие «Аксессуаров» даёт 685 строк вместо одной, итог группы остаётся
37 634 100, общий ИТОГО — 150 977 000 (не пересчитан по загруженной части); зритель видит агрегированный
отчёт целиком. Один запрос идёт в момент клика, остальное — как раньше. Группы агрегата стартуют
**свёрнутыми** (▸): строк в браузере ещё нет, и показывать «раскрыто» при пустой группе — обещание без данных;
первый клик и подгружает строки, и раскрывает. «Развернуть всё» подгружает все группы (по лимиту на каждую).
- **Ограничения:** детали грузятся только по одной группе и не кэшируются на сервере (клиент помнит их до
перезагрузки данных); лимит 5000 строк на группу, при большем объёме видна подсказка, догрузки «ещё» нет;
итог группы всегда серверный, поэтому суммы в раскрытой группе и в её строке итога могут не совпадать,
если группа обрезана; сводные строки внутри группы (подуровни) не появляются — группировка остаётся
одноуровневой, как её отдал `GROUP BY`.

**ADR-64. Ширины колонок виртуализированной таблицы считаются по модели (версия 1.37).**
- **Проблема:** контрольные замеры дали два дефекта под шапкой у сгруппированных таблиц. Первый: на месте
разреза объединения (прозрачная ячейка + подпись) рисовалась горизонтальная линия — она читается как
граница группы, хотя группа продолжается, и при прокрутке линия «всегда сверху». Второй: при
`table-layout: auto` ширину колонки задаёт **набор строк, попавших в окно**: пока в окне детальные строки,
колонка узкая, но как только в окно входит строка итога с более длинной подписью («Итого 01.10.2025»),
колонка скачком расширяется, таблица выходит за контейнер и появляется горизонтальная прокрутка; при
уходе строки всё сжимается обратно. Окно меняется на каждом шаге прокрутки — таблица «дышит».
- **Решение:** ширины колонок вычисляются **по всей модели** (самые длинные тексты шапки и зон, измерение
через `canvas.measureText` с шрифтами зон), подставляются в `<colgroup>`, раскладка всегда `fixed`;
вычисленные ширины сжимаются пропорционально, если сумма не влезает в контейнер (явные ширины шаблона не
трогаются); ширина контейнера отслеживается `ResizeObserver`. Прозрачная ячейка разреза получила класс
`phantom` без нижней границы и без фона. Поле `layout.tableLayout` принимается, но на раскладку не влияет.
- **Следствия:** ширины не меняются ни при прокрутке (замер: одна и та же строка ширин на 90 позициях),
ни при попадании строки итога в окно; таблица не выезжает за контейнер; в 9 отчётах обрезанных ячеек — 0.
Два новых e2e закрепляют это и падают на прежней версии компонента.
- **Ограничения:** ширина считается по длине строк, а не по реальной отрисовке шрифта для каждой ячейки:
  самый длинный текст выбирается по числу символов из 12 кандидатов, поэтому редкий «широкий» символ может
  получить запас в 4 px, а не точную ширину. При экзотическом шрифте с широкими глифами возможен многоточие;
  ширина колонки не интерактивна — пользователь не может растянуть её мышью.

**ADR-63. Окно виртуализации и подпись группы при прокрутке (версия 1.36.1).**
- **Проблема:** у отчётов с объединёнными групповыми колонками при прокрутке между липкой шапкой и
первой строкой появлялась пустая полоса — от 30 до 48 px («Финансы: план и факт по центрам затрат»).
Причина: окно начиналось со строки, чей верх лежит НИЖЕ шапки, а предыдущая, частично видимая строка не
рендерилась; к этому добавлялся сдвиг на высоту шапки (`scrollTop + headerHeight`), который был нужен,
чтобы подпись группы не рисовалась под шапкой. Ещё один дефект того же узла: при свёртывании группы
модель сокращается, элемент прокрутки молча упирается в новый максимум, событие `scroll` не приходит —
окно остаётся посчитанным по прежнему `scrollTop`, и таблица показывает хвост с пустотой сверху.
- **Решение:** окно начинается со строки, которая пересекает верх окна (`lowerBound(offsets, scrollTop)`
и шаг на строку назад), поэтому видимый остаток предыдущей строки закрывает полосу. Подпись группы
переносится: объединение режется на две ячейки — прозрачную часть под шапкой (держит выравнивание
колонок) и подпись, начинающуюся на первой полностью видимой строке; текст берётся у головы серии,
потому что в остальных строках группы значение групповой колонки пустое. После изменения модели
`scrollTop` пересчитывается от элемента (`watch` + `nextTick`).
- **Следствия:** полоса исчезла (замер: 42 px → 0 при `scrollTop=400`), подпись и шеврон всегда видны
под шапкой, свёртывание после прокрутки возвращает окно к началу, e2e это проверяет (2 новых теста).
- **Ограничения:** строка, попавшая под шапку, видна частично и обрезана посередине — так ведёт себя и
обычная таблица без виртуализации; в печатном слое окно не используется, там рендерится вся модель.
Прокрутка остаётся по строкам, а не по пикселям: шапку нельзя «протащить» поверх первой строки.

**ADR-62. Заём подписки и устойчивость отправки (версия 1.36).**
- **Проблема:** «заём» подписки на время отправки был зашит в SQL двумя минутами: при медленной сборке
файла второй экземпляр успевал взяться за ту же подписку, а при быстрой — подписка оставалась занятой
дольше нужного. Кроме того, попытка попадала в журнал только после завершения: падение процесса
в середине отправки не оставляло следа, и никто не знал, ушло письмо или нет.
- **Решение:** длительность заёма задаётся `REP_SUBSCRIPTION_LEASE_SECONDS` (120 с по умолчанию,
10…3600), период планировщика — `REP_SCHEDULER_TICK_SECONDS` (30 с). Попытка пишется в
`subscription_runs` до отправки (`finished_at = NULL`), в конце та же строка обновляется результатом;
при старте незавершённые попытки старше заёма закрываются как прерванные. Журнал отправок показывает
только завершённые строки. Добавлен частичный индекс `subscription_runs_open_idx`.
- **Следствия:** обрыв процесса больше не «тихий»: в журнале есть прерванная попытка, подписка
освобождается через заём и отправка повторяется. Медленная сборка файла не приводит к двойной отправке,
если заём больше времени сборки.
- **Ограничения:** доставка — at-least-once: обрыв ровно в момент передачи письма может дать дубль,
избежать этого без транзакции на SMTP нельзя. Заём — время, а не сердцебиение: при сборке дольше заёма
второй экземпляр всё равно возьмётся за подписку, поэтому значение надо держать выше худшего времени
сборки. Прерванные попытки закрываются только при старте процесса — на живом экземпляре строка
с `finished_at = NULL` может висеть, если поток отправки завис.

**ADR-61. Повтор отправки рассылки при сбое SMTP (версия 1.34).**
- **Проблема:** Сбой почтового сервера не должен терять выпуск: раньше единственной попыткой дело и заканчивалось, в журнале оставался `ok=false`.
- **Решение:** Повтор планируется в БД (`retry_count`, `retry_at`), а не сном в потоке. Пауза растёт экспоненциально (60 → 120 → 240 с, настраивается). Повтор не сдвигает `next_run_at`. При выборе подписки планировщик ставит «заём»: `next_run_at` уезжает вперёд на 2 минуты и перезаписывается настоящим расписанием в конце отправки. Номер попытки — в `subscription_runs.attempt`, исчерпание — в журнал действий (`subscription.given_up`). Ручной запуск повторов не планирует.
- **Следствия:** Письмо не теряется при кратком сбое; при двух экземплярах не уходит дважды (заём закрывает окно на всё время отправки).
- **Ограничения:** Очередь не персистентна на уровне писем: падение процесса во время отправки не переотправит письмо; суммарная длительность серии повторов ограничена только числом попыток и задержкой.

### 5.2 Грамматика выражений (полностью закрытая)

```ebnf
expr    := add
add     := mul (('+' | '-') mul)*
mul     := unary (('*' | '/') unary)*
unary   := '-'? primary
primary := NUMBER | 'null' | 'true' | 'false'
         | field | agg
         | '(' expr ')'
field   := IDENT | '[' IDENT ']'      (* IDENT: [A-Za-z_][A-Za-z0-9_]* *)
agg     := ('sum'|'avg'|'min'|'max'|'count'|'countDistinct') '(' expr? ')'
```

Семантика:
1. Область действия выражения — строка, для которой оно вычисляется. Для детальной строки область = эта строка; для строки промежуточного итога — соответствующая группа; для общего итога — весь набор.
2. `field` в строке итога разрешается в значение группового ключа или в агрегат по этому полю, если поле не является ключом группировки.
3. `agg(e)` агрегирует `e` по детальным строкам текущей области; `count()` без аргумента — число детальных строк области.
4. Вычисляемые колонки пересчитываются на **каждом** уровне области (детальная строка, каждый уровень группировки, общий итог) — та же семантика, что Scope в SSRS.
5. `null`-операнд → `null`; `/0` → `null`; `NaN`/`Infinity` → `null`.
6. Сравнений, условий (`if`), строковых функций и ссылок между блоками в v1 нет — фиксируется в `docs/expressions.md` как известное ограничение; при необходимости такие поля считаются в SQL.

### 6.1 Порядок и зависимости

```
Ф0 ──► Ф1 ──► Ф2a ──► Ф2b ──► Ф3 ──► Ф4
        │       │                  │
        └─ 1.1–1.2 (схема+API) ────┴─► 4.1 (примеры) можно готовить заранее на Ф2a
```

- Жёсткая последовательность: Ф0 → Ф1 → Ф2a → Ф2b. Причина: Ф2b зависит от плоской модели Ф2a; Ф1 даёт API и шаблон, без которых Ф2a нечего рендерить.
- Внутри Ф0 порядок: 0.0 → 0.2 → 0.3 обязательны первыми (без сборки и БД остальное не проверить); 0.4 (vxe-table) — независимо, можно параллельно с 0.3; 0.5 — после 0.2.

- 2a.2 (выражения) и 2a.3 (группировки) независимы по коду — можно вести одновременно.
- Ф8 (экспорт и печать, 1.4) идёт после Ф7; 8.1–8.3 (Excel) и 8.5 (печать) независимы.
- Ф7 (админка, 1.3) идёт после Ф6; 7.1–7.4 (бэкенд) и 7.5–7.7 (UI) можно вести параллельно, 7.8 — в конце.

- сборка с нуля по README (Conan v1 из venv, `./scripts/check.sh`) на чистом кэше;
- отсутствие ошибок в консоли браузера; бюджет рендера 50k строк ≤ 2 с до интерактивности.

## 9. Управление изменениями

- Базовый объём = этот документ. Любое требование вне его — отдельная фаза с собственной оценкой и гейтом; в текущие 52 чел.-дн. не входит.
- Изменение ADR-1…ADR-19 допускается только с записью в `docs/adr.md` и переоценкой затронутых фаз.
- Вне объёма (ТЗ §6, подтверждено): визуальный конструктор, экспорт Excel/PDF, drill-through, планировщик/рассылка, аутентификация на уровне отчётов, не-реляционные источники, справочники параметров из БД, условия/`if` в выражениях, фильтры и пользовательская сортировка таблицы.
