# Оценка: аутентификация при обращении к REST-источникам

Запрос PO: BASIC + прозрачные механизмы — NTLM/SSPI под Windows, Kerberos под Linux.
Документ отвечает на вопрос «возможно ли и сколько стоит», кода не содержит.

## Что есть сейчас

- транспорт — `drogon::HttpClient` (`rest_client.cc`, `newHttpClient` + `sendRequest`), один GET/POST
  на набор, пагинация, таймауты, allowlist хостов, кеш по `baseUrl + path + query + headers + body`;
- заголовки: `connections.<ключ>.headers` (значения могут быть `${ENV}`) и `rest.headers`
  (плейсхолдеры из наборов, ADR-118);
- секреты в шаблоне запрещены: только имя переменной окружения (`passwordEnv`, `${ENV}`);
- `drogon::HttpClient` **не умеет** ни NTLM, ни Negotiate — только «положи заголовок сам».

Значит BASIC сегодня возможен «вручную»: положить в `headers` готовый `Authorization: Basic <base64>`.
Неудобно (base64 надо готовить заранее) и опасно (значение светится в шаблоне/логах).

## Окружение (проверено на этой машине)

| Что | Статус |
|---|---|
| `libkrb5-dev`, `gssapi.h`, `libgssapi_krb5.so` | есть |
| `kinit`/`klist`/`krb5kdc`, KDC, домен | **нет** — проверить Kerberos локально не на чем |
| `libcurl` (системный и в Conan-кэше) | **нет** (в Conan есть только `openssl`, `zlib`) |
| Windows/AD для NTLM | **нет**, Windows не целевая система |

## Варианты

### 1. BASIC (на drogon, без новых зависимостей) — 0,5–1 день

```json
"connections": {
  "crm": { "kind": "rest", "baseUrl": "…",
           "auth": { "type": "basic", "userEnv": "CRM_USER", "passwordEnv": "CRM_PASSWORD" } }
}
```

Сервер сам собирает `Authorization: Basic base64(user:password)`; значения — только из окружения,
в логах и ошибках маскируются (`***`), в публичном JSON шаблона поля нет. Тесты: unit на сборку
заголовка, e2e на демо-сервис, который проверяет BASIC.

Риск: низкий. Зависимостей нет.

### 2. Kerberos / SPNEGO на Linux (GSSAPI напрямую) — 3–4 дня

`libgssapi_krb5` в системе есть, значит можно без libcurl:

1. `gss_import_name("HTTP@host")` → `gss_init_sec_context` → токен;
2. запрос с `Authorization: Negotiate <base64(токен)>`;
3. `401` + `WWW-Authenticate: Negotiate <токен>` → продолжить контекст (2–3 раунда);
4. `gss_wrap` на последующих запросах (опционально), keep-alive обязателен;
5. учётная запись — сервисная: `keytab` по пути из env, `KRB5CCNAME` для ccache, `krb5.conf` с realm.

Риски и ограничения:
- **проверить негде**: нет KDC и `kinit` — понадобится либо домен заказчика, либо локальный MIT KDC
  (установка пакетов и настройка — вне репозитория, требует прав);
- в контейнере/службе нужны `krb5.conf`, keytab с правами 600 и синхронизация часов (допуск 5 мин);
- имя SPN должно совпадать с `baseUrl` (или задаваться отдельным полем `spn`) — частая причина
  `Server not found in Kerberos database`;
- делегирования нет: сервер отчётов ходит **под своей** учётной записью, а не под учёткой
  пользователя, смотрящего отчёт; «прозрачно для пользователя» = без ввода пароля, но не «от его имени».

Оценка: 3–4 дня кода и тестов на заглушке + отдельный день на проверку с настоящим KDC.

### 3. Kerberos/NTLM через libcurl — 3–5 дней

Один клиент закрывает всё: `CURLOPT_HTTPAUTH = CURLAUTH_BASIC | CURLAUTH_NTLM | CURLAUTH_GSSAPI`
(сборка curl с GSSAPI/NTLM), `CURLOPT_USERPWD`, `--negotiate`. Но:

- `libcurl` в проекте нет — новая зависимость в Conan (лицензия MIT-подобная, ограничений не создаёт);
- придётся переписать `restFetch` на пул потоков (drogon-клиент асинхронный, curl — блокирующий),
  сохранив allowlist, таймауты, кеш, пагинацию и подсчёт строк — это и есть основная стоимость;
- NTLM в curl: только HTTP/1.1, keep-alive, не работает через прокси и с редиректами.

Оценка: 3–5 дней; из них 1–2 дня — перенос текущей логики на новый клиент.

### 4. NTLM/SSPI под Windows (своими руками) — 5–10 дней, не рекомендую

`AcquireCredentialsHandle`/`InitializeSecurityContext` + ручная сборка сообщений, Type1/Type2/Type3.
Работает только на Windows, тестировать негде, Windows выведена из целевых. Выгода против варианта 3
(тот же NTLM через curl) — только отсутствие зависимости.

## Что рекомендую

1. **Сделать BASIC сейчас** — дёшево, закрывает большинство «сервис просит логин/пароль».
2. **Kerberos делать вариантом 2 (GSSAPI), а не через libcurl** — библиотека уже в системе, не тянем
   вторую HTTP-реализацию; но планировать вместе с доступом к KDC для проверки.
3. **NTLM не делать**, пока Windows не вернётся в целевые: это единственный механизм, который
   требует libcurl или своей SSPI-реализации, и проверить его негде.

## Вопросы, без которых оценка не превращается в план

1. Кто клиент REST-сервисов: IIS с NTLM, Kerberos-прокси (SPNEGO) или обычный сервис с паролем?
   Если NTLM — нужен ли он вообще при нецелевой Windows?
2. Есть ли доступ к KDC/домену для проверки (realm, KDC-хост, тестовая служба), или писать «вслепую»
   и проверять у заказчика?
3. Учётная запись: сервисная (keytab) или нужна персонализация «от имени пользователя»
   (это уже delegation/constrained delegation — отдельная история и другие сроки)?
4. Допустима ли зависимость `libcurl` в Conan, если выберем вариант 3?

## Статус на 2026-11-16

| Вариант | Статус |
|---|---|
| BASIC | **сделано** — ADR-121: `auth: {type: "basic", userEnv, passwordEnv}`, `422 REST_AUTH` при пустой переменной, демо требует BASIC |
| Kerberos/SPNEGO (Linux, GSSAPI) | **сделано и проверено** — ADR-122: локальный KDC `REP.LOCAL`, SPNEGO-сервис, отчёт `crm-kerberos` возвращает `demo@REP.LOCAL` |
| NTLM/SSPI (Windows) | **не делаем** — Windows выведена из целевых; проверить негде |
| libcurl как второй клиент | не понадобился: GSSAPI-библиотека есть в системе |

Проверка вручную: `./scripts/dev-kerberos.sh` (KDC без root + SPNEGO-демо) и
`./scripts/check-kerberos.sh` (отчёт должен вернуть `demo@REP.LOCAL`). В CI Kerberos не проверяется —
KDC там поднимать не на чем, а GitHub Actions отключены.

Остаётся на будущее: автоматическое обновление тикета (сейчас нужен `kinit` заранее; при истёкшем
тикете сервер подсказывает команду), делегирование учётных данных (сейчас сервер ходит под своей
учётной записью) и NTLM, если Windows вернётся в целевые.
