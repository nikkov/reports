# Администрирование отчётов

Страница: `http://127.0.0.1:8080/reports/admin.html` — отдаёт сам сервер (ADR-79).

Включается переменной окружения `REP_ADMIN=1` (в `scripts/demo.sh` включена по умолчанию).
Без неё все маршруты записи отвечают `404 ADMIN_DISABLED` — в обычном режиме сервис остаётся
только для чтения, как раньше.

## Что можно делать

| Действие | Как |
|---|---|
| Создать отчёт | кнопка «Создать»: `id` (латиница, цифры, дефис) + заголовок, тело — минимальный шаблон |
| Изменить | выбрать отчёт в списке → редактор JSON (CodeMirror, подсветка, номера строк, сворачивание) |
| Дублировать | «Дублировать» → копия с `id = <id>-copy`, дальше правится как обычно |
| Удалить | «Удалить» с подтверждением вводом `id` |
| Проверить | «Проверить»: полная клиентская валидация + серверная структурная проверка |
| Сохранить | «Сохранить» (существующий → `PUT`) или «Сохранить как…» (новый `id` → `POST`) |
| Предпросмотр | «Предпросмотр (черновик)»: шаблон кладётся в `localStorage` и открывается `report.html?report=<id>&draft=1` — без записи в БД; данные и справочники считаются по телу черновика (`draft: true`), доступно автору и администратору |
| История | «История»: до 20 снапшотов, «Откатить» восстанавливает версию (сам откат тоже пишется в историю) |

Сохранение применяется **без рестарта сервиса**: сервис обновляет шаблон в памяти под мьютексом —
сначала разбор JSON, затем атомарная замена. Битый шаблон не сохраняется.

## Параметры и SQL их запросов

Под панелью действий редактора показывается секция «Параметры и их запросы»: имя, подпись, тип,
вид (`lookup`/`static`/`date`), мультивыбор, зависимость от другого параметра и **текст SQL** для
справочников. Для каждого SQL стоит метка серверной проверки: `SELECT ok` — пройдёт, `guard: не SELECT` —
сервер отклонит сохранение. У параметров без SQL (даты, статические наборы) так и написано:
«SQL не задан — параметр берёт значение из контрола».

Секция строится из текущего содержимого редактора и обновляется по мере правки, поэтому видно,
что именно уйдёт на сервер. Полный JSON с `source.sql` приходит из `GET /api/admin/reports/{id}` —
публичный `GET /api/reports/{id}` SQL вырезает.

## API

| Метод | Маршрут | Ответ |
|---|---|---|
| GET | `/api/admin/reports` | `[{id, title, size, updated}]` |
| GET | `/api/admin/reports/{id}` | сырой шаблон, **с** `source.sql` (для редактора) |
| POST | `/api/reports` | `{id, title, body}` → `{id, saved:true}`; 409 если `id` занят |
| PUT | `/api/reports/{id}` | `{body}` → `{id, saved:true}` |
| DELETE | `/api/reports/{id}` | `{id, deleted:true}` |
| POST | `/api/reports/{id}/validate` | `{body}` → `{ok:true}` или `{ok:false, error}` |
| GET | `/api/admin/reports/{id}/history` | `[{id, title, size, saved}]` (до 20) |
| POST | `/api/admin/reports/{id}/rollback/{snapshot}` | `{id, restored:true}` |

Коды ошибок — `{ "error": { "code", "message" } }`: `ADMIN_DISABLED` (404), `REPORT_EXISTS` (409),
`TEMPLATE_INVALID` (422), `REPORT_NOT_FOUND` (404), `SNAPSHOT_NOT_FOUND` (404).

## Валидация

Двухуровневая:

- **клиент** — полный валидатор (`frontend/src/template/validate.js`): схема, ссылки на колонки,
  выражения, правила, стили, параметры; ошибки показываются путём (`blocks.2.columns.4`);
- **сервер** — структурный минимум: JSON-объект, `version = 1`, `id` совпадает (сервер сам подставляет
  `id` из URL), непустой `title`, массивы `params`/`blocks`, у справочников есть `sql` и нет `queryId`,
  тело ≤ 256 КБ (`REP_MAX_TEMPLATE_BYTES`).

Серверная семантическая проверка не портировалась — это осознанный компромисс (ADR-26).

## Безопасность

- `source.sql` из шаблона исполняется сервером, поэтому админка включена только локально и только
  по флагу; наружу не выставлять;
- серверный guard справочников: SQL обязан начинаться с `SELECT`/`WITH`, не содержать `;`, `--`, `/*`
  и DML/DDL-операций;
- это **временная** мера: соединение работает под ролью `postgres`, read-only роль (задача 5.9)
  остаётся обязательной перед вынесом админки за пределы доверенного контура;
- удаление требует подтверждения, история и откат защищают от потери версии.

## Что стоит знать

- шаблон, полученный публичным `GET /api/reports/{id}`, **не содержит** `source.sql` — для редактора
  используется `GET /api/admin/reports/{id}`, иначе сохранение теряло бы SQL справочников;
- страница админки грузится отдельным чанком: CodeMirror не попадает в бандл отчёта
  (проверено: `report-*.js` — 32,8 КБ, `admin-*.js` — 589 КБ / 190 КБ gzip);
- `scripts/templates-push.mjs` по-прежнему требует рестарта: он пишет в БД в обход процесса.

## Доступ

Админка требует роль `admin` (ADR-34): без входа страница уводит на `/login.html`, для роли `viewer`
и `author` показывается «Недостаточно прав». Права проверяет сервер: `403 FORBIDDEN` на
`/api/admin/**`, публикацию, удаление и откат, поэтому скрытие кнопок — только удобство.

Роли: `viewer` — чтение отчётов; `author` — плюс создание и черновики; `admin` — плюс публикация,
удаление, история, откат. Пользователи создаются `scripts/auth-init.sh`.

## Черновик и публикация (ADR-31)

Правка существующего отчёта не попадает в отчёт сразу:

| Действие | Что происходит |
|---|---|
| «Сохранить черновик» | тело уходит в `draft`, публичный отчёт не меняется |
| «Опубликовать» | `draft` → `body`, снапшот прежней версии в историю, память обновляется без рестарта |
| «Отменить черновик» | `draft` удаляется, редактор возвращается к опубликованной версии |

Метка «черновик от …» в шапке означает, что открыта неопубликованная правка. Новый отчёт создаётся
сразу опубликованным: черновик существует только для правок.

## Проверка шаблона

Кнопка «Проверить» гоняет два валидатора: клиентский (быстро, прямо в редакторе) и серверный
(`POST /api/reports/{id}/validate`). Сервер отдаёт полный список замечаний с путями
(`blocks.0.columns.2`, `params.0.source.dependsOn`, …) и предупреждений; в панели они помечены
префиксом `(сервер)`. Сохранение и публикация проверяют шаблон заново — если шаблон невалиден,
ответ 422 `TEMPLATE_INVALID` с путём и причиной.

## Рассылка

Страница `subscriptions.html` (ссылка из админки, роль admin): список подписок и форма.
Подписка хранит отчёт, cron-расписание, параметры (JSON), получателей, формат вложения (`csv` или `xlsx`)
и флаг включения.
Рядом с каждой подпиской — следующий и последний запуск, ошибка последней отправки и кнопки
«Отправить сейчас» (не сдвигает расписание), «Выключить/Включить», «Удалить».
Журнал открывается кнопкой «Журнал» у подписки: дата и время, результат, строк, писем, длительность,
текст ошибки. После «Отправить сейчас» страница сама дожидается новой записи в журнале и показывает итог.
То же доступно по API: `GET /api/admin/subscriptions/{id}/runs?limit=20`.

## Журнал действий

`audit.html`: таблица «когда — кто — действие — объект — детали — адрес», фильтры по действию и
пользователю, постраничная загрузка. Пишутся публикация/сохранение/удаление/откат шаблонов,
создание и изменение пользователей, действия с подписками, вход (в том числе неудачный).
Детали содержат только безопасные поля — пароли и тела шаблонов в журнал не попадают.

**Выгрузка (ADR-67).** Журнал чистится по сроку (`REP_LOG_RETENTION_DAYS`) безвозвратно, поэтому архив
снимают заранее:

```bash
# для SIEM: UTF-8 без BOM, запятая, CRLF, ISO-8601 UTC, от старых к новым
curl -b cookie.txt -o audit.csv 'http://127.0.0.1:8080/api/admin/audit/export.csv?from=2026-11-01&to=2026-11-08'

# для Excel: BOM и точка с запятой
curl -b cookie.txt -o audit.csv 'http://127.0.0.1:8080/api/admin/audit/export.csv?excel=1'
```

Фильтры те же, что у списка: `action`, `actor`, плюс `from`/`to` (ГГГГ-ММ-ДД) и `limit` (по умолчанию
100 000, максимум 200 000). Если записей больше лимита — `422 AUDIT_LIMIT` с числом записей: сузьте период.
Сама выгрузка пишется в журнал действием `audit.export` с числом строк и фильтрами. На странице журнала
есть поля периода и две ссылки — «Выгрузить CSV» и «Excel».

## Расписание и повторы отправки

Подписка хранит часовой пояс (`UTC`, `Europe/Moscow`, `Asia/Novosibirsk`…): время cron считается
по нему, а не по времени сервера. Если SMTP недоступен, сервер сам повторяет отправку —
пауза растёт (60, 120, 240 с по умолчанию), в списке подписок видно «повтор ДД.ММ ЧЧ:ММ (попытка N)».
После исчерпания попыток повтор снимается, а в журнале действий появляется `subscription.given_up`.
Ручное «Отправить сейчас» повторов не планирует: ошибку сразу видит человек.

Попытка пишется в журнал **до** отправки. Если процесс остановили посреди отправки, строка
останется незавершённой и при следующем старте закроется с ошибкой «прервано: процесс остановлен»;
через `REP_SUBSCRIPTION_LEASE_SECONDS` подписка освободится и отправка повторится. Доставка —
**at-least-once**: при обрыве ровно в момент отправки письмо может прийти дважды, но не пропадёт.

## Вход через реверс-прокси

Если приложение стоит за прокси, который сам проверяет пользователя, включите `REP_AUTH=proxy`:
имя приходит в заголовке `X-Remote-User`, роль берётся из справочника `users`. Заголовку сервер
верит только с адресов `REP_AUTH_PROXY_TRUSTED`. Неизвестный логин — отказ 403; чтобы такие
пользователи заводились автоматически (роль `viewer` по умолчанию, без пароля), задайте
`REP_AUTH_PROXY_AUTOCREATE=1`. Автосоздание видно в журнале как `user.autocreate`.

### Доменные учётные записи (ADR-93)

Прокси обычно передаёт имя вместе с доменом — `CORP\ivanov` (Windows) или
`ivanov@corp.example` (UPN). Поэтому в админке:

- **логин** — латинские буквы в любом регистре, цифры, `_`, `.`, `-`, `\`, `@`; длина 3…128.
  Доменные имена хранятся как пришли, с регистром;
- сравнение логинов — **без учёта регистра**: `CORP\ivanov` и `corp\Ivanov` — одна учётная запись
  (уникальный индекс `users_login_lower_key`), поэтому прокси может присылать имя в любом регистре;
- **пароль можно не задавать**: пустое поле создаёт учётную запись без пароля — вход для неё
  возможен только через доверенный прокси (попытка входа по паролю вернёт 401). Пароль можно
  задать позже кнопкой «Пароль» в списке — тогда заработает и обычный вход;
- проверки в `scripts/check-proxy-auth.sh`: доменный логин, другой регистр того же логина
  (запись остаётся одна), пустой хеш пароля.
