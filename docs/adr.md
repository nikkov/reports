<a id="adr-1"></a>

## ADR-1. Единственный источник истины для таблицы — плоская модель строк

Движок отдаёт `FlatRow[]`: `{ kind: 'detail' | 'subtotal' | 'grandtotal', level, groupPath: string[], groupId, visible, cells }`.
Колонки vxe-table, `mergeCells` и общий итог выводятся из этого массива. Причина: `mergeCells` в vxe-table адресуется индексами строк/колонок; при сворачивании и вставке строк итогов индексы меняются. ТЗ называло риски для пар (`footerMethod`×`mergeCells`, `subtotals`×`mergeCells`), но не для третьей — `collapsible`×`mergeCells`. Модель снимает все три риска конструктивно.

<a id="adr-2"></a>

## ADR-2. Общий итог — последняя строка массива, `footerMethod` не используется

Устраняет риск рассинхронизации подвала и объединений из §3 ТЗ; выравнивание по листовым колонкам получается автоматически, т.к. строка строится тем же маппингом, что и заголовки.

<a id="adr-3"></a>

## ADR-3. Группировка описывается только колонками, `groupBy` в шаблоне отсутствует

ТЗ содержало два источника истины (`groupBy: [...]` и `columns[].group: true`). Оставлено одно: порядок колонок с `group: true` задаёт порядок группировки. Промежуточные итоги — `subtotal: true` на групповой колонке (вместо массива `subtotals`).

<a id="adr-4"></a>

## ADR-4. Шаблоны и SQL живут на сервере

`backend/templates/<id>.json` и `backend/config/queries.json` в репозитории; Drogon валидирует оба на старте и отказывается подниматься при ошибке (fail-fast). Фронтенд получает шаблон по `GET /api/reports/{id}` — шаблон не дублируется в бандле. В dev-режиме — горячая перезагрузка шаблонов.

<a id="adr-5"></a>

## ADR-5. Параметры — часть шаблона, состояние — в URL

Шаблон объявляет `params: [{name, type, label, required, default, options?}]`; `ReportViewer` строит форму, значения уходят в API и в query-строку браузера (`/reports/sales?from=2026-01-01&to=2026-03-31`) — ссылка на отчёт воспроизводима. Тип `select` берётся из `options` статически (справочники из БД — вне объёма Ф1–Ф3).

<a id="adr-6"></a>

## ADR-6. SQL — только подготовленные выражения с именованными параметрами

`queries.json`: `{ "sales_by_region": { "sql": "SELECT ... WHERE d >= :from::date AND d <= :to::date", "params": {"from":"date","to":"date"} } }`. Подстановка строк в текст запроса запрещена; проверка — ревью + тест на попытку инъекции через параметр.

<a id="adr-7"></a>

## ADR-7. Агрегация только на клиенте; на сервере — лимиты вместо агрегатов

Сервер не считает ни одного агрегата (ТЗ §2). Защита от «всё в браузер»: `maxRows = 50000` (превышение → HTTP 422 `ROW_LIMIT` с подсказкой сузить параметры), `statement_timeout = 30s`, отмена запроса на клиенте через `AbortController`. Запасной вариант из ТЗ («кэш агрегатов на бэкенде») отклонён: это вторая реализация семантики агрегации и источник расхождений; при росте объёмов правильный путь — серверный `GROUP BY`, генерируемый из той же декларации (отдельная фаза, вне текущего объёма).

<a id="adr-8"></a>

## ADR-8. Числа: `int` (включая bigint), `float`, `string`, `date`, `bool`; без decimal-типа

Целые суммы в `double` точны до 2^53 — при 50k строк и значениях в минорных единицах переполнение недостижимо (проверяется тестом-стражем). Денежные величины с копейками агрегируются в SQL как целые минорные единицы. Округление — только на форматировании, никогда не накапливается.

<a id="adr-9"></a>

## ADR-9. Ошибки и `null` в выражениях — типизированы

Любой `null`-операнд → `null`; деление на 0 → `null`; `NaN`/`Infinity` → `null`. В ячейке `null` рендерится как `nullText` (по умолчанию «—»). Пустая группа или пустое значение ключа → подпись «(пусто)».

<a id="adr-10"></a>

## ADR-10. vxe-table — только MIT-ядро, фиксированная версия

В README vxe-table (main, v4.x) как **[企业版] enterprise** помечены: сводные/итоговые данные (`数据汇总`), агрегатные функции (`聚合函数`), выделение/copy-paste/поиск, встроенные диаграммы. Они запрещены. Разрешены (бесплатное ядро): многоуровневые заголовки, данные подвала, объединение ячеек, объединение подвала, группировка строк, виртуальный скролл, виртуальное объединение — **статус последнего проверяется в спайке S1 на зафиксированной версии** (в разных источниках маркировка расходится). Версия пинована, внесена в `THIRD_PARTY.md`; CI проверяет отсутствие enterprise-API регуляркой.

<a id="adr-11"></a>

## ADR-11. Все агрегаты и выражения считает собственный движок (TypeScript)

Библиотеки выражений (expr-eval и подобные) отклонены: им не хватает областей действия (row / group / grand total) и агрегатных функций, пришлось бы писать пред-обработку — то же, но с лишней зависимостью.

<a id="adr-12"></a>

## ADR-12. Форматы — закрытый каталог

`number` (разделитель тысяч — неразрывный пробел, `decimals` по умолчанию 0), `percent` (вход — доля 0..1, вывод ×100, `decimals` по умолчанию 1), `currency` (₽ / $ / €, `decimals` 2), `date` (dd.MM.yyyy), `integer`. Локаль ru-RU фиксирована; произвольные шаблоны форматирования — вне объёма.

<a id="adr-13"></a>

## ADR-13. Conan v1 — единственный пакетный менеджер C++; вызов только из venv

Факт окружения: `conan` в `PATH` (`~/.local/bin/conan`) — это **Conan 2.28.1** с кэшем `~/.conan2`, а требуемый v1 (**1.66.0**) стоит в `~/python_venv/bin/conan` с кэшем `~/.conan`. Голый вызов `conan` уже выдаёт `WARN: Downgrading cache from Conan 2.33.0 to 2.28.1` — смешивание кэшей недопустимо.
Правила: любой вызов — `~/python_venv/bin/conan` (или `scripts/conan` — обёртка, которая это гарантирует); `scripts/check.sh` падает, если `conan --version` ≠ 1.66.x; профиль `default` из `~/.conan/profiles/default`, `settings.compiler.libcxx=libstdc++11`; генератор `cmake_find_package_multi` (проверенный v1-путь; при проблемах с `find_package(Drogon CONFIG)` — fallback на генератор `cmake`); пакеты: `drogon/1.9.8` (опции `with_postgres=True, with_orm=True, with_brotli=True, with_profile=True, with_sqlite=False, with_mysql=False, with_redis=False`) и `catch2/3.7.1`. Наличие рецептов в v1-remote `conancenter` проверено: `drogon` до 1.9.8, `catch2` до 3.7.1. Первая сборка из исходников (openssl, jsoncpp, libpq, trantor, drogon) — ~15–25 мин, далее кэш. По итогам спайка S2: `with_boost=False` (boost нужен только для C++14), `with_brotli=False` (рецепт не прокидывает include-пути brotli → сборка падает на `brotli/decode.h`; остаётся gzip/deflate), `with_profile=False` (профилировщик coz не нужен).

<a id="adr-14"></a>

## ADR-14. Catch2 v3 — тесты C++ (`catch2/3.7.1`, `Catch2::Catch2WithMain`)

Отдельная цель `rep_tests`, регистрация в `ctest`. Покрытие бэкенда: парсинг и валидация `queries.json` и шаблонов, разбор и приведение типов параметров, привязка параметров (включая тест на попытку SQL-инъекции), маппинг ошибок в коды API, соблюдение `maxRows`/`statement_timeout`, корректность JSON-сериализации чисел (`int`/`bigint`/`float`). Интеграционные тесты ходят в реальную БД `reporting` (схема `test_*`, данные создаются и удаляются тестом) — синтетика, изолированно. Фронтенд-тесты остаются vitest/Playwright; Catch2 бэкенд не дублирует.

<a id="adr-15"></a>

## ADR-15. Секреты — только через `.env`

`backend/.env` (в `.gitignore`) + `.env.example` с плейсхолдерами. Drogon читает DSN/host/port/user/password из переменных окружения; в `queries.json`, шаблонах и коде пароля нет. Значения из ответа PO (`192.168.0.3:32770`, `postgres`/`postgres`) — dev-уровня и фиксируются в `.env.example` только после подтверждения (§10); в репозиторий `.env` не попадает, пароль не пишется в логи и тексты ошибок.

<a id="adr-16"></a>

## ADR-16. Синтетические данные — детерминированный SQL-генератор

`db/schema.sql` (таблицы `sales`, `finance`, `ops`) + `db/seed.sql` (`setseed()` + `generate_series`): 50 000 строк фактов, 3 иерархии (регион → категория → продукт), намеренно включены `null`-ключи, нулевые знаменатели, отрицательные суммы, одна строка-выброс. Тот же seed используется в эталонах golden-тестов. Никаких Python-зависимостей для генерации (в venv нет psycopg2 — не добавляем; всё через `psql`), экспорт эталонов — `psql -c "COPY (SELECT json_agg(...)) TO STDOUT"`.

<a id="adr-17"></a>

## ADR-17. PostgreSQL 18.6 на 192.168.0.3:32770 — общий инстанс, работаем только в своей БД

Проверено: TCP открыт, `psql` (клиент 15.14) подключается и выполняет запросы (SCRAM). На инстансе есть только `postgres`, `template0`, `template1` — БД `reporting` создаётся скриптом `db/init.sh` (idempotent: `SELECT ... WHERE NOT EXISTS` → `CREATE DATABASE`). Чужие БД не читаем и не изменяем; DDL — только в `reporting`, схема `public`. Резерв при недоступности сервера — локальный Postgres в Docker Compose для тестов (тот же DDL/seed), чтобы работа не блокировалась.

<a id="adr-18"></a>

## ADR-18. Типы колонок объявляются в реестре запросов

Drogon не отдаёт OID/типы колонок результата (`Field` не имеет `oid()`, `Result` — только имена).
Поэтому `queries.json` для каждого запроса содержит секцию `columns: {имя: int|float|text|date|bool}`;
это же значение уходит клиенту в `columns[].type`. Если колонка не объявлена — тип выводится из первого
непустого значения (int/float/text) и попадает в ответ как есть. Дублирование схемы оправдано:
типы нужны фронтенду до получения данных (форматирование, группировка), а объявление живёт рядом с SQL.

<a id="adr-19"></a>

## ADR-19. (заменён ADR-20) Сгруппированные таблицы рендерятся постранично

Замер спайка S1: `mergeCells` с `rowspan` в тысячи строк вместе с виртуальным скроллом блокирует
главный поток браузера (> 60 с на 20 000 строк; DOM успевает отрисовать 20 строк и страница висит).
Без объединений виртуальный скролл работает (13 строк в DOM), но групповые колонки теряют объединение.
Принято: сгруппированная таблица показывает 200 строк на страницу, `mergeCells` считаются по странице.
Уточнённые замеры прод-сборки (см. `docs/renderer-assessment.md`): 200 строк — 861 мс, 1 000 — 2 690 мс,
2 000 — 4 818 мс. Ранняя цифра «115 мс» была снята до завершения рендера и недействительна.
**Узкое место — не `mergeCells`, а базовый рендер vxe-table: 2,4–4 мс/строку (нативная таблица — 0,1 мс).**
Следствие для ТЗ: объединение ячеек не переносится через границу страницы.
На основании этих замеров оценивается смена рендерера (`docs/renderer-assessment.md`): варианты —
остаться на vxe с пагинацией, своя витрина поверх vxe, свой лёгкий рендерер на Vue. Выбор фиксируется
как ADR-20 после ответа PO; до этого в коде действует ADR-19.

<a id="adr-20"></a>

## ADR-20. Свой лёгкий рендерер таблиц на Vue вместо vxe-table (решение PO от 2026-11-05)

Замеры (`docs/renderer-assessment.md`): базовый рендер vxe-table — 2,4–4 мс/строку (200 строк = 861 мс,
2 000 = 4 818 мс), нативная таблица — 0,1 мс/строку; `mergeCells` × виртуальный скролл при больших
`rowspan` вешает страницу (> 60 с на 20 000 строк). Решение: отчёты рендерит собственный компонент
`ReportTable` — нативная `<table>`, `rowspan`/`colspan` из модели (ADR-1), собственная витрина по
фиксированной высоте строки, sticky-подпись группы при прокрутке. Это **отклонение от ТЗ §2**, где
таблицей назван vxe-table; согласовано постановщиком.
Последствия: vxe-table выводится из зависимостей (после замены спайка); задачи 2a.6 и 2b.1–2b.4
переходят на собственный компонент; лицензионный манифест сокращается.

<a id="adr-21"></a>

## ADR-21. Шаблоны отчётов хранятся в БД (решение PO от 2026-11-05), заменяет ADR-4 в части хранения

Таблица `report_templates(id text primary key, title text, body jsonb, updated_at timestamptz)`.
Файлы `backend/templates/*.json` остаются источником в репозитории и проверяются CLI-валидатором;
`scripts/templates-push.mjs` загружает их в БД (upsert, dollar-quoting тела, без интерполяции SQL).
Сервис читает шаблоны из БД на старте (`REP_TEMPLATES_SOURCE=db`, по умолчанию; `files` — запасной режим),
валидирует JSON и держит в памяти; `GET /api/reports/{id}` отдаёт исходный JSON.
Следствие: изменение шаблона требует `templates-push` + перезапуск сервиса (hot-reload не делаем).

<a id="adr-23"></a>

## ADR-23. Внешний вид таблицы задаётся шаблоном (требование PO от 2026-11-05, версия 1.1)

Необязательная секция `styles` (верхний уровень) + `blocks[].styles` + `columns[].style`: шрифты
(family/size/weight/style/lineHeight), цвета текста/фона/границ, выравнивание, отступы, ширины колонок
(px, %, min/max), высоты зон (шапка, строки, подытоги, общий итог), границы, зебра. Зоны стилизуются
независимо; порядок применения: умолчания → `preset` → `styles` → `styles.<зона>` → `blocks[].styles` →
`columns[].style`. Реализация — CSS-переменные на корне таблицы и классы зон, **без inline-стилей
на ячейках** (иначе 50 000 строк теряют производительность). Высоты — фиксированные по зонам;
виртуализация переводится с умножения на константу `rowHeight` на префиксные суммы + бинарный поиск.
Переменная высота строки (перенос текста) и условное форматирование — вне 1.1.
Проект и оценки: `rep/docs/styling-design.md` (6 чел.-дн., фаза Ф5).

## ADR-24. SQL справочников параметров живёт в шаблоне (требование PO 2026-11-05, заменяет часть ADR-22)

`params[].source` для `kind: "lookup"` содержит `sql` (обязателен) и не содержит `queryId` — валидатор
запрещает `queryId`. API: `GET /api/reports/{reportId}/lookups/{param}?<родитель>=…` — SQL берётся
из шаблона по имени параметра, клиент SQL не присылает; `GET /api/reports/{id}` вырезает `sql`
из ответа, поэтому браузер его не видит. Плейсхолдеры `:name` подставляются из query-строки через
binding, `::` остаётся кастом типа. Серверного кеша справочников нет (решение PO: кэш только на клиенте);
защита от тяжёлого SQL — `statement_timeout` 2 с и read-only роль БД (см. ниже — роль пока не заведена).
Реестр `queries.json` больше не содержит `lookup_*`; 6 шаблонов переведены на `source.sql`.

<a id="adr-25"></a>

## ADR-25. Условное форматирование — декларативные правила в блоке таблицы (версия 1.2)

`blocks[].rules[]`: `when {column, op, value}`, `apply` (тот же стиль-объект, что у зон), `scope`
(`cell` — целевая колонка, `row` — вся строка), `zones` (`detail`/`subtotal`/`grandtotal`), `priority`.
Операторы: `= != > >= < <= between empty notEmpty contains`. Сравнение идёт по сырому значению
`row.values[]`, поэтому работает и для вычисляемых колонок; форматирование (форматы чисел) применяется
после правил. Порядок: зона → `styles.columns` → правила по `priority`. Правила считаются только
для видимого окна виртуализации, в модель строк не попадают. Грамматику выражений не расширяем:
сложные условия — отдельным шагом. Проект и оценки: `rep/docs/conditional-formatting-design.md`
(4 чел.-дн., фаза Ф6).

<a id="adr-26"></a>

## ADR-26. Администрирование отчётов: запись через API с hot-reload (версия 1.3)

Появляются `GET /api/admin/reports`, `POST /api/reports`, `PUT /api/reports/{id}`, `DELETE /api/reports/{id}`,
`POST /api/reports/{id}/validate`; все они доступны только при `REP_ADMIN=1` (иначе 404). После успешной
записи сервис обновляет шаблон в памяти под мьютексом — **рестарт больше не нужен для правок из админки**
(частично заменяет ADR-21; `templates-push.mjs` по-прежнему требует рестарта, он пишет в обход процесса).
История версий — append-only таблица `report_templates_history`, откат = обычная запись прежней версии.
Валидация двухуровневая: клиент — полный Ajv + семантика, сервер — структурный минимум (JSON, version,
id, наличие `sql` у справочников, запрет `queryId`, тело ≤ 256 КБ); серверная семантическая проверка
не портируется (риск расхождения правил). SQL из шаблонов до выполнения задачи 5.9 проходит серверный
guard «только SELECT» (без `;`, `--`, DML/DDL) — иначе админка даёт исполнение произвольного SQL
под ролью `postgres`. UI — отдельная страница `/admin.html` с CodeMirror 6. Проект и оценки:
`rep/docs/admin-design.md` (9 чел.-дн., фаза Ф7).

<a id="adr-27"></a>

## ADR-27. SQL наборов данных живёт в шаблоне (требование PO 2026-11-05, заменяет ADR-4/ADR-21 в части запросов)

`datasets.<key>` содержит `sql` (обязателен) и `params` (отображение «параметр SQL → `$параметр отчёта`»);
`queryId` запрещён и на клиенте, и на сервере. Сервер исполняет SQL из шаблона, подставляя значения
по `:name` через binding (тот же приём, что у справочников), типы колонок определяет по результату.
`GET /api/reports/{id}` вырезает `datasets.*.sql`; админский `GET /api/admin/reports/{id}` отдаёт полный
шаблон. Реестр `queries.json` оставлен только для служебного `slow_probe` (тест таймаута).
12 шаблонов переведены на `datasets.sql`.

<a id="adr-28"></a>

## ADR-28. Экспорт в Excel и печатный вид (версия 1.4)

Excel собирается **на клиенте** из модели витрины (ExcelJS, MIT, ленивый чанк), а не из DOM и не на сервере:
виртуализация держит в DOM ~40 строк, а группировка, подытоги, форматы (`format.js`) и правила (`rules.js`)
уже реализованы на клиенте — второй экземпляр на C++ разошёлся бы с экраном. В файл переносятся
объединения многоуровневой шапки, подытоги и общий итог, числовые форматы Excel (`numFmt`), цвета и шрифты
зон, совпадения правил; отдельный лист «Параметры» с подписями значений. Диаграммы не переносятся.
Печать — `@media print` + `window.print()` (PDF через диалог браузера), шапка повторяется на страницах,
группы не разрываются. Лимиты: 100 000 строк на Excel, 20 000 на печать; сверх лимита — отказ с сообщением.
Серверный экспорт (`libxlsxwriter`, BSD-2) зафиксирован как запасной вариант для объёмов больше 50 000
и для рассылки. Проект и оценки: `rep/docs/export-design.md` (9,5 чел.-дн., фаза Ф8).

<a id="adr-29"></a>

## ADR-29. Drill-through (версия 1.5)

Переход объявляется в табличном блоке секцией
`drill: { report, label?, params }`; значения — `group.<field>` (из группы строки), `param.<name>`
(текущий параметр) или литерал. Ссылкой становится ячейка группы; параметры уходят в URL целевого
отчёта. Альтернатива (отдельный API-эндпоинт перехода) отклонена: переход — это обычное открытие
отчёта с параметрами, отдельный контракт не нужен.

<a id="adr-30"></a>

## ADR-30. Каталог отчётов (версия 1.5)

Папка и теги объявляются в шаблоне (`folder`, `tags`),
`GET /api/reports` отдаёт их вместе с описанием и параметрами. Экран списка: боковая панель папок
с количеством, фильтр по тегам, поиск по названию/описанию/id/тегам, избранное в `localStorage`.
Отдельной таблицы каталога нет: источник истины — сами шаблоны, поэтому перенос отчёта в другую
папку не требует миграций.

<a id="adr-31"></a>

## ADR-31. Черновик и публикация (версия 1.6)

Правка в админке пишется в отдельную колонку
`report_templates.draft` и не влияет на публичный отчёт. Публикация (`POST …/publish`) переносит
черновик в `body`, предварительно записав снапшот прежней версии в историю, и обновляет память
без рестарта. Альтернатива (флаг «черновик» в истории с фильтрацией на чтении) отклонена: она
заставляет каждый читающий путь знать про черновики, а разделение колонок делает публичный контракт
неизменным. Создание отчёта сразу публикует его — черновик существует только для правок.

<a id="adr-32"></a>

## ADR-32. Кэш результатов (версия 1.7)

Ответы `POST /api/report/data` кэшируются в памяти
процесса по ключу «отчёт + версия шаблонов + параметры»; TTL 60 с, `ETag`, `X-Cache`, поддержка
`If-None-Match` с `304`. Инвалидация — через версию шаблонов: публикация, правка, откат и удаление
поднимают счётчик и очищают кэш, поэтому устаревшие данные не отдаются. Альтернатива (кэш в
PostgreSQL или Redis) отклонена: объём — сотни записей, внешняя зависимость не оправдана.
Крупные ответы (> 2 МБ) не кэшируются, ошибки не кэшируются.

<a id="adr-33"></a>

## ADR-33. Роль БД только-чтения (версия 1.8, пункт 5.9). Закрыт 2026-11-05:

роль `reporting_ro`
создаётся `scripts/db-ro.sh`, чтение `sales` проходит, `INSERT` отклоняется СУБД. Данные отчётов и справочники читаются
отдельным пулом подключений под ролью `reporting_ro` (`REP_RO_DB_USER`/`REP_RO_DB_PASSWORD`),
запись шаблонов и админка остаются на основной роли. Роль создаётся `scripts/db-ro.sh`:
`CREATE ROLE … LOGIN`, `GRANT SELECT` на схему, `default_transaction_read_only = on`.
Проверка встроена в скрипт: чтение `sales` проходит, `INSERT` получает
«cannot execute INSERT in a read-only transaction». Если переменные не заданы, сервис работает
на основной роли и пишет предупреждение в лог — обратная совместимость сохранена.
Серверный guard «только SELECT» остаётся первой линией, но теперь он подкреплён правами СУБД.

<a id="adr-34"></a>

## ADR-34. Аутентификация и роли (версия 1.9)

Пользователи и сессии в БД: `users`
(PBKDF2-HMAC-SHA256, 120 000 итераций, соль на пользователя) и `sessions` (токен 32 байта,
TTL 12 ч). Cookie `rep_session` — `HttpOnly`, `SameSite=Lax`, `Path=/`. Проверка одна, до
маршрутизации: матрица «метод + путь → минимальная роль»; неизвестные пути требуют admin
(безопасное умолчание). Роли: viewer (чтение), author (+ создание и черновик), admin (+ публикация,
удаление, откат, админка). Альтернатива (JWT в заголовке) отклонена: cookie проще для браузерных
страниц, а отзыв сессии через БД нужен и так.

<a id="adr-36"></a>

## ADR-36. Несколько наборов данных в шаблоне (версия 1.10)

`datasets` — словарь наборов;
табличный блок ссылается на набор через `dataKey`, клиент запрашивает каждый набор отдельно
(`POST /api/report/data` с полем `dataset`), сервер без поля отдаёт первый набор — обратная
совместимость сохраняется. Ключ кэша включает имя набора. Альтернатива (один запрос с JOIN
и разбор на клиенте) отклонена: наборы описывают разные гранулярности, JOIN раздувает выборку.

<a id="adr-37"></a>

## ADR-37. Серверная агрегация (версия 1.11)

Блок объявляет `aggregate: {groupBy, measures}`;
сервер выполняет `GROUP BY` поверх SQL набора (`FROM (<sql>) AS base GROUP BY 1..N`), имена колонок
и агрегаты валидируются как идентификаторы, параметры подставляются тем же компилятором.
Альтернатива (агрегация в движке на клиенте) уже есть и остаётся для WYSIWYG-режима; серверная нужна,
когда строк десятки тысяч и передавать их целиком дорого. Функция агрегатов ограничена
`sum|avg|min|max|count` — расширение (median, percentile) отклонено до появления запроса.

<a id="adr-38"></a>

## ADR-38. Серверный экспорт в Excel (версия 1.12)

`POST /api/report/export.xlsx` собирает книгу
на сервере (`libxlsxwriter`, BSD-2): шапка и форматы — из табличного блока шаблона, данные — из набора,
с применением `aggregate` блока, если он объявлен; второй лист — параметры. Клиентский экспорт (ADR-28)
остаётся WYSIWYG; серверный нужен для рассылки, больших объёмов и сценариев без браузера.

<a id="adr-39"></a>

## ADR-39. Автообновление отчёта (версия 1.13)

Период задаётся шаблоном (`refreshSeconds`),
страница перезапрашивает данные тем же запросом с сохранением параметров и состояния групп.
Тик пропускается, если вкладка в фоне или запрос уже идёт; есть пауза. Ограничение 0…3600 с,
меньше 5 — предупреждение. Функция клиентская: сервер ничего не помнит о подписках, поэтому
автообновление не требует прав и не влияет на других пользователей. Серверная сторона (рассылка)
— отдельная задача.

<a id="adr-40"></a>

## ADR-40. CSV на сервере (версия 1.14)

Отдельный маршрут `POST /api/report/export.csv`, а не параметр
`format` у `.xlsx`: другой обработчик проще отладить, а рассылке нужен именно файл-вложение. Расчёт повторяет
`.xlsx` — тот же набор данных, та же агрегация блока, тот же порядок колонок шаблона. Формат: UTF-8 с BOM,
`;`, CRLF, кавычки при спецсимволах — Excel открывает двойным щелчком без мастера импорта. Числа пишутся
без форматирования (сырыми), чтобы CSV оставался пригодным для машинной обработки.

<a id="adr-41"></a>

## ADR-41. Поиск и пагинация каталога на сервере (версия 1.14)

`GET /api/reports` принимает `q`, `folder`,
`tag`, `limit`, `offset`; без `limit` отдаёт прежний массив — клиенты и e2e не ломаются, с `limit` —
`{items,total}`. Фильтрация идёт по снимку шаблонов в памяти (их сотни, не миллионы). Страница каталога
грузит по 10 и догружает кнопкой; поиск отправляется с задержкой 250 мс. Избранное остаётся локальным:
это список в `localStorage`, сервер о нём не знает.

<a id="adr-42"></a>

## ADR-42. Обновление по событию (версия 1.14) — заменён ADR-44 (версия 1.14)

Вместо постоянного опроса — long-poll
`GET /api/report/changes?report=<id>`: сервер держит запрос до 20 с и отвечает сразу после публикации
или отката шаблона (`notifyChange` из `applyTemplateInMemory`). Это дешевле таймера (нет запросов в простое
и нет задержки до периода), не требует WebSocket-инфраструктуры и живёт на штатных таймерах Drogon.
Цена — висящее соединение на каждого зрителя; при десятках подписчиков логично перейти на SSE/WebSocket.
Шаблон включает режим полем `live: true`; `refreshSeconds` и `live` не смешиваются.

<a id="adr-43"></a>

## ADR-43. Drill-through с диаграмм (версия 1.15)

Спецификация `drill` та же, что у таблицы
(`report`, `label`, `params`), но ссылки другие: `x` — категория кликнутой точки, `series` — имя серии.
`group.<field>` отклоняется валидатором: у диаграммы нет табличных групп, а подменять смысл ссылки молча —
источник ошибок в шаблонах. Обработчик клика живёт в `ChartBlock` (ECharts `click`), решение о переходе —
в `ReportViewer` (`onChartDrill`), поэтому URL-схема перехода одна и та же для таблицы и диаграмм.
Круговой график отдаёт только `name` (серии нет) — для него в `params` допустим лишь `x`/`param.`/литерал.

<a id="adr-44"></a>

## ADR-44. SSE вместо long-poll (версия 1.16)

Long-poll из ADR-42 держал запрос до 20 с и требовал
нового запроса после каждого ответа: на каждое событие — два HTTP-обмена, в простое — вечная ротация
соединений. Теперь одно SSE-соединение `GET /api/report/events?report=<id>` на всё время работы страницы
(`HttpResponse::newAsyncStreamResponse` в Drogon), сервер пишет `event: change` после публикации и
`: ping` раз в 15 с; отвалившиеся клиенты вычищаются на пульсе по результату `send()`. Клиент —
`EventSource`, переподключение штатное; пауза закрывает поток. Цена: потоковые ответы буферизуют прокси,
поэтому в nginx нужен `proxy_buffering off`, а прокси стенда пробрасывает поток вручную
(`frontend/sse-proxy.js`) — Vite-прокси отдавал SSE как `Content-Length: 0`.

<a id="adr-45"></a>

## ADR-45. Полная серверная валидация (версия 1.17)

Раньше сервер делал «структурную» проверку и
отдавал одну строку ошибки, а вся семантика жила в клиентском `validate.js` — значит, шаблон можно было
сохранить в обход браузера. Теперь правила перенесены в `backend/src/validate.cc` и возвращают список
`{path, message}`; клиентский валидатор остаётся ради мгновенной подсказки в редакторе, но истина — сервер.
Parity проверяется фикстурами `docs/fixtures/validation-cases.json`, которые читают оба теста: если правила
разъедутся, упадёт и Catch2, и vitest. Дополнительно на сервере появились проверки, которых на клиенте нет:
шаблон `id` и совпадение с URL, уникальность параметров, `chartType`, размер и SQL-гард для наборов данных
(раньше SQL набора данных вообще не проверялся на запись — дыра в 5.9). Цена: правила описаны дважды,
поэтому фикстуры — обязательная часть изменений, а не «приятное дополнение».

<a id="adr-46"></a>

## ADR-46. Рассылка по расписанию (версия 1.18)

Подписки лежат в БД (`report_subscriptions`), расписание —
cron из пяти полей; время серверное, без таймзон (для одного сервера этого достаточно, часовые пояса
получателей — забота почтового клиента). Планировщик — отдельный поток с собственным соединением libpq:
отправка блокирующая и не должна занимать цикл событий. Просроченные подписки забираются одним
`UPDATE … FOR UPDATE SKIP LOCKED`, поэтому два процесса не отправят одно письмо дважды, а ручная
кнопка «Отправить сейчас» не сдвигает расписание. Файл собирает тот же `buildCsv`, что и HTTP-экспорт —
один расчёт, нет расхождений между экраном, скачиванием и письмом. Почта — свой минимальный SMTP-клиент
(OpenSSL, без внешних зависимостей): STARTTLS, AUTH PLAIN/LOGIN, вложение в base64. Журнал
`subscription_runs` хранит результат каждой отправки, ошибка доставки не теряется и видна в админке.
Ограничения осознанные: только CSV (xlsx — следующий шаг), SMTP без проверки сертификата (стенд/интранет),
нет повторов при временной недоступности SMTP и нет per-user подписок.

<a id="adr-47"></a>

## ADR-47. E2E в CI (версия 1.19)

Сквозные тесты запускаются в GH Actions на эфемерной БД в сервисе
`postgres:16`; стенд поднимает `scripts/ci-e2e.sh` — тот же скрипт работает локально с отдельной базой
и своими портами, поэтому «работает у меня» и «зелено в CI» проверяют одно и то же. Бэкенд и фронтенд
собираются шагами workflow (Conan-кэш обязателен), Playwright ставится с chromium. Стенд изолирован:
`REP_CI_DB` не может совпасть с `reporting` (проверка в скрипте), порты 8081/5174/1026, локальный
SMTP-приёмник. Две ловушки, найденные при отладке: ro-роль `reporting_ro` кластерная, права нужно выдавать
в каждой новой БД (иначе `permission denied`), а `global-setup` Playwright логинится по `REP_API` —
без этого он получает cookie от бэкенда на :8080 и все страницы отвечают 401. Ограничения: сервис
Postgres в CI — контейнер с паролем по умолчанию (только внутри job'а), тяжёлая сборка Drogon требует кэша,
иначе job выходит за таймаут.

<a id="adr-48"></a>

## ADR-48. XLSX в рассылке (версия 1.20)

Лист отчёта собирается одной функцией `buildSheet` (выборка,
агрегация блока, колонки с числовыми форматами, заголовок, параметры), а форматы — это тонкие обёртки:
CSV (`toCsv`) и XLSX (`writeXlsx` во временный файл → байты в письмо). Так письмо, скачивание и экран
считаются одним кодом, и «в письме не то, что на экране» невозможно по построению. Формат — поле подписки
(`csv`/`xlsx`), проверяется при сохранении; MIME вложения выбирается по формату. Ограничение: серверный
XLSX — плоская таблица с форматами чисел, без объединённых ячеек и outline-группировки (это делает
браузерный экспорт); для рассылки этого достаточно, а полноформатный файл доступен кнопкой экспорта.

<a id="adr-49"></a>

## ADR-49. Объединения и outline в серверном XLSX (версия 1.21)

Сводная книга должна выглядеть как
таблица на экране, иначе письмо читают «вслепую». `applyGrouping` считает по групповым колонкам блока
вертикальные объединения одинаковых значений и уровни структуры; `writeXlsx` ставит `mergeCells`,
`outlineLevel` и `summaryBelow=0`. Порядок строк **не пересортировывается**: он приходит из SQL, совпадает
с экраном, а объединяются только подряд идущие значения — сортировка по байтам разошлась бы с экранным
порядком на кириллице. Уровни: строка, начинающая новую группу глубины d, получает уровень d, продолжение
самой глубокой группы — d+1 (аналог «показать детали»). Ограничение: сервер не строит строки подытогов
и ИТОГО — их даёт модель клиента (`kind: subtotal|grandtotal`); в книге остаются детальные строки с
объединениями и структурой. Полный WYSIWYG-файл по-прежнему даёт браузерный экспорт (ADR-28).

<a id="adr-50"></a>

## ADR-50. Управление пользователями (версия 1.22)

Пользователей создаёт админка, а не скрипт на сервере:
раньше единственным способом был `scripts/auth-init.sh` с доступом к shell. Роли остаются тремя
(viewer/author/admin), пароли — тот же PBKDF2 с солью на пользователя. Отключение (`enabled=false`)
используется вместо удаления там, где нужна история: вход запрещён, все сессии пользователя удаляются
сразу, а сессионная проверка дополнительно требует `u.enabled` — на случай гонки. Защита от потери
управления явная: нельзя удалить себя, отключить себя или снять роль с последнего включённого
администратора (`SELF_PROTECTED`, `LAST_ADMIN`). Ограничения: нет самообслуживания (смены своего пароля),
нет истории изменений пользователей (это задача аудита) и нет ограничения попыток входа — оно в отдельной
задаче про безопасность.

<a id="adr-51"></a>

## ADR-51. Версионирование шаблона и миграции (версия 1.23)

`version` перестал быть константой
«должно быть 1» и стал версией формата: текущая — 2, поддерживается диапазон 1…2, шаблоны старее
поднимаются цепочкой миграций, новее — отклоняются с текстом «обновите сервер». Миграция выполняется
в двух местах осознанно: сервер — при сохранении, публикации и загрузке в память (источник истины в БД),
клиент — при открытии в админке (чтобы автор видел актуальный формат). Логика продублирована (C++ и JS),
поэтому тесты обеих сторон проверяют один и тот же набор кейсов, а parity-фикстуры валидации дополнены
кейсом старой версии. Содержание версии 2: `chartType` обязателен у диаграмм (при миграции — `bar`);
версия 1 остаётся читаемой. Побочно выравнены шаблоны `id` на сервере и в схеме. Ограничения:
миграции применяются только вперёд и необратимы; шаблон с `queryId` (эпоха ADR-27) миграция не спасёт —
SQL из удалённого реестра не восстановить, такие шаблоны нужно править вручную.

<a id="adr-52"></a>

## ADR-52. Аудит действий (версия 1.24)

Пишем отдельную таблицу `audit_log`, а не общий лог приложения:
записи нужны для разбора «кто это сделал», их читают через админку, а не grep по файлам. Событие пишется
только при успехе — неудачные попытки фиксируются лишь для входа (`auth.login_failed`), потому что там
важен сам факт. Детали — безопасный минимум (логин, роль, включённость, формат, число писем): пароли,
хэши и тела шаблонов в журнал не попадают. Запись делается коротким отдельным соединением libpq прямо
в обработчике: админских действий немного, а асинхронная копия колбэков усложнила бы код без пользы.
Актор берётся из сессии (`session_login`), у планировщика — `system`. API только на чтение: журнал нельзя
подчистить через интерфейс, что и делает его журналом. Ограничения: нет ретеншена (журнал растёт),
нет выгрузки в файл/SIEM и нет записи чтения отчётов — только изменения.

<a id="adr-53"></a>

## ADR-53. Префикс приложения для реверс-прокси (версия 1.25)

Сервер отчётов должен ставиться не только
в корень домена: у заказчика он живёт рядом с другими системами. База сборки задаётся `REP_BASE`, адрес API —
`VITE_API_BASE`; по умолчанию оба пустые/корневые, поэтому стенд и e2e не меняются. Префикс не «зашит»
в код страниц: Vite подставляет базу в ассеты, `import.meta.env.BASE_URL` даёт базу для редиректа на вход,
`API_BASE` — для всех fetch, EventSource и ссылок на ручки API. Сборка при этом остаётся
переносимой: ассеты подключаются относительными путями (`base: './'`), а адрес API вычисляется на клиенте
из расположения страницы (`/reports/report.html` → `/reports/api`), поэтому один и тот же `dist`
копируется на другой хост или в другой каталог без пересборки; жёсткое переопределение на случай
нестандартной схемы — `<meta name="rep-api-base">` или `window.REP_API_BASE`. Прокси обязан снимать
префикс (`/reports/api/… → /api/…`), тогда бэкенд остаётся прежним и не знает о префиксе; для SSE нужен
отдельный блок с `proxy_buffering off`, иначе события не доходят (та же ловушка, что была с Vite-прокси,
ADR-44).
Cookie сессии живёт на `Path=/` и работает под префиксом; `Secure` появится вместе с HTTPS.
Проверка без nginx — `scripts/serve-subpath.mjs`: статика под префиксом + прокси API. Подпрефиксная
сборка кладётся в отдельный каталог `frontend/dist-reports` (`scripts/build-subpath.sh`), чтобы не
затирать обычный `dist`; стенд по умолчанию отдаёт именно её и предупреждает, если каталог собран
без префикса. Ограничение: подпрефиксная сборка не входит в обычный `check.sh` (нужна вторая
сборка), поэтому проверяется отдельным прогоном стенда — это записано в DoD.

<a id="adr-54"></a>

## ADR-54. Аутентификация на реверс-прокси (версия 1.26)

Есть внедрения, где вход выполняет прокси
(basic, SSO, `auth_request`), и второй вход в приложении не нужен. Режим `REP_AUTH=proxy` берёт логин из
заголовка, роль — из `users`, поэтому матрица viewer/author/admin остаётся единой для обоих режимов.
Заголовок — недоверенный ввод: он принимается только с адресов `REP_AUTH_PROXY_TRUSTED` (по умолчанию
loopback, сравнение с учётом `::ffff:`), проверяется по безопасному набору символов (пробелы, `;`, CRLF,
кириллица отсекаются — логин идёт в SQL и журнал), а клиентский заголовок прокси обязан затирать
(`proxy_set_header ... $remote_user`). Неизвестный логин — 403, а не «гость»: молчаливое понижение
прав маскировало бы ошибку настройки. Автосоздание включается явно (`REP_AUTH_PROXY_AUTOCREATE=1`),
создаёт пользователя с пустым паролем (вход по паролю невозможен) и пишется в журнал как
`user.autocreate` с `source: proxy`. Роль кэшируется на 60 с — компромисс между нагрузкой и задержкой
применения изменений; для мгновенного запрета есть `REP_AUTH_PROXY_CACHE_SECONDS=0`. Вход и выход
в прокси-режиме отключены (400 `AUTH_ON_PROXY`), чтобы UI не обещал несуществующего. Ограничения:
доверие к заголовку защищено только адресом прокси (без mTLS/подписи), заголовок не несёт групп —
роли назначаются в справочнике приложения, нет выхода по инициативе пользователя.

<a id="adr-55"></a>

## ADR-55. Схема шаблона — контракт формата, а не пожелание (версия 1.28)

Проверка полноты документации
показала расхождение: сервер и шаблоны использовали у табличного блока `title` (имя листа Excel) и
`aggregate` (серверная агрегация, ADR-37), а схема их не объявляла — три рабочих шаблона считались
невалидными. Причина, по которой это жило незамеченным: в `check.sh` проверка шаблонов стояла в
`npm run … && echo "templates ok"` — левая часть `&&` не подпадает под `set -e`, и провал валидатора
тонул в успешном выводе. Решения: (1) поля, которые реально работают, объявляются в `schema.js`,
`docs/template.schema.json` перегенерируется (иначе машиночитаемая схема врёт); (2) `check.sh` проверяет
код возврата явно и падает с «шаблоны не проходят валидацию»; (3) мёртвые поля из шаблонов убираются
(в `sales-drill` был корневой `layout`, которого формат не знает). Валидатор проверяет структуру и
допустимые значения, но не существование колонок в SQL: их знает только база, поэтому неверное имя
в `groupBy`/`measures` даёт 422 при построении отчёта — это записано в справочнике шаблона.

<a id="adr-56"></a>

## ADR-56. Виды диаграмм gauge и sankey (версия 1.29)

Заказчику нужны не только ряды, но и «одно число»
и «потоки»: спидометр для KPI и sankey для распределения сумм между категориями и регионами. Оба вида —
надстройка над тем же блоком `chart`, чтобы не появлялся третий тип блока: у `gauge` поля `yField` +
`aggregate` (одно значение по всей выборке) и шкала `min`/`max`/`unit`, у `sankey` — `sourceField`,
`targetField`, `valueField`. Обязательность полей переехала из JSON Schema в семантический валидатор:
структурная схема не умеет «required зависит от значения», а разрешать все поля всем видам — значит
пропускать опечатки. Поэтому правила «для gauge нужен yField, xField не используется» продублированы
на клиенте и на сервере и закреплены parity-фикстурами. Агрегация остаётся клиентской: сервер отдаёт
строки как есть, пары потоков суммируются на странице, поэтому `sankey` работает и на серверных
наборах без спец-эндпоинта. Проверка выявила два старых дефекта: диаграммы игнорировали `dataKey`
(читали первый набор — ADR-36 работал только для таблиц) и `block.aggregate`-строка принималась за
серверную агрегацию, из-за чего уходил 422. Ограничения: диаграммы не экспортируются в Excel и не
печатаются; sankey не поддерживает промежуточные уровни (только «источник → приёмник», без цепочек),
gauge показывает одно значение без порогов и зон.

<a id="adr-57"></a>

## ADR-57. Цветовые зоны gauge (версия 1.30)

Для KPI мало одного числа: нужно «плохо/терпимо/хорошо».
В шаблоне это `thresholds` (границы) и `zoneColors` (цвета), а не список диапазонов с повторами
`from/to`: границы монотонны, поэтому пары избыточны и в них легко ошибиться. N границ дают N+1 зону —
столько же цветов; правило проверяется на клиенте и на сервере, количество ограничено (2…8 границ).
Цвета допускают hex и токены `styles.palette`, чтобы палитра шаблона оставалась единственным местом
правки оформления. Полоса прогресса при зонах отключается: два слоя цветов на одной оси читаются
плохо. Границы вне `min…max` обрезаются — это защита от опечаток, а не повод падать. Недостаток:
пороговая логика привязана к виду «gauge», у таблиц и линий её нет (для них есть `rules`, ADR-25),
и зоны не попадают в Excel — диаграммы в выгрузку не входят вовсе.

<a id="adr-58"></a>

## ADR-58. Диаграмма band: значение и коридор (версия 1.31)

Для эксплуатационных отчётов нужен не только
ряд значений, но и допустимый разброс: у точки три числа — значение, нижняя и верхняя границы.
Отдельный `chartType: "band"` вместо «линии с параметром области» выбран потому, что обязательность
трёх полей и правила их различия нужно проверять, а необязательная область у линии сделала бы
валидацию развилкой. Заливка рисуется двумя невидимыми стековыми рядами (основание «низ» плюс разница
«верх − низ»), значение — третьим рядом: это работает на любых данных, включая отрицательные нижние
границы, и не требует ни `custom`-серии, ни вычисления полигонов на клиенте. Прозрачность 0,22
фиксирована — полоса не должна перекрывать линию значения. Ограничения: одна полоса на график
(несколько коридоров не поддерживаются), полоса не попадает в Excel и печать (диаграммы вообще
не экспортируются), при перепутанных границах полоса вырождается в ноль, а не подсвечивается ошибкой —
валидатор полей не видит данных.

<a id="adr-59"></a>

## ADR-59. Ретеншен журналов (версия 1.32)

`audit_log` и `subscription_runs` растут монотонно, и «чистить
руками, когда станет много» — это отложенный инцидент: на стенде за месяц накопилось 44 записи, на
работе будет на порядки больше. Глубина хранения задаётся `REP_LOG_RETENTION_DAYS` (90 дней по умолчанию,
`0` — бессрочно), одна настройка на оба журнала: разный срок жизни у них не нужен, оба описывают операции.
Чистка живёт в отдельном потоке, а не в планировщике рассылки: `REP_SCHEDULER=0` выключает отправку,
но не должен оставлять журналы без обслуживания. Запуск при старте плюс раз в 6 часов — компромисс между
точностью и лишними запросами; удаление идёт пачкой по индексу даты. Факт чистки пишется в журнал
(`logs.purge`) только при ненулевых удалениях, иначе шум: каждый тик писал бы строку «удалено 0».
`/api/health` показывает действующую глубину, чтобы на развёрнутом экземпляре не гадать, применилась ли
настройка. Ограничения: удаление необратимо (архивации в файл/SIEM нет — это отдельная задача), глубина
считается по времени сервера, а не по часовому поясу зрителя.

<a id="adr-60"></a>

## ADR-60. Часовой пояс расписания в подписке (версия 1.34)

«Каждый будний день в 9:00» — это 9:00
по месту работы, а не по UTC сервера: до этой версии cron считался в поясе процесса, и рассылка уходила
на 3–7 часов позже или раньше ожидаемого. Пояс хранится в подписке (`timezone`, IANA-идентификатор),
а не в переменной окружения: у разных подписок могут быть разные получатели и регионы. Пересчёт
«местное время ↔ UTC» отдан PostgreSQL (`AT TIME ZONE`): только база знает переходы на летнее время,
самодельная арифметика на них ломается дважды в год. В C++ остаётся календарный поиск следующей
минуты по cron — он не зависит от DST. Неизвестный пояс отклоняется при сохранении (422), а не
принимается молча: опечатка иначе дала бы расписание не в том поясе. Ограничения: старые подписки
получают `UTC` при миграции (их расписание не менялось), поле одно на подписку — производственного
календаря (праздников) нет, только дни недели.

<a id="adr-61"></a>

## ADR-61. Повтор отправки рассылки при сбое SMTP (версия 1.34)

Сбой почтового сервера не должен
терять выпуск: до этой версии единственной попыткой дело и заканчивалось, а в журнале оставался
`ok=false`. Повтор планируется в БД (`retry_count`, `retry_at`), а не сном в потоке: подписка переживает
перезапуск процесса. При выборе подписки планировщик ставит «заём»: `next_run_at` уезжает вперёд на
две минуты (и перезаписывается настоящим расписанием в конце отправки), `retry_at` снимается.
Без заёма второй экземпляр успевал забрать ту же подписку, пока первый ещё собирал файл, — при
двух процессах письмо уходило дважды. `FOR UPDATE SKIP LOCKED` защищает только внутри одного тика;
заём закрывает окно на всё время отправки. Пауза растёт экспоненциально (60 → 120 → 240 с, настраивается), потому что мгновенные повторы
добивают и без того больной SMTP. Повтор не сдвигает `next_run_at` — иначе серия сбоев «съедала» бы
плановое время и отчёт за период не уходил вовсе. Номер попытки пишется в `subscription_runs.attempt`,
исчерпание попыток — в журнал действий (`subscription.given_up`). Ручной запуск повторов не планирует:
человек видит ошибку сразу. Ограничения: очередь не персистентна на уровне писем (при падении процесса
во время отправки письмо не переотправится), нет ограничения сверху на суммарную длительность серии
повторов — оно задаётся числом попыток и задержкой.
