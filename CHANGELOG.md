## v1.10.0 — 2026-11-05

Несколько наборов данных в одном шаблоне (ADR-36), задача 4 из плана.

### Как устроено

- шаблон может объявить несколько наборов: `datasets.<key> = { sql, params }`;
  каждый проходит валидацию (`queryId` запрещён, `sql` обязателен);
- табличный блок выбирает набор полем `dataKey`, клиент запрашивает данные по каждому ключу
  отдельно: `POST /api/report/data {reportId, dataset, params}`;
- без `dataset` сервер отдаёт первый набор шаблона — старые шаблоны работают как раньше;
- неизвестный ключ → `422 DATASET_NOT_FOUND` с именем набора;
- ключ кэша включает имя набора, поэтому блоки с разными запросами не смешиваются;
- публичный `GET /api/reports/{id}` вырезает `sql` у **всех** наборов, полный шаблон — только в админке;
- новый пример `sales-two-sets`: два независимых запроса (итоги по регионам и по категориям)
  в одном отчёте, два блока рядом.

## v1.9.0 — 2026-11-05

Аутентификация и роли (ADR-34) + план и ТЗ добавлены в репозиторий.

### Вход и роли

| Роль | Права |
|---|---|
| `viewer` | читает отчёты, справочники, данные и каталог |
| `author` | то же + создание отчёта и работа с черновиком |
| `admin` | всё: публикация, удаление, история, откат, админка |

- таблицы `users` (PBKDF2-HMAC-SHA256, 120 000 итераций, своя соль) и `sessions`
  (токен 32 байта, TTL 12 ч, `REP_SESSION_TTL_HOURS`);
- `POST /api/auth/login` ставит cookie `rep_session` (`HttpOnly`, `SameSite=Lax`, `Path=/`),
  `POST /api/auth/logout` удаляет сессию, `GET /api/auth/me` отдаёт логин и роль;
- проверка до маршрутизации: одна точка, матрица «метод + путь → минимальная роль»
  (`/api/health` и `/api/auth/*` публичны, чтение — viewer, черновик и создание — author,
  публикация/удаление/`/api/admin/**` — admin); неизвестный путь требует admin;
- 401 `UNAUTHORIZED`, 403 `FORBIDDEN` с JSON-ошибкой, как у остальных маршрутов;
- страница `/login.html`: форма, сообщение о неверном пароле, возврат на `next`;
- все страницы (каталог, отчёт, админка) проверяют `/api/auth/me` и уводят на вход;
  админка для не-admin показывает «Недостаточно прав»;
- `scripts/auth-init.sh` создаёт `admin` и `viewer`, пароли дописывает в `backend/.env`,
  `--rotate` меняет их; `scripts/demo.sh` включает `REP_AUTH=1`.

### Документация в репозитории

`PLAN.md` и ТЗ (`rep.txt`) больше не живут в единственном экземпляре вне git:
копии — `docs/plan/PLAN.md` и `docs/plan/spec.txt`.

### Проверки

`REP_E2E=1 ./scripts/check.sh` → `ALL CHECKS PASSED`: ctest **17 тест-кейсов / 59 проверок**
(добавлены хэширование, уникальность токена, матрица ролей), vitest 102, golden 15/15, e2e **39**
(+6: 401 без сессии, редирект с `next`, неверный пароль, вход через форму, права viewer,
admin видит админку и полный шаблон).

### Ограничения

- нет политики паролей, блокировки после неудачных попыток и 2FA;
- cookie без `Secure` — стенд локальный, HTTPS не используется;
- пользователи создаются скриптом, интерфейса управления пользователями нет.

## v1.7.0 — 2026-11-05

Кэш результатов отчётов (ADR-32). Выбранный постановщиком пункт 1 из плана.

### Как работает

- `POST /api/report/data` кэшируется в памяти процесса: ключ — отчёт, версия шаблонов и значения
  параметров; TTL по умолчанию 60 с (`REP_CACHE_TTL_SECONDS`, 0 — выключен);
- ответы несут `ETag` и `X-Cache: miss|hit`; повторный `If-None-Match` возвращает `304`;
- публикация, правка, откат или удаление шаблона поднимают версию шаблонов и очищают кэш —
  устаревшие данные не отдаются;
- ограничения памяти: не более `REP_CACHE_MAX_ENTRIES` записей (200) и тело до
  `REP_CACHE_MAX_BODY_BYTES` (2 МБ), крупные ответы не кэшируются;
- ошибки (422/404/504/503) не кэшируются.

### Замеры (`sales-summary`, 2026-02-01…2026-03-10, 2,2 МБ ответа)

| Сценарий | Время | Заголовок |
|---|---|---|
| холодный запрос | 380 мс | `X-Cache: miss` |
| повтор | 48 мс | `X-Cache: hit` |
| повтор с `If-None-Match` | — | `304` |
| после публикации шаблона | — | `X-Cache: miss`, `ETag` другой |

Тела холодного и кэшированного ответов побайтово совпадают (2 282 332 Б).

## v1.6.0 — 2026-11-05

Публикация и черновик в админке (ADR-31). Выбранный постановщиком пункт 4 из плана.

### Как теперь устроена правка

- в `report_templates` появились колонки `draft jsonb` и `draft_updated_at` (миграция
  `ALTER TABLE … ADD COLUMN IF NOT EXISTS`, схема обновлена);
- правка в админке сохраняется в черновик и **не меняет опубликованный отчёт**:
  публичный `GET /api/reports/{id}` продолжает отдавать прежнее тело;
- редактор при открытии отчёта подхватывает черновик, если он есть; в шапке — метка
  «черновик от ДД.ММ ЧЧ:ММ»;
- «Опубликовать» переносит черновик в опубликованное тело: снапшот прежней версии пишется в историю,
  черновик очищается, память обновляется без рестарта;
- «Отменить черновик» возвращает редактор к опубликованной версии.

### API

| Метод | Маршрут | Смысл |
|---|---|---|
| GET | `/api/admin/reports/{id}/draft` | тело черновика (404 `DRAFT_NOT_FOUND`) |
| PUT | `/api/admin/reports/{id}/draft` | сохранить черновик (валидируется, в память не идёт) |
| DELETE | `/api/admin/reports/{id}/draft` | отменить черновик |
| POST | `/api/admin/reports/{id}/publish` | опубликовать (409 `NO_DRAFT`, если черновика нет) |

`GET /api/admin/reports` дополнительно отдаёт `hasDraft` и `draftAt`. Создание отчёта (`POST /api/reports`)
по-прежнему публикует сразу — черновик нужен только для правок существующих.

## v1.4.2 — 2026-11-05

Замечание постановщика: в Excel сворачивалась только верхняя группировка (регион), категория — нет.

Причина: уровни структуры выводились из подытогов, а в шаблоне подытоги есть только у региона,
поэтому все детали попадали на один уровень и Excel группировал их по границам строк «Итого».

Исправление: иерархия строится по путям групп, а не по подытогам. Первая строка каждой категории
остаётся видимой опорой (уровень 1), её детали уходят на уровень 2. Результат на `sales-summary`
за 1–10 марта:

| Уровень | Строк | Что это |
|---|---|---|
| 0 | 9 | подытоги регионов и общий итог |
| 1 | 22 | опорные строки категорий (видны при сворачивании деталей) |
| 2 | 2 726 | детальные строки |

Сворачивание: кнопка «2» скрывает детали, оставляя по строке на категорию; «1» скрывает категории,
оставляя подытоги регионов. e2e проверяет наличие обоих уровней.

## v1.4.1 — 2026-11-05

Исправления по замечаниям постановщика к версии 1.4.

### Excel: вернулось сворачивание

- строки получили уровень структуры Excel (`outlineLevel`), включён `outlineProperties.summaryBelow`:
  у детальных строк — уровень группировки, у подытога группы — на уровень выше, итог — вне структуры;
- глубину берём по фактическим подытогам: если подытоги только у верхней группы, детали идут уровнем 1,
  а не «висящим» вторым уровнем без родителя (иначе в Excel нет кнопок «+»);
- работает штатное сворачивание Excel (кнопки 1/2 слева, «−» у группы); свёрнутость экрана не переносится.

### Печать: таблица больше не пропадает

Причина: у контейнера таблицы `contain: strict` — при печати он схлопывался в 0 px, браузер
не пагинировал содержимое, в PDF оставались только canvas-диаграммы. Что изменено:

- в `@media print` добавлено `contain: none` — контейнер получает фактическую высоту таблицы;
- `window.print()` вызывается после фактической отрисовки: `nextTick` + два кадра `requestAnimationFrame`
  + 250 мс на снятие раскладки (иначе в макет попадали диаграммы и пустое место);
- кнопка показывает состояние «Готовим печать…» и защищена от повторного нажатия;
- лимит печати снижен с 20 000 до **5 000** строк: полный DOM на 24 000 строк браузер строит слишком
  долго; сверх лимита — `PRINT_LIMIT` с предложением Excel.

- лист «Параметры»: имя, подпись (NAME), значение, отчёт, дата выгрузки;
- имя файла `<id>-<ГГГГ-ММ-ДД>.xlsx`; свёрнутые на экране группы выгружаются развёрнутыми;
- диаграммы не переносятся (решение PO); серверный экспорт (`libxlsxwriter`) отложен как запасной путь.

### Печать

- кнопка «Печать / PDF»: `window.print()`, PDF через диалог браузера;
- `@media print`: скрыты панель параметров, тулбар и кнопки, фон белый, таблица без виртуализации;
- шапка повторяется на каждой странице (`table-header-group`), строки и диаграммы не разрываются;
- лимит печати 20 000 строк: сверх — сообщение `PRINT_LIMIT` с предложением выгрузить в Excel.

### Проверки

`REP_E2E=1 ./scripts/check.sh` → `ALL CHECKS PASSED`: ctest 13, vitest 102, golden 15/15,
e2e **29** (включая разбор скачанного файла через ExcelJS и `emulateMedia('print')`).
Замеры: 2 748 строк → файл 2 757 строк (с шапкой и итогом), 28 объединений, подготовка 0,7 с.

### Известные ограничения

- диаграммы в файл не попадают;
- печать больше 20 000 строк не поддерживается (ограничение браузера на построение DOM);
- ExcelJS грузится при первом экспорте (~1 МБ), в офлайне без кеша это заметная пауза;
- условное форматирование переносится как статичные цвета, а не как правила Excel.
