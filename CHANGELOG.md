## v1.26.0 — 2026-11-08

Аутентификация средствами реверс-прокси (ADR-54).

### Что появилось

- `REP_AUTH=proxy`: имя пользователя приходит от прокси в заголовке
  (`REP_AUTH_PROXY_HEADER`, по умолчанию `X-Remote-User`). Сессий и пароля у приложения нет —
  вход и выход выполняет прокси (`login`/`logout` отвечают 400 `AUTH_ON_PROXY`);
- заголовку верим только с адресов из `REP_AUTH_PROXY_TRUSTED` (по умолчанию `127.0.0.1,::1`,
  понимает `::ffff:` форму dual-stack). Запрос с другого адреса — 403 «не от доверенного прокси»;
- роль берётся из `users` по логину: `viewer` не попадает в админку, публикация и удаление — только
  `admin`. Ответ кэшируется на `REP_AUTH_PROXY_CACHE_SECONDS` (60 с), поэтому отключение
  пользователя видно не дольше TTL;
- `REP_AUTH_PROXY_AUTOCREATE=1` заводит неизвестного пользователя с ролью
  `REP_AUTH_PROXY_ROLE` (по умолчанию `viewer`) и пустым паролем — войти по паролю им нельзя;
  факт автосоздания пишется в журнал (`user.autocreate`, `source: proxy`);
- `/api/health` отдаёт `authMode: off|session|proxy`, `/api/auth/me` в режиме прокси возвращает
  `{auth:true, mode:"proxy", login, role}`;
- имя пользователя от прокси — автор всех записей аудита;
- фронтенд: страница входа в режиме прокси показывает объяснение вместо формы; каталог пишет
  «вход через прокси: логин (роль)»; `deploy/nginx-reports.conf` — `auth_basic` +
  `proxy_set_header X-Remote-User $remote_user`.

### Проверено (`./scripts/check-proxy-auth.sh`)

15 проверок, все пройдены: без заголовка 401; неизвестный пользователь 403; `admin` — каталог и
админский API 200; `viewer` — каталог 200, админский API и публикация 403; логин с пробелом и с
`;` — 401; вход по паролю 400; заголовок с чужого адреса 403; автосоздание — пользователь
`viewer` с пустым паролем и записью `user.autocreate` в журнале.

Браузер под `/reports` (стенд с заголовком `X-Remote-User: admin`): каталог открывается без входа,
подпись «вход через прокси: admin (admin)», отчёт `sales-aggregate` — 5 строк, журнал — 50 записей,
0 ошибок JS и 0 ответов ≥ 400.

### Проверки

`ctest 59` (+3: режим, логин прокси, доверенные адреса), `vitest 131`, `golden 15/15`, `e2e 50` —
`ALL CHECKS PASSED` (сессионный режим не изменился).

## v1.23.0 — 2026-11-07

Версионирование схемы шаблона и миграции (ADR-51).

### Что появилось

- текущая версия формата — **2**; константа живёт в двух местах и сверяется тестами:
  `backend/src/template_migrate.cc` и `frontend/src/template/migrate.js`;

- клиент мигрирует при открытии в админке и сообщает: «Шаблон переведён в версию 2: …»,
  чтобы автор видел актуальный формат и не сохранял старое;
- валидатор предупреждает о старой версии («будет переведён в версию 2») и принимает обе версии;
- id шаблона: сервер и схема согласованы (`^[a-z0-9][a-z0-9_-]*$`), раньше расходились.

## v1.19.1 — 2026-11-07

Понятный выход при занятом порте (нашлось при отладке CI-стенда).

Раньше повторный запуск бэкенда на занятом порте давал не сообщение, а аварию:
drogon уходил в `abort()`, а разрушение статики под работающим потоком планировщика
превращалось в `corrupted double-linked list` / SIGSEGV — в CI это выглядело как
необъяснимое падение вместо «порт занят».

- порт проверяется до запуска сервера: занят — в лог пишется
  «порт N уже занят — сервер не запущен», выход с кодом 1;
- поток планировщика стартует только после этой проверки, поэтому на фатальном
  пути работающих потоков нет;
- фатальный выход идёт через `std::_Exit(1)` — статику drogon не разрушаем;
- проверено: второй экземпляр на :8080 завершается с сообщением, без SIGSEGV
  и без следов порчи памяти; рабочий стенд продолжает отвечать 200.

Проверки: `ctest 46`, `vitest 124`, `golden 15/15`, e2e 47 — `ALL CHECKS PASSED`.

### Стили таблиц из шаблона (ADR-23)

- секция `styles` (верхний уровень) + `blocks[].styles` + `columns[].style`; порядок применения:
  умолчания → `preset` → `styles` → `styles.<зона>` → блок → колонка;
- зоны отдельно: `header`, `body`, `subtotal`, `grandtotal` — шрифт, цвета текста и фона, выравнивание,
  вертикальное выравнивание, отступы;
- раскладка: `rowHeight`, `headerHeight`, `subtotalHeight`, `grandtotalHeight`, `cellPadding`,
  `borders` (`none`/`horizontal`/`grid`), `zebra`, `stripeColor`, `tableLayout`;
- колонки: `width` в px или `%`, `minWidth`, `maxWidth`, `align`, `headerAlign`, `format`;
- пресеты: `default` (вид 1.0), `compact`, `print`, `dark`;
- реализация — CSS-переменные на корне таблицы и классы зон, без inline-стилей на ячейках;
  виртуализация переведена на префиксные суммы высот (строки, подытоги и итог могут быть разной высоты).

### Выравнивание и форматы чисел

- `layout.numericAlign` — политика для числовых колонок (`right` по умолчанию, `left`, `center`, `inherit`);
- `headerAlign` у колонки — заголовок можно выровнять иначе, чем данные;
- форматы: `number`, `integer`, `percent`, `currency`, `date` — строкой или объектом
  (`style`, `decimals`, `group`, `decimal`, `prefix`, `suffix`, `negative`: `minus`/`parentheses`);
- резолвер `report/format.js`, 12 юнит-тестов; формат из `styles.columns` сильнее формата колонки.

### Справочники параметров: SQL в шаблоне (ADR-24, заменяет часть ADR-22)

- `params[].source.sql` — обязателен для `kind: "lookup"`; `queryId` удалён и запрещён валидатором;
- API: `GET /api/reports/{reportId}/lookups/{param}?<родитель>=…`, `GET /api/lookups/{id}` удалён;
- `GET /api/reports/{id}` вырезает `sql` из ответа — клиент SQL не видит;
- серверный кэш и `REP_LOOKUP_TTL_SECONDS` удалены, кэш только на клиенте;
- из `queries.json` удалены четыре `lookup_*`; 6 шаблонов переведены на `source.sql`.
