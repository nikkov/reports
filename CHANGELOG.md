# История версий

## v2.6.0 — 2026-11-12

Журнал по объектам и уровням, файловый приёмник, глубина цепочек (ADR-111).

### Что сделано
- `open_report`/`export_report` пишут `object_type = "report"` и `object_id` отчёта (раньше «log»);
- `/api/admin/audit` принимает `level` и отдаёт его в элементах; на странице журнала — колонка
  «Уровень» с бейджем и фильтр, выгрузка CSV по тем же фильтрам;
- файловый приёмник логов: `REP_LOG_FILE`, `REP_LOG_FILE_LEVEL` (по умолчанию `debug`),
  ротация `REP_LOG_FILE_MAX_BYTES` (10 МБ, архив `.1`);
- глубина цепочки объединений ограничена 8 (`MAX_JOIN_DEPTH` / `kMaxJoinDepth`), parity-фикстура
  на цепочку из десяти наборов (106 фикстур);
- e2e на offset-пагинацию REST (`crm-paged-offset`, 2500 строк тремя страницами).

### Проверки
Журнал: `open_report info report crm-paged-offset`; `level=warning` — 8 записей, только неудачные
входы. Файл `/tmp/rep-audit.log` — 12 JSON-строк. ctest 128 кейсов, vitest 331 + parity 106.

Совместимость журнала после перевода админских действий (ADR-110).

## v2.4.0 — 2026-11-12

Единая функция логирования (ADR-109).

### Что было не так

Логи писались напрямую `LOG_*` drogon — свободный текст без типа действия и пользователя; журнал
аудита заполнялся отдельно и только для админских действий («кто открыл отчёт» и «кто выгрузил Excel»
в нём не было).

### Что сделано
- модуль `logging.{h,cc}`: `rep::log::event(level, action, user, message, context)` — уровень
  (`trace|debug|info|warning|error`), тип действия (enum: `open_report`, `export_report`,
  `print_report`, `login`, `logout`, `create_user`, `change_user`, `delete_user`, `change_roles`,
  `change_template`, `publish_template`, `run_subscription`, `access_denied` + технические), логин
  (пусто — системное/анонимное), метка времени ISO-8601 UTC с мс, текст, контекст;
- JSON-строка в stdout + сменный приёмник: пишет `reports.audit_log` (`actor`, `action`, `details`);
- макросы `REP_LOG_INFO/WARN/ERROR(action, user) << …`; заменены все 30 прежних `LOG_*` в `main.cc`;
- события действий: `open_report` (открытие набора отчёта) и `export_report` (выгрузка xlsx);
- документация — раздел «Логирование» в `configuration.md`.

### Проверки
Живой прогон: `open_report` — JSON с `context.reportId/rows` и `user: admin`, та же запись в
`audit_log` (`actor=admin`, `action=open_report`); `export_report` — с `bytes=18063`, `format=xlsx`.
Catch2: 6 кейсов на уровни, имена enum, JSON-поля, пустого пользователя, метку времени и приёмник.

## v2.2.0 — 2026-11-12

Серверный экспорт и рассылка для rest/join (ADR-107).

### Что было не так

Для наборов `rest`/`join` `.xlsx`, `.csv` и рассылка отвечали `EXPORT_UNSUPPORTED`: лист собирался
только из SQL-набора. Попытки включить падали в SIGSEGV — причина в лямбде `take` (`fetchDatasetRows`),
которая захватывала окружение по ссылке и вызывалась асинхронно.

### Что сделано

- лист для не-SQL набора собирается из `DatasetRows` — те же `leaves`, подытоги и ИТОГО через
  `buildGroupedSheet`;
- восстановлен потерянный цикл `walk` по колонкам блока: без него лист выходил пустым у всех наборов;
- `EXPORT_UNSUPPORTED` убран; обработчик SIGSEGV с backtrace остаётся для диагностики.

### Проверки
`sales-crm` → CSV 27 670 байт («Регион;Менеджер;Дата;Сумма;Кол-во», 550 строк), xlsx 18 063 байта
(лист A1:E552 + «Параметры»); `sales-summary` → CSV 505 631 байт (SQL-путь не сломан); health 200
после всех запросов. В логе: `export: sales-crm — rows 550, leaves 5, cols 6`.

## v2.1.2 — 2026-11-12

Причина падения экспорта rest/join и безопасный отказ.

### Что нашли

Сборка листа для `rest`/`join` роняла процесс SIGSEGV за 40 мс без записи в лог. Добавили обработчик
сигналов с backtrace: стек показал падение в лямбде `take` внутри `fetchDatasetRows` — она захватывала
окружение по ссылке (`[&, …]`), а вызывается асинхронно из колбэка REST, когда локальные переменные
уже уничтожены. Захват переведён на значения (`done`, `failed`, `left`, `right`, `joinSpec`, `onOk`,
`onErr`, `maxRows`); после этого падение прекратилось.

### Что осталось

Лист для `rest`/`join` после исправления собирается, но выходит пустым (`leaves 0` — блок таблицы не
находится при построении листа), поэтому вместо пустого файла возвращается прежний отказ
`EXPORT_UNSUPPORTED`. Задача вынесена: найти, почему `block` пуст в `buildSheet` для join-набора,
и включить экспорт.

### Проверки

`gdb`-стек, `addr2line` — падение в `fetchDatasetRows::{lambda(bool, DatasetRows)}`; после правки
`export.xlsx` для `sales-crm` отвечает 422 `EXPORT_UNSUPPORTED`, health 200 (раньше процесс умирал).
Обработчик сигналов (`SIGSEGV`/`SIGABRT` + backtrace в stderr) остаётся в сборке для диагностики.

## v2.0.0 — 2026-11-12

Объединение наборов из разных источников: REST и join (ADR-104).

### Что было не так

Набор данных мог быть только SQL. Отчёт, где факты в PostgreSQL, а справочник регионов и
менеджеров — в REST-сервисе, собрать было нечем; `kind: rest` был зарезервирован, но не работал.

### Что сделано
- REST-источник: `connections.<ключ>` с `kind: "rest"`, `baseUrl`, `headers` (секреты только через
  `${ENV}`), `timeoutMs`, `cacheSeconds`; набор `rest { path, query, rowsPath, columns[] }`;
- набор-объединение `join { left, right, on[], type, columns[] }`: hash join в прокси, 1–4 ключа с
  нормализацией по типу, `inner`/`left`, переименование колонок через `as`;
- единый контейнер строк `DatasetRows`: `/api/report/data`, `/aggregate`, `/group`, `/text`,
  клиентский Excel и печать работают для всех видов наборов одинаково;
- защита: allowlist хостов `REP_REST_ALLOW_HOSTS` (без него REST выключен), запрет редиректов,
  лимит размера ответа, LRU-кеш ответов, понятные коды `REST_FORBIDDEN/ERROR/TIMEOUT/INVALID/TOO_LARGE`;
- валидация клиента и сервера: ровно один вид набора, ссылки и циклы join, повторы `as`,
  литеральные секреты в заголовках, `public` + REST — предупреждение;
- пример `sales-crm` и демонстрационный REST `scripts/rest-demo.mjs`.

### Проверки
`/data` для `sales-crm`: 24 723 строки с колонками из REST; `/aggregate` — 5 регионов и группа без
пары; `/group` — детали с `detailOrder` и пагинацией; клиентский Excel содержит «Менеджер».
e2e «объединение источников: PostgreSQL + REST в одной таблице». ctest 8 join + 10 rest, parity
99 фикстур. Осталось ограничением: серверный экспорт и рассылка для rest/join — `EXPORT_UNSUPPORTED`.

- числа остаются числами: `numFmt` из `format.js` (`# ##0`, `0.00 %`, `dd.mm.yyyy`, валюта), отрицательные
  в скобках; даты пишутся как даты;
- стили зон и совпадения правил: шрифт, начертание, цвета текста и фона, границы;
- лист «Параметры»: имя, подпись (NAME), значение, отчёт, дата выгрузки;

- диаграммы не переносятся (решение PO); серверный экспорт (`libxlsxwriter`) отложен как запасной путь.

### Печать

- кнопка «Печать / PDF»: `window.print()`, PDF через диалог браузера;
- `@media print`: скрыты панель параметров, тулбар и кнопки, фон белый, таблица без виртуализации;
- шапка повторяется на каждой странице (`table-header-group`), строки и диаграммы не разрываются;
- лимит печати 20 000 строк: сверх — сообщение `PRINT_LIMIT` с предложением выгрузить в Excel.

`REP_E2E=1 ./scripts/check.sh` → `ALL CHECKS PASSED`: ctest 13, vitest 102, golden 15/15,

- диаграммы в файл не попадают;
- печать больше 20 000 строк не поддерживается (ограничение браузера на построение DOM);
