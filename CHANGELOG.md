# История версий

## v1.53.0 — 2026-11-08

Самодостаточное развёртывание: один процесс отдаёт API и фронтенд (ADR-79).

### Что было не так

Статику раздавали снаружи: `vite preview` на стенде и nginx в эксплуатации. Демонстрация
требовала двух процессов и node, установка — обязательного веб-сервера. На вопрос «где должны
лежать файлы фронтенда относительно бинарника» ответа не было: сервер их не искал.

### Что сделано

- drogon отдаёт статику сам: `REP_WEB_ROOT` → `./web` → `../web` → `<бинарник>/web` →
  `<бинарник>/../../frontend/dist`;
- `scripts/build.sh` кладёт сборку в `backend/build/web` — комплект «`rep` + `web/`»;
- маршрут через `registerHandlerViaRegex` (обычный `registerHandler` считает «/.*» литералом);
- html — `no-cache`, `/assets/*` — `immutable`, остальное — час;
- SPA: путь без расширения отдаёт `index.html`; файл с расширением и без файла — 404;
  `/api/*` — JSON-404; `..` и `%2e%2e` отклоняются;
- матрица прав: не-`/api` пути — `Public` (иначе страница входа получала 401), API — как раньше;
- `scripts/demo.sh` поднимает один процесс; `REP_WEB_PORT=5173` оставлен для сверки.

### Проверено

## v1.52.0 — 2026-11-08

Скрипт создания и ротации эксплуатационных ролей БД (ADR-75).

### Что было не так

Роли `reporting_srv` и `reporting_ro` создавались только внутри `scripts/dev-db-init.sh` —
вместе со схемой и демо-данными. На стенде, где база уже есть, создать или сменить пароль
этих ролей было нечем: оставалось вручную писать `CREATE ROLE`/`GRANT` и помнить порядок.

### Что сделано

- `scripts/db-users.sh`: создаёт/обновляет обе роли (`LOGIN`, `NOSUPERUSER`, `NOCREATEDB`,
  `NOCREATEROLE`), ставит пароли, выдаёт права владельцем объектов через `db/roles.sql`
  и проверяет результат;
- пароли берутся из `backend/.env`, при отсутствии — генерируются и записываются туда
  (`chmod 600`); в лог попадает только факт, не значение;
- `--rotate` — новые пароли для обеих ролей, `--role <имя>` — только одна,
  `--password-stdin` — пароли из stdin (строка 1 — srv, строка 2 — ro), `--dry-run` — план;
- встроенные проверки: вход по паролю, `SELECT`/`INSERT` в ядре для сервера, чтение примеров,
  запрет записи в примеры, запрет `CREATE` в схеме, отсутствие суперпользователя, закрытое
  ядро для зрителя;
- документация: `docs/configuration.md` (как создать роли), `docs/deployment.md` (шаг установки
  и плановая ротация), README; `db-ro.sh` оставлен для точечной работы с ролью чтения.

## v1.51.0 — 2026-11-08

SQL справочников переехал в блок данных: справочник — это набор (ADR-78).

### Что было не так

Запрос «Центр затрат» лежал в `params[].source.sql`, рядом с которым нет ни соединения, ни набора.
В админке шаблон выглядел разорванным: данные описаны в `datasets`, а запрос справочника — в параметре.

### Что сделано

- справочник — обычный набор `datasets.<ключ>` (`sql` + `connection`), параметр ссылается полем
  `source.dataset`;
- `source.sql` и `source.connection` удалены из формата — ошибка валидатора с подсказкой;
  обратной совместимости нет по решению постановщика;
- переведены все 11 справочников в 8 шаблонах (`cost_center_lookup`, `region_lookup`,
  `category_lookup`, `service_lookup`);
- админка: панель параметров показывает набор и источник, SQL берёт из набора;
- каскад `dependsOn` сохранён: параметр родителя уходит в SQL набора как `:name`.

## v1.50.0 — 2026-11-08

Источники данных вынесены в блок у всех шаблонов примеров (ADR-77).

### Что было не так

Блок `connections` появился в v1.49, но примеры (кроме `sales-external`) продолжали читать данные
«по умолчанию»: в шаблоне не было видно ни адреса, ни роли, ни схемы. Перенастроить пример на
другую роль было нельзя.

### Что сделано

- у всех 21 шаблона примеров явный источник `connections.main`:
  `host: ${PGHOST}`, `port: ${PGPORT}`, `database: ${PGDATABASE}`, `user: ${REP_RO_DB_USER}`,
  `passwordEnv: REP_RO_DB_PASSWORD`, `schema: reports_examples`;
- каждый набор данных и каждый справочник параметров ссылается на `main` полем `connection`;
- поля `host`, `port`, `database`, `user`, `schema` поддерживают подстановку окружения `${ИМЯ}`
  (целиком, без смеси с текстом); незаданная переменная — ошибка с её именем;
- валидаторы клиента и сервера: правило подстановки и 2 новых parity-кейса (67/67);
- CI: `REP_RO_DB_USER`/`REP_RO_DB_PASSWORD` для стенда, где отдельной роли чтения нет.

### Проверено

| Проверка | Результат |
|---|---|
| Все примеры | 21 из 21 отдают данные через `main` |
| Роль внутри сессии | `current_user = reporting_ro`, `current_database = reporting` |
| Только чтение | `default_transaction_read_only = on` |
| Адрес из окружения | `${PGHOST}`/`${PGDATABASE}` подставляются; при отсутствии переменной — `422 CONNECTION_ERROR` |
| Смесь в поле | `host: "db-${ID}"` → ошибка валидатора `connections.main.host` |
| Переносимость | шаблоны не содержат имени базы и хоста: dev и CI используют один и тот же файл |
| Публичный API | `connections` вырезается, как и раньше |

## v1.49.0 — 2026-11-08

Источники данных в шаблоне: блок `connections` и второй PostgreSQL (ADR-76).

### Что было не так

SQL жил в шаблоне, а адрес, база и учётная запись — в окружении сервера. Один отчёт не мог
читать второй PostgreSQL, а перенос отчёта на другой стенд требовал менять переменные процесса.

### Что сделано

- блок `connections`: `kind` (`postgres`/`rest`), `host`, `port`, `database`, `user`, `schema`,
  `sslmode`, `connectTimeout`, `statementTimeoutMs`, `passwordEnv`;
- пароль — только **имя** переменной окружения: поле `password` в шаблоне отклоняется валидатором;
- наборы данных и справочники параметров ссылаются на источник полем `connection`; пусто или
  `default` — сервер из окружения (старые шаблоны работают без правок);
- клиенты внешних источников создаются лениво и кэшируются по строке подключения (до 16);
- каждое внешнее соединение открывается с `default_transaction_read_only=on`;
- источник учитывается во всех путях: `data`, `aggregate`, `group`, `lookups`, серверный
  `.xlsx`/CSV, рассылка;
- публичный `GET /api/reports/{id}` вырезает `connections`; админский отдаёт полностью;
- `rest` зарезервирован: структура валидируется, запрос отвечает `422 CONNECTION_ERROR`;
- новый пример `sales-external`: продажи из БД сервера и отгрузки из отдельной базы
  `reporting_ext.warehouse` (`db/examples/external.sh` создаёт её и роль только-чтения);
- валидаторы клиента и сервера: 8 новых parity-кейсов (65/65);
- попутно исправлено: заголовок табличного блока (`blocks[].title`, ADR-55) задавался в
  одиннадцати местах шаблонов, но не выводился — теперь таблица его показывает, как диаграмма.

## v1.48.0 — 2026-11-08

Три эксплуатационные роли БД: владелец, сервер, зритель (ADR-75).

### Что было не так

Сервер работал под одной ролью `rep_app`, которая была и владельцем схем/таблиц, то есть могла
выполнять DDL. Граница «кто владеет структурой» и «кто работает с данными» не была разведена,
а суперпользователя ничто не мешало использовать в эксплуатации.

### Что сделано

- `reporting_owner` — владелец схем и таблиц: DDL, миграции, развёртывание (`REP_OWNER_DB_*`);
- `reporting_srv` — сервер: SELECT/INSERT/UPDATE/DELETE в `reports`, последовательности ядра,
  чтение `reports_examples`; **CREATE в схеме запрещён**;
- `reporting_ro` — прежняя роль чтения: только `reports_examples`;
- роль `rep_app` переименована в `reporting_owner`, владение объектами сохранено;
- `db/roles.sql` — единая декларация прав (GRANT + ALTER DEFAULT PRIVILEGES), `db/init.sh` делает DDL
  под владельцем, `db-ro.sh` выдаёт права владельцем и проверяет чтение/запрет записи;
- `scripts/dev-db-init.sh` создаёт три роли и пишет в `.env` пароли owner/srv/ro;
- сервер при старте проверяет `current_user`: предупреждение под суперпользователем, отказ стартовать
  при `REP_STRICT_ROLE=1`; `/api/health` отдаёт `dbUser` и `superuser`.

### Проверено

|---|---|

## v1.47.0 — 2026-11-08

Ядро и примеры разведены по схемам: `reports` и `reports_examples` (ADR-74).

### Что было не так

В одной схеме `public` лежали и продукт, и демонстрация: `report_templates`, `users`, `sessions`,
`audit_log`, `report_subscriptions` — рядом с `sales`, `finance`, `ops`, `regions`. Ядро нельзя было
поставить на чистую базу без синтетики, а граница «продукт / примеры» держалась только на именах таблиц.
`db/schema.sql` был одновременно ядром и демо-данными, миграции создавали таблицы ядра без схемы.

### Что сделано

- `db/core.sql` — ядро в схеме `reports`: `report_templates`, `report_templates_history`, `users`,
  `sessions`, `audit_log`, `report_subscriptions`, `subscription_runs` (структура совпадает с текущей,
  включая `timezone`, `retry_*`, `attempt`);
- `db/examples/schema.sql` + `db/examples/seed.sql` — примеры в схеме `reports_examples`: `regions`,
  `sales`, `finance`, `ops` (50 000 / 576 / 540 строк);
- `db/init.sh` получил режимы `--core-only` и `--examples-only`; права выдаются отдельно: приложение
  пишет в `reports` и читает `reports_examples`, роль `reporting_ro` видит только примеры;
- приложение подключается с `search_path=reports` (`REP_DB_SCHEMA`), пул только-чтения — с
  `search_path=reports_examples` (`REP_RO_DB_SCHEMA`); `scripts/env.sh` выставляет
  `PGOPTIONS=-c search_path=reports` для psql-скриптов;
- все 20 шаблонов и документация переведены на `reports_examples.*`; миграции квалифицированы схемой
  `reports` и остаются идемпотентными;
- `scripts/dev-db-init.sh` больше не держит свой DDL: роли, базы, `.env` — здесь, структура — в `db/init.sh`;
- старые `db/schema.sql` и `db/seed.sql` удалены (два источника правды), `db/roles.sql` выдаёт SELECT только
  на `reports_examples`, а страховки `ALTER ROLE` вынесены в `db/roles-hardening.sql` — их применение требует
  прав суперпользователя, поэтому `scripts/db-ro.sh` под ролью приложения их пропускает с замечанием;
- `check-delivery.sh`, `db-ro.sh`, `golden.mjs` и e2e-фикстуры переведены на схему примеров;
- очищены старые объекты в dev-БД: шаблон `live-e2e` и история версий тестовых отчётов (`agg-e2e`,
  `cache-e2e`, `draft-e2e`, `live-e2e`, `migrate-e2e`, `refresh-e2e`) — шаблонов 21 → 20, версий 57 → 40;
  в `public` обеих баз объектов нет, `reporting_ci` пуста;
- e2e-тест «обновление по событию» теперь удаляет свой шаблон в конце — мусор в каталоге больше не копится;
- добавлен `scripts/db-cleanup.sh` (`--dry-run`): убирает историю версий по удалённым шаблонам и истёкшие
  сессии. Каждый прогон e2e оставляет снимки своих тестовых отчётов (FK между историей и шаблоном нет по
  ADR-26), поэтому чистка нужна периодически; журнал аудита, подписки, шаблоны и пользователей скрипт не трогает.
  `check.sh` вызывает её в конце прогона: e2e оставил 9 сирот — проверка закончилась с «осталось сирот: 0».

Рассылка: повтор отправки при сбое SMTP и часовой пояс расписания (ADR-60, ADR-61).

### Часовой пояс расписания (ADR-60)

- у подписки появилось поле `timezone` (IANA: `Europe/Moscow`, `Asia/Novosibirsk`), по умолчанию `UTC`;
- cron считается в этом поясе: «0 9 * * 1-5» + `Asia/Novosibirsk` → 09:00 по Новосибирску (02:00 UTC);
- пересчёт «местное ↔ UTC» с переходами на летнее время делает PostgreSQL (`AT TIME ZONE`),
  в C++ остаётся только календарная арифметика — самодельный расчёт DST ошибается дважды в год;
- неизвестный пояс отклоняется при создании и правке: 422 «неизвестный часовой пояс «Mars/Olympus»»;
- в админке пояс выбирается из списка с подсказкой, в списке подписок виден рядом с форматом.

### Повтор отправки (ADR-61)

- при сбое SMTP отправка повторяется: пауза `REP_SMTP_RETRY_DELAY_SECONDS` (60 с) и удваивается,
  всего попыток `REP_SMTP_RETRY_ATTEMPTS` (3);
- повторы не сдвигают плановое время: сбой не «съедает» выпуск отчёта;
- планировщик ставит «заём» на время отправки (`next_run_at` +2 минуты), поэтому второй экземпляр
  не заберёт ту же подписку, пока первый собирает файл — без заёма при двух процессах письмо
  уходило дважды;
- номер попытки пишется в журнал отправок (`subscription_runs.attempt`), в списке подписок
  видно «повтор ДД.ММ ЧЧ:ММ (попытка N)»;
- успешная попытка сбрасывает счётчик; после исчерпания попыток повтор снимается и в журнал
  действий пишется `subscription.given_up` с текстом ошибки;
- ручное «Отправить сейчас» повторов не планирует — ошибку сразу видит человек.

### Стили таблиц из шаблона (ADR-23)

- секция `styles` (верхний уровень) + `blocks[].styles` + `columns[].style`; порядок применения:
  умолчания → `preset` → `styles` → `styles.<зона>` → блок → колонка;
- зоны отдельно: `header`, `body`, `subtotal`, `grandtotal` — шрифт, цвета текста и фона, выравнивание,
  вертикальное выравнивание, отступы;
- раскладка: `rowHeight`, `headerHeight`, `subtotalHeight`, `grandtotalHeight`, `cellPadding`,
  `borders` (`none`/`horizontal`/`grid`), `zebra`, `stripeColor`, `tableLayout`;
- колонки: `width` в px или `%`, `minWidth`, `maxWidth`, `align`, `headerAlign`, `format`;
- пресеты: `default` (вид 1.0), `compact`, `print`, `dark`;
- реализация — CSS-переменные на корне таблицы и классы зон, без inline-стилей на ячейках;
  виртуализация переведена на префиксные суммы высот (строки, подытоги и итог могут быть разной высоты).

### Выравнивание и форматы чисел

- `layout.numericAlign` — политика для числовых колонок (`right` по умолчанию, `left`, `center`, `inherit`);
- `headerAlign` у колонки — заголовок можно выровнять иначе, чем данные;
- форматы: `number`, `integer`, `percent`, `currency`, `date` — строкой или объектом
  (`style`, `decimals`, `group`, `decimal`, `prefix`, `suffix`, `negative`: `minus`/`parentheses`);
- резолвер `report/format.js`, 12 юнит-тестов; формат из `styles.columns` сильнее формата колонки.

### Справочники параметров: SQL в шаблоне (ADR-24, заменяет часть ADR-22)

- `params[].source.sql` — обязателен для `kind: "lookup"`; `queryId` удалён и запрещён валидатором;
- API: `GET /api/reports/{reportId}/lookups/{param}?<родитель>=…`, `GET /api/lookups/{id}` удалён;
- `GET /api/reports/{id}` вырезает `sql` из ответа — клиент SQL не видит;
- серверный кэш и `REP_LOOKUP_TTL_SECONDS` удалены, кэш только на клиенте;
- из `queries.json` удалены четыре `lookup_*`; 6 шаблонов переведены на `source.sql`.
